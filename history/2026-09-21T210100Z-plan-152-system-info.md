# Plan 152 — System Information

Diagnostics, monitoring tools, and resource-aware programs (a job queue
that backs off under memory pressure, a build tool that caps parallelism
at the real core count rather than a hardcoded guess) all need the same
basic system-introspection primitives Emerald has no way to reach today.
`sysinfo` (v0.39.6 as of this session, its own crates.io listing —
"Library to get system information such as processes, CPUs, disks,
components and networks" — actively maintained, current MSRV 1.95) is
the standard, cross-platform crate for exactly this, abstracting over
`/proc`, `sysctl`, and the Windows performance-counter APIs behind one
consistent interface. Everything this plan exposes is read-only: there is
no `System.kill_process`, no `System.set_priority`, nothing that changes
anything about the machine it reports on — a program using this plan's
entire surface can observe but never act.

## Concrete proof this plan targets

```ruby
cpus: Int64 = System.cpu_count
puts cpus > 0

total: Int64 = System.total_memory_bytes
used: Int64 = System.used_memory_bytes
puts total >= used
puts used >= 0

n: Int64 = System.disk_names_count
puts n >= 0

pids: Array[Int64] = System.process_ids
m: Int64 = System.process_ids_count
puts m > 0

name: String? = System.process_name(pids[0])
name ||= "unknown"
puts name.length > 0
```

Expected output, in order, on any real machine this compiles and runs on:
```
true
true
true
true
true
true
```

Trace: every assertion is relative/derived (`> 0`, `>=`) rather than a
literal machine-specific number, deliberately — a real CPU count, real
memory total, real disk count, and real live process count vary by
machine and CI environment, and are not themselves the property this
proof needs to establish. That `System.cpu_count`/`total_memory_bytes`/
`disk_names_count`/`process_ids_count` return genuinely populated,
internally-consistent values (not zero, not a stub, not `total < used`)
is the real, falsifiable claim this proof makes, and it holds on any
real machine, deterministically, regardless of that machine's actual
specs.

## Decision log

- **This plan is read-only introspection, full stop — stated as a
  deliberate design boundary, not merely an accurate description of
  what nine getter functions happen to do.** Every `sysinfo`-backed call
  in this plan reads a value and returns it; none of them construct or
  hold a `sysinfo::System` with any intent to later call one of its own
  real mutating/control methods (`sysinfo` itself exposes no process-
  kill or priority-change API on most platforms in the first place, but
  the point is stated as a positive design commitment of this plan, not
  merely an accident of what the underlying crate happens to expose). A
  program wanting to *act* on what it observes here — kill a runaway
  process, throttle itself — combines this plan's read with plan 145's
  `Process.run`/plan 151's `Signal` primitives itself; this plan supplies
  no control surface of its own.
- **No long-lived cached `sysinfo::System` snapshot is held across
  calls — every function builds, refreshes, reads, and drops its own
  short-lived instance.** `sysinfo`'s own documented usage pattern
  favors holding one `System` and calling its `refresh_*` methods
  repeatedly for efficiency in a long-running Rust program; this plan
  declines that pattern deliberately, since a cached snapshot living
  inside `emerald-rt`'s static state would need its own explicit
  refresh/invalidation story — stale CPU/memory readings from a snapshot
  an Emerald program never explicitly refreshed would be a real,
  confusing correctness surprise (values silently going stale) for a
  first version of this plan to introduce. The disclosed cost is real:
  a fresh `sysinfo::System::new_all()`-style construction plus refresh on
  every single `System.*` call is measurably more expensive than reusing
  one warm instance — an accepted simplicity-over-throughput tradeoff for
  a diagnostics-oriented primitive that is not expected to run in any
  program's hot path. A cached, explicitly-refreshable `SystemSnapshot`
  handle (its own opaque type, under plan 93's model, with a
  `.refresh()` method) is a natural, disclosed future optimization this
  plan does not attempt.
- **`process_ids(): Array[Int64]` is this batch's first array-of-scalars
  intrinsic — every prior `Array[T]`-returning function in plans 45/
  144/145/146/150 returned `Array[String]`.** The representation is a
  straightforward generalization, not a new mechanism: a heap-allocated,
  contiguous run of `i64` values (rather than a `char**` array of
  pointers to separately-allocated strings), still paired with a
  companion `_count` function per this batch's now-five-times-confirmed
  convention (plans 45/144/145/146/150). No `Array[T]` polymorphism is
  added at the type-system level to make this general — this plan adds
  exactly the one new concrete codegen case (`Array[Int64]` construction/
  indexing) its own `process_ids` needs, the same narrow, non-general-
  purpose posture plan 45's own Decision log already took toward its own
  intrinsic set.
- **Per-pid lookups (`process_name`/`process_memory_bytes`) can
  legitimately miss even immediately after `process_ids()` enumerated
  that exact pid — a real, disclosed TOCTOU-shaped race inherent to
  process introspection on every operating system, not a defect in this
  plan's own implementation.** A process can exit at any point between
  `System.process_ids()` returning its snapshot and a subsequent
  `System.process_name(pid)` call looking it up — this is true of `ps`,
  `/proc`, `tasklist`, and every other process-enumeration tool on every
  OS, not a Rust- or `sysinfo`-specific weakness. This plan surfaces a
  miss as a disclosed not-found sentinel (`nil` for `process_name`'s
  `String?`, a provisional `-1` for `process_memory_bytes`'s scalar
  `Int64` — see the next bullet for why the two differ) rather than
  treating it as an exceptional condition worth raising over, since a
  process disappearing between two calls is routine, expected system
  behavior, not a program error.
- **The `-1`-sentinel used for `process_memory_bytes`'s not-found case is
  explicitly provisional, pending plan 92's general scalar-return error
  convention — the same disclosed placeholder posture plan 91 itself
  already took for its own proof function.** Plan 91's own Decision log
  states its FNV-1a proof function's `-1`-on-panic return is a
  "placeholder" and that a real "error-code/`Result` marshaling
  convention" is "plan 92's job, generalized." Nullable reference types
  (`String?`, used here for `process_name`) already have a real, free,
  zero-cost not-found representation via plan 43/59's null-pointer
  convention; a bare scalar `Int64` has no equivalent spare bit pattern
  to spend on "not found" the same way, and this plan does not invent
  one — it uses the same disclosed interim sentinel plan 91 already
  used, explicitly flagged here as provisional rather than presented as
  this plan's own considered final answer.
- **Logical CPU count, not physical core count, is what `System.
  cpu_count` reports — the more broadly useful number for the resource-
  aware-parallelism use case this plan's own overview names.** `sysinfo`
  exposes both (`System::cpus().len()` for logical, including
  hyperthreads, versus `System::physical_core_count()` for physical
  cores only); a program sizing a thread/worker pool almost always wants
  the logical count (the number of hardware execution contexts the OS
  scheduler can actually run in parallel), matching what `std::thread::
  available_parallelism()` itself reports and what most language
  standard libraries expose as their own default "how many workers should
  I spawn" answer. A separate `System.physical_cpu_count` accessor for
  the narrower physical-core number is a small, natural, declined-for-now
  addition.
- **Out of scope.** Network interface/bandwidth enumeration (`sysinfo`
  supports it via its own separate `Networks` collection, but this
  plan's own Concrete Proof and stated scope — "CPU/memory/disk/process"
  — do not need it; a natural, independent follow-up leaf); temperature/
  fan/battery sensor readings (`sysinfo`'s `Components` API, platform-
  support is markedly patchier than CPU/memory/disk/process and not
  needed here); any control surface whatsoever (kill/renice/suspend —
  see the read-only-boundary bullet above); a cached, explicitly-
  refreshable snapshot handle (see the no-long-lived-cache bullet
  above); any change to `runtime/emerald_runtime.c`.
