# Plan 103 — gRPC (Exploratory / Stretch Tier)

This is plan 103 of the 91-191 batch, the fourth of four plans
(100-103, this agent's assignment) wrapping vetted Rust crates as
native Emerald stdlib surface through plan 91's `emerald-rt` archive.
It is named here, plainly, as the heaviest-lift, lowest-priority,
optional/stretch-tier plan in the entire batch — not a hedge, a
description. Every other plan this agent authored (100-102) ends its
Decision log with a concrete, verified, shovel-ready mechanism. This
plan cannot honestly do that for its core problem. It is included
because the batch's brief asked for it, and because writing up *why* it
is hard, precisely, with real evidence, is itself useful groundwork for
whichever future plan actually attempts it — not because this plan
believes it has solved gRPC integration.

Depends on: plan 91 (`2026-09-21T200000Z-plan-91-rust-native-runtime-crate.md`
— `emerald-rt`'s build/embed mechanism; this plan is the first in the
batch to actually need plan 91's own still-open item 2, "whether the
wasm32-wasip1 cross-compile path... gets a matching `emerald-rt`-for-wasm
build," since `tokio`'s multi-thread runtime has no meaningful WASI
story — flagged here, not resolved by either plan), plan 101
(`2026-09-21T220500Z-plan-101-http-server.md` — its own trampoline
design is this plan's one working precedent, reused unmodified for the
single-method minimal slice, and explicitly NOT extensible to a
multi-method, schema-generated service, see Decision log), plan 10 and
plan 55 (`2026-09-08T192515Z-plan-10-blocks-closures.md`,
`2026-09-09T125000Z-plan-55-scheduler-and-message-passing.md`, both
read in full this session — the real, current state of "does this
language have first-class, storable callables": it does not; every
block/lambda mechanism that exists is either call-site-inlined (plan
10) or resolved to a single statically-known function pointer at one
call site (plan 55's trampolines, plan 101's reuse of that idea) —
there is no existing mechanism for a *dynamically selected, per-method*
callback table, which is exactly what a generated gRPC service needs).
Cites by number, not yet on disk: plan 92 (FFI/ABI — this plan's
`(ptr, len)`-per-message-field marshaling would follow it, but message
marshaling itself is blocked on the open problem below, not merely
unwritten), plan 93 (resource handles — a `tonic::transport::Channel`
client handle would follow plan 102's own `WebSocketConnection` model
directly; this is one of the few sub-problems in this plan that *is*
straightforward, see Decision log), plan 94 (async-to-sync bridging —
this plan is the batch's primary example of its heaviest branch,
explicitly named as such in the batch brief), plan 95 (crate vetting),
plan 99 (TLS via `rustls` — `tonic`'s own default TLS backend already
matches).

## Concrete proof this plan targets

Given the open problems below, this plan's Concrete Proof is
deliberately the smallest possible slice — a single, hardcoded,
non-`.proto`-generated RPC method, not a usable gRPC service surface:

```ruby
Grpc.serve(50051, "Echo") { |msg: String| msg }
```

Run against a real client from the same test harness (a Rust `#[test]`
using `tonic`'s own generated client against a single, hand-written
`.proto` — `service Echo { rpc Call(EchoRequest) returns (EchoResponse); }`
— compiled once, into the *test*, not into `emerald-rt` or any
`.em`-facing mechanism): a `Call` RPC carrying `"hello"` gets back
`"hello"`. This proves only that `tonic`'s async server, running inside
`emerald-rt`'s embedded `tokio::Runtime`, can invoke a single,
statically-resolved Emerald trampoline function pointer once per
request and return its result over real HTTP/2 — the same class of
proof plan 101 gives for HTTP, reduced to exactly one hardcoded method
name and one hardcoded message shape (`String -> String`), specifically
because a real `.proto`-driven multi-method service needs the
build-time code generation named as an open problem below. **This
example is not what a real `Grpc.serve` surface should look like** — it
exists only to prove the narrowest possible end-to-end slice (tonic
inside emerald-rt, invoking Emerald code once, over real gRPC) actually
links and runs, the same load-bearing-but-narrow role plan 91's own
FNV-1a proof played for the Rust-archive mechanism itself.

## Decision log

- **Why `tonic`, restated briefly since the choice itself is not in
  question — only the integration difficulty is.** `tonic` 0.14.6 (May
  7, 2026, confirmed via `lib.rs`/`docs.rs` this session), 28.6M
  downloads/month, used in 7,588 crates, is unambiguously the standard
  Rust gRPC implementation — maintained under the `hyperium` GitHub
  organization (the same org behind `hyper`/`h2`, the HTTP/2 stack every
  gRPC implementation needs), built on `prost` for protobuf codegen.
  There is no meaningful sync alternative in the Rust gRPC ecosystem to
  weigh against it the way plan 100 weighed `ureq` against `reqwest` —
  `tonic`'s own dependency list (read in full this session) is `tokio`,
  `hyper` 1.0 (`+http1 +http2`), `hyper-util`, `h2`, `tower`, `axum`
  0.8 (its `router` feature), `tower-http`, `tokio-rustls` — a fully
  async stack with no blocking-mode escape hatch anywhere in its public
  API. This is stated plainly, not softened: choosing `tonic` means
  fully accepting plan 94's heaviest branch, an embedded multi-thread
  `tokio::Runtime`, for this one domain — there is no smaller crate that
  gets Emerald real gRPC interoperability.
- **The load-bearing, honestly-unsolved problem: `tonic`'s generated
  service trait needs ONE Rust method per RPC defined in a `.proto`
  file, each of which must call back into Emerald code — a
  fundamentally different shape from every prior plan's callback
  problem, not a bigger version of the same one.** Plan 101's
  `Http.serve(port) { |req| ... }` has exactly one call site, one
  block, one statically-resolved function pointer — the compiler knows,
  at the point it compiles that one expression, the complete, final
  identity of the one function native code will ever call. A `.proto`
  file with, say, five RPC methods needs *five* separate dispatch
  targets, discovered not from Emerald source structure at all but from
  an external schema file, each with its own message-type signature.
  There is no existing mechanism anywhere in this compiler for
  "generate N distinct extern-callable entry points from a schema file
  parsed at build time and wire each one to N correspondingly-named
  pieces of Emerald source" — this is a strictly harder code-generation
  problem than plan 101's single trampoline, and this plan does not
  design it. The honest options this plan can only enumerate, not
  choose between: (a) `tonic-build`/`prost-build` run at `emerald-rt`'s
  own build time against a fixed `.proto`, generating Rust trampoline
  stubs whose *bodies* are hand-written per method (workable for a
  small, fixed, compile-time-known service, not for arbitrary
  user-authored `.proto` files); (b) a genuinely new Emerald-side
  interface-declaration mechanism (`grpc_service Echo ... end`, methods
  matched by name against a parsed `.proto`) that the compiler's own
  codegen would need to turn into per-method exported symbols, then
  have `emerald-rt`'s `tonic` glue resolve by name at either compile or
  link time — a real, substantial new compiler feature, not a stdlib
  wrapper. Neither is designed here; both are named so a future plan
  does not have to rediscover the shape of the problem from scratch.
- **The second, independent open problem: even a single resolved
  trampoline runs inside an async `tokio` task, and Emerald code is
  synchronous — a mismatch plan 55's own honest scope call already
  flags for a different reason, now recurring here.** Plan 55's
  Decision log states plainly that this codegen has "not one function
  whose job is saving/restoring an arbitrary call stack, spawning a
  fiber, or transforming a function into resumable states" — Emerald
  functions run to completion once called, with no yield point. Calling
  directly into compiled Emerald code from inside a `tonic` service
  method's `async fn` body blocks whichever `tokio` worker thread is
  currently polling that future for the entire duration of the Emerald
  call — for a fast handler this is a minor, tolerable inefficiency
  (the same "block one worker briefly" cost any FFI call into
  synchronous code pays inside an async runtime); for a slow one it can
  stall every other in-flight RPC sharing that worker. `tokio::task::
  spawn_blocking` is the standard, real fix — but this plan has not
  verified it interacts safely with anything else in this codebase
  running Emerald code concurrently (plan 55's actors, this batch's own
  `Http.serve` handlers). A `spawn_blocking` closure invoking Emerald
  code is not itself an actor and gets none of plan 55's "at most one
  in-flight message per actor" safety argument — if the invoked Emerald
  code happens to touch any shared state also reachable from an actor
  or an `Http.serve` handler running concurrently elsewhere, this plan
  cannot currently rule out a real data race. Stated as an open
  question, not resolved.
- **One resource-handle sub-problem this plan CAN answer cleanly: a
  `tonic` client channel.** Unlike the server-side callback problem
  above, a gRPC *client* call (Emerald code calling OUT to a real gRPC
  server) is architecturally identical to plan 100's `Http.get` —
  Emerald calls into `emerald-rt`, `emerald-rt` calls `tonic`'s client,
  blocks the embedded `tokio::Runtime`'s `block_on` on the response, and
  returns a value — no callback-direction problem at all, since the
  caller already knows what it's calling. A long-lived `tonic::
  transport::Channel` (connection pool to one gRPC server) fits plan
  93's opaque-`u64`-handle model directly, the same shape as plan 102's
  `WebSocketConnection`. This sub-problem is genuinely shovel-ready —
  named here so a future execution pass does not have to rediscover
  that the client and server halves of this plan have wildly different
  difficulty, the same asymmetry plan 100/101 already demonstrated for
  HTTP (client: easy, reuses plan 94's preferred branch; server: the
  hard direction) — except here even the *client* direction still needs
  the `.proto`-to-Rust-message-type codegen problem solved for anything
  beyond a fixed, hardcoded method signature, since `tonic`'s generated
  client stubs are themselves `.proto`-derived.
- **Why the minimal slice (one hardcoded method, no `.proto` codegen)
  is still worth stating as this plan's actual Concrete Proof, rather
  than declining to give one at all.** Plan 91's own methodology —
  prove the mechanism with the smallest possible real example before
  building on it — applies here even though this plan cannot complete
  the larger feature: confirming that `tonic`'s async server, `hyper`'s
  HTTP/2 stack, and a `tokio::Runtime` embedded inside `emerald-rt`'s
  static archive actually link, start, accept a real gRPC connection,
  and call back into one statically-known Emerald function is itself a
  nontrivial, independently useful fact to establish — it rules out a
  category of failure (the embedding/linking mechanism itself doesn't
  work under `tonic`'s heavier dependency footprint) separately from
  the harder, unresolved code-generation and concurrency-safety
  questions above.
- **Leaves are marked exploratory, not shovel-ready, because they
  describe design work, not implementation work — a real, disclosed
  distinction from every other plan in this batch.** Plans 100-102 each
  give their assigned executor a concrete signature list, a concrete
  representation, and a concrete integration point verified against
  real, current source and real, current crate documentation. Three of
  this plan's five leaves (`leaf-open-problem-*`) do not — they are
  scoped explicitly as "write the problem up precisely," not "build the
  thing," because this plan does not have an implementation to hand
  off. Marking them otherwise would misrepresent this plan's own
  actual state of readiness, the exact failure mode plan 91's own
  Decision log discipline (state a real limitation plainly rather than
  hiding it in a stale summary) exists to prevent.
- **Out of scope, some of it possibly permanently rather than merely
  "for v1."** Bidirectional/server/client streaming RPCs (even harder
  than the unary-call minimal slice above — a streaming RPC needs
  Emerald code to produce or consume a sequence of messages over time,
  compounding both open problems at once), gRPC reflection, load
  balancing, interceptors/middleware, and any `.proto`-to-Emerald-class
  code generation tool are all declined. A `DEPENDENCIES.md` ledger
  entry for `tonic`/`prost`/`tokio` (plan 95's checklist) should still
  be added by whoever executes even this plan's minimal slice, flagged
  as the heaviest dependency addition in the batch.

## Not yet decided

1. Which of the two named directions (build-time `.proto` codegen with
   hand-written trampoline bodies, vs. a new Emerald-side
   `grpc_service`/interface declaration form) is the right long-term
   design — genuinely open, not merely unresearched; both have real
   costs this plan does not have enough information to compare.
2. Whether `spawn_blocking`-per-call is actually safe against this
   project's other concurrency mechanisms (plan 55's actors, plan 101's
   `Http.serve` handlers) — requires either a careful, dedicated
   concurrency-safety analysis or a real, executable stress test neither
   of which this plan performs.
3. Whether this plan should exist as one plan at all, or whether the
   client-channel sub-problem (genuinely shovel-ready, see Decision log)
   should be split out into its own, separate, actually-shippable plan,
   leaving everything server-side explicitly blocked on the open
   problems above — left to whoever next touches this plan's scope.
4. The `wasm32-wasip1` question inherited from plan 91's own "Not yet
   decided" item 2, now concretely forced by `tokio`'s multi-thread
   runtime requirement rather than hypothetical — deferred, not
   resolved, exactly as plan 91 itself deferred it.
