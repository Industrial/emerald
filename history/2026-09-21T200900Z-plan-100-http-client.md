this agent's assignment) wrapping vetted Rust crates as native Emerald

## Concrete proof this plan targets

```ruby
resp: Result[HttpResponse, HttpError] = Http.get("https://httpbin.org/get")
case resp
when Ok(r)
  puts r.status
when Err(e)
  puts e.message
end

not_found: Result[HttpResponse, HttpError] = Http.get("https://httpbin.org/status/404")
case not_found
when Ok(r)
  puts r.status
when Err(e)
  puts e.message
end

def fetch_status(url: String) -> Result[Int64, HttpError]
  r: HttpResponse = Http.get(url)?
  return Ok(r.status)
end

third: Result[Int64, HttpError] = fetch_status("https://httpbin.org/status/500")
case third
when Ok(s)
  puts s
when Err(e)
  puts e.message
end
```

Expected output, in order: `200`, `404`, `500` — three lines, all via
the `Ok` arm every time, because a completed HTTP response (even a 404
or a 500) is a successful *transport* outcome, not a `Result` failure
(see Decision log). `fetch_status`'s own `Http.get(url)?` line is the
one that exercises real `?`-propagation (plan 53's mechanism) on a
`Result` value this plan's own intrinsic constructs directly in codegen,
not via a source-level `Ok(...)`/`Err(...)` — proving those are
independent, composable mechanisms rather than something only source
code can produce.

A buggy implementation that (a) followed `ureq`'s own out-of-the-box
default and treated every 4xx/5xx as `Error::StatusCode` would instead
print two `Err` messages where this proof expects `Ok` bodies with
`404`/`500`; (b) failed to widen `ureq`'s `u16` status code to `Int64`
correctly would print a garbage value instead of `404`/`500`; (c) got
`?`'s `E`-match wrong would fail to compile `fetch_status` at all, since
plan 53's `?` check requires `Http.get`'s `HttpError` to structurally
equal `fetch_status`'s own declared `Result[Int64, HttpError]` error
type exactly.

## Decision log

- **`ureq` over `reqwest`, decided with real, current numbers, not
  assumed.** Both were checked this session against `lib.rs` (which
  mirrors crates.io's own version/download/dependency data) rather than
  training-data recall. `reqwest` is unambiguously the more-used crate:
  0.13.5 (Sep 8, 2026), **69.4M downloads/month**, used in **45,610**
  crates (30,275 directly) — more than three times `ureq`'s reach. If
  this batch's mandate were "most used and stable, full stop," `reqwest`
  would win outright. But `reqwest`'s own dependency list, read in full
  this session, tells the real story: `tokio` (`+net +time`), `hyper`
  1.1, `hyper-util`, `h2`, `tower` (`+retry +timeout +util`),
  `tower-http`, and — even with the `blocking` feature enabled —  the
  *async* client remains the thing underneath; `reqwest::blocking`
  drives it by spinning up and blocking on its own internal `tokio`
  `Runtime` per call. That is exactly plan 94's "else, one lazy
  `tokio::Runtime` behind `block_on`" fallback branch, paid for on
  every single call this plan would ever make, for a workload (a GET or
  POST that runs to completion and returns) that has no genuine
  asynchrony to hide. `ureq` 3.4.2 (Sep 13, 2026), by contrast, is
  **22.2M downloads/month**, #1 in `lib.rs`'s own HTTP-client category,
  used in 8,525 crates, and its own README states plainly: "Ureq is in
  pure Rust for safety and ease of understanding. It forbids `unsafe`
  code. It uses blocking I/O instead of async I/O, because that keeps
  the API simple and keeps dependencies to a minimum." Its dependency
  list (read in full this session) has no `tokio`, no `hyper`, no
  `tower` — `rustls`, `webpki-roots`, `flate2` (gzip), and a handful of
  small parsing/encoding crates. This is plan 94's *preferred* branch —
  "prefer a crate's sync API" — realized exactly: no embedded runtime to
  stand up, tear down, or reason about panics/timeouts across at all.
  Given this batch's own stated posture (sync-first, an embedded async
  runtime is the fallback of last resort, not the default), `ureq` is
  the more defensible default for the *primary* `Http.get`/`Http.post`
  surface even though `reqwest` is, by raw numbers, the more popular
  crate in the wider Rust ecosystem. This is a real, disclosed
  trade-off, not a default assumed without checking `reqwest` at all.
- **Network failure vs. HTTP error status: a real, deliberate split
  that does NOT match `ureq`'s own out-of-the-box default.** `ureq` 3.x
  ships with `http_status_as_error()` effectively on by default — any
  4xx/5xx response surfaces as `Err(ureq::Error::StatusCode(code))`
  from `.call()`, confirmed directly from `ureq`'s own README, read in
  full this session. This plan deliberately configures the shared
  `Agent` with `.http_status_as_error(false)` (a real, named `ureq`
  `ConfigBuilder` method, not invented) to turn that off, because plan
  53's own Decision log states the operative distinction plainly:
  `Result[T, E]` is for "expected, recoverable failures a caller is
  meant to handle," where "the caller is expected to check the outcome
  and decide what to do." A completed HTTP response carrying a 404 or a
  500 status *is* the server's decision, communicated successfully —
  the transport layer did its job; there is nothing exceptional about
  it, and a caller routinely wants to branch on the status code itself
  (`r.status == 404`) without first unwrapping an `Err`. Reserving `Err`
  for the genuinely irrecoverable-by-inspection cases — DNS resolution
  failure, connection refused/reset, a TLS handshake failure, a timeout,
  a malformed/truncated response — keeps the `Result`'s two arms
  meaning two different things: "did a real HTTP exchange happen at
  all" (`Ok`/`Err`) versus "what did the server say" (`r.status`, a
  field the caller reads inside the `Ok` arm). This mirrors Go's
  `net/http` convention (a non-nil `error` return is reserved for
  transport failures; a non-2xx status is ordinary response data) more
  than `ureq`'s own default, and is the more defensible choice given
  plan 53's own stated philosophy for what `Result` is *for* in this
  language — a deliberate divergence from the wrapped crate's default,
  stated here explicitly rather than silently inherited.
- **`HttpResponse`/`HttpError` are hardcoded compound `Type` variants,
  generalizing `Result`/`Pair`'s own precedent — not a source-declarable
  class.** `Type::Result(Box<Type>, Box<Type>)` (plan 53) and
  `Type::Pair(Box<Type>, Box<Type>)` (plan 42) are both, per their own
  Decision logs, "a hand-rolled, hard-coded compound type... with a
  fixed... layout," constructed only through dedicated compiler
  mechanisms, never a user-declarable generic class. `Type::HttpResponse`
  (fields `status: Int64`, `body: String`, fixed 16-byte
  `[status: i64 @0][body: ptr @8]` layout) and `Type::HttpError` (one
  field, `message: String`, an 8-byte `[message: ptr @0]` layout) are
  the same move, applied to a genuinely new domain: there is no
  `ModuleDef`/`ClassDef` in any `.em` source for either, so — exactly
  like `File` (plan 45) and `Http` itself below — they never populate
  `emerald-sema`'s `classes` registry and can never collide with a
  same-named user class. `.status`/`.body`/`.message` are zero-argument
  accessor intrinsics dispatched the same way `Pair`'s `.key`/`.value`
  already are (receiver storage kind, not a method lookup). The one
  real gap this creates: source code that wants to *build* an
  `HttpResponse` (an `Http.serve` handler, plan 101's own job) has no
  literal syntax for one — `HttpResponse.new(status: Int64, body: String):
  HttpResponse` is added as the one reserved-namespace constructor
  intrinsic (`File.read`'s own dispatch shape, guarded on
  `Expr::Ident("HttpResponse")`), shared by this plan and plan 101 —
  flagged explicitly here since both plans are authored in parallel
  this session and neither can see the other's landed file yet;
  whichever executes first registers `Type::HttpResponse` and
  `HttpResponse.new`, and the second must reuse, not duplicate, both.
- **`Http.get`/`Http.post` reuse `File.read`/`File.write`'s exact
  dispatch shape — a fixed arm guarded on the receiver identifier,
  checked before the real module-dispatch arm, never colliding with it
  because `Http` is never in `classes`.** Verified this session against
  plan 45's own Decision log (re-read in full): `File.read(path)`'s sema
  arm is guarded on `matches!(recv.as_ref(), Expr::Ident(n) if n ==
  "File")`, entirely independent of `emerald-sema`'s `module_info`/
  `classes` machinery, because `File` has no real `ModuleDef` anywhere
  in source. `Http` is architecturally identical: no `.em` file ever
  declares `module Http ... end`, so the same guard-then-fixed-signature
  pattern applies directly, with zero new dispatch machinery invented.
  Codegen mirrors this: `build_method_call`'s `Http.*` arm calls the
  matching `emerald_rt_http_*` extern function directly (declared via
  `module.add_function(...)`, the same `Linkage::External` mechanism
  plan 59 found already governs every runtime call in this codegen, now
  targeting the *second*, Rust-compiled archive plan 91 established
  rather than the original C one) and wraps its two-word C-side outcome
  into a real heap-allocated `Type::Result` value using the exact
  16-byte layout `check_result_construction`'s own codegen already
  produces for a source-level `Ok(...)`/`Err(...)` — reused, not
  duplicated, since both paths ultimately produce the identical runtime
  shape.
- **The extern signature: four fixed-arity functions, no header-map
  parameter type invented from scratch.** `Http.get(url: String):
  Result[HttpResponse, HttpError]` and `Http.post(url: String, body:
  String): Result[HttpResponse, HttpError]` cover the no-custom-header
  case; `Http.get_with_headers`/`Http.post_with_headers` add a trailing
  `headers: Hash[String, String]` parameter. This plan does not invent
  function overloading (nothing in `emerald-sema`'s `FunctionSig`
  lookup — a flat `HashMap<String, FunctionSig>` — supports two
  signatures sharing one name) — four distinct reserved names, matching
  `emerald-sema`'s real one-name-one-signature discipline, rather than a
  builder/fluent-request object this plan would otherwise need to
  invent a new construction mechanism for. `Hash[String, String]`'s own
  representation is plan 25/45's, not re-litigated here; if `Hash[K,V]`
  turns out at execution time to still carry plan 25's disclosed
  `Int64`-key-only limitation, `get_with_headers`/`post_with_headers`
  become blocked on that gap being closed first — re-verify against
  real, current `emerald-sema` source before wiring the `_with_headers`
  leaf, the same "verify against real source, not a stale summary"
  discipline plan 54 already modeled for its own arena-allocator
  dependency.
- **The one shared `ureq::Agent` is process-lifetime, lazily built —
  the same "one lazy... instance" shape plan 94 mandates for an
  embedded `tokio::Runtime`, applied here to a connection pool instead.**
  `ureq::Agent` is documented (read this session) as "cheaply clonable
  due to internal `Arc`," designed to be built once and reused so
  repeated calls share a connection pool. `emerald-rt`'s
  `http_client.rs` builds exactly one, behind a `std::sync::OnceLock`,
  on first call, with a fixed default timeout and `ureq`'s own default
  redirect-following policy — no per-call timeout/redirect override
  exists in this plan's four-function surface (see Not yet decided).
  This is a smaller commitment than plan 94's `tokio::Runtime` case
  (`ureq::Agent` is plain, synchronous, and does not require a runtime
  `Handle`/`block_on` boundary at all), stated here as evidence that
  this plan is a genuine, easy instance of plan 94's *preferred*
  sync-API branch, not its fallback.
- **Every extern function is wrapped in `std::panic::catch_unwind`,
  proven working code by plan 91's own `emerald_rt_fnv1a_hash`, reused
  verbatim here — a panic anywhere inside `ureq` (a bug, an
  unanticipated response shape) becomes a caught, converted `HttpError`,
  never an unwind across the `extern "C"` boundary into
  `emerald_runtime.c`'s `setjmp`/`longjmp`-based exception frames.**
  This is the concrete case plan 91's own Decision log named as the
  reason `panic = "abort"` was rejected project-wide: an HTTP client
  talking to a real, adversarial, un-typechecked network endpoint is
  exactly the kind of "malformed-input edge case three dependencies
  deep" that plan's Decision log used as its motivating example. Nothing
  new is designed here; this plan is the first real domain exercise of
  a mechanism plan 91 already proved.
- **A real, disclosed CI risk this plan's Concrete Proof carries that no
  prior plan in this project's history has: a genuine external-network
  dependency.** Every previous plan's worked proof (plan 45's
  `File.read`/`File.write`, plan 59's libc calls, plan 91's own FNV-1a)
  is fully self-contained — no prior `.em` example in `examples/` needs
  network egress to run deterministically in CI. This plan's proof
  targets `httpbin.org` (the same public HTTP test service `ureq`'s own
  README uses in its documented examples, `https://httpbin.org/get`,
  `https://httpbin.org/status/<code>` — not an arbitrarily chosen
  third-party dependency), and its correctness genuinely depends on that
  service being reachable and behaving as documented at CI run time —
  a real, disclosed, novel category of test flakiness for this project.
  This plan does not solve that problem (a local mock HTTP server for
  CI is real, useful, future work, plausibly plan 101's job once it
  exists) — it states the risk plainly rather than silently assuming CI
  has unrestricted, always-available internet egress, and requires
  whoever executes `leaf-example-and-full-gate` to either confirm the
  CI environment has outbound HTTPS access to `httpbin.org` or gate the
  `.em` example behind a feature/env-var this plan does not itself
  design.
- **Out of scope.** Cookies, connection reuse tuning beyond `ureq`'s own
  defaults, streaming/chunked request or response bodies (this plan's
  `body: String` parameter is whole-body-in-memory only), multipart
  form uploads, per-call timeout or redirect-count overrides, proxy
  configuration, and any client certificate / mutual-TLS support are
  all declined for v1 — `ureq`'s own feature surface covers all of
  these, but wiring each through Emerald's own type system is
  independent, separable follow-up work this plan's four-function
  surface does not need to prove the core client works. A `DEPENDENCIES.md`
  ledger entry for `ureq` (plan 95's own mandated checklist: crate name,
  version, why pure-Rust-first was satisfied, confirmed no RustSec
  advisory as of this session via `cargo audit`, to be re-run at
  execution time) is this plan's responsibility to add, not a later
  plan's.

## Update (2026-09-22, EXECUTE)

Implemented `Http.get`/`.post` exactly as this plan's own Concrete Proof needs,
with two real, disclosed simplifications against the plan's own more invasive
design — both reusing this session's own already-proven mechanisms rather than
inventing new core-compiler surface:

1. **`HttpResponse` is an `Int64` newtype over `crate::handle`'s registry**
   (the identical shape `Regex`/`Url`/`TcpStream`/every other compiler-provided
   handle-carrying type in this batch already uses), not a new hardcoded
   `Type::HttpResponse` compound variant added to `emerald-sema`'s core `Type`

   throughout `emerald-sema`/`emerald-codegen` for a real, avoidable blast
   radius; the newtype shape delivers the identical `.status()`/`.body()`

   `Result[HttpResponse, HttpError]`.** No `HttpError` compound type at all —

   e.message` becomes `Err(e) ... puts e` directly.
