# Plan 147 — Temporary Files & Directories

Creating a temporary file correctly is a known hard problem, not a
formality: the file's name must be unpredictable enough that another
process (or attacker) cannot guess it and race to create it first
(a classic TOCTOU symlink-attack vector when temp-file creation is
hand-rolled with a predictable name and a naive `open()`), and its initial
permissions must be restrictive from the very first `open()` call, not
fixed up with a `chmod` afterward, which leaves a real window where the
file briefly exists with default, too-permissive permissions. The
`tempfile` crate (v3.27.0 as of this session, its own crates.io listing
describing itself as "A secure, cross-platform, temporary file library for
Rust", actively maintained) exists specifically to get these details
right once, audited, rather than have every consumer re-derive them —
exactly the case where this batch's "prefer a vetted crate over hand-
rolled code" directive is at its strongest: this is precisely the kind of
security-sensitive primitive plan 91's own framing anticipates, and
precisely the kind of primitive plain `std::fs` alone (used naively) is
most likely to get subtly, dangerously wrong.

## Concrete proof this plan targets

```ruby
tf: Tempfile = Tempfile.create
p: String = tf.path
File.write(p, "temporary contents")
back: String = File.read(p)
puts back
puts Path.exists(p)

tf.close
puts Path.exists(p)
```

Expected output, in order:
```
temporary contents
true
false
```

Trace: `Tempfile.create` allocates a real, race-free-named file on disk
(via `tempfile::NamedTempFile::new()`) and hands back its real path;
plan 45's `File.write`/`File.read` operate on that path exactly as they
would any other, proving `Tempfile`'s path is a genuinely ordinary
filesystem path, not a special in-memory construct. `Path.exists(p)` (plan
144) is `true` while the handle is open. `tf.close` triggers `tempfile`'s
own real `unlink` via this plan's explicit-drop mechanism; `Path.exists(p)`
is `false` immediately after — the deterministic-cleanup proof this
plan's whole design exists to deliver.

## Decision log

- **`Tempfile`/`Tempdir` follow plan 93's ordinary explicit-`.close()`
  discipline — this is a considered decision against making them an
  exception, not an oversight of the task's own suggestion that they
  might deserve one.** The case *for* an exception is real: `tempfile`'s
  whole value proposition, as a crate, is "you cannot forget to clean
  this up" — `NamedTempFile`/`TempDir`'s `Drop` impls delete the
  underlying file/directory the moment the Rust value goes out of scope,
  with no explicit call needed, in ordinary Rust code. But Emerald's own
  memory model has no equivalent trigger to offer: `emerald_alloc`'s own
  doc comment, already cited by plan 45, discloses "no free... no
  lifetime tracking" — heap values in Emerald are never individually
  freed at all; arenas are bulk-freed at coarse boundaries (function
  return, per plan 51; actor termination, per plan 57), with no
  per-object finalizer/destructor hook anywhere in this architecture. A
  `Tempfile` handle that merely goes out of scope on the Emerald side —
  the local variable stops being referenced — triggers *nothing* on the
  Rust side; the `NamedTempFile` this plan's registry is still holding
  keeps right on existing, unlinked-from-Emerald but not unlinked-from-
  disk, until either an explicit `.close()` call reaches it or the whole
  process exits. Given that, an "automatic cleanup" promise this plan
  cannot actually keep would be strictly worse than an honest, uniform
  `.close()` requirement matching every other resource in plan 93's
  model — a false promise of automatic safety is a worse failure mode
  than an honest, consistent manual one.
- **`tempfile`'s creation-time security guarantees remain fully real and
  fully used even though this plan declines its auto-cleanup half.**
  Unpredictable naming and correct-from-creation permissions are
  properties of the `open()`/name-generation call itself — they exist
  the instant `NamedTempFile::new()` returns, independent of whether
  anything later calls `.close()` or not. This plan is not "half-using"
  `tempfile` apologetically; it uses the entire creation-time security
  surface the crate exists to provide, and simply routes the deletion
  half through an explicit call instead of an implicit one — the crate's
  `Drop` impl still performs the actual `unlink`/`remove_dir_all`
  syscall in both cases, this plan only chooses *when* that trigger
  fires, never reimplementing the deletion logic itself.
- **A forgotten `.close()` leaks the temp file until process exit — a
  real, disclosed gap, not a silent one, and no worse than the
  equivalent gap in plan 93's model for every other resource.** If an
  Emerald program never calls `.close()` on a `Tempfile`, the entry
  in this plan's Rust-side registry (and the real file on disk) survives
  for the life of the process; nothing in Emerald's own memory model can
  detect or reclaim it. This mirrors the same forgotten-resource risk
  plan 93 already accepts as the tradeoff of an explicit-close model in
  general (a forgotten `FileLock.close()`, per plan 148, leaks a held
  advisory lock the identical way) — `Tempfile` is not carrying a new or
  worse risk than its siblings, and OS-level temp-directory cleaners
  (`systemd-tmpfiles`, cron-based `/tmp` sweeps) provide the same
  eventual, best-effort backstop a leaked file already relies on with or
  without this plan's own explicit-close discipline.
- **The registry, not a raw pointer stashed inside an Emerald heap
  value, is what actually owns the live `tempfile::NamedTempFile`/
  `TempDir` value — a deliberate structural choice forced by the
  Drop-trigger problem above.** If this plan instead boxed the
  `NamedTempFile` and handed Emerald a raw pointer to it (the pattern
  plan 144's `FileMetadata` uses, since that type is inert plain data
  with no `Drop` impl that matters), there would be no single, obvious
  place to call `drop()` on it explicitly — `.close()` would have to
  reconstruct a `Box` from a raw pointer and drop that, which is exactly
  what the registry approach already does more safely, with an ordinary
  `i64` handle id (plan 93's own recommended shape for exactly this
  situation) instead of a raw pointer round-tripping through Emerald-
  visible memory.
- **Out of scope.** Anonymous/unnamed temp files (`tempfile::tempfile()`,
  which never has a nameable path at all, useful for scratch space a
  program never needs to hand to another process/tool) — declined
  because this plan's own Concrete Proof specifically needs a real path
  to exercise plan 45's `File.read`/`File.write` and plan 144's
  `Path.exists` against, which an anonymous handle cannot provide; a
  distinct `Tempfile.create_anonymous` entry point is a natural, small,
  independent follow-up. Any process-exit-time best-effort sweep of
  still-open `Tempfile`/`Tempdir` handles beyond what the OS's own
  standard temp-directory cleanup already provides (deferred, see `Not
  yet decided`). Any change to `runtime/emerald_runtime.c` or to plan
  45's `File.read`/`File.write` themselves.
