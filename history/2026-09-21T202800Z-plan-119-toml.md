# Plan 119 — TOML

This is plan 119 of the 91-191 batch, sibling to plan 118 (JSON), whose
`JsonValue` tagged-union enum and `emerald-rt`/`emerald_alloc`/
`catch_unwind` mechanism this plan depends on directly and does not
re-derive. Crate: `toml`.

This plan's framing is different from every other plan in this batch in
one specific, load-bearing way, worth stating up front: **this
repository already depends on `toml`.** Verified this session, read
directly: `crates/emerald-cli/Cargo.toml` line 24 has `toml = "0.8"`
sitting right next to `serde = { version = "1", features = ["derive"]
}`, and `crates/emerald-cli/src/manifest.rs` uses `serde::Deserialize`
to parse `emerald.toml` itself into a real `Manifest { package:
PackageMeta, dependencies: BTreeMap<String, DependencySpec>, ffi:
FfiSpec }` struct — exactly the package-manifest mechanism plan 46
(`2026-09-09T112000Z-plan-46-package-manager-and-build.md`) designed
and, per this verified evidence, shipped. Every Emerald project on this
machine that has ever run `emerald build` has already trusted this
crate to parse its own build configuration. This plan's job is
therefore narrower than plan 118's: not "should Emerald trust `toml`"
(already answered, years of this project's own bootstrapping depend on
the answer being yes) but "expose that same trust to Emerald *user*
programs" — `Toml.parse`, not a new dependency-vetting decision.

The dynamic-value question plan 118 already answered is not re-derived
here. A parsed TOML document becomes the *same* `JsonValue` enum plan
118 defines — `Toml.parse` does not introduce a second, parallel
`TomlValue` tagged union. This is a deliberate, real design choice
(see Decision log), not laziness: TOML's own value model (string,
integer, float, boolean, datetime, array, table) is a strict *subset*
of JSON's tagged-union shape once datetimes are folded into strings, so
introducing a second enum would mean either (a) two structurally
near-identical enums with none of `case`/`when`'s exhaustiveness
checking able to unify them, or (b) `TomlValue` variants that never
appear in the `JSON` half of any program using both formats. Reusing
`JsonValue` means a value read from a TOML config file and a value read
from a JSON API response are the *same type*, destructured by the same
`case`/`when` arms — a real, concrete convenience this plan gets for
free by not inventing a second representation.

## Concrete proof this plan targets

```ruby
input: String = "[package]\nname = \"demo\"\nversion = \"0.1.0\"\n\n[package.tags]\nlang = \"emerald\"\n"

match Toml.parse(input) do
Ok(doc) do
  pkg: JsonValue? = doc.get("package")
  pkg ||= JsonNull()
  case pkg
  when JsonObject(fields)
    name: JsonValue? = fields.get("name")
    name ||= JsonNull()
    case name
    when JsonString(s)
      puts s
    else
      puts "missing"
    end
  else
    puts "missing"
  end
end
Err(msg) do
  puts msg
end
end
```

Expected output: `demo` — a real proof that a nested TOML table
(`[package]`, itself containing a further-nested `[package.tags]` this
example doesn't even need to touch) round-trips through the `toml`
crate's own parser into `JsonValue`'s `JsonObject(Hash[String,
JsonValue])` shape, and that plan 118's `.get` intrinsic works
identically regardless of which parser produced the `JsonValue` tree.
A second, real negative proof: `Toml.parse("not = valid = toml")`
reaches `Err(msg) do ... end` with the `toml` crate's own real parse-
error text (a duplicate-key/unexpected-token diagnostic, not a crash).

## Decision log

- **`Hash[String, JsonValue]` for `JsonObject`, not a `Vec<(String,
  JsonValue)>`-shaped `Array[Pair[String,JsonValue]]`.** Plan 118
  already made and justified this choice (`Hash[K,V]`'s literal
  construction has no key-type restriction; only `[]` indexing is
  broken for non-`Int64` keys, worked around by `.get`) — this plan
  inherits it unchanged rather than re-litigating it, since reusing
  `JsonValue` means reusing every design decision baked into it, not
  just its variant list.
- **Version skew, disclosed rather than silently carried forward.**
  `crates/emerald-cli/Cargo.toml`'s real, current pin is `toml = "0.8"`
  — but `toml`'s own current release, verified this session against
  `lib.rs`'s real crate page, is **1.1.6+spec-1.1.0** (published Sep 10,
  2026), a full major version ahead, now targeting TOML spec 1.1.0
  rather than 0.8.x's spec 1.0.0 support. This plan pins `emerald-rt`'s
  own `toml` dependency to `"1"` (the current, spec-1.1.0-capable
  major), not `"0.8"` — `emerald-rt` is a separate crate with its own
  `Cargo.toml`; Cargo workspaces tolerate two member crates depending on
  different semver-incompatible majors of the same library with no
  conflict (each gets compiled and linked as its own, independent unit).
  This is a real, deliberate divergence from "reuse the exact in-tree
  version," stated plainly: bumping `emerald-cli`'s own `emerald.toml`-
  parsing dependency to match is a reasonable, small, disclosed
  follow-up this plan does not fold in as a side effect (touching
  `emerald-cli`'s manifest-parsing path is a real behavior change to
  this project's own build tooling, outside a stdlib-for-user-programs
  plan's surgical-edit charter) — verified via `toml`'s own real version
  history (`lib.rs`), not assumed stable across a year and a half.
- **TOML's own type system is a proper subset of `JsonValue`'s six
  variants once `Datetime` is folded into `JsonString`.** `toml::Value`'s
  real variants (verified: `docs.rs/toml/latest/toml/enum.Value.html`)
  are `String`, `Integer`, `Float`, `Boolean`, `Datetime`, `Array`,
  `Table` — a strict subset of JSON's `null`/`bool`/`number`/`string`/
  `array`/`object`, missing only `null` (TOML has no null literal at
  all — an absent key is simply absent, never present-and-null) and
  gaining exactly one extra concept, `Datetime` (TOML's own native
  timestamp literal, `1979-05-27T07:32:00Z`), that JSON has no
  equivalent for. `Integer`/`Float` both widen to `JsonNumber(Float64)`
  (plan 118's own numeric-widening decision, reused unchanged — the
  same `is_i64()`-vs-`is_f64()` argument against a dual variant applies
  identically here). `Datetime` lowers to `JsonString(<TOML's own
  canonical RFC 3339 text>)` — a disclosed, one-way simplification: a
  round-tripped TOML datetime becomes an ordinary Emerald `String`, not
  a distinguishable value a `case` arm could tell apart from a plain
  string that merely looks like a timestamp. A `JsonDatetime` seventh
  variant was considered and declined: it would mean either JSON's own
  five-variant proof (plan 118) grows a sixth variant no JSON document
  can ever construct, or this plan's `toml::Value -> JsonValue` lowering
  becomes the only place in the whole batch that produces it —
  asymmetric complexity for a type this plan's own worked example
  doesn't need to distinguish.
- **`Toml.parse` returns `Result[JsonValue, String]`, mirroring `Json.
  parse` byte-for-byte — same intrinsic dispatch shape, same FFI
  out-parameter convention, same `catch_unwind` wrapping, cited to plan
  92 the identical way plan 118 already did.** No new sema/codegen
  mechanism is introduced by this plan at all: `Toml.parse` is a second
  arm of the exact `File`/`Json`-namespace-style intrinsic dispatch
  plan 118 already built (guarded on `Expr::Ident(n) if n == "Toml"`,
  parallel to the existing `n == "Json"`/`n == "File"` guards, per plan
  45's own established arm-ordering hygiene — these names can never
  collide with a `ClassInfo`/`ModuleDef` registration because none of
  them are ever declared in `.em` source).
- **`JsonValue.to_toml` is `Result[String, String]`, not a total
  `String` — because not every `JsonValue` a JSON document can produce
  is representable in TOML, and this plan does not pretend otherwise.**
  TOML has no `null` literal (see above) — a `JsonNull()` value
  anywhere inside a tree passed to `.to_toml` (as a top-level value, an
  array element, or an object field's value) cannot be serialized; the
  `toml` crate's own `Serialize` implementation for an equivalent
  Rust-side `Option::None`/unit-like absence already returns a real
  `toml::ser::Error` for exactly this shape, and `emerald_rt_json_to_
  toml` propagates that as `Err(<the crate's own Display text>)` rather
  than silently dropping the null field or crashing. This is the
  concrete, disclosed reason `.to_toml` cannot share `.to_s`'s (plan
  118, JSON serialization) total, always-succeeds signature.
- **No `TomlValue`, no second enum, no schema-first typed-deserialize
  path — for the identical reasons plan 118 already gave for JSON, not
  re-derived here.** Reusing `JsonValue` also means this plan inherits
  plan 118's typed-deserialization scope cut unchanged: Emerald has no
  macro/attribute system, so a `#[derive(Deserialize)]`-equivalent for
  TOML is exactly as unbuildable here as it is for JSON, for the exact
  same reason (no reflection, no `method_missing`, no codegen-attribute
  mechanism) — restated briefly rather than left to an implicit
  "obviously the same," since the task's own instructions ask every
  plan to state this honestly rather than assume a sibling plan's
  answer travels silently.
- **`emerald.toml`'s own already-shipped manifest parsing is untouched
  by this plan.** `crates/emerald-cli/src/manifest.rs`'s `Manifest`/
  `PackageMeta`/`DependencySpec`/`FfiSpec` structs stay exactly as they
  are, deserializing directly into typed Rust structs via `serde::
  Deserialize` the way they already do (plan 46) — this plan's `Toml.
  parse` is a completely separate code path (`emerald-rt`, reachable
  only from compiled Emerald *user* programs) that happens to reuse the
  same underlying crate, not a refactor of the compiler's own bootstrap
  tooling to route through it. `emerald build`/`emerald new`/`emerald
  run` do not change behavior in any way as a result of this plan.
- **Out of scope.** Bumping `emerald-cli`'s own `toml = "0.8"` pin to
  `"1"` (see the version-skew bullet — a real, disclosed, small, but
  separate follow-up); a `JsonDatetime` variant or any TOML-specific
  value distinction beyond what folding into `JsonString` already
  covers; typed/derive deserialization (inherited scope cut from plan
  118); TOML document *editing* that preserves comments/formatting
  (the real, different problem `toml_edit` — a sibling crate under the
  same `toml-rs` GitHub organization, not evaluated here — solves; this
  plan is read-and-reserialize only, and a reserialized document is not
  guaranteed to preserve the original's comments, key order beyond what
  `JsonObject`'s own `Hash[K,V]` buffer order already carries, or exact
  formatting); TOML's array-of-tables (`[[array]]`) distinction from a
  plain nested array — the `toml` crate's own `Value::Array` already
  collapses this at the Rust level, so `JsonArray` inherits the same
  collapse, disclosed rather than treated as a gap this plan introduces.
