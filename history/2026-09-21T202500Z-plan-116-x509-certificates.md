# Plan 116 — X.509 Certificate Generation & Parsing

Generating and parsing a certificate are different enough jobs, with
different enough trust models, that a single crate rarely does both well
— `rcgen`'s own README is a generator, full stop, and `x509-parser`'s own
README is a parser, full stop; this plan wires one of each together
rather than searching for a do-everything alternative.

`rcgen` — verified this session via `lib.rs`, current release `0.14.10`
(2026-08-28), maintained under the `rustls` GitHub org (Dirkjan Ochtman
and est31, the same maintainers behind `rustls` itself), MIT/Apache-2.0,
12.1M downloads/month, used directly by 1,739 crates — exists to *mint*
certificates: self-signed ones for local development and test fixtures,
or CA-signed ones for programmatic issuance. Its own README's worked
example is exactly this plan's core use case: `generate_simple_self_
signed(subject_alt_names)` returning a `CertifiedKey { cert, signing_key
}` pair, `cert.pem()` and `signing_key.serialize_pem()` giving back
ready-to-use PEM text. Verified against its `docs.rs` dependency listing,
`rcgen`'s default crypto backend is `ring` 0.17 (an `aws_lc_rs` feature
exists as an alternative, not enabled by this plan), with an *optional*
`x509-parser` 0.18 dependency for the crate's own self-verification —
this plan enables that same feature so `rcgen`'s own round-trip tests and
this plan's separate parsing path exercise one shared `x509-parser`
version, not two potentially-diverging ones.

`x509-parser` — verified this session via `lib.rs` and its own README,
current release `0.18.1` (2026-02-05), maintained by Pierre Chifflier
under the `rusticata` project, MIT/Apache-2.0, 14.9M downloads/month, used
directly by 668 crates — exists to *read* an existing DER- or PEM-encoded
certificate apart: "written in pure Rust, fast, and makes extensive use
of zero-copy... aims to be panic-free," built on the `nom` parser-
combinator framework. Its default feature set does no cryptographic
signature verification at all (that's the crate's own optional `verify`/
`verify-aws` features, which pull in `ring`/`aws-lc-rs` respectively and
which this plan does not enable) — this plan uses it purely to read a
certificate's own self-declared fields (subject, issuer, validity window,
public key algorithm), which requires no trust decision about whether the
certificate is legitimate, only that it parses as well-formed X.509.
Verifying a certificate's signature against a trusted root, and the full
chain-of-trust question, belongs to plan 99 (TLS) and `rustls` itself —
this plan's `.parse()` is a data-structure reader, not a validator, and
that distinction is the plan's whole scope boundary.

## Concrete proof this plan targets

```ruby
names: Array[String] = ["localhost", "hello.world.example"]
pair: Tuple[String, String] = X509.generate_self_signed(names)
cert_pem: String = pair.first
key_pem: String = pair.second

cert: X509Certificate = X509.parse(cert_pem)
puts cert.subject()
not_before: String = cert.not_before()
not_after: String = cert.not_after()
puts not_before < not_after
puts key_pem.length > 0
```

Expected output: line 1 contains `CN=localhost` (`rcgen`'s own default
subject naming for `generate_simple_self_signed`'s first SAN entry,
verified against the crate's own worked example producing exactly this
subject shape); line 2 is `true` (a freshly generated certificate's
`not_before` always sorts lexically before its `not_after` in RFC 3339
text, since RFC 3339 timestamps are lexically sortable by construction
and `rcgen` sets a validity window ending after it starts); line 3 is
`true` (the generated private key's PEM text is non-empty).

## Decision log

- **Generation and parsing are two independently-choosable crates,
  bridged only by a shared PEM `String`, not one library wrapped twice.**
  `rcgen` produces PEM text; `X509.parse` accepts PEM text; nothing in
  this plan's Rust implementation passes an `rcgen`-internal type
  directly into `x509-parser` (even though `rcgen`'s own optional
  `x509-parser` feature dependency, enabled here, lets the crate do
  exactly that internally for its own round-trip self-tests) — the two
  halves of this plan only ever communicate through the same PEM text an
  external tool (`openssl x509 -text`, a browser, a second Emerald
  program) would also produce and consume. This keeps the plan's two
  entry points genuinely independent: a caller can parse a certificate
  this plan never generated (one issued by Let's Encrypt, one pasted from
  a config file) exactly as easily as one it minted itself.
- **`X509.parse`'s return value is an opaque handle governed by plan 93's
  resource/lifetime model, not a struct with Emerald-visible fields —
  because the underlying Rust type genuinely cannot be flattened into one
  safely.** `x509_parser::certificate::X509Certificate<'a>` is a borrowed
  view into the DER bytes `parse_x509` was given — verified against the
  crate's own `from_der` signature and usage example, which keeps the
  original DER buffer (`IGCA_DER` in the crate's own doctest) alive
  alongside the parsed `cert` for as long as `cert` is used. Emerald has
  no borrow checker and no lifetime system (plan 59's `CString` design
  faced the same shape of problem for a much simpler bare pointer); this
  plan's handle resolves it exactly as plan 91's own architecture
  anticipates such cases being resolved — by boxing the owned DER bytes
  and the parsed view together behind one opaque handle whose lifetime
  plan 93 governs, never exposing the borrowed reference or the raw DER
  buffer to Emerald source directly.
- **Accessor methods return freshly-formatted `String`s on every call,
  not cached values — a real, disclosed cost, not an oversight.** `.subject()`
  and `.issuer()` re-run the underlying `X509Name`'s `Display`
  formatting, and `.not_before()`/`.not_after()` re-format the parsed
  `ASN1Time` as RFC 3339 text, on every accessor call rather than once at
  parse time. This is a deliberate simplicity choice for this plan's v1
  surface: caching would mean deciding where the cached `String`s live
  relative to the handle's own plan-93-governed lifetime, a real design
  question this plan defers rather than answers casually; re-formatting
  on each call is slower but trivially correct, and nothing in this
  batch's proof calls these accessors in a hot loop where the difference
  would matter.
- **No signature-verification feature (`verify`/`verify-aws`) is enabled
  on `x509-parser` in this plan, even though the crate offers one.**
  Verified against the crate's own README: `X509Certificate::verify_
  signature()`, gated behind the `verify`/`verify-aws` features, checks
  "certificate was signed by issuer" against a `ring`- or `aws-lc-rs`-
  backed cryptographic check. Enabling it here would pull a second,
  different crypto backend (`ring` or `aws-lc-rs`) into `emerald-rt`
  alongside the RustCrypto-ecosystem crates plans 109/111/112/114/115/117
  already select, purely to answer a question — "was this certificate
  chain properly signed by a trusted root" — that plan 99's TLS design
  (built on `rustls`, itself `ring`/`aws-lc-rs`-backed already) is the
  correct place to answer once, not a question this plan's narrower
  "read a certificate's own fields" scope needs to duplicate.
- **`rcgen`'s `generate_simple_self_signed` is this plan's only generation
  entry point — no CA-signing, intermediate-chain, or custom-extension
  API in v1, despite `rcgen` supporting all three.** The crate's own
  richer `CertificateParams`/`Certificate::from_params` API (building a
  cert signed by a separate CA key, or with custom X.509 extensions —
  key usage, extended key usage, custom OIDs) is real and documented, but
  exposing it faithfully as an Emerald API is a substantially larger
  surface (an Emerald-visible way to express arbitrary X.509 extensions,
  which has no natural home in Emerald's existing type system today) this
  plan's proof — mint a usable self-signed cert, read it back — does not
  need. `generate_simple_self_signed` alone is enough to produce a real,
  working TLS server certificate for local development, this plan's
  actual target use case.
- **Certificate/key PEM output crosses the FFI boundary as plain
  `String`s with no `(ptr, len)` buffer convention needed, unlike this
  batch's raw-random-bytes plans.** PEM is ASCII-armored text by
  definition (base64 plus `-----BEGIN...-----`/`-----END...-----`
  delimiters) — plan 59's finding that Emerald's `String` is a bare
  null-terminated `char*` imposes no hazard here the way it does for
  plan 113's raw random bytes or plan 115's raw KDF input/output, since
  PEM text is already guaranteed ASCII and NUL-free by its own encoding.
  This plan is a case where plan 92's binary-safe convention is
  correctly *not* invoked, stated explicitly here so a reader doesn't
  wonder why it's missing.
- **Out of scope.** No CA-signing or certificate-chain construction (see
  above). No CSR (Certificate Signing Request) generation or parsing —
  `rcgen` supports CSR generation and `x509-parser` has a sibling crate
  for CSR parsing, but neither is this plan's proof's concern. No CRL
  (Certificate Revocation List) parsing, despite `x509-parser` supporting
  it (its own README shows a CRL-iteration example) — a real, separate
  feature with its own use case (checking whether a cert has been
  revoked) this plan's "mint and inspect a single certificate" scope
  doesn't need. No OCSP. No cryptographic signature verification (see
  above — deferred to plan 99). No integration code in this plan itself
  wiring `X509.parse`'s output into plan 99's TLS handshake logic — plan
  99 is the consumer of this plan's parsing surface, not the other way
  around, and this plan does not reach into plan 99's scope to wire that
  consumption up itself.
