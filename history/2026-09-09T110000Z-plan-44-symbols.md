# Plan 44 — Symbols

This is plan 44 of the 36-47 follow-up batch — twelve independent
sibling plans, each owning one distinct, identity-preserving gap
between Emerald's post-plan-35 surface (~10-15% of standard Ruby) and
this project's stated strategic ceiling of ~45%: close every gap
compatible with Emerald's identity, decline anything that actually
requires dynamism. Like the 28-35 batch before it, this plan is post-v1
scope — it is not, and will not become, a row in
[`plan-of-plans`](../../history/2026-09-08T174011Z-plan-of-plans.md),
whose own Completion note already calls Emerald v1 done at row 15.
`plan-of-plans.md` will be updated once, separately, after all twelve
36-47 plans are authored; this plan does not touch it or any other
plan file.

Concrete proof this plan targets — a `Hash[Symbol, Int64]` built from
symbol keys, read, and overwritten, plus a direct proof that symbol
equality is a real, cheap, interned-integer comparison rather than a
string comparison:

```ruby
scores: Hash[Symbol, Int64] = {:alice => 90, :bob => 82, :carol => 95}
puts scores[:bob]
scores[:bob] = 100
puts scores[:bob]

if :foo == :foo
  puts 1
else
  puts 0
end

if :foo == :bar
  puts 1
else
  puts 0
end
```

Expected output, compiled, linked, and run:
```
82
100
1
0
```

(The last two `if`s route their `Boolean` `Expr::Compare` result through
an `if`/`puts 1`/`puts 0` idiom rather than `puts (:foo == :foo)`
directly — see the Decision log's first `puts` bullet for why a literal
`puts :foo == :foo` does not type-check on the actual, verified current
`puts` implementation, and why this plan does not fix that.)

## Decision log

- **`puts` cannot print a `Boolean` today, verified against real source,
  which changes this plan's worked example from what a first draft of
  this brief describes.** `crates/emerald-sema/src/lib.rs`'s
  `infer_expr_type`'s `Expr::Call(name, args) if name == "puts"` arm
  rejects any argument type but `Int64`/`Float64`/`String` — `Boolean`
  is not in that list, confirmed by direct read this session. This is
  plan 25's own already-disclosed cut ("Printing a bare `Boolean`/`Nil`
  value via `puts` is out of scope... route through an `if` condition
  into an `Int64` result before printing"), not something this plan
  introduces or should re-litigate. The worked example above therefore
  proves `:foo == :foo`/`:foo == :bar` the same way plan 25's own
  `Boolean` examples do — through an `if`/`puts 1`/`puts 0` idiom — not
  through a direct `puts <Boolean expr>`, which would fail to type-check
  today regardless of anything this plan does.
- **The full set of distinct `:foo` spellings in a compilation unit is
  enumerable at compile time, so each gets a small dense integer ID with
  no runtime interning table at all.** This is a deliberate, disclosed
  simplification versus Ruby's actual runtime symbol table: CRuby
  maintains one real, mutable, global intern table because Ruby can
  create a brand-new symbol at runtime from an arbitrary computed string
  (`("prefix_" + suffix).to_sym`) — a data-dependent, unbounded-cardinality
  runtime structure. Emerald's symbol set is instead closed: every
  `:foo` a program can ever produce is a literal token sitting in that
  program's own source, so the compiler can walk the whole AST once,
  before generating any code, and hand out IDs `0, 1, 2, ...` in
  first-occurrence order. Verified this session that no such mechanism
  (or `Symbol` type, or `:foo` lexical support) exists anywhere today:
  `crates/emerald-parser/src/ast.rs`'s `Expr` enum has no `SymbolLit`
  variant (the only mention of `Symbol` in the whole `crates/` tree is a
  single doc comment on `Expr::HashLit` — plan 25's own text noting the
  gap, not code); `spec/TYPE_SYSTEM.md` §1/§2/§6 and `spec/GRAMMAR.md`
  §1 already describe `Symbol` as a `KEEP`/listed primitive value type
  interned "in O(1) via identity of the interned entry" — this plan is
  the first to actually build that.
- **The compile-time ID assignment reuses this codegen's existing
  `class_tags`-style pattern, not a new mutability idiom.** Verified
  this session: `crates/emerald-codegen/src/lib.rs`'s `compile_to_object`
  already builds exactly one such table — `class_tags: HashMap<String,
  i64>` (lines ~3606-3612), a single pass over `program.items` assigning
  `class_tags.len() as i64` to each class name in declaration order,
  built once before any function body is compiled and threaded through
  `Ctx` (a `#[derive(Clone, Copy)]` struct of immutable references — see
  `Ctx`'s definition, ~line 640) as `&'a HashMap<String, i64>`. This
  plan's `symbol_table` field follows the identical shape. The one real
  difference, stated plainly: `class_tags`' scan is flat (a `class`
  declaration is always a top-level `Item`), while a `:foo` literal can
  appear at arbitrary nesting depth inside any function/method/lambda/
  `if`/`while`/`case` body — so this plan's collector needs a genuine
  recursive descent, which it gets by mirroring the shape of this same
  file's existing `collect_idents_in_expr`/`collect_idents_in_stmt` pair
  (verified this session, ~lines 240-400 — the exhaustive `Expr`/`Stmt`
  walker plan 10's closure-conversion free-variable analysis already
  uses), substituting "record every distinct `Expr::SymbolLit` spelling,
  first occurrence wins" for "record every `Expr::Ident` reference." Not
  a novel traversal category for this file — a second use of one it
  already has.
- **`Symbol` is a genuinely separate type and runtime representation
  from `String`, not a `String` alias with a different name.**
  `Expr::SymbolLit(String)` (the new AST node) carries the literal's raw
  spelling, the same shape `Expr::StringLit(String)` (plan 19) already
  uses for diagnostics — but where `ValKind::Str` (plan 19, verified
  this session at `crates/emerald-codegen/src/lib.rs` ~line 951,
  `build_global_string_ptr`) is a pointer to a null-terminated UTF-8
  buffer, this plan's `ValKind::Symbol` is a plain `i64` constant,
  exactly like the existing `ValKind::Int64`/`ValKind::Nil` storage
  kinds (verified: `local_llvm_type`'s `Int64 | Nil => i64_type()` arm,
  ~line 94). Depends on plan 19 for the contrast, not the mechanism —
  verified this session that plan 19's own scope is deliberately narrow
  (plain `"..."` literals, `\"`/`\n` escapes only, no interpolation, no
  `Symbol`; its own Decision log explicitly defers `:foo` as "genuinely
  separate scope from this plan"). The payoff this plan delivers on that
  deferral: `Expr::Compare`'s new `(ValKind::Symbol, ValKind::Symbol)`
  arm for `Eq`/`Ne` is a plain `icmp eq`/`icmp ne` on two `i64`s — the
  same one-instruction shape as the existing `(ValKind::Nil,
  ValKind::Nil)` arm (verified, ~line 1284) — while the `(ValKind::Str,
  ValKind::Str)` arm just above it (verified, ~line 1267) must call out
  to the `emerald_string_eq` runtime helper (a real `strcmp`). Symbol
  equality never leaves the current basic block; string equality is a
  real function call. That is the concrete, disclosed performance
  argument for giving tag-like values their own type instead of reusing
  `String` for them.
- **`Hash[Symbol, V]` needs exactly one new line of codegen, not a new
  Hash mechanism — and that fact reveals plan 25's own Decision log
  overstated its own restriction.** Plan 25's Decision log says Hash
  get/set are "restricted to Int64 keys in this leaf." Verified this
  session against the actual committed implementation, not that prose:
  `emerald-sema`'s `resolve_type`'s `"Hash[K, V]"` branch
  (`crates/emerald-sema/src/lib.rs` ~lines 109-117) recurses via a plain
  `resolve_type(k_name, classes)` call with no `Int64`-specific check at
  all; `infer_hash_lit_type` (~lines 620-651) infers the key type from
  the literal's first pair generically and only requires internal
  consistency; and in codegen, `parse_hash_type` (~lines 1697-1705) and
  `build_index`/`build_set_index` (~lines 1819-1900) dispatch purely on
  whatever `ValKind` the key's type name maps to, requiring only
  `idx_kind == key_kind` and calling `.into_int_value()` on the result —
  never hardcoding `Int64` anywhere. Plan 25 shipped a fully key-type-
  generic `Hash[K, V]`; its own text just never described a second key
  type because it never built one. This plan's `Hash[Symbol, Int64]`
  worked example is therefore not new Hash codegen at all — it is the
  first program to actually exercise the generic path plan 25 already
  (if unknowingly) shipped, unlocked by adding one
  `"Symbol" => ValKind::Symbol` arm to `value_kind_for_type` (~line 64)
  so a `Symbol` key produces the `i64` `IntValue` that mechanism has
  always required.
- **Declined: `.to_sym` (`String` → `Symbol` at runtime).** The entire
  design above rests on the symbol set being closed and known at parse
  time. `.to_sym` lets a Ruby program synthesize a symbol from a
  computed, runtime-only string — reopening that closed set requires a
  real, mutable, runtime-populated intern table (CRuby's actual
  mechanism), the exact dynamic, data-dependent structure this design
  exists specifically to avoid. This is a hard decline tied to the
  identity ceiling's no-dynamism stance, not a "not yet" — there is no
  incremental version of this plan's mechanism that also supports
  `.to_sym` without abandoning compile-time enumerability entirely.
- **Declined: `Symbol#to_proc` / the `&:method_name` block shorthand.**
  Ruby's `&:upcase` converts a symbol into a `Proc` that, when finally
  invoked with some receiver, calls the method *named by that symbol* on
  it — meaning the call target isn't known until the receiver shows up,
  resolved by a runtime name lookup (`send`-shaped) or a vtable-style
  indirect dispatch keyed off the receiver's runtime type tag. Both are
  explicitly ruled out by this project's identity constraints
  ("no method_missing/eval/send/reflection," "no dynamic/virtual
  dispatch or vtables... all method resolution stays static, from the
  receiver's declared type"). Emerald's `Proc`/lambda values (plan 10)
  are always closures over one statically fixed call target
  (`Expr::Lambda`, dispatched through `Type::Proc`'s carried signature);
  `&:method_name` has no way to produce that shape without inventing the
  indirect-dispatch mechanism this language refuses to have. Declined
  outright, not deferred.
- **Out of scope, disclosed, real reasons — not bundled into this
  plan's narrower literal-only scope:**
  - **`{a: 1}` Symbol-keyed hash-literal shorthand.** `spec/TYPE_SYSTEM.md`
    §6 types `{a: 1}` as `Hash[Symbol, T]`; plan 25 declined it for lack
    of any `Symbol` type to type it with. Now that `Symbol` exists, the
    natural next question is whether this plan should add the sugar
    too — declined here because it needs a *new* grammar production
    (`Ident ":" Expr` inside hash-pair position) sharing the exact same
    bare `":"` token this plan's own Decision log above already shows is
    lexically delicate (see the `leaf-parser-symbols` section) in a
    *different* grammar position, needing its own independent LALR(1)
    conflict check against `Param`/`Let`'s `Ident ":" TypeName` shape —
    real, separate follow-up work, not a two-line addition.
  - **`Symbol#to_s`.** Unlike `.to_sym`, this doesn't reopen the closed
    symbol set (it only ever needs to return the spelling of an ID that
    was already one of finitely many, known at compile time via a
    reverse `i64 -> String` table baked into the binary) — a real,
    buildable, non-dynamism-violating feature, just not one this plan's
    worked example needs. A genuine "smaller than it looks, not needed
    yet" cut, in the same spirit as plan 31 declining `||=`/`&&=` — not
    a Ruby-dynamism decline like `.to_sym`/`&:` above.
  - **Ordering comparisons (`<`, `>`, `<=`, `>=`) on two `Symbol`s.**
    Declined in codegen (a descriptive `Err`, mirroring the existing
    `(ValKind::Nil, ValKind::Nil)` non-`Eq`/`Ne` arm, ~line 1301) because
    a symbol's integer ID is assigned by arbitrary first-occurrence
    source order, not by spelling — exposing `<`/`>` on symbols would
    silently expose a compiler implementation detail as if it were a
    meaningful ordering. An easy, disclosed cut, not a limitation of the
    ID mechanism itself.
  - **`case`/`when` over `Symbol` scrutinees.** Verified this session:
    `grammar.lalrpop`'s `CaseValues` production (plan 20, ~lines 497-504)
    only ever derives `Num` literals — widening it to accept `Symbol`
    values is a real, separate grammar change to `CaseValues`, not
    something this plan's narrower "add one literal form" scope touches.

## Leaf: leaf-parser-symbols

### 1. Context
- Why: no lexical, grammar, or AST support for `:foo` exists anywhere
  today — verified this session (`crates/emerald-parser/src/ast.rs`'s
  `Expr` enum has no `SymbolLit` variant; `grammar.lalrpop` has no `:`-
  prefixed regex terminal).
- Target state: `Expr::SymbolLit(String)` in `ast.rs`, carrying the raw
  spelling with the leading `:` stripped (mirrors `decode_string_lit`'s
  precedent of storing the literal's *real* value, not raw source
  text). A new `SymbolLitTok: String = <s:r":[A-Za-z_][A-Za-z0-9_]*"> =>
  s[1..].to_string();` terminal in `grammar.lalrpop`, added as a new
  alternative in both `PrimaryExpr` and `StmtPrimaryExpr` (a bare `:foo`
  statement is side-effect-free but harmless and unambiguous to allow —
  unlike `HashLit`'s documented, real conflict with `BlockLiteral`'s
  leading `{` at the `StmtPrimaryExpr` position, `:` starts no other
  production there, verified by re-reading the full 731-line grammar
  file this session).
- **The lex-priority interaction to verify and disclose, not silently
  assume safe**: LALRPOP's tokenizer picks the longest match at a given
  position; the only two pre-existing bare `":"` literal uses in this
  grammar are `Stmt`'s `<name:Ident> ":" <ty:TypeName> "=" <value:Expr>`
  (line 138) and `Param`'s `<name:Ident> ":" <ty:TypeName>` (line 684) —
  verified these are the *only* two. If a program ever wrote a
  spaceless `x:Int64` (colon immediately abutting the type name, no
  space), the new 6-character `SymbolLitTok` match would win over the
  1-character `":"` token, changing that program's tokenization. Grepped
  this session across every `examples/*.em` file and every
  `emerald-parser` test fixture for `[A-Za-z_]\w*:[A-Za-z_]` — zero
  matches; this codebase's own convention, and every example, already
  always writes `name: Type` with a space. Real, disclosed, narrow
  restriction (a spaceless annotation now requires a space), not a
  silent landmine.

### 2. Acceptance Criteria
1. `:foo` parses to `Expr::SymbolLit("foo".to_string())` (leading `:`
   stripped, matching `decode_string_lit`'s "AST already holds the real
   value" convention).
2. `x: Symbol = :foo` parses to `Stmt::Let { name: "x", ty: "Symbol",
   value: Expr::SymbolLit("foo".to_string()) }` — proving `Symbol` is
   accepted as an ordinary type-annotation name at the grammar level
   (`TypeName`'s existing bare-`Ident` alternative already covers it;
   no grammar change needed there).
3. `x: Int64 = 1` (and every other existing `name: Type = value`
   annotation in every prior plan's example) still parses identically —
   proving the lex-priority interaction disclosed above does not
   actually regress any real program, only a hypothetical spaceless one
   nothing in this codebase writes.
4. `{:alice => 90, :bob => 82}` parses to `Expr::HashLit(vec![
   (Expr::SymbolLit("alice".into()), Expr::Int(90)),
   (Expr::SymbolLit("bob".into()), Expr::Int(82))])` — `HashPair`'s
   existing `<k:Expr> "=>" <v:Expr>` production needs no change at all,
   since `Expr::SymbolLit` reaches it through the ordinary `PrimaryExpr`
   ladder.
5. Regression: every prior plan's example (`hello.em`, `Point`,
   `classes.em`, collections/exceptions/module examples, plan 25's own
   `Hash[Int64, Int64]` example) still parses identically.

  `crates/emerald-parser/src/lib.rs` (tests)

## Leaf: leaf-sema-symbols

### 1. Context
- Why: no `Type::Symbol` exists (verified: `emerald_sema::Type`'s
  variant list has no `Symbol` entry today); `resolve_type` has no
  `"Symbol"` arm; `infer_expr_type` has no `Expr::SymbolLit` case.
- Target state: `Type::Symbol` added to `emerald-sema`'s `Type` enum;
  `resolve_type`'s match gains `"Symbol" => Ok(Type::Symbol)` alongside
  its other primitives (`Int64`/`Float64`/`String`/`Boolean`/`Nil`);
  `infer_expr_type`'s match gains `Expr::SymbolLit(_) => Ok(Type::
  Symbol)`. `Expr::Compare` needs **no** code change — its existing
  generic `if lt != rt { mismatch } ... Ok(Type::Boolean)` rule
  (verified this session, ~lines 427-436) already covers `Symbol ==
  Symbol` the moment `Expr::SymbolLit` produces a real `Type::Symbol`,
  the identical "for free" shape plan 19's Decision log already
  documented for `String`. `puts`'s existing `Int64`/`Float64`/`String`
  allow-list is deliberately **not** widened to include `Symbol` (no
  worked example needs `puts` on a bare symbol, and doing so would be
  a `to_s`-shaped formatting question this plan doesn't answer, matching
  plan 25's own precedent of not widening `puts` for `Boolean`/`Nil`
  either).

### 2. Acceptance Criteria
1. `x: Symbol = :foo` type-checks `Ok(())`.
2. `:foo == :foo` and `:foo == :bar` both type-check `Ok(())`, producing
   `Type::Boolean` — real proof `Expr::Compare`'s pre-existing generic
   rule covers `Symbol` with no code change, per the Decision log.
3. `:foo == "foo"` (a `Symbol` compared against a `String`) is rejected
   with the existing generic type-mismatch diagnostic ("type mismatch:
   `Eq` requires both operands to have the same type, found Symbol and
   String") — real, executed proof that `Symbol` is a genuinely
   *separate* type from `String`, not silently comparable to it despite

4. `x: Symbol = 5` (an `Int64` literal assigned to a `Symbol`-typed

   `Int64` despite sharing the same `i64` codegen storage kind.
5. `h: Hash[Symbol, Int64] = {:a => 1, :b => 2}` type-checks `Ok(())`
   with `h`'s inferred type exactly matching the declared annotation —
   real proof `infer_hash_lit_type`/`resolve_type`'s `Hash[K, V]` branch
   needs no `Symbol`-specific change (per the Decision log's finding
   that both were already key-type-generic).
6. Regression: `cargo test -p emerald-sema` — every existing
   `Boolean`/`Nil`/`String`/`Hash` test still passes unmodified.

## Leaf: leaf-codegen-symbols

### 1. Context
- Why: nothing compiles `Expr::SymbolLit`, `Symbol` equality, or a
  `Hash[Symbol, V]`-typed local to machine code; no whole-program
  compile-time symbol-ID table exists (verified this session: no
  `ValKind::Symbol`, no `"Symbol"` arm in `value_kind_for_type`, and the
  only existing whole-program-scoped compile-time ID table is
  `class_tags`, which is flat/top-level-only — see Decision log).
- Target state: `ValKind::Symbol` added to the `ValKind` enum
  (`i64`-backed, alongside `Int64`/`Nil`, in both `local_llvm_type` and
  `make_fn_type`'s match arms); `value_kind_for_type` gains
  `"Symbol" => ValKind::Symbol`; `collect_idents_in_expr`/
  `collect_idents_in_stmt` gain a no-op `Expr::SymbolLit(_) => {}` leaf
  arm (it contains no `Ident` to collect, same as `Expr::StringLit`/
  `Expr::Bool`/`Expr::Nil` today). A new `collect_symbols_in_expr`/
  `collect_symbols_in_stmt` pair, structurally mirroring
  `collect_idents_in_expr`/`_stmt` exactly (see Decision log), builds
  `symbol_table: HashMap<String, i64>` by walking every top-level
  `Item::Function` body, every `ClassDef` method body, every
  `ModuleDef` method body, and every top-level `Item::Stmt`, in
  `program.items` order, assigning the next unused ID (`symbol_table.
  len() as i64`) to each newly-seen spelling. Built once in
  `compile_to_object`, alongside `class_tags`, and threaded into `Ctx`
  as a new `symbol_table: &'a HashMap<String, i64>` field. `build_expr`
  gains an `Expr::SymbolLit(name)` case: `ctx.symbol_table[name]` looked
  up (an internal-error `Err` — never a panic — if somehow missing,
  which the pre-pass's completeness should make unreachable) and lowered
  to `context.i64_type().const_int(id as u64, false)`, returning
  `(_, ValKind::Symbol)`. `Expr::Compare`'s match on `(lk, rk)` gains a
  `(ValKind::Symbol, ValKind::Symbol)` arm for `Eq`/`Ne` (a plain
  `icmp eq`/`icmp ne`, mirroring the existing `Nil` arm exactly) and a
  fallthrough `(ValKind::Symbol, ValKind::Symbol) => Err(...)` for the
  other four `CompareOp` variants (mirroring `Nil`'s own decline arm).
  `Hash[Symbol, V]` needs **no** change to `parse_hash_type`/
  `build_index`/`build_set_index`/`build_hash_lookup` at all — see the
  Decision log's finding that this path was already key-type-generic.

### 2. Acceptance Criteria
1. This plan's own worked example — the `Hash[Symbol, Int64]` build/
   read/write, plus the `:foo == :foo`/`:foo == :bar` proof routed
   through `if`/`puts 1`/`puts 0` — compiled, linked, and run, prints
   exactly:
   ```
   82
   100
   1
   0
   ```
   Real executed proof, not simulated or hand-typed.
2. Two distinct `Expr::SymbolLit("foo")` occurrences anywhere in the
   same program (e.g. one inside a function body, one at top level)
   produce the exact same `i64` constant — real proof the whole-program
   collector assigns one ID per distinct spelling, not one per
   occurrence (unlike plan 19's deliberate *non*-deduplication of
   `String` literals — the opposite, disclosed choice, and the entire
   reason a compile-time symbol table exists at all: two `:foo`s must be
   `==` by cheap integer identity, not by re-comparing spellings).
3. `:foo` used only inside a function body that is never called from
   `main`'s reachable top-level statements (dead code) still receives a
   real ID and still compiles cleanly — the collector walks every
   declared function/method regardless of call reachability, not just
   what a particular run happens to execute (no reachability analysis
   exists in this compiler to make that distinction safely).
4. An attempted ordering comparison on two symbols (`:foo < :bar`,
   reached only by directly constructing the AST in a codegen unit test,
   since the parser has no `<` grammar path that type-checks two
   `Symbol` operands into codegen — sema's `Compare` arm doesn't reject
   it, so this is a real codegen-level defensive check) returns a
   descriptive `Err`, not a panic and not silently-wrong generated code —
   same discipline as every prior codegen plan's "unsupported shape"
   criterion.
5. Regression: `cargo test --workspace` — every existing `Hash`/`Nil`/
   `Boolean`/`String`/class/exception/module test still passes
   unmodified; in particular, plan 25's own `Hash[Int64, Int64]`
   linked-and-run test is unaffected by `value_kind_for_type` gaining a
   new arm.

### 3. File & Module Structure
- **Modify:** `crates/emerald-codegen/src/lib.rs`
- **No change:** `runtime/emerald_runtime.c` — unlike every prior plan
  that added a new value kind (`String` needed `emerald_print_str`/
  `emerald_string_concat`/`emerald_string_eq`; `Hash`/`Array.new` needed
  `emerald_hash_key_not_found`/`emerald_alloc_zeroed`), `Symbol` needs
  zero new runtime C helpers: it has no allocation, no `puts` support,
