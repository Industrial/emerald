# Plan 158 — Markdown Parsing & Rendering

This project already produces and consumes Markdown constantly — every
`history/*.md` plan file (this one included), `spec/*.md`, and this
project's own `emerald doc` subcommand's output are all Markdown documents.
Nothing in Emerald today can parse or render one; a program written in
Emerald that wanted to turn Markdown into HTML, or extract plain searchable
text from a directory of plan files, would have no path to do it natively.
This plan wraps `pulldown-cmark`, the standard pure-Rust CommonMark
implementation — verified this session against its own `lib.rs`/`docs.rs`
listing: version 0.13.4 (released 2026-05-20), MIT, 16.96 million downloads
a month, 4,303 dependent crates, #16 in crates.io's Text-processing
category, and its own README states its design goals plainly: "Fast...
Safe; written in pure Rust with no unsafe blocks (except in the opt-in SIMD
feature)... Correct; the goal is 100% compliance with the CommonMark spec."
It is a *pull* parser specifically — `pulldown_cmark::Parser` implements
`Iterator<Item = Event>` rather than building a fixed AST a caller walks —
which is exactly the architecture this plan's two functions exploit two
different ways: `to_html` hands the whole event stream straight to the
crate's own `html::push_html` renderer, while `strip_to_text` walks the same
stream itself to collect only the text content.

## Concrete proof this plan targets

```ruby
doc: String = "# Title\n\nSome **bold** and *italic* text.\n\n- one\n- two\n"
html: String = Markdown.to_html(doc)
puts html

text: String = Markdown.strip_to_text(doc)
puts text
```

Expected output:
```
<h1>Title</h1>
<p>Some <strong>bold</strong> and <em>italic</em> text.</p>
<ul>
<li>one</li>
<li>two</li>
</ul>

Title
Some bold and italic text.
one
two
```

`to_html`'s output is the standard CommonMark reference rendering of the
input (an H1, a paragraph with `<strong>`/`<em>` inline runs, an unordered
list) — this exact shape matches the CommonMark spec's own reference
examples for headings/emphasis/lists, not a bespoke rendering choice.
`strip_to_text`'s output follows this plan's own defined semantics: each
block's collected text content on its own line, formatting markers
(`**`/`*`/`-`) gone entirely — a fully self-defined, self-tested contract
(see Decision log), which is why it can be asserted exactly here.

## Decision log

- **`Markdown.to_html` uses one fixed `Options` preset, not the full
  bitflag surface — the same "curated, fixed set of behavior, never a
  general configuration mechanism" precedent plan 45 established for its
  whole String surface, applied to a bitflags type this stdlib has no
  clean way to expose anyway.** `pulldown_cmark::Options` is a real
  `bitflags`-generated struct with 15 real flags confirmed this session
  (`ENABLE_TABLES`, `ENABLE_FOOTNOTES`, `ENABLE_STRIKETHROUGH`,
  `ENABLE_TASKLISTS`, `ENABLE_SMART_PUNCTUATION`,
  `ENABLE_HEADING_ATTRIBUTES`, `ENABLE_YAML_STYLE_METADATA_BLOCKS`,
  `ENABLE_PLUSES_DELIMITED_METADATA_BLOCKS`, `ENABLE_OLD_FOOTNOTES`,
  `ENABLE_MATH`, `ENABLE_GFM`, `ENABLE_DEFINITION_LIST`,
  `ENABLE_SUPERSCRIPT`, `ENABLE_SUBSCRIPT`, `ENABLE_WIKILINKS`) — Emerald
  has no bitflags/flag-enum type to expose that surface faithfully
  without either a new sema type or fifteen boolean parameters, neither
  of which this plan takes on. The chosen preset (tables, footnotes,
  strikethrough, tasklists, smart punctuation, YAML frontmatter blocks)
  targets exactly the GitHub-Flavored-Markdown-adjacent feature set this
  project's own plan files and `spec/*.md` already use.
- **`ENABLE_YAML_STYLE_METADATA_BLOCKS` is turned on specifically because
  this very batch of plan documents is itself the concrete, self-
  referential proof case the task asked for.** Every `history/*.md` file
  in this repository — this one included — opens with a `---`-delimited
  YAML block (`name:`, `overview:`, `maestro:`, `todos:`, `isProject:`)
  before its Markdown body begins. With this option enabled, that block
  parses as a distinct `Event::Start(Tag::MetadataBlock(MetadataBlockKind
  ::YamlStyle))` region rather than being swallowed into the document's
  regular text/heading flow — a real, concrete win for any future Emerald
  program (a `history/` indexer, a plan-file linter) built on top of this
  plan specifically because this project's own files are shaped this
  way, not a hypothetical benefit.
- **`strip_to_text` is a plan-defined transformation, not an external
  spec's — its exact output is pinned by this plan's own `#[test]`s, not
  by CommonMark itself, which defines no canonical \"plain text
  extraction\" operation at all.** `to_html`'s expected output in the
  Concrete Proof above is checkable against the CommonMark spec's own
  reference examples (a real, external authority); `strip_to_text`'s
  block-per-line joining rule has no such external authority to check
  against, because none exists for this operation — stated directly so a
  future reader does not mistake this plan's own design choice for a
  transcription of somebody else's spec.
- **Fenced code blocks render as plain `<pre><code>` with no
  per-language syntax highlighting — wiring a fenced block's language
  tag into plan 159's `SyntaxHighlight.highlight` is a natural follow-on
  this plan deliberately does not build.** `to_html`'s output for a
  ```` ```rust ```` fence is exactly what `pulldown-cmark`'s own default
  HTML renderer produces (a `<pre><code class="language-rust">` block,
  unhighlighted) — combining this plan with plan 159 to actually colorize
  that block is a real, valuable integration this plan names explicitly
  but leaves to be built on top of both, not folded into either.
- **No Emerald-native AST/event type is exposed — `strip_to_text` is the
  one, fixed, compiled-into-Rust consumer of the real `Event` stream;
  Emerald source code itself never sees an `Event` value.** Modeling
  pulldown-cmark's ~20 real `Event`/`Tag` variants as Emerald `Enum`/
  `Class` values so user code could write its own event-stream consumer
  is a substantially larger feature (real sum-type modeling across the
  FFI boundary, which nothing in this batch has needed yet) that this
  plan declines to build for a first Markdown integration — `to_html`
  and `strip_to_text` are the two consumers this plan judges to cover
  the realistic near-term need (render to HTML; extract searchable text)
  without it.
- **Out of scope.** A general Emerald-visible `Event`/AST type (see
  above), rendering `ENABLE_MATH`'s math spans as actual typeset
  math (CommonMark's math extension only marks text as math-flavored; it
  does not render LaTeX — real LaTeX/MathML rendering needs a
  completely different, much larger dependency, e.g. a KaTeX binding,
  and its own plan), round-tripping edited HTML or Markdown back into
  Markdown text (a Markdown *writer*, not a parser — a different crate,
  a different plan), and syntax-highlighted code fences (plan 159, named
  above as a real follow-on, not built here).
