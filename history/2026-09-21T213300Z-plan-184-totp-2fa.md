# Plan 184 — TOTP/HOTP Two-Factor Authentication

Time-based one-time passwords (RFC 6238, built on HOTP/RFC 4226) are the
algorithm every "scan this QR code with Google Authenticator" 2FA flow
runs on: a shared secret and the current 30-second time window feed an
HMAC, six digits come out, and both sides — the authenticator app and
the server — compute the same code independently with no network
round-trip needed at verification time. This plan wraps `totp-rs`, a
real, RFC-compliant Rust implementation of that algorithm, rather than
hand-rolling HMAC-and-counter arithmetic directly against plan 109's
hashing primitives — the RFC's own step/skew/digit-count details are
exactly the kind of narrow, easy-to-get-subtly-wrong specification logic
a vetted, widely-used crate is worth depending on for, the same posture
plan 95's crate-vetting policy asks of every domain in this batch.

Depends on: plan 91 (`emerald-rt` archive), plan 92 (`catch_unwind`
convention, `NativeError`), plan 93 (opaque-handle resource model for
`Totp`), plan 95 (crate-vetting policy and checklist), plan 109 (HMAC-
SHA1/SHA256 hashing — a real, load-bearing dependency: `totp-rs` links
`hmac`, `sha1`, and `sha2` directly rather than calling back into
Emerald's own plan-109 hashing surface, so this plan's dependency on
109 is architectural/conceptual — the same primitive, independently
linked — not a literal function-call dependency; stated explicitly
rather than glossed over, see Decision log), and plan 113 (CSPRNG, the
randomness source behind `Totp.generate_secret`).

## Concrete proof this plan targets

```ruby
totp: Totp = Totp.new("Emerald Corp", "alice@example.com", "JBSWY3DPEHPK3PXP")

code: String = totp.generate_current()
puts code

valid: Boolean = totp.check_current(code)
puts valid

invalid: Boolean = totp.check_current("000000")
puts invalid

uri: String = totp.provisioning_uri()
puts uri
```

Expected output: a real 6-digit numeric string (its exact value is
time-dependent, so the example's own test harness checks it is six
ASCII digits and that `check_current` immediately accepts it, rather
than asserting a fixed literal); `true`; `false` (the fixed literal
`"000000"` genuinely does not match, except by the same one-in-a-million
chance any fixed 6-digit guess has against a real code — acceptable,
disclosed test-flakiness odds this plan does not attempt to eliminate,
consistent with how any TOTP conformance test must work); and an
`otpauth://totp/Emerald%20Corp:alice@example.com?secret=JBSWY3DPEHPK3PXP&issuer=Emerald%20Corp&algorithm=SHA1&digits=6&period=30`-
shaped URI string (exact query-parameter order/encoding per `totp-rs`'s
own real, current `get_url()` output, verified against its `#[test]`
suite rather than hand-typed here from memory).

## Decision log

- **`totp-rs`, verified as RFC-compliant and actively maintained this
  session.** crates.io lists `totp-rs`'s own stated purpose as
  "RFC-compliant TOTP implementation," most recently published 6 August
  2026 (six weeks before this plan), version 6.0.0, maintained by a
  single consistent owner (`constantoine`) since its first release —
  a real, current, non-stale dependency, not an abandoned or
  speculative one.
- **Dependency on plan 109 is architectural, not a call-graph edge —
  stated plainly rather than implied.** `totp-rs`'s own `Cargo.toml`
  (verified via docs.rs this session) depends directly on `hmac ^0.13`,
  `sha1 ^0.11`, and `sha2 ^0.11` — the same class of RustCrypto HMAC/SHA
  primitives plan 109 presumably wraps for Emerald's own general-purpose
  hashing surface, but `totp-rs` links and uses its own copies of those
  crates internally; it does not call back into `emerald-rt`'s plan-109
  exports. The two plans therefore share an algorithmic foundation (both
  ultimately trust the RustCrypto `hmac`/`sha1`/`sha2` implementations)
  without a literal code dependency between them. This is named
  explicitly here because it would be a real, false assumption for a
  future reader to believe this plan somehow reuses plan 109's own
  exported hash functions to build TOTP from scratch — it does not; it
  depends on a crate that already built TOTP correctly, on top of the
  same lower-level algorithm family plan 109 also wraps.
- **Constructor defaults match RFC 6238 and real-world authenticator-app
  compatibility, not this plan's own preference.** SHA1, 6 digits, a
  30-second step, and one step of clock-skew tolerance are `totp-rs`'s
  own documented defaults and are also, not coincidentally, what Google
  Authenticator, Authy, and effectively every other real TOTP app
  actually implements and expects — a server issuing a QR code with
  different parameters (SHA256, 8 digits, a 60-second step) would be
  RFC-compliant but incompatible with the overwhelming majority of real
  authenticator apps a user might scan it with. `Totp.new`'s fixed
  four-argument shape does not expose those parameters for v1
  specifically so the common path can't be misconfigured into silent
  incompatibility; a more advanced constructor overload exposing
  algorithm/digit-count/step/skew as explicit parameters is a natural,
  bounded follow-up (see Not yet decided), not attempted here.
- **Secret generation goes through `totp-rs`'s own `rand`-feature-gated
  path, keeping exactly one CSPRNG in the archive.** `Totp.generate_
  secret` enables `totp-rs`'s optional `rand ^0.10` dependency (per its
  own `Cargo.toml`, verified this session) rather than this plan
  generating random bytes itself and hand-assembling a `Secret::Raw`. A
  future `emerald-rt` archive with a dozen crates each pulling in their
  own independent RNG crate/version is a real, avoidable proliferation
  risk (differing RNG implementations, differing quality/audit
  histories) — plan 113's own CSPRNG choice (its crate, not re-derived
  here) is the project's one blessed randomness source; where a wrapped
  crate's own optional `rand`-feature dependency can be made to resolve
  to the same underlying `rand`-ecosystem crate plan 113 settles on,
  this plan takes that path rather than adding a second, parallel RNG.
- **RFC 6238's own published test vectors are the correctness bar, not
  `totp-rs`'s self-consistency alone.** `leaf-example-and-gate`'s
  `#[test]` uses the RFC's own Appendix B fixed secret/timestamp/
  expected-code triples (public, independently checkable, not authored
  by this plan or by `totp-rs`'s own maintainers) — the same "prove it
  against an external, unimpeachable source" posture plan 91 used FNV-1a
  for, applied here to a case where the algorithm genuinely does need a
  real crate (unlike FNV-1a, hand-rolling RFC 6238 correctly, including
  its specific big-endian 8-byte counter encoding and dynamic
  truncation step, is real, easy-to-get-wrong cryptographic-adjacent
  logic this plan is right not to reimplement).
- **HOTP (the counter-based, non-time-based predecessor RFC 4226)
  rides along as a byproduct, not a separately designed surface.**
  `totp-rs` implements TOTP as HOTP-plus-a-time-derived-counter
  internally; this plan does not expose a standalone `Hotp` type or a
  manual-counter API in v1 — every real 2FA integration this plan's own
  worked proof and stated scope target is TOTP (QR-code app-based 2FA),
  not HOTP's now-rare manual-counter hardware-token use case. A future
  plan can expose `totp-rs`'s lower-level counter-driven methods
  directly if a real HOTP use case appears.
- **Out of scope.** QR code image generation/rendering — `totp-rs` has
  an optional `qrcodegen-image` feature that can rasterize a
  provisioning URI into an actual PNG, but this plan exposes the URI
  string only (`.provisioning_uri()`); rendering it as a scannable image
  is a distinct capability better paired with whatever general image-
  encoding plan this batch's kitchen-sink coverage eventually adds, not
  bundled into a 2FA-specific module. Backup/recovery codes (the
  one-time codes most real 2FA systems issue alongside TOTP for a
  lost-device fallback) — not a `totp-rs` feature at all; that is
  ordinary application-level random-code generation plus storage, with
  no algorithm-specific library dependency, and is left to the
  application built on this plan. Rate-limiting/lockout after repeated
  failed `check_current` attempts — a real, important production 2FA
  concern, but a policy decision belonging to the application or to a
  future auth-framework-level plan, not to this thin TOTP algorithm
  wrapper.
