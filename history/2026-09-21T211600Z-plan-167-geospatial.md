# Plan 167 — Geospatial Primitives (Niche/Stretch Tier)

**This is the narrowest-audience plan in this entire batch, and it says
so plainly rather than dressing itself up as broadly useful.**
Geospatial calculation — distance between coordinates, polygon area —
is a real capability some Emerald programs will genuinely need (a
logistics tool, a location-aware service, a mapping utility), but it is
a smaller slice of realistic Emerald use cases than even plan 165's
linear algebra or plan 166's statistics, both of which at least serve a
broader "scientific/graphics computing" category. This plan is scoped
correspondingly narrow: one point type, two distance functions, one
polygon-area function. Nothing else.

`geo` is the obvious, uncontested pick for this territory: verified this
session, crates.io shows it last published 2026-04-20, its own
description states it provides "geospatial primitive types such as
Point, LineString, and Polygon, and provides algorithms and operations";
`georust.org` describes the whole GeoRust ecosystem plainly as "geospatial
tools and libraries written in Rust." It is the closest thing this space
has to a default, dominant, actively-maintained choice — no live
rivalry this session's research surfaced, and no reason to look further.

## Concrete proof this plan targets

```ruby
a: Point = Point.new(0.0, 0.0)
b: Point = Point.new(3.0, 4.0)
puts Geo.euclidean_distance(a, b)

london: Point = Point.new(-0.1276, 51.5074)
paris: Point = Point.new(2.3522, 48.8566)
distance_km: Float64 = Geo.haversine_distance(london, paris) / 1000.0
puts distance_km

square_xs: Array[Float64] = [0.0, 1.0, 1.0, 0.0]
square_ys: Array[Float64] = [0.0, 0.0, 1.0, 1.0]
area_result: Result[Float64, String] = Geo.polygon_area(square_xs, square_ys, 4)
case area_result
when Ok(area)
  puts area
when Err(e)
  puts e
end

bad_area: Result[Float64, String] = Geo.polygon_area(square_xs, square_ys, 2)
case bad_area
when Ok(area)
  puts "unexpected"
when Err(e)
  puts e
end
```

Expected output, in order: `5` (the classic 3-4-5 right-triangle
Euclidean distance, exact); a value near `344` (London to Paris
great-circle distance in kilometers — the real, publicly checkable
approximate value, asserted within a stated tolerance in this plan's own
`#[test]`, not asserted as an exact literal here since the precise
figure depends on `geo`'s own internal Earth-radius constant); `1`
(the unit square's area, exact — the shoelace formula's simplest
possible checkable case); and a disclosed error string for the
degenerate two-point "polygon."

## Decision log

- **Flagged niche/stretch-tier explicitly, and ranked even narrower
  than plan 165/166 — a real, honest relative-priority statement, not
  false modesty.** Geospatial calculation serves a genuinely smaller
  slice of realistic Emerald programs than linear algebra or statistics
  do; stating that plainly here, rather than claiming equal footing
  with the rest of this batch's stretch-tier plans, is the accurate
  picture.
- **`Point` is a new, separate class from plan 165's `Vector2`, despite
  being structurally identical (two named `Float64` fields) — a real
  domain-semantics reason, not duplication for its own sake.** A
  `Vector2` is a directionless-or-directional magnitude used for
  physics/graphics math (addition, dot product, length); a `Point`
  here is a COORDINATE — specifically, for `.haversine_distance`, a
  (longitude, latitude) pair on a sphere, a fundamentally different
  semantic category where "adding two points" or "the dot product of
  two points" is meaningless. Reusing `Vector2` for both would either
  expose vector-arithmetic methods on coordinate data where they make
  no sense, or require this plan to add coordinate-specific methods to
  a class plan 165 owns and scopes independently — two separate,
  small, purpose-built classes is the cleaner design even though their
  underlying field layout happens to coincide.
- **The (x, y) = (longitude, latitude) convention is stated explicitly
  and tested against a known real-world pair, specifically because
  this is a common, easy transposition bug across the wider geospatial
  software ecosystem, not merely this crate.** GeoRust's own `Point`
  type follows the (x, y) = (lon, lat) convention consistently — the
  opposite ordering from the colloquial "lat, long" phrasing most
  people say out loud. This plan's own worked proof uses two real,
  well-known cities (London, Paris) specifically so a wrong-order bug
  would produce a visibly, checkably wrong distance (a coordinate typo
  here doesn't merely shift a number slightly — swapping lon/lat for
  these two specific cities would produce a distance nowhere near the
  real ~344 km, making the mistake obvious rather than silently
  plausible).
- **No `Polygon` class at all — polygon area takes two flat `Array
  [Float64]` buffers plus a count, not a `Point`-array or a handle.**
  This is a deliberate, narrow choice for a plan that ships exactly one
  polygon operation: introducing a full `Polygon` class (with its own
  construction, validation, and any future operations like
  point-in-polygon or perimeter) is real, additional design surface
  this plan's actual scope — one area computation — does not need. The
  two-parallel-array-plus-count shape reuses the exact
  disclosed-count-parameter convention plan 45 established for
  `Array[T]`'s own missing length metadata and this batch's other
  plans (165's `Matrix3.from_flat`, 166's `Stats.mean`) already reuse —
  consistency with an established pattern over introducing a new
  vertex-list abstraction for one function.
- **Haversine distance is the only "real-world" (spherical) distance
  function shipped — no geodesic (ellipsoidal, e.g. Vincenty's
  formulae) distance in v1, a real, disclosed accuracy tradeoff.**
  Haversine distance treats Earth as a perfect sphere; a true geodesic
  calculation accounting for Earth's actual oblate-spheroid shape is
  more accurate (differing by up to ~0.5% depending on the path) but
  meaningfully more complex to implement correctly and verify. For the
  scale this plan targets (a rough distance check, not survey-grade
  precision), haversine's simplicity and this plan's own testable
  tolerance are the right tradeoff; a future plan can add geodesic
  distance as an additional, opt-in function without displacing this
  one.
- **Coordinate reference systems (CRS) and projections are explicitly
  out of scope — every coordinate this plan touches is assumed WGS84
  longitude/latitude in degrees (for haversine) or plain unitless
  Cartesian (for euclidean/polygon area), with no reprojection logic
  anywhere.** A real GIS system needs to reconcile data in different
  reference systems (UTM zones, state plane coordinates, etc.) — that
  is the `proj` crate's job (a PROJ C-library binding, notably NOT
  pure-Rust, a materially different dependency-trust profile than this
  plan's pure-Rust `geo` choice) and a substantially larger, separate
  undertaking this narrow plan does not attempt.
- **Out of scope.** No `Polygon`/`LineString`/`MultiPoint` classes of
  any kind (above); no point-in-polygon test, no polygon intersection/
  union/buffering, no convex hull, no centroid (all real `geo`
  algorithms this plan declines to wrap in v1 — each a small,
  independent follow-up leaf once this plan's representation pattern
  is established); no geodesic (ellipsoidal) distance (above); no CRS/
  projection support (above, and explicitly not `proj`, a non-pure-Rust
  dependency this plan does not pull in); no GeoJSON or any other file-
  format I/O (`geo`'s own ecosystem offers `geojson`/`geozero` as
  separate crates for this — not touched here).
