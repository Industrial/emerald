# Plan 174 — QR Code Generation

A small, fun, genuinely useful "kitchen sink" capability: `qrcode` is a
mature (docs.rs shows an unbroken maintenance history under one owner,
`kennytm`), pure-Rust, dual-licensed QR code encoder with zero required
dependencies (its only dependency, `image`, is optional and needed only
for raster output — verified this session via docs.rs). Wrapping it lets
an Emerald program generate a real, scannable QR code with no external
tool and no C dependency — for a payment link, a Wi-Fi config, a URL, or
any short text payload.

## Concrete proof this plan targets

```ruby
code: QrCode = QrCode.encode("https://emerald-lang.org")
svg: String = code.to_svg
puts svg.length > 0
```

Expected output: `true` — `svg` contains real, valid SVG markup
rendering a scannable QR code encoding the given URL.

## Decision log

- **`qrcode` (the `kennytm/qrcode-rust` crate) is chosen over the
  alternative `qrcode-generator` crate on real, checked grounds, not
  arbitrarily.** Both were found via search this session; `qrcode`'s
  own crates.io description states it "generates ISO/IEC 18004 QR Code
  and Micro QR Code symbols and ISO/IEC 23941 rMQR symbols in pure
  Rust" — broader standards coverage, and its docs.rs page shows a
  dependency graph of exactly one *optional* crate (`image`), the
  minimal footprint this batch's plan-95 policy favors. `qrcode-
  generator` was not selected as the primary dependency; this plan does
  not re-derive a full bake-off, but records that the choice was made
  on verified, not assumed, grounds.
- **This plan exposes only standard QR codes in v1, not Micro QR or
  rMQR, even though the underlying crate supports both — a real,
  disclosed scope cut for API-surface minimalism, not a technical
  limitation.** Standard QR is what virtually every real-world scanner
  (phone camera apps) recognizes; Micro QR and rMQR are narrower,
  specialized variants. Adding all three to the v1 Emerald API would
  triple the surface area for negligible real benefit — a second QR
  code "mode" argument can be added later with zero breaking change to
  the `.encode(data)` shape already shipped.
- **SVG output needs no new dependency; PNG output reuses plan 172's
  Image module and plan 92's binary buffer convention rather than
  inventing a third way to move image bytes across the FFI boundary.**
  SVG is plain, self-describing text — `.to_svg` returns an ordinary
  Emerald `String`, zero-conversion per plan 59's finding. `.to_png_bytes`
  is the one place this plan needs the binary-safe `(ptr, len)`
  convention, consistent with every other binary-data-producing plan in
  this batch.
- **Error-correction level defaults to M (medium, ~15% recoverable),
  the standard's own general-purpose recommendation — not the highest
  level by default.** Level H (~30% recoverable) produces a visually
  denser, harder-to-scan-at-small-sizes code for no benefit in the
  common case (clean digital display or print, not a damaged/dirty
  physical label); callers needing damage-resistance for a printed
  label in a harsh environment can explicitly request H.
- **Out of scope.** Micro QR and rMQR symbol variants (named above,
  real future extension), QR code *decoding* (reading a QR code from an
  image — a different, unaddressed problem needing a camera/image-
  processing pipeline this plan does not build), and styled/branded QR
  codes (embedded logos, custom colors beyond plain black-on-white) are
  all explicitly deferred.
