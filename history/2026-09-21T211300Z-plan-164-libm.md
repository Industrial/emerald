# Plan 164 — Portable Math Functions (libm)

Every other plan in this batch justifies itself by giving Emerald a
capability it didn't have at all. This one is different, and says so
plainly: Emerald can *already* call real libc `sin`/`cos`/`pow`/`exp`
today, with zero new Rust dependency, via plan 59's `unsafe extern "C"`
mechanism — `unsafe extern "C" { fn pow(x: Float64, y: Float64):
Float64 }` compiles and links against the platform's own real `libm`
right now, exactly the same way plan 59's own worked proof already calls
real `llabs`/`strlen`/`strstr`. This plan's honest job is not to invent
a capability that didn't exist — it's to make the SAME capability
available on a target where "the platform's real libc" is not a safe
assumption: `wasm32-wasip1`, plan 64's WebAssembly codegen target, whose
own Decision log discloses "a real, disclosed no-arbitrary-FFI
restriction WASI's sandboxing model forces on this target alone."

## Why a pure-Rust libm, given that real libc math already works

Stated as the actual, disclosed tradeoff, not oversold: on this
project's default native target (`x86_64-unknown-linux-gnu`), calling
real libc math via plan 59's `extern "C"` mechanism works today, needs
no new crate, and is almost certainly at least as fast and at least as
numerically accurate as any pure-Rust reimplementation, since it's the
same `libm` the operating system itself ships and the same one every
other program on the machine already uses. **This plan does not claim
libc math is deficient on that target.** The concrete case for `libm`
is narrower and specific: `wasm32-wasip1` cross-compilation, per plan
64's own verified finding, needs a WASI sysroot to provide any libc
symbols at all, and plan 64's own Decision log discloses that arbitrary
C FFI is restricted under WASI's sandboxing model for that target
specifically — whether a given WASI sysroot's libc actually bundles and
correctly links a `libm` for a cross-compiled `emerald-rt` archive is a
real toolchain question with real failure modes (a missing symbol at
link time, a subtly different rounding behavior from a different libm
implementation than the one tested on the native target). `libm`
(`rust-lang/libm`) sidesteps the entire question: it is pure Rust
source, compiles straight into `emerald-rt`'s own object code via
ordinary `cargo build --target wasm32-wasip1` with no libc, no sysroot
math library, and no linker flag of any kind — literally the same
mechanism `core`'s own float math already relies on for every other
`#![no_std]` Rust target that has no OS-provided math library to call
into (embedded microcontrollers, kernels, and — the case this plan
actually cares about — WASI). Shipping `libm` gives every target this
compiler supports, present and future, one identical, portable math
implementation, rather than "libc's math on native, and an unresolved
question on wasm."

## Concrete proof this plan targets

```ruby
puts Math.sqrt(2.0)
puts Math.pow(2.0, 10.0)

nan_result: Float64 = Math.sqrt(-1.0)
puts nan_result.is_nan

identity: Float64 = Math.sin(1.0) * Math.sin(1.0) + Math.cos(1.0) * Math.cos(1.0)
puts identity
```

Expected output, in order: `1.4142135623730951` (`sqrt(2)`, agreeing
with Rust's own `f64::sqrt` to full double precision — this plan's own
`#[test]` pins the exact bit-identical value, not an approximation);
`1024` (`2^10`, exact); `true` (`sqrt(-1.0)` is a real IEEE 754 domain
error, producing `NaN`, not a crash and not a `Result` — the same
convention libc's own `sqrt` uses); and a value equal to `1` within
floating-point tolerance (the `sin²+cos²=1` trigonometric identity,
computed entirely through `libm`'s pure-Rust implementations, proof the
transcendental functions are internally consistent with each other, not
merely individually plausible).

## Decision log

- **`libm`'s own real provenance is the strongest evidence for trusting
  it — it is not a third-party gamble, it is the fallback `core` itself
  already depends on.** Verified this session: `rust-lang/libm` is
  maintained under the official `rust-lang` GitHub organization, and its
  own crates.io description states plainly it "provides fallback
  implementations for Rust's float math functions in core" — meaning
  every `#![no_std]` Rust program on a target with no OS math library
  (which is a real, common, already-shipping situation across the wider
  Rust ecosystem, not a hypothetical this plan invents) already runs on
  exactly this code today. Choosing it here is choosing the version of
  "trust a math implementation" with the least new trust actually being
  extended — Rust's own compiler team already made and continuously
  validates this exact call.
- **This plan does not claim libc math is wrong, slow, or deficient on
  the native target — the honest scope is portability, not
  correctness.** Stated plainly because overclaiming here would be easy
  and wrong: on `x86_64-unknown-linux-gnu`, `libm`'s pure-Rust `sqrt`/
  `sin`/`pow` and glibc's own hand-tuned, often hardware-accelerated
  equivalents may differ in the last bit or two of precision or in raw
  throughput for some functions — this plan's own `#[test]`s compare
  against Rust's own `std` float math with an explicit epsilon
  (`leaf-example-and-gate`) specifically because bit-for-bit equality
  with libc is not guaranteed or promised by either implementation.
  Nothing in this plan proposes replacing plan 59's real, working
  `extern "C"` libc math calls on the native target — both paths remain
  independently available; a caller who wants libc's exact rounding
  behavior on native still has plan 59's mechanism for it.
- **The wasm32-wasip1 portability claim is proven by an actual
  cross-compiled build in this plan's own gate, not left as an
  assertion resting on `libm`'s documentation alone.**
  `leaf-wasm-portability-note-and-feature-gate` requires a real
  `wasm32-wasip1` build of a program calling `Math.sin` to succeed with
  zero additional linker flag introduced by this plan — the same "prove
  it in code, not just prose" posture plan 91 established for `catch_
  unwind` and plan 92 established for the panic-to-`NativeError`
  boundary. If that build needed a new WASI-sysroot math-library flag
  after all, this plan's own central claim would be falsified by its
  own gate, not merely under-tested.
- **Domain errors follow libc's own real convention (`NaN` on
  `sqrt(-1.0)`), not a new `Result`-wrapped convention invented for this
  plan alone.** `libm`'s functions, like the C `libm` they reimplement,
  are TOTAL over `f64`'s full input range — every input produces some
  `f64` output, including `NaN` and `±Infinity` for out-of-domain
  inputs, never a panic. Wrapping every call in `Result[Float64, String]`
  the way plan 160's `parse_rfc3339` or plan 163's `Decimal.from_s` do
  would misrepresent these functions as fallible in the same sense
  those genuinely are — they are not; they are total functions with a
  well-defined out-of-band sentinel value, and `NaN` propagation through
  further arithmetic is itself a well-understood, standard numerical
  convention this plan inherits rather than works around.
- **`emerald_rt_fn!`'s `catch_unwind` wrapper is applied uniformly even
  though these specific functions cannot actually panic — consistency
  over cleverness.** `libm`'s functions have no panicking code path over
  any real `f64` input (no allocation, no fallible parsing, no assertion
  that could fail on valid float input) — an unwrapped, bare `extern
  "C"` function here would be just as safe in practice. This plan wraps
  them anyway, through the same macro every other `emerald-rt` export
  uses, because plan 92's own stated rationale for the macro (a human
  forgetting to apply catch_unwind at one of ~200+ future call sites is
  a real, foreseeable failure mode) argues for uniform application, not
  a per-function judgment call about whether THIS particular function
  happens to be provably panic-free today — a future `libm` version
  could in principle add an internal `assert!` this plan's authors
  didn't anticipate, and the wrapper costs nothing to keep in place.
- **`log` is exposed as `.ln` at the Emerald surface, not `.log`, to
  avoid a real naming ambiguity, not a stylistic preference.** `libm::
  log` is the natural logarithm (base *e*); a bare `Math.log` reads to
  most programmers coming from Ruby/Python/JavaScript as EITHER natural
  log OR "the log function you'd reach for by default," an ambiguity
  this plan resolves the same way Rust's own standard library does —
  `.ln()` for natural log, `.log2()`/`.log10()` for the named bases, no
  bare `.log()` at all. This is a real, disclosed naming decision
  worth stating rather than leaving a reader to wonder why `.log` is
  conspicuously absent from the function list.
- **Out of scope.** No `Float32`-precision variants (`libm` offers
  `f32` equivalents of most functions, e.g. `libm::sinf` — Emerald's own
  `Type` enum has no `Float32` variant at all, verified against plan
  59's own finding, still true against the current `Type` enum read
  this session, so there is no Emerald-facing type these would even
  attach to); no complex-number math (`sin`/`cos`/`exp` of a complex
  argument — a distinct, much larger feature needing a `Complex` type
  this plan does not introduce); no SIMD/vectorized batch math (`libm`
  operates one scalar at a time; a `Math.sin_batch(xs: Array[Float64],
  n: Int64): Array[Float64]`-style bulk operation is a real, separate,
  larger design — plan 165's nalgebra vectors are the more natural home
  for batched numeric work, not this plan); no arbitrary-precision math
  (that composes with plan 163's `BigInt`/`Decimal` in some future plan,
  not this one — `libm` operates exclusively on hardware `f64`).
