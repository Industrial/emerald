# Plan 102 — WebSocket Client & Server

This is plan 102 of the 91-191 batch, the third of four plans (100-103,
this agent's assignment) wrapping vetted Rust crates as native Emerald
stdlib surface through plan 91's `emerald-rt` archive. It sits directly
on top of the previous two: `WebSocket.connect` is architecturally close
to plan 100's `Http.get` (a client-initiated, synchronous, one-shot-ish
call, now returning a long-lived handle instead of a single value), and
the server-side upgrade path is only possible because plan 101 already
gives every `Http.serve` handler a real, live `tiny_http::Request` to
upgrade — this plan does not stand up its own listening socket at all.

Depends on: plan 91 (`2026-09-21T200000Z-plan-91-rust-native-runtime-crate.md`),
plan 100 (`2026-09-21T220000Z-plan-100-http-client.md` — the
`Http`/`HttpResponse` reserved-namespace and hardcoded-compound-type
precedents this plan's own `WebSocket`/`WebSocketMessage` types repeat),
plan 101 (`2026-09-21T220500Z-plan-101-http-server.md`, authored earlier
this same session — the server-side upgrade path is literally
impossible without plan 101's `Http.serve`/`HttpRequest` machinery
already existing; this plan adds exactly one new method,
`HttpRequest.upgrade`, onto plan 101's own `Type::HttpRequest`), plan 53
(`Result[T, E]`'s real, current representation, reused for every
fallible operation here the same way plan 100 already reuses it). Cites
by number, not yet on disk: plan 92 (FFI/ABI — the `(ptr, len)` buffer
convention this plan's binary-frame marshaling follows), plan 93

long-lived, explicitly-`.close()`d native resource, unlike plan 100's

(async-to-sync — not invoked; both `tungstenite`'s sync mode and

`std::net::TcpStream` directly, the first plan in this batch to do so
rather than delegating socket ownership to a higher-level crate; cited
for the raw-socket primitive itself, not reused as an Emerald-facing
API), plan 99 (TLS via `rustls` — `wss://` support, see Decision log).

## Concrete proof this plan targets

```ruby
Http.serve(8081) { |req: HttpRequest|
  if req.path == "/ws"
    conn: Result[WebSocketConnection, WebSocketError] = req.upgrade()
    case conn
    when Ok(ws)
      msg: Result[WebSocketMessage, WebSocketError] = ws.recv()
      case msg
      when Ok(m)
        ws.send_text("echo: " + m.text)
      when Err(e)
        puts e.message
      end
      ws.close()
    when Err(e)
      puts e.message
    end
    HttpResponse.new(200, "")
  else
    HttpResponse.new(404, "not found")
  end
}
```

Run against a real client from the same test harness (a Rust
`#[test]`, not `.em` source, spawning the compiled binary and driving a
`tungstenite::connect("ws://127.0.0.1:8081/ws")` client directly from
Rust — the reverse role from every other proof in this batch, since the
*Emerald* side here is the server): the test client sends a text frame
`"hello"` and asserts it receives back exactly `"echo: hello"`, then
sends a `Close` frame and asserts the connection closes cleanly. This is
a self-contained loopback proof, deliberately avoiding plan 100's own
disclosed external-network CI risk. A buggy implementation that (a) tried
to call `tungstenite::accept`/`accept_hdr` on the stream `Request::
upgrade` returns (re-running the handshake `tiny_http` already
completed) would double-handshake and fail the connection; (b) used
`from_raw_socket` with the wrong `Role` would corrupt frame masking
(RFC6455 requires client-to-server frames to be masked, server-to-client
frames not to be — `tungstenite` enforces this per `Role`, and getting
it backwards produces a protocol violation on the very first frame).

## Decision log

- **`tungstenite` (sync), not `tokio-tungstenite` — verified this
  session to still be the actively maintained, currently documented
  posture, not merely assumed from the crate's age.** `tungstenite`
  0.30.0 (Jul 11, 2026, confirmed via `lib.rs` and `docs.rs` this
  session) sits behind four releases in the last twelve months (0.27
  → 0.28 → 0.29 → 0.30), 31.1M downloads/month, used in 10,599 crates —
  a crate under active, current maintenance, not a frozen artifact.
  Its own README (read in full this session) leads with the plain
  synchronous example this plan's own design follows almost verbatim:
  `TcpListener::bind(...)`, `tungstenite::accept(stream)`,
  `websocket.read()`/`.send()` — and explicitly frames `tokio-tungstenite`
  as the *alternative* for callers who specifically want "non-blocking
  sockets and... full-duplex communication" via an existing async event
  loop, not as `tungstenite`'s successor or a required upgrade. Since
  this batch's `Http.serve` (plan 101) is itself synchronous and
  thread-per-connection, and `WebSocket.connect`'s client path has no
  async event loop to integrate with either, plain `tungstenite` is the
  correct fit with zero of plan 94's bridging machinery needed anywhere
  in this plan — the same sync-first posture plans 100/101 already
  established, now confirmed to hold for this crate specifically rather
  than assumed to carry over by analogy.
- **`WebSocketConnection` is an opaque `u64` handle (plan 93's model),
  not a hardcoded compound `Type` with fields — the first genuinely
  stateful, explicitly-closed resource this batch introduces, and the
  reason plan 93 is load-bearing here where it was only cited in
  passing by plans 100/101.** Unlike `HttpResponse` (an immutable,
  fully-materialized value returned once) or `Http.serve` (which never
  returns control to Emerald source at all in v1), a WebSocket
  connection is a live, mutable, native `tungstenite::WebSocket<TcpStream>`
  that must be read from and written to repeatedly across multiple
  Emerald statements, and must eventually be torn down. Storing the
  real Rust value behind an opaque `u64` key into a
  `Mutex<HashMap<u64, WebSocketConnState>>` inside `emerald-rt` —
  rather than trying to represent a live socket/TLS/framing state
  machine as an Emerald-visible compound type the way `HttpResponse`
  is — means the handle crosses the FFI boundary as a single `Int64`
  with no marshaling at all, and `.close()` is the one, explicit,
  required cleanup call (no GC, no destructor, matching plan 93's own
  stated "opaque `u64` handles + explicit `.close()`, no GC" model
  exactly, cited here as the reason this design needs no new mechanism
  beyond what that plan already establishes).
- **`WebSocketMessage` is a fourth hardcoded compound `Type`, reusing
  `Result[T, E]`'s single-8-byte-payload-slot-reinterpreted-by-discriminant
  trick for a genuinely two-shaped payload (`String` for text, `Array
  [Int64]` for binary), not a new representation technique.** A
  received frame is one of five kinds (Text, Binary, Ping, Pong, Close);
  plan 53's own Decision log already established that this codegen
  backend's every runtime value is naively one machine word — a bare
  pointer works identically as a payload slot regardless of what it
  points to, so `Type::WebSocketMessage`'s `[kind: i64 @0][payload: ptr
  @8]` layout reuses the identical trick with no new machinery: `kind
  0` (Text) points at a `String`, `kind 1` (Binary) points at an
  `Array[Int64]`, `kind 2/3/4` (Ping/Pong/Close) leave `payload` null
  and unused. `.text`/`.bytes` are unchecked against `.kind` — reading
  `.text` on a Binary message is real, disclosed undefined behavior, the
  identical "unchecked, matching `Array`'s own existing precedent"
  posture plan 45's Decision log already accepted for `str[i]`/
  `.slice`, not a new UB surface this plan introduces independently.
- **Binary frames are represented as `Array[Int64]`, one element per
  byte — a real, disclosed, deliberately inefficient stopgap, not a
  proper `Bytes` type, because no such type exists anywhere in this
  language yet.** Verified this session: nothing in the current `Type`
  enum represents a packed byte buffer distinct from UTF-8 `String` —
  every existing integer-bearing collection is `Array[Int64]`, 8 bytes
  per logical byte. This plan does not invent a `Bytes`/`Vec<u8>`-style
  type to fix this properly (a real, separate, cross-cutting type-system
  addition that would also benefit plan 92's own binary-buffer
  convention and any future crypto/compression plan in this batch far
  more broadly than this plan alone) — `.send_binary(bytes: Array
  [Int64])`/`.bytes: Array[Int64]` accept the real, disclosed 8x memory
  overhead and per-element masking (`byte & 0xFF`) needed to keep each
  `Int64` element honestly representing one octet. This is named here
  explicitly as the kind of gap a later, dedicated plan should close
  once more than one domain plan in this batch needs it.
- **The server-side upgrade is `tiny_http::Request::upgrade` feeding
  `tungstenite::WebSocket::from_raw_socket` directly — verified this
  session against both crates' real, current API surfaces, not assumed
  to compose.** `tiny_http::Request::upgrade<R: Read>(self, protocol:
  &str, response: Response<R>) -> Box<dyn ReadWrite + Send>` (confirmed
  from `docs.rs/tiny_http/0.12.0` this session — its own doc comment:
  "The main purpose of this function is to support websockets... you
  can call this function to obtain full control of the socket stream")
  sends the caller-supplied `response` (which `emerald_rt_ws_upgrade_
  from_http` builds as a `101 Switching Protocols` with a correctly
  computed `Sec-WebSocket-Accept` header — the RFC6455 SHA1-then-base64
  of the client's `Sec-WebSocket-Key` plus the protocol's fixed magic
  GUID, a small, well-specified, independently-checkable computation)
  and hands back the raw duplex stream. `tungstenite::protocol::WebSocket
  ::from_raw_socket(stream, role: Role, config: Option<WebSocketConfig>)
  -> Self` (confirmed from `docs.rs/tungstenite/0.30.0` this session —
  its own doc comment: "Call this function if you're using Tungstenite
  as a part of a web framework or together with an existing one. If you
  need an initial handshake, use `connect()` or `accept()`") is
  precisely the "already-upgraded, skip the handshake" constructor this
  integration needs — calling `tungstenite::accept`/`accept_hdr` instead
  would incorrectly attempt a *second* HTTP-level handshake read against
  a stream `tiny_http` has already fully consumed the request from. This
  is a real, verified, two-crate integration seam, not a guessed one.
- **TLS (`wss://`) is deferred to align with plan 99, not designed
  independently here — `tungstenite`'s own feature flags (`native-tls`,
  `rustls-tls-native-roots`, `rustls-tls-webpki-roots`) are real and
  already support it, but this plan does not pick a default ahead of
  plan 99's own, shared, batch-wide TLS convention.** Verified this
  session: `tungstenite` ships with *no* TLS feature active by default
  ("By default no TLS feature is activated... make sure you use one of
  the TLS features, otherwise you won't be able to communicate with the
  TLS endpoints" — its own README) — a deliberate, safe default this
  plan inherits by leaving TLS off for its own first execution pass,
  `ws://` only. A `wss://` client mode is real, disclosed, near-term
  follow-up once plan 99 lands and this plan's own feature-flag choice
  can be reconciled with it, rather than guessed here and possibly
  conflicting with whatever `rustls` `ClientConfig`/certificate-store
  convention plan 99 establishes for `ureq` (plan 100) and `tonic`
  (plan 103) to share.
- **Out of scope.** The `permessage-deflate` compression extension
  (`tungstenite`'s own README states plainly "There is no support for
  permessage-deflate at the moment"), WebSocket subprotocol negotiation
  beyond the fixed literal `"websocket"` upgrade this plan hardcodes,
  connection-level ping/keepalive scheduling from the Emerald side
  (`tungstenite` already auto-responds to a peer's `Ping` with a queued
  `Pong` on the next `read`/`write`/`flush`, confirmed from its own
  `WebSocket::write` docs this session — this plan relies on that
  built-in behavior rather than reimplementing it), and `wss://` (see
  above) are all declined for v1. A `DEPENDENCIES.md` ledger entry for
  `tungstenite` (plan 95's checklist) is this plan's responsibility.

1. **Typed `WebSocketError`, not `Result[T, String]`.** Plan 195

   | Protocol(String) | Other(String)` — the identical `<Domain>Error`
   shape `RegexError`/`JsonError` already establish, classified via
   `tungstenite::Error`'s own variants and delivered through plan 195's
   own `emerald_rt_result_err_tagged` FFI extension, not the plain
   `emerald_rt_result_err_str` this plan's own text assumed.
2. **Binary frames are `Bytes`, not `Array[Int64]`.** This plan's own
   Decision log proposed `Array[Int64]` as a deliberate stopgap,
   explicitly naming the gap a later plan should close once a second
   consumer needed a packed byte buffer. Plan 109 (Hashing, landed
   between this plan's authoring and its own execution) already
   shipped exactly that type (`Bytes` — a zero-cost `Int64` newtype
   over a `[len: i64][data]` heap block, `bytes.rs`). `.send_binary`/
   `WebSocketMessage#bytes` use it directly; this plan never touches
   `Array[Int64]` at all, avoiding the disclosed 8x overhead outright
   rather than accepting it.
3. **`WebSocketConnection` is a single `Int64` newtype handle over one
   shared `tungstenite::WebSocket<WsStream>` type, not two separate
   client/server instantiations.** `WsStream` (`websocket.rs`) is a
   small enum (`Client(TcpStream)` / `Server(Box<dyn tiny_http::
   ReadWrite + Send>)`) implementing `Read`/`Write` itself by
   dispatching to whichever variant is stored — mirroring `tls.rs`'s
   own `TlsStreamInner` precedent one level up, so exactly one
   `crate::handle` registry entry type exists regardless of which side
   opened the connection, and every instance method
   (`.send_text`/`.send_binary`/`.recv`/`.close`) has one implementation,
   not two.
4. **`WebSocketMessage` is an ordinary compiler-synthesized `Type::Class`
   with real `ClassInfo.methods` entries (`FileMetadata`'s own shape),
   not a new hardcoded `Type` variant.** The plan's own text proposed
   adding a fourth hardcoded compound `Type` reusing `Result`'s
   discriminant-plus-payload-slot trick directly — a real, avoidable
   blast radius across every exhaustive `Type` match in `emerald-sema`/
   `emerald-codegen`, the same "avoid touching core `Type`" reasoning
   plans 100/101 already applied to `HttpResponse`/`HttpRequest`. The
   *runtime* representation still reuses the identical `[kind: i64 @0]
   [payload: i64 @8]` heap-block trick this plan's own Decision log
   describes (`websocket.rs`'s own `build_ws_message`) — only the
   *compiler-type* side changed, not the wire/memory shape.

A real, load-bearing bug found and fixed only by actually compiling and
running `examples/websocket_proof.em` end to end, not caught by any
unit test in isolation: `Http.serve`'s own per-request loop
(`http_server.rs`) unconditionally called `request.as_reader()
.read_to_string(&mut body)` for every incoming request before ever
invoking the handler. For an ordinary request this is safe (`tiny_http`
resolves an absent `Content-Length`/`Transfer-Encoding` to a real
zero-length body); for a genuine WebSocket handshake request (carrying
`Upgrade: websocket`), `tiny_http` does not make that same resolution
and this call blocks indefinitely waiting for body bytes a WebSocket
client — already waiting on the server's own 101 response — is never
going to send, hanging the connection before `HttpRequest#upgrade` is
ever reached. Fixed by skipping the eager body read entirely for any
request carrying an `Upgrade` header (case-insensitive), which has no
meaningful body per the handshake's own spec regardless.
