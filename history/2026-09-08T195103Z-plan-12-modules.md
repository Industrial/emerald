# Plan 12 — Modules

This is `modules-mixins`, row `12` of
[`plan-of-plans`](../../history/2026-09-08T174011Z-plan-of-plans.md),
implementing inception §19's module questions exactly as
`spec/SEMANTICS.md` §10 already resolved them: modules survive as
**namespacing only** — `include`/`extend` (mixin composition) are
explicitly **not retained in v1**, and modules cannot define fields
(no instance state to hold them). Inception/GRAMMAR.md give no single
worked example; this plan's concrete proof, self-designed per the
established practice from plans 07–11, is:

```ruby
module MathUtils
  def double(x: Int64) -> Int64
    x + x
  end
end

puts MathUtils.double(21)
```

Expected output: `42`.

## Decision log

- **No nested classes/modules, no module-level constants.**
  `SEMANTICS.md` §10.1's fuller feature set ("can hold constants, nested
  classes/modules") is deferred — this plan proves the core claim (a
  namespace holding static methods, called via `Name.method`), not the
  full namespace-nesting surface. A flat top-level `module Name ... end`
  containing only method definitions is the whole feature this plan
  ships.
- **Modules reuse `emerald-sema`'s existing `ClassInfo`/`classes`
  registry and `emerald-codegen`'s existing `ClassLayout`/`classes`
  registry**, tagged with a new `is_module: bool` field, rather than
  threading a brand-new `modules: HashMap<...>` parameter through every
  type-checking/codegen function that already carries `classes` (which
  is most of them). This is a real design choice, not just a shortcut:
  it's what makes `MathUtils.new()` a genuine, correctly-rejected sema
  error (`is_module` gates `Expr::New`) rather than a silent type-system
  hole — the alternative (a fully separate module registry) would either
  need the same wide threading anyway, or accept that gap.
  `Module` methods reuse `Function`'s existing AST shape, sig-checking
  (`function_signature`), and body-checking (`check_function_body`)
  unchanged — a module method type-checks exactly like a free function,
  because it *is* one, just namespaced.
- **`Name.method(args)` reuses the existing `Expr::MethodCall` grammar
  and AST shape** — no new call syntax. Sema/codegen distinguish "this
  receiver names a module" from "this receiver is a class instance/Proc
  value" by checking whether `Ident`'s name resolves to a module in the
  `classes`/`ClassLayout` registry *before* attempting to type-check it
  as an ordinary value expression (a module reference isn't a value in
  this design — there's no `Type::Module` variant, matching how modules
  aren't first-class values needing storage anywhere).
- **Module methods compile exactly like free functions — no implicit
  `self` parameter**, unlike class methods (which always take a leading
  `self: i64`). This is the direct consequence of modules having no
  instance state to point `self` at, not an extra restriction; codegen
  reuses `define_user_function` for module method bodies unchanged.

## Leaf: leaf-ast-modules

### 1. Context
- Why: no AST shape exists for `module ... end`.
- Target state: `ModuleDef { name: String, methods: Vec<Function> }`;
  `Item::Module(ModuleDef)`; grammar production `"module" Ident FuncDef*
  "end"`. `module` becomes a reserved keyword (same LALR(1) reason
  `class`/`def` etc. already are — disjoint FIRST sets, no conflict
  expected).

### 2. Acceptance Criteria
1. `ModuleDef`/`Item::Module` exist as described.
2. This plan's full example parses: `Item::Module` with one method
   `double`, plus a top-level `puts MathUtils.double(21)` statement
   parsing as the *existing* `Expr::MethodCall` shape (no new AST node
   for the call site).
3. Regression: every prior plan's example still parses identically.

## Leaf: leaf-sema-modules

### 1. Context
- Target state: `ClassInfo` gains `is_module: bool`; `check_program`
  registers each `Item::Module`'s methods into `classes` (empty
  `fields`, `is_module: true`) via the existing `function_signature`/
  `check_function_body` — no separate module-specific checking
  functions. `Expr::New` on a module-tagged `ClassInfo` is rejected.
  `Expr::MethodCall`'s existing arm checks "is the receiver `Ident` a
  known module" first, dispatching to the module's method table without
  ever type-checking the receiver as a value.

### 2. Acceptance Criteria
1. This plan's full example type-checks `Ok(())`.
2. `MathUtils.new()` is rejected with a diagnostic naming modules as
   non-instantiable, not silently accepted.
3. `MathUtils.missing(1)` (undeclared module method) is rejected with a
   diagnostic, not a panic.
4. `MathUtils.double(1, 2)` (wrong arity) is rejected the same way an
   arity mismatch on a class method already is.

### 3. File & Module Structure
- **Modify:** `crates/emerald-sema/src/lib.rs`

### 4. Quality Gates

| Test | `cargo test -p emerald-sema` | all pass | agent-claimed-locally |

## Leaf: leaf-codegen-modules

### 1. Context
- Target state: `ClassLayout` gains `is_module: bool`; `compile_to_object`
  declares each module method as `{Module}_{method}` with the *same*
  signature a free function would have (no leading `self`) and defines
  its body via the existing `define_user_function`, unchanged.
  `build_method_call` checks "is the receiver a module" first — if so,
  it never builds a receiver value at all, just evaluates `args` and
  calls `{Module}_{method}` directly.

### 2. Acceptance Criteria
1. This plan's full example, compiled, linked, and run, prints `42\n` —
   real executed proof.
2. An unsupported shape (calling a method on a module the compiler
   doesn't recognize) defensively returns a descriptive `Err`, not a
   panic — same AC standard as every prior codegen plan.

### 3. File & Module Structure
- **Modify:** `crates/emerald-codegen/src/lib.rs`
