# Plan 189 — CBOR Binary Format

CBOR (RFC 8949, the Concise Binary Object Representation) is, by
design, structurally the same data model as JSON — maps, arrays,
strings, numbers, booleans, null — just serialized as compact binary
instead of text, with a handful of real, useful extensions JSON lacks
(a native byte-string type, tagged values, a canonical-encoding
option). Plan 118 already had to answer the harder design question for
Emerald's stdlib: what does a dynamic, schema-less, arbitrary-JSON-tree
value even *look like* as an Emerald-facing type, given Emerald's own
static type system has no native sum-of-everything value? This plan
does not re-answer that question. It reuses plan 118's answer directly
and unmodified, adding only the two functions — `encode`/`decode` — that
convert between that one dynamic-value representation and a CBOR byte
buffer. Restated plainly, as the task assigning this plan requires: CBOR
is structurally JSON-shaped, so the same dynamic-value design applies
directly, and this plan states that explicitly rather than re-deriving
a second, parallel dynamic-value model that would leave Emerald with
two different answers to the identical representational problem.

Depends on: plan 91 (`emerald-rt` archive), plan 92 (`catch_unwind`
convention, `Result[T,E]` helpers, and the binary-safe `(ptr, len)`
buffer convention this plan's own byte-array parameters/returns are
built on), plan 93 (cited for completeness — this plan introduces no
new resource-handle type of its own; see Decision log), plan 95
(crate-vetting policy and checklist), and plan 118 (a hard, structural
dependency: this plan has no dynamic-value type of its own and cannot
function without plan 118's `DynValue` already existing).

## Concrete proof this plan targets

```ruby
original: DynValue = Json.parse("{\"name\": \"Ada\", \"scores\": [1, 2, 3], \"active\": true}")

encoded: Array[UInt8] = Cbor.encode(original)
puts encoded.length > 0

decode_result: Result[DynValue, String] = Cbor.decode(encoded, encoded.length)

case decode_result
when Ok(decoded)
  puts Json.stringify(decoded)
when Err(msg)
  puts msg
end
```

Expected output: `true` (a non-empty CBOR byte buffer was produced),
then the same `{"name":"Ada","scores":[1,2,3],"active":true}`-shaped
JSON text `Json.stringify` would have produced from the *original*
value — a real, working proof that a value built through plan 118's own
JSON surface survives an `encode`-then-`decode` round trip through CBOR
with no bespoke CBOR-specific value-construction code anywhere in this
plan's own worked example. (`Json.parse`/`Json.stringify` are plan
118's own real function names, assumed here as the natural counterparts
to this plan's `Cbor.encode`/`Cbor.decode` — if plan 118 lands under
different names, this plan's own leaves adopt whatever plan 118 actually
ships, not this placeholder.)

## Decision log

- **No new dynamic-value type — the single most important decision
  this plan makes, and it is a decision *not* to design something.**
  Plan 118 must already have solved "what Emerald type represents an
  arbitrary JSON value" — the options it faced (a compiler-synthesized
  tagged-union enum akin to `Option[T]`'s own `Some`/`None` shape per
  plan 73, a handle into an opaque Rust-side `serde_json::Value`-
  equivalent tree per plan 93's resource model, or something else
  entirely) are that plan's call, not this one's to re-litigate. This
  plan's own `leaf-scaffold-cbor-module` names the type `DynValue` only
  as a placeholder for whichever concrete type/handle plan 118 actually
  produces — the real implementation leaf imports and reuses that type
  directly. A future reader should not interpret this plan's `DynValue`
  references as introducing a second type; they name plan 118's one
  type throughout.
- **`ciborium`'s own `Value` type is the natural intermediate — CBOR's
  own dynamic-value type, not something this plan invents either.**
  `ciborium` 0.2.2 (published 29 August 2026, Apache-2.0, maintained
  under the `enarx` organization, `serde`-based, depending on the
  companion `ciborium-io`/`ciborium-ll` crates for the actual RFC 8949
  wire encoding) exposes `ciborium::Value`, a real, already-built
  dynamic CBOR tree type with variants `Integer`, `Float`, `Bool`,
  `Text`, `Bytes`, `Array`, `Map`, `Tag`, and `Null`. This plan's real
  conversion work is walking between plan 118's `DynValue` and
  `ciborium::Value`, not between plan 118's `DynValue` and raw bytes
  directly — `ciborium::into_writer`/`from_reader` handle the actual
  binary encoding once a `ciborium::Value` tree exists, so this plan
  never hand-writes a single CBOR major-type byte itself.
- **CBOR's native byte-string type (`Value::Bytes`) and tag mechanism
  (`Value::Tag`) have no plan-118 counterpart and are declined in v1,
  named explicitly rather than silently dropped.** JSON has no native
  binary-blob type (a JSON dynamic value can only ever be a string,
  number, bool, array, object, or null), so plan 118's own `DynValue`
  almost certainly has no variant for "raw bytes" or "a tagged value"
  either. `leaf-decode`'s conversion therefore has two real CBOR
  variants with no destination in plan 118's type: a `Value::Bytes` or
  `Value::Tag` anywhere in a decoded CBOR document produces `Err`
  (unsupported CBOR feature), not a silent, lossy downgrade (e.g.
  base64-encoding bytes into a string variant, which would break the
  round-trip symmetry this plan's whole worked proof depends on making
  visible). A CBOR value that only uses the JSON-shaped subset of the
  format — which is what `leaf-encode`'s own output always produces —
  always round-trips cleanly; a foreign CBOR document using CBOR-only
  features may not, and this plan states that boundary plainly instead
  of quietly mishandling it.
- **No new resource-handle type, so no dependency on plan 93's
  handle-table machinery beyond citation.** Every other plan in this
  batch that needs cross-call state (a parser spec, an open connection,
  an index writer) registers a compiler-provided class behind an opaque
  `u64` handle. This plan needs none of that: `encode`/`decode` are
  both single-call, stateless conversions — a `DynValue` tree in, a
  byte buffer out, or the reverse — with nothing that needs to survive
  between two separate Emerald-visible calls. Plan 93 is cited in this
  plan's Depends-on line for completeness and consistency with the rest
  of the batch's citation style, not because this plan's own leaves
  actually allocate a handle.
- **Byte-array marshaling follows plan 92's binary-safe convention, not
  plan 59's plain `char*` `String` convention.** A CBOR-encoded buffer
  is genuinely binary — it can and regularly does contain embedded NUL
  bytes as ordinary, valid content (unlike a null-terminated Emerald
  `String`, which cannot, per plan 59's own verified finding that
  `String` has no length header and relies entirely on the terminating
  NUL). This plan's `encode`/`decode` therefore use plan 92's `(ptr:
  *const u8, len: i64)` two-parameter convention (with an `out_len: *mut
  i64` out-parameter on the encode side, per that plan's own documented
  shape) rather than treating a CBOR buffer as if it were a `String` —
  the exact hazard plan 92's own `leaf-binary-safe-buffer-convention`
  names by name ("compression, crypto, binary serialization, images")
  and this plan is a direct, concrete instance of.
- **Out of scope.** CBOR's canonical-encoding mode (RFC 8949 §4.2's
  deterministic-encoding rules, useful for content-addressed
  hashing/signing of CBOR documents) — `ciborium`'s own encoder does
  not currently guarantee canonical output by default, and adding a
  canonicalization pass is real, separate, non-trivial logic this plan
  does not attempt. CBOR tags with semantic meaning (RFC 8949's own
  registered tags — e.g. tag 0/1 for date/time, tag 2/3 for bignums) —
  named above as producing `Err` on decode; giving any of them real
  Emerald-level semantic handling (e.g. decoding a tag-0 value into
  some future Emerald date/time type) is a distinct, later feature, not
  this plan's. Streaming encode/decode (processing a CBOR document
  larger than fits comfortably in memory, incrementally) — this plan's
  `encode`/`decode` are both whole-buffer, in-memory operations, the
  same posture plan 118 presumably takes for JSON.
