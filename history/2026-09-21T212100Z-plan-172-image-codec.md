# Plan 172 — Image Decode/Encode

This is the fifth of eight sibling plans (168-175) in the 91-191
batch, and the one the commissioning brief specifically asked to be
precise about rather than making a blanket "it's pure Rust" claim. The
`image` crate is an umbrella over a dozen independently-versioned
per-format codec crates, and this session checked each one that
matters to v1 directly against `image` 0.25.10's own `Cargo.toml`
rather than assuming.

## Concrete proof this plan targets

```ruby
data: Bytes = File.read_bytes("examples/fixtures/plan172_input.png")
img: ImageHandle = Image.decode(data)
puts Image.width(img)
puts Image.height(img)

resized: ImageHandle = Image.resize(img, 4, 3)
puts Image.width(resized)
puts Image.height(resized)

out: Bytes = Image.encode(resized, "jpeg")
File.write_bytes("examples/fixtures/plan172_output.jpg", out)

Image.close(img)
Image.close(resized)
```

Expected output (the fixture is committed at exactly `8x6` pixels):

```
8
6
4
3
```

`plan172_output.jpg` is a real, valid JPEG file after this program
exits — re-decoding it with `Image.decode` and checking `.width`/
`.height` returns `4`/`3` is the follow-up assertion the Rust-side
`#[test]`s make directly, closing the loop from real PNG bytes on disk,
through decode, resize, encode, back to a second real file on disk,
with no step of that pipeline asserted only in prose.

## Decision log

- **`image` 0.25.10, verified today: owned by `theotherphil`/
  `fintelia`/`197g` under the `image-rs` GitHub organization, dual
  MIT/Apache-2.0, published 17 September 2026.** It is the umbrella
  crate the brief describes it as — its own `[dependencies]` table
  (checked this session, in full, against `Cargo.toml.orig`) shows
  every format codec as a separate, independently-versioned, mostly
  optional dependency, not code `image` itself implements from
  scratch for every format.
- **The precise, per-format pure-Rust-vs-C-backed audit this plan was
  specifically asked to do, not hand-waved.** Checked directly against
  `image` 0.25.10's real `Cargo.toml.orig` `[dependencies]`/`[features]`
  tables this session:
  - **PNG** — `png ^0.18.0`, pure Rust (the `image-rs` organization's
    own PNG codec).
  - **JPEG** — decode via `zune-jpeg ^0.5.5` (pure Rust) plus
    `zune-core`; encode via a pure-Rust encoder built directly into
    `image` itself (no separate encoder crate dependency at all).
  - **GIF** — `gif ^0.14.0` (pure Rust) plus `color_quant ^1.1` (pure
    Rust, palette quantization for encode).
  - **WebP** — `image-webp ^0.2.0`, `image-rs`'s own pure-Rust
    implementation (the `webp` feature's only dependency — no
    `libwebp`/`libwebp-sys` C binding anywhere in this path).
  - **TIFF** — `tiff ^0.11.2`, pure Rust.
  - **QOI** — `qoi ^0.4`, pure Rust.
  - **BMP, ICO, TGA, PNM** — no separate codec dependency at all;
    their `[features]` entries (`bmp = []`, `tga = []`, `pnm = []`,
    `ico = ["bmp", "png"]`) show they are implemented directly inside
    `image`'s own source, pure Rust by construction.
  - **AVIF — the one genuinely mixed case, and the reason this plan
    declines it entirely in v1.** The default `avif` feature is
    `["dep:ravif", "dep:rgb"]` — `ravif` (wrapping `rav1e`) is a real,
    pure-Rust AV1 *encoder*, so AVIF **encoding** is pure Rust by
    default. AVIF **decoding** is a separate, opt-in feature,
    `avif-native = ["dep:mp4parse", "dep:dav1d"]` — `dav1d` is a
    binding to the C `libdav1d` AV1 decoder, not enabled by default.
    An Emerald `Image` module built on `image`'s default `avif`
    feature could therefore *write* AVIF files it can never read back
    through the same code path — an asymmetry this plan declines to
    ship. AVIF support (either accepting the `avif-native` C
    dependency for decode, or shipping encode-only with that asymmetry
    disclosed loudly) is real follow-up work for plan 95's
    crate-vetting policy to rule on explicitly, not a default this
    plan backs into silently.
- **`Bytes` (plan 92) is the load-bearing prerequisite this entire
  plan depends on, more than any other plan in this batch so far.**
  Every value plans 168-171 moved across the FFI boundary was either a
  scalar or a plain Emerald `String` — always NUL-terminated, always
  assumed UTF-8, per plan 59's own finding about `String`'s real
  runtime representation. Raw image bytes satisfy neither property: a
  PNG/JPEG/GIF file's byte stream routinely contains embedded `0x00`
  bytes, and decoded RGBA8 pixel data is not text at all. This plan is
  the first in the batch where plan 92's `(ptr, len)` binary-safe
  buffer convention is not an optional refinement but the only correct
  representation — every function in `leaf-pixel-buffer-roundtrip` and
  `leaf-encode` above is signed in terms of it.
- **Pixel format convention: tightly packed, row-major RGBA8, chosen
  because it is `image`'s own canonical in-memory shape, not an
  Emerald-specific choice needing its own conversion step.**
  `DynamicImage::to_rgba8()` already returns exactly this layout
  (`ImageBuffer<Rgba<u8>, Vec<u8>>`, `width * height * 4` bytes,
  no row padding/stride beyond `width * 4`) — `emerald_rt_image_pixels
  _rgba8` hands that buffer's bytes across the FFI boundary unchanged,
  and `emerald_rt_image_from_pixels_rgba8`'s `RgbaImage::from_raw` is
  the same representation in reverse. No format this plan supports
  needs bit-depth/channel-count negotiation in v1 — every decoded
  image is normalized to 8-bit RGBA on the way out, and `image`'s own
  `to_rgba8()` already performs whatever palette-expansion or
  grayscale-to-RGBA conversion a given source format needs.
- **`ImageHandle` is a genuinely different resource shape than
  plans 168/171's create-mutate-consume handles — an open-read-many-
  times-then-close shape, closer to a file descriptor.** `decode`,
  `resize`, and `crop` each *produce* a new handle rather than mutating
  an existing one in place (mirroring `DynamicImage`'s own
  by-value/immutable-transform methods), and a single handle is
  expected to be read from repeatedly (`.width`, `.height`,
  `.pixels_rgba8`, `.encode` can all be called on the same handle, in
  any order, any number of times) before an explicit `.close()` frees
  it — a real, disclosed leak if omitted, per this project's existing
  no-implicit-free precedent (plan 45's `Array`/`String`, plan 91's
  `emerald_alloc`). This is offered to plan 93 as a second concrete
  worked resource shape alongside plan 168's `LogFields`, since the two
  are genuinely not the same pattern and a general resource model
  needs to account for both.
- **`resize`/`crop` reuse real, existing `DynamicImage` methods with no
  new algorithm of this plan's own invention.** `resize` uses
  `image::imageops::FilterType::Lanczos3` unconditionally in v1 — the
  crate's own highest-quality resampling filter, a real named enum
  variant — with no Emerald-facing way to choose a cheaper filter
  (`Nearest`/`Triangle`) yet; `crop` is `DynamicImage::crop_imm`, the
  non-mutating variant, chosen specifically so a cropped view does not
  invalidate or consume the handle it was cropped from (consistent
  with the "produces a new handle" posture above).
- **Encode format selection is an unchecked `String`, matching plan
  171's `tera::Error`-is-a-disclosed-abort posture, not a new
  convention.** `"png"`/`"jpeg"`/etc. map to `image::ImageFormat`
  variants; a string this plan doesn't recognize, or an
  `image::ImageError` the underlying encoder genuinely returns, aborts
  the process with a disclosed error message rather than silently
  producing corrupt bytes or being routed through `raise`/`rescue` —
  the same choice plan 45 made for `File.read`/`File.write` and plan
  171 made for template errors, for the same reason: a real,
  `rescue`-able error-class hierarchy for image codec failures is
  separate, larger design work this plan does not need in order to
  prove decode/encode/resize/crop work at all.
- **Binary file I/O (`File.read_bytes`/`File.write_bytes`) is cited
  from plan 144, not re-derived here.** Plan 45's existing `File.read`/
  `File.write` are `String`-typed (NUL-terminated, UTF-8-assumed) and
  are the wrong tool for reading a PNG fixture or writing a JPEG
  output file — this plan's Concrete Proof assumes plan 144 adds a
  `Bytes`-typed `File.read_bytes`/`File.write_bytes` pair, the same
  forward-citation discipline plan 60 used for plan 59 before that
  file existed. This plan does not itself add file I/O of any kind.
- **Out of scope.** AVIF (see above); HEIC/HEIF (not supported by the
  `image` crate at all, by the crate's own long-standing project
  scope, primarily due to the HEVC codec's patent-licensing
  situation — there is no feature flag to enable it even with a C
  dependency accepted); animated GIF/WebP frame sequences (v1 decodes
  and encodes single still frames only — `image::AnimationDecoder` is
  real but unused here); ICC color profile application; EXIF metadata
  reading or writing; any drawing/compositing/filter API beyond
  `resize`/`crop` (no rotate, no blur, no overlay/composite); and
  `exr`/`dds`/`hdr`/`ff` (Farbfeld) — all real, pure-Rust, default-
  formats-eligible features this plan simply declines to enable for
  v1, being the more niche formats of the set, not because of any
  purity or dependency concern.
