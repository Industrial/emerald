# Plan 114 — JSON Web Tokens (JWT)

`jsonwebtoken` — verified this session via `lib.rs`, current release
`11.1.0` (2026-09-16, five days before this plan was written), MIT
licensed, by Vincent Prouillet (`Keats`) with 93 contributors, 18M
downloads/month, used directly by 1,797 crates — supports HS256/384/512,
RS256/384/512, PS256/384/512, ES256/384, and EdDSA. Verified directly
against its own README's "Algorithms" list: there is no `none` entry.
This matters specifically because of JWT's best-known historical
vulnerability class: the JOSE spec permits an unsecured JWT with
`"alg":"none"` and an empty signature, and several early JWT libraries
across languages accepted a token in that shape and returned its claims
as if they'd been verified, because the library's `decode` function
trusted the token's own header to say which algorithm to check against.
An attacker who can get a relying party to accept a `"none"`-algorithm
token can forge arbitrary claims with no key at all. `jsonwebtoken`
closes the first half of this by construction — its `Algorithm` enum
simply has no variant a `"none"` header value can parse into, so a token
claiming `"alg":"none"` fails to decode as a header at all, verified
fact, not assumed behavior. This plan's job is closing the second half:
making sure Emerald's own wrapper never reopens the hole the crate itself
closed, by never offering a decode-without-a-key entry point in the first
place.

Two crypto backends are available for `jsonwebtoken` 11, selected via
Cargo feature: `aws_lc_rs` (pulling in `aws-lc-rs`, a BoringSSL/AWS-LC-
derived FFI wrapper) and `rust_crypto` (pulling in the RustCrypto crates
listed in the `leaf-jwt-module-scaffold` task above). This plan selects
`rust_crypto` deliberately — verified this session against the crate's
own `lib.rs` dependency listing, the `rust_crypto` feature depends on
`hmac`, `sha2`, `ed25519-dalek`, `p256`, `p384`, and `rsa`, all RustCrypto-
maintained, pure-Rust crates, matching the ecosystem plan 95's vetting
policy already prefers and the same crates plans 109/111 independently
select. This is recorded here specifically because "does `jsonwebtoken`
depend on `ring`" is a natural but, as of this version and backend
choice, incorrect question to ask — it depends on neither `ring` nor
`aws-lc-rs` once `rust_crypto` is the selected backend, a fact worth
stating plainly in plan 95's `DEPENDENCIES.md` ledger rather than assumed
from older `jsonwebtoken` versions (pre-9.x releases defaulted to `ring`
with no backend choice at all).

## Concrete proof this plan targets

```ruby
claims: Hash[String, String] = { "sub" => "1234567890", "name" => "John Doe", "iat" => "1516239022" }
secret: String = "your-256-bit-secret"

token: String = Jwt.encode_hs256(claims, secret)
puts token

verified: Hash[String, String]? = Jwt.verify_hs256(token, secret)
verified ||= { "error" => "verification failed" }
puts verified["name"]

tampered: String = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkphbmUgRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c"
bad: Hash[String, String]? = Jwt.verify_hs256(tampered, secret)
bad ||= { "error" => "verification failed" }
puts bad["error"]
```

Expected output: line 1 is the well-known jwt.io HS256 debugger example
token,
`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`
— a real, independently-verifiable value anyone can reproduce by pasting
this plan's exact claims and secret into jwt.io's own public debugger, or
by decoding the token's header/payload segments as plain base64url JSON
by hand; line 2 is `John Doe` (the real claim, extracted after real
signature verification succeeds); line 3 is `verification failed` — the
third token is the *same* debugger example with `"name"` changed from
`John Doe` to `Jane Doe` in the payload but its original signature
left unchanged (a hand-tampered forgery), which must fail verification
against the original signature.

## Decision log

- **The "alg: none" defense is structural in two independent, stacked
  ways — the crate's own enum, and this plan's own API shape — not one
  defense repeated twice for emphasis.** First: `jsonwebtoken`'s
  `Algorithm` enum, verified against its README's algorithm list, has no
  `None` variant — a token whose header claims `"alg":"none"` cannot even
  be parsed into a value the crate's own decode path can dispatch on, so
  it fails before signature checking is even reached. Second, independent
  of the crate: this plan's Emerald surface has no `Jwt.decode(token):
  Hash[String,String]` entry point that takes a token and *no* key — every
  `verify_*` function requires a secret or a public key as a mandatory
  argument, and the one function that doesn't (`Jwt.peek_header`) is
  named and documented specifically to make clear it never returns
  verified claims (see below). Even if a future crate swap or version
  bump ever reintroduced a `none`-tolerant decode path at the Rust layer,
  this plan's own Emerald-visible API shape would still have no caller-
  reachable way to invoke it, because no function signature in this
  module accepts a token without also requiring a key.
- **`Jwt.peek_header` is named `peek_`, not `decode_header` or
  `inspect_`, as a deliberate, visible warning label — matching plan 59's
  "risk marker visible at the point of use" posture exactly.** The crate's
  own `decode_header` function is real and legitimate — its own README
  documents it as the way to "grab the `kid`" before you know which key
  to verify against, a real and necessary step in key-rotation scenarios
  — but its name alone ("decode") invites a careless caller to treat its
  return value as trustworthy claims. This plan's Emerald wrapper renames
  it to `peek_header` specifically so `Jwt.peek_header(token)["role"]`
  reads, at the call site, as obviously wrong — nothing named "peek" a
  reasonable reader expects to be an authorization signal.
- **`verify_*` failures collapse to `nil`/`Result`'s error case, never a
  distinguishable "which check failed" value reachable by ordinary
  control flow — mirroring plan 112's identical choice for
  `Password.verify`, cited rather than re-derived.** An expired token,
  a bad signature, a malformed token, and a token signed with the wrong
  key all fail the same way from the caller's perspective. This is a
  narrower version of plan 112's oracle-closing argument: a caller who
  can distinguish "signature invalid" from "token expired" via a return
  value gets a small but real information leak about *why* a forged or
  stale token was rejected, useful to an attacker iterating on a forgery
  attempt. A future, more detailed `JwtError` enum for legitimate
  debugging/logging purposes (server-side only, never surfaced to the
  token's own presenter) is a reasonable addition this plan's binary
  success/failure surface doesn't preclude, just doesn't build yet.
- **Claims are `Hash[String, String]`, not an arbitrary JSON value or a
  user-defined class, in this plan's v1 surface — a real, disclosed
  simplification, not a claim that JWT claims are inherently string-
  typed.** Real-world JWT claims routinely include numbers (`exp`, `iat`
  as Unix timestamps), nested objects, and arrays — `Hash[String,String]`
  cannot represent those faithfully, and this plan's worked proof above
  stores `"iat"` as a stringified number specifically because of this
  limitation, disclosed here rather than hidden. A richer typed-claims
  story (an Emerald `class` with `#[derive]`-style JSON
  (de)serialization, matching the crate's own `#[derive(Serialize,
  Deserialize)] struct Claims` pattern in its README) is a real,
  substantially larger feature — it needs a working JSON library and a
  serialization-attribute mechanism neither of which this plan's narrow
  scope builds. `Hash[String,String]` is the smallest thing that lets
  this plan's Concrete Proof round-trip real claims end to end today.
- **RS256/ES256 key parameters are plain PEM `String`s, deliberately not
  yet a shared `PrivateKey`/`PublicKey` type plan 111 might define.**
  This plan is authored in parallel with plan 111 (asymmetric crypto)
  this same session and does not assume or wait on its exact key-value
  representation — `jsonwebtoken`'s own `EncodingKey::from_rsa_pem`/
  `DecodingKey::from_ec_pem` constructors (verified against the crate's
  README) already take PEM bytes directly, so a plain `String` parameter
  is both correct today and the natural bridge point if plan 111 later
  exposes its own key type with a `.to_pem(): String` accessor — this
  plan's `Jwt.encode_rs256(claims, private_key_pem)` signature would need
  no change, only a caller passing `key.to_pem()` instead of a literal
  PEM string.
- **Signature comparison inside `decode`/`verify_password`-equivalent
  logic is the crate's own problem, inherited rather than duplicated —
  plan 117 is cited by reference, not re-implemented.** Per plan 117's
  own cross-cutting rule, JWT signature verification must be constant-
  time; `jsonwebtoken`'s `rust_crypto` backend performs this via the
  underlying RustCrypto primitives (`hmac`'s own constant-time tag
  comparison for HS256, `ed25519-dalek`/`p256`/`p384`/`rsa`'s own
  signature-verification routines for the asymmetric algorithms), and
  this plan's wrapper never re-extracts or re-compares raw signature
  bytes itself — exactly the same "inherit, don't duplicate" posture
  plan 112 documents for `argon2`.
- **Out of scope.** No PS256/384/512 or EdDSA entry points in this plan's
  initial surface, despite the crate supporting both — RS256/ES256/HS256
  cover this plan's three named algorithm families (HMAC, RSA, ECDSA)
  with no new design question the omitted algorithms would raise; adding
  `Jwt.encode_eddsa`/`verify_eddsa` keyed by plan 111's Ed25519 key type
  is a small, additive follow-up once that type exists. No JWK
  (JSON Web Key) parsing/thumbprint support, despite the crate offering
  it — a real, separate feature (fetching and caching a key from a
  `.well-known/jwks.json` endpoint) this plan's static-key-parameter
  design doesn't need. No refresh-token/token-family rotation semantics —
  an application-level concern layered on top of this plan's raw
  encode/verify primitives, not part of the JWT format itself. No `kid`-
  based automatic key lookup — `Jwt.peek_header` exists specifically so a
  caller can implement this themselves at the Emerald level once they
  have a key store, which this plan does not design.

Five real, disclosed corrections found only by actually running this
plan's own Concrete Proof against the real, current compiler — not
assumed from this plan's own text:

1. **`default-features = false` silently drops the crate's own
   `default = ["use_pem"]` feature.** `EncodingKey`/`DecodingKey`'s
   own `from_rsa_pem`/`from_ec_pem` constructors — this plan's own
   RS256/ES256 key parameters — are `#[cfg(feature = "use_pem")]` and
   do not exist at all without it. Fixed by adding `"use_pem"`
   alongside `"rust_crypto"` in `Cargo.toml`.
2. **`jsonwebtoken::Validation::new`'s own real default REQUIRES an
   `exp` claim to be present at all** (`required_spec_claims` defaults
   to `{"exp"}`, verified directly against `validation.rs`), but this
   plan's own Concrete Proof is the real jwt.io HS256 debugger
   example, whose claims never include `exp` (independently verified
   by base64url-decoding the plan's own quoted token). Requiring it
   would make the plan's own worked proof fail to verify. `jwt.rs`'s
   own `verify_with_key` clears `required_spec_claims` while leaving
   `validate_exp` at the crate's own default `true` — "always
   validates `exp`" (this plan's own leaf text) now means "checked
   when present, never mandatory," not "every token must carry one."
3. **`leaf-claim-validation`'s own literal syntax
   (`Jwt.verify_hs256(token, secret, issuer: "my-app")`) does not
   parse — Emerald has no keyword-argument call syntax at all**
   (checked directly against `spec/GRAMMAR.md` and the whole
   compiler's own grammar; nothing resembling a `name: value`
   call-site argument exists anywhere). Adapted to a separate,
   explicitly-named function per algorithm (`.verify_hs256_with_
   issuer`/`.verify_rs256_with_issuer`/`.verify_es256_with_issuer`)
   taking `issuer` as a plain, mandatory, positional trailing
   `String` — the base `verify_*` functions' own 2-argument arity
   (required by the Concrete Proof's own calls) is unchanged, and the
   Decision log's real functional intent (additive validation on top
   of the always-on signature/`exp` checks, via the crate's own real
   `Validation.iss`/`.set_issuer`) is still delivered exactly.
4. **The plan's own Concrete Proof text uses `Hash[String, String]?`
   and `||=` — both were removed outright by plan 73, real, disclosed
   findings `charset_encoding_proof.em`/`environment_variables_proof.em`
   already made for other plans.** The real, current annotation is
   `Option[Hash[String, String]]`, matched via `match ... Some(...)/
   None ... end`.
5. **Claim access via direct bracket indexing (`verified["name"]`)
   does not compile — `emerald-codegen`'s own `build_index` only
   supports `Int64`-keyed `Hash` indexing** (plan 25's own Decision
   log, "a flat linear-scan representation," verified directly
   against the source — `build_hash_lookup` hard-requires an
   `IntValue` index). A `Hash[String, String]` value is read via
   `.each do |pair: Pair[String, String]| ... end`, the exact pattern
   `csv_demo.em`'s own `Hash[String, String]` records already
   establish. A further, real, previously-undisclosed codegen gap
   found the same way: calling `.each` directly on a `Hash[String,
   String]` bound by a `match ... Some(claims_out) do ... end` pattern
   arm fails with an internal codegen error ("enumerable Proc argument
   is not a plain local") — worked around exactly the way
   `csv_demo.em` itself already does, a `var` declared outside the
   `match`, assigned inside each arm, `.each` called on that outer
   `var` after the `match` closes.

None of these five are `jwt.rs`-specific bugs — all five are either
this plan's own text predating a later, cross-cutting language change
(3, 4) or genuine compiler-wide limitations this plan's own Concrete
Proof happened to be the first to exercise (2 is jsonwebtoken's own
crate default, not a compiler limitation; 1 and 5 are real gaps in
`Hash[String,String]` bracket-indexing and match-arm-bound-local

Fixing 5's own codegen gaps generally (String-keyed `Hash` bracket
