# Plan 118 — JSON

This is plan 118 of the 91-191 batch extending Emerald's stdlib by
wrapping vetted Rust crates, built directly on plan 91's `emerald-rt`
mechanism (a second, Rust-compiled static archive linked alongside
`runtime/emerald_runtime.c`, every export `catch_unwind`-wrapped) and
depending on plan 92's FFI/ABI conventions and plan 93's resource-handle
model wherever this plan needs either. Crate: `serde_json` (with
`serde`, transitively). Verified this session via `lib.rs`'s real,
current crate page: `serde_json` 1.0.151 (published Jul 20, 2026), owned
by `dtolnay`/`serde-rs`, ranked **#1** in the "Encoding" category,
**116,478,133 downloads per month**, used directly in **104,181** other
crates. There is no serious competing choice for a "vetted, widely-used"
JSON crate in the Rust ecosystem — `simd-json`/`sonic-rs` exist and are
faster, but both trade `unsafe`-heavy SIMD parsing and non-default
`serde` integration for that speed, and nothing about this plan's own
target (correctness, not throughput) asks for it; `serde_json` is the
default, boring, proven choice, and this plan makes it deliberately.

This plan is the one this batch's four sibling data-format plans (119
TOML, 120 YAML, and 125/126 elsewhere in the batch) all point back to
for one specific, hard design question, stated here first and answered
directly, not dodged: **when a Rust crate parses an arbitrarily-shaped
document — an object nested inside an array nested inside an object,
whose exact shape is only known at runtime — how does that value live
inside Emerald, a language with no reflection, no `method_missing`, and
a `Type` checked entirely at compile time?**

The answer: a real, closed, tagged-union **`JsonValue` enum**, using
the exact mechanism plan 52 already built and shipped — `case`/`when`
pattern matching with real, compiler-enforced exhaustiveness — not a
schema declared up front. A parsed document is a `JsonValue` tree;
Emerald code destructures it the same way it already destructures
`Shape`/`Option[T]`/`Result[T,E]`, because it *is* the same mechanism,
reused, not a new one invented for this plan.

## Concrete proof this plan targets

```ruby
input: String = "{\"name\": \"Ada\", \"age\": 36, \"active\": true, \"tags\": [\"math\", \"cs\"]}"

match Json.parse(input) do
Ok(doc) do
  name: JsonValue? = doc.get("name")
  name ||= JsonNull()
  case name
  when JsonString(s)
    puts s
  else
    puts "missing"
  end

  nickname: JsonValue? = doc.get("nickname")
  nickname ||= JsonNull()
  case nickname
  when JsonString(s)
    puts s
  else
    puts "missing"
  end

  tags: JsonValue? = doc.get("tags")
  tags ||= JsonNull()
  case tags
  when JsonArray(items)
    puts items.count
  else
    puts "missing"
  end

  puts doc.to_s
end
Err(msg) do
  puts msg
end
end
```

Expected output:
```
Ada
missing
2
{"name":"Ada","age":36.0,"active":true,"tags":["math","cs"]}
```
(`age`'s `36` prints back as `36.0` — see the Decision log's numeric-
widening bullet; this is disclosed, not accidental.) A second, real
negative proof this plan equally targets: `Json.parse("{not json")`
reaches the `Err(msg) do ... end` arm with a real, non-empty parser
error string (`serde_json::Error`'s own `Display` text, e.g. `"key must
be a string at line 1 column 2"`), not a crash, not an empty string.

## Decision log

- **The dynamic value is a real Emerald `enum`, generalizing plan 52's
  tagged union — and two facts verified directly against current
  source, not assumed, are exactly what make this work for a
  *recursive*, JSON-shaped type.** First: `crates/emerald-sema/src/
  lib.rs`'s enum-registration pass (its whole-program `Item::Enum`
  loop, ~L10970-11033) runs in two passes — every enum name is inserted
  into `classes` with an *empty* `enum_variants: Some(Vec::new())`
  placeholder first (L11018), and only *then*, in a second loop
  (L11027+), does `resolve_type` get called on each variant's own field
  types. A variant field naming the enum's own type (`JsonArray(Array[
  JsonValue])`) resolves fine, because `JsonValue` is already present
  in `classes` by the time that second pass runs — this is not a
  hypothetical; `instantiate_generic_enum`'s own doc comment (L1243-1244)
  names this exact hazard and cites a real, already-working precedent:
  "a recursive generic enum — `enum Tree[T] = Node(T, Tree[T]) | Leaf`
  — hits the identical hazard a recursive generic class does" and is
  handled. Second: `value_kind_for_type` (`emerald-codegen/src/lib.rs`
  L376-379) puts every bare class-or-enum name in the generic `ValKind::
  Ptr` bucket, unconditionally — an Emerald enum VALUE is always a
  heap-allocated pointer to its own tag+payload block (verified against
  the `??`/`Option[T]` codegen path, which loads a tag via `load_field`
  off a `PointerValue` it got by calling `.into_pointer_value()` on the
  scrutinee). That means `Array[JsonValue]`'s elements and `Hash[String,
  JsonValue]`'s value slots are each an ordinary 8-byte pointer — bit-
  for-bit the same slot size `Array[String]`/`Array[SomeClass]` already
  use. `JsonValue` needs zero new codegen machinery beyond what
  `Array[T]`/`Hash[K,V]`/`EnumLayout` already provide; a recursive,
  arbitrarily-deep JSON tree is just pointers to more of the same
  16-byte (`tag:i64` + one 8-byte payload slot, since every `JsonValue`
  variant carries at most one field) blocks, all the way down.
- **`JsonValue` is compiler-synthesized, not written in `.em` source —
  mirroring the one non-generic precedent already alive in this
  compiler, `Option[T]`'s own `option_enum_def`.** Verified: `check_
  program`'s enum-collection pass pre-seeds `generic_enums` with `
  generic_enums.insert("Option".to_string(), &option_enum_def)` before
  it ever looks at `program.items` — `Option[T]` is a real `EnumDef`
  value built directly in Rust, never parsed from a `.em` file, and
  every one of `resolve_type`/`check_case`/`find_all_variants` treats it
  identically to a user-written enum because it lives in the exact same
  `classes` registry. `JsonValue` (non-generic, so it doesn't need
  `generic_enums` — it's inserted straight into `classes` the way this
  plan's own leaf describes) follows the identical pattern: a `Vec<
  EnumVariant>` built once in Rust (`JsonNull` with zero fields, `
  JsonBool(Boolean)`, `JsonNumber(Float64)`, `JsonString(String)`, `
  JsonArray(Array[JsonValue])`, `JsonObject(Hash[String, JsonValue])`),
  present in every compilation unconditionally. Zero grammar changes;
  `EnumVariant`'s own grammar (`crates/emerald-parser/src/grammar.
  lalrpop` L447-448, `EnumFieldTypes` allowing zero elements) already
  admits a bare `JsonNull()` — verified: the same trailing-comma-list
  production `Args`/`BindingNames` already use, empty-list-safe.
- **Every JSON number becomes `Type::Float64` — Emerald has no unified
  "Number" type to preserve JSON's own int-or-float ambiguity, and this
  plan does not add one.** Verified: `emerald-sema`'s real `Type` enum
  (`crates/emerald-sema/src/lib.rs` L23-151) has exactly `Int64`/
  `Float64` for numerics, nothing narrower or wider, no untagged union
  of the two. `JsonNumber(Float64)` widens every JSON number
  unconditionally — matching JSON's own de facto interoperability
  convention (JavaScript's own `Number` is IEEE-754 double for exactly
  this reason). The real, disclosed cost: `.to_s`'s round-trip is not
  byte-identical to the input for integer-looking numbers — `36`
  parses, widens, and re-serializes as `36.0` (this plan's own Concrete
  Proof shows this happening, not hides it). A dual `JsonInt(Int64)` /
  `JsonFloat(Float64)` split was considered and declined: it would push
  the int-vs-float decision onto `serde_json::Number`'s own `is_i64()`/
  `is_f64()` heuristic (itself imperfect — `1.0` and `1` are
  indistinguishable in JSON's own grammar, only in a given parser's own
  choice of Rust representation), doubling every downstream `case`
  arm's numeric handling for a distinction JSON's own spec doesn't
  actually make.
- **Object field access is `.get(key)`, never `obj["key"]` — because
  `Hash[K,V]`'s real, current `[]` indexing genuinely cannot handle a
  `String` key today, verified directly, not inferred.** `crates/
  emerald-codegen/src/lib.rs`'s `build_hash_lookup` (L10636-10642)
  takes `key_val: IntValue<'ctx>`, and both of its call sites inside
  `build_index` (L10822-10827 for a read, L10957-10962 for a write) pass
  it `idx.into_int_value()` unconditionally — `inkwell`'s `BasicValueEnum
  ::into_int_value()` panics if the value isn't actually an LLVM integer.
  A `String`-typed key (`ValKind::Str`, a `PointerValue`) sails past
  `emerald-sema`'s own key-type check (`infer_hash_lit_type`, `crates/
  emerald-sema/src/lib.rs` L4743-4784, has no Int64-only restriction —
  only same-type-across-all-keys) and then hits this `into_int_value()`
  call in codegen, which is a real, reachable compiler panic today for
  any `Hash[String, V]` ever indexed with `[]`. Fixing `Hash[K,V]`
  indexing in general is explicitly out of scope for this plan (see
  below) — instead, `.get` is a `JsonValue`-receiver-gated intrinsic
  (`recv_ty == Type::Enum("JsonValue")`, the exact dispatch shape plan
  45 already established for `Type::String`-gated intrinsics) backed by
  a *new* Rust function, `emerald_rt_json_object_get`, that reads
  `Hash[String, JsonValue]`'s own already-stable buffer format directly
  — an `i64` pair-count header at offset 0, then `n` flat `(key_ptr:
  8, value_ptr: 8)` pairs starting at offset 8 (verified against `build_
  hash_lit`'s own doc comment and body, `crates/emerald-codegen/src/
  lib.rs` L6940-6995) — comparing each `key_ptr` (a null-terminated
  UTF-8 buffer, plan 59's own verified `String` representation) against
  the requested key via ordinary Rust `CStr` equality, never touching
  `build_hash_lookup`/`into_int_value()` at all. This is legitimate
  because the buffer layout it reads is a real, internal, already-fixed
  ABI this compiler's own codegen produces — not a hack reading
  undocumented memory.
- **The underlying `Hash[K,V]` indexing defect is fixed directly by this
  plan, not merely routed around — a deliberate scope expansion beyond
  the minimum this plan strictly needed.** `.get`'s own buffer-reading
  workaround (above) is sufficient for `JsonValue` alone and would have
  been enough to ship this plan's own Concrete Proof; `leaf-fix-hash-
  generic-indexing` goes further, generalizing `build_hash_lookup`/
  `build_index` themselves so `Hash[String, V]`'s ordinary `[]`/`[]=`
  operators stop panicking for *any* Emerald program, not only code
  written against this plan's own `JsonValue` type. This was judged
  worth doing here rather than leaving it, as originally drafted, for
  "a future plan's job": the defect was discovered by this plan, is
  fully understood and already cited with exact file:line evidence in
  the bullet above, and leaving a known, reachable compiler panic
  undocumented-but-unfixed once its exact fix is already known would be
  a worse outcome than the small amount of extra scope required to fix
  it now.
- **`.get`/`.to_s` are compiler intrinsics on an enum receiver, not
  ordinary enum methods — because plan 52 deliberately gave enums none.**
  Plan 52's own Decision log states this outright: "An enum is pure
  data — no methods, no `implements`... not possible to write `enum
  Shape = ... def area -> Float64 ... end`." `JsonValue.get`/`.to_s`
  therefore cannot be declared the way a class method is; they reuse
  the *other* existing dispatch shape this compiler already has for
  exactly this situation — plan 45's `Type::String`-gated intrinsic arm
  (`infer_expr_type`'s generic `MethodCall` case, gating on the
  receiver's *inferred type* after `infer_expr_type(recv)` already
  runs, not on the method name, avoiding any collision with a real
  user-defined method of the same name on an unrelated class) — applied
  here to `Type::Enum("JsonValue")` instead of `Type::String`. No new
  dispatch mechanism, no exception carved into plan 52's "pure data"
  rule for enums in general — `JsonValue` gets exactly the same kind of
  one-off, hardcoded special case `File` already is, nothing more
  general.
- **Constructing a `JsonValue` by hand needs zero new API surface — it
  is already free.** `JsonString("hi")`/`JsonNumber(3.0)`/`JsonBool(
  true)`/`JsonArray([JsonNumber(1.0), JsonNumber(2.0)])`/`JsonObject({
  "a" => JsonString("hi")})` are all just ordinary enum-variant
  construction, plan 52's own `Expr::Call`-reuse mechanism, already
  fully working for any enum including this plan's compiler-synthesized
  one. `Hash[String, JsonValue]` *literal* construction (`build_hash_
  lit`) has no key-type restriction either (see above) — only `[]`
  *indexing* is broken for non-`Int64` keys, so `JsonObject({"a" => ...,
  "b" => ...})` compiles and runs correctly today; this plan adds no
  construction-side code at all, only `Json.parse`/`.get`/`.to_s`.
- **Typed deserialization (a `#[derive(Deserialize)]` equivalent) is
  explicitly out of scope for v1 — stated honestly, not silently
  dropped.** Emerald has no macro system, no attribute/annotation
  syntax on `class`/`enum` declarations, and no reflection (`method_
  missing`/`eval`/`send` are permanently declined project-wide, per
  plan 59's own restated identity list) — there is no mechanism by
  which a compiler pass could inspect an arbitrary user-defined class's
  field names/types at compile time and generate matching decode logic
  the way `serde`'s own proc-macro does. Building that mechanism from
  scratch (a real macro/codegen-attribute system) is a project on the
  scale of several of this batch's other plans combined, not a natural
  extension of wrapping `serde_json`. The real, available alternative
  needs no new feature at all: a user writes their own `def from_json(v:
  JsonValue): Result[Person, String]` by hand, pattern-matching `v`'s
  fields with ordinary `case`/`when` — fully expressible today, and
  this plan's own Concrete Proof already demonstrates every piece
  (`.get`, `case`/`when` on the result, `Result[T,E]` construction) that
  pattern needs.
- **One allocator for the whole program — `emerald_rt_json_parse`'s
  lowering pass calls the exact same `emerald_alloc` C symbol `emerald-
  codegen`'s own generated code calls, not a second, Rust-side
  allocator.** `emerald-rt` declares `unsafe extern "C" { fn
  emerald_alloc(size: i64) -> *mut u8; }` (plan 92's calling-convention
  work makes this declaration real and checked; until then it's an
  ordinary `extern "C"` block, the same shape plan 59 already
  generalizes for user code) and every `JsonValue`/`Array`/`Hash`/
  `String` buffer this plan's lowering pass builds goes through it —
  identical to how every value any other Emerald program allocates
  already does. This sidesteps a real hazard a naive implementation
  would hit: if the lowering pass used Rust's own global allocator
  (`Box::new`/`Vec::new`) instead, the resulting pointers would be
  indistinguishable, at the type level, from `emerald_alloc`-backed
  ones, but freeing (or, more likely here, never freeing — this project
  has no tracing GC and `emerald_alloc`'s own contract is already
  disclosed as "no free, no lifetime tracking", per plan 45's citation)
  would be operating on the wrong heap's bookkeeping. One allocator
  means this question never comes up. No resource handle, no explicit
  release, no plan 93 involvement needed for this plan specifically —
  `Json.parse` returns an ordinary owned value with the same "lives
  forever on the shared heap" contract every other Emerald value
  already has. A genuinely *streaming*/incremental JSON parser (reading
  a multi-gigabyte document off a `File` handle without materializing
  the whole `JsonValue` tree at once) would need a real resource handle
  with an acquire/release lifetime — that variant is explicitly
  deferred to whatever convention plan 93 establishes, not designed
  here; this plan's `Json.parse` is buffer-in, tree-out, matching
  `File.read`'s own already-shipped whole-file-at-once precedent.
- **`serde_json`'s `preserve_order` feature is enabled, not left at its
  default.** Verified against `serde_json`'s own real dependency list
  (`lib.rs`): `preserve_order` is a real, optional Cargo feature, backed
  by `indexmap` — without it, `serde_json::Map`'s default backing store
  is a `BTreeMap`, meaning `JsonObject`'s keys would come back sorted
  alphabetically, silently reordering the source document's own field
  order every time `.each`/`.to_s` runs. Since this plan's own `.get`
  reads the raw buffer directly (key order the lowering pass wrote it
  in) and `Hash[K,V]`'s own `.each`/`.map`/`.count` (plan 70) walk that
  same buffer in storage order, enabling `preserve_order` costs one
  Cargo feature flag and makes "the order you get back is the order you
  parsed" actually true, matching what a reasonable reader of `JsonValue
  .get`'s own name would already expect.
- **FFI/ABI notes (plan 92).** `Json.parse`'s error path returns a `
  Result[JsonValue, String]`, which needs two independently-valid
  outputs from one C call — a genuine ABI wrinkle `String.from_cstring`'s
  single-pointer-in/single-pointer-out shape (plan 59) doesn't have to
  solve. `emerald_rt_json_parse(s: *const c_char, err_out: *mut *mut
  c_char) -> *mut u8` uses an out-parameter: on success it returns the
  `JsonValue` tree's root pointer and leaves `*err_out` untouched
  (null, by the caller's own zero-initialization); on failure it
  returns a null pointer and writes a fresh `emerald_alloc`-backed,
  null-terminated `String` (`serde_json::Error`'s own `Display` text)
  into `*err_out`. `emerald-codegen`'s `Json.parse` intrinsic arm
  branches on the returned pointer being null exactly the way `Type::
  Result`'s existing `check_result_construction`/codegen already
  branches for any other `Ok`/`Err` construction — no new Result
  machinery, just a new producer of one. Every exported `emerald-rt`
  function in this plan is wrapped in `std::panic::catch_unwind` per
  plan 91's own established, load-bearing convention (a malformed UTF-8
  key inside `serde_json`'s own error path, say, becomes a caught panic
  and an honest `Err`, never an unwind into `emerald_runtime.c`'s
  `setjmp`/`longjmp`-based C frames).
- **Out of scope.** Typed/derive-style deserialization into
  user-defined classes (see above);
  `serde_json`'s `arbitrary_precision`/`raw_value` features (neither
  serves this plan's dynamic-`JsonValue` design); streaming/incremental
  parsing over a `File` handle (deferred to plan 93's resource-handle
  model); JSON5/JSONC/comment-tolerant parsing (`serde_json` itself
  doesn't support these without a different crate); `JsonValue`
  mutation methods (`.set(key, value)`, array `.push`) — `JsonValue` is
  produced by `Json.parse` or hand-built via variant construction, both
  already covered, and this plan does not add an in-place-editing API
  on top of an immutable-by-construction tree. (`Hash[K,V]`'s generic
  `[]`-indexing defect, originally going to be deferred here, is instead
  fixed directly by `leaf-fix-hash-generic-indexing` — see the Decision
  log bullet above — not left as a future plan's job.)
