# Plan 35 — Source-Level Debug Info

This plan is **not** a row in
[`plan-of-plans`](../../history/2026-09-08T174011Z-plan-of-plans.md) —
post-v1 tooling scope, same posture as plan 17: it doesn't touch
`plan-of-plans.md` or any other plan file. It closes a gap no prior plan
has even mentioned: `emerald-codegen` emits an object file with a real
`.text` section (every prior plan's `compiled, linked, and run, prints
X` acceptance criterion proves that) but **no debug info at all** — a
compiled Emerald program is currently opaque to `gdb`/`lldb`: no source
filename, no line numbers, no way to set `break sum.em:12` and have it
mean anything.

Concrete proof this plan targets: compile a real `.em` example (this
plan's own worked fixture, below), start a debugger against it
non-interactively, set a breakpoint at a specific source line, run, and
assert the debugger actually stops there and reports that exact line
number back — a real, executed, tool-verified proof that the emitted
DWARF is *correct*, not merely present.

```ruby
def add(a: Int64, b: Int64) -> Int64
  sum: Int64 = a + b
  sum
end

puts add(20, 22)
```

The breakpoint target is the `sum: Int64 = a + b` line.

## Decision log — this plan's backend uncertainty is real, not hypothetical

- **This plan does not assume which codegen backend it's building
  against, and says so explicitly, because the answer is genuinely
  unsettled right now.** Plan 16 (`2026-09-08T212216Z-plan-16-codegen-
  backend-bakeoff.md`, read in full this session) is a live Cranelift-
  vs-LLVM bake-off whose own stated scope keeps Cranelift
  (`emerald-codegen`) as the full-language, default backend and scopes
  the new `emerald-codegen-llvm` crate to *only* the two benchmark
  programs' narrow AST subset ("LLVM feature parity with the Cranelift
  backond is... disproportionate to what the bake-off needs... [LLVM]
  supports exactly the AST subset the two existing benchmark programs
  use"). Separately, this session's own `git diff` shows **live,
  uncommitted, in-progress work by a different agent** that looks like
  it's going further than plan 16's own written scope: `crates/
  emerald-codegen/Cargo.toml`'s dependencies are currently swapped from
  `cranelift`/`cranelift-jit`/`cranelift-object`/`cranelift-module`/
  `cranelift-native` to `inkwell = { version = "0.10", features =
  ["llvm21-1"] }` directly, the standalone `emerald-codegen-llvm` crate
  has been deleted, and `crates/emerald-codegen/src/lib.rs` itself is
  currently deleted outright (empty `src/` directory) — i.e. a
  consolidation onto LLVM may be underway that supersedes plan 16's own
  "Cranelift stays the full-language default" scope note. This is an
  **unsettled, actively-changing, uncommitted state**, not a decided
  fact this plan should build on. Both `gimli` (0.34.0) and `object`
  (0.40.0) — needed for the Cranelift-path design below — and `inkwell`
  (0.10.0, matching the version already in the uncommitted diff) are
  confirmed live on crates.io this session.
- **Path A — Cranelift stays (or a Cranelift-based backend exists
  alongside LLVM):** Cranelift does not emit DWARF the way LLVM does.
  The realistic mechanism is: (1) attach a `SourceLoc` (Cranelift's own
  per-instruction source-position type, already a first-class concept
  in `cranelift-codegen`'s IR) to every instruction as it's built in
  `build_expr`/`build_stmt` — read from a real span (see the "spans"
  note below); (2) after codegen, walk the compiled function's
  instruction-to-`SourceLoc` mapping and emit a DWARF line-number
  program (`.debug_line`) by hand via `gimli`'s `write` module
  (`gimli::write::LineProgram`), plus a minimal `.debug_info`/
  `.debug_abbrev` compile-unit DIE (just enough for a debugger to find
  the line table and resolve `sum.em` as the compile unit's source
  file — no variable/type DIEs, see scope below); (3) write those
  sections into the object file via `object`/`cranelift-object`'s
  section-writing API (the same crate `emerald-codegen` already depends
  on for the `.text`/`.data` sections it emits today). This is real,
  hand-rolled systems work — Cranelift gives you the per-instruction
  source positions; everything DWARF-shaped has to be built by hand on
  top.
- **Path B — LLVM/`inkwell` wins the bake-off:** LLVM has mature,
  first-class debug-info generation built in and exposed through
  `inkwell`'s `debug_info` module (`DebugInfoBuilder`,
  `create_compile_unit`, `create_function`, `create_lexical_block`,
  `create_debug_location`) — attaching a `DebugLoc` to each instruction
  as it's built (via `builder.set_current_debug_location(...)`) is
  enough for LLVM's own backend to emit correct DWARF automatically at
  object-emission time. Comparatively far less custom work than Path A;
  the entire hand-rolled `.debug_line`/`.debug_info` construction step
  in Path A doesn't exist here at all — LLVM's own codegen does it.
- **This plan's leaves are structured around that uncertainty rather
  than pretending it's resolved:** `leaf-backend-research` (below) is
  real, immediate content — both paths' concrete mechanisms are
  described precisely enough that whichever one applies can proceed
  directly once plan 16 settles, and that research work doesn't need
  plan 16 to finish first. `leaf-line-table-generation`, the actual
  implementation, is explicitly **conditioned on plan 16's outcome**
  and isn't executable until that's known — this plan documents both
  variants' acceptance criteria so either is ready to execute the
  moment the backend question resolves, rather than silently assuming
  one and needing a rewrite if the bake-off goes the other way.
- **v1 scope is line-table-only debug info, not variable/type debug
  info.** `break sum.em:12` + `next`/`step` hitting the right source
  lines needs only a correct line-number program. Making `print sum`
  show a real, typed value inside a debugger needs DWARF variable DIEs
  with per-variable, per-scope location expressions (a stack-slot or
  register location, tracked live across the whole function) and type
  DIEs for every `Type` variant (`Type::Class`'s field layout would need
  its own structure DIEs) — real, substantially larger scope, explicitly
  deferred. This plan proves "a debugger can tell you which source line
  you're on," not "a debugger can inspect your variables."
- **Reuses plan 22's spans, doesn't redo them.** A sibling plan in an
  earlier batch (`2026-09-08T221500Z-plan-22-sema-diagnostic-spans.md`,
  read this session) threads a real `Spanned<T> { span: (usize, usize),
  node: T }` wrapper through every `Expr`/`Stmt` for diagnostic
  purposes. The same byte-offset spans are exactly what this plan needs
  to attach a real source line to each instruction (a byte offset is
  trivially converted to a 1-based line number via the source text's own
  newline count) — this plan takes a **real, disclosed dependency** on
  plan 22 having landed first, rather than re-deriving its own separate
  span-tracking mechanism. If plan 22 hasn't landed when this plan is
  executed, `leaf-line-table-generation` is blocked on it explicitly,
  not worked around with a parallel span scheme.
- **Debugger availability in this sandbox is unverified, and that's
  disclosed, not assumed.** This session's shell policy blocks invoking
  `gdb`/`lldb` at all (a hard tool-allowlist restriction, confirmed this
  session — not a "command not found," a policy block), so this plan
  cannot itself confirm either debugger is even installed here. Whoever
  executes `leaf-debugger-verification` must verify real availability
  first (the same discipline plan 15 applied to `ruby` and plan 17
  applied to `npm`) rather than assuming a debugger is present — and if
  neither is, adapt the acceptance mechanism (e.g. `objdump --dwarf=
  decodedline` / `llvm-dwarfdump` to verify the line table's *content*
  is correct against known source lines, a weaker but still real proof)
  rather than silently skipping verification.
- **Linux DWARF/ELF only.** Matches plan 15's own stated Linux-only
  benchmarking target — no Windows PDB, no macOS dSYM/Mach-O debug maps.
- **Optimized-code line-table accuracy is a non-issue today and a
  one-line forward disclosure for later:** neither backend has any
  optimization/instruction-reordering pass that would desynchronize a
  line table from the source it describes (Cranelift's own optimization
  levels only affect register allocation/redundancy elimination within
  a still-linear instruction stream per plan 16's own investigation; no
  reordering pass exists in this compiler at all) — this won't stay true
  forever, and whoever adds a reordering optimization pass later should
  revisit line-table accuracy then, not assume it still holds.

## Leaf: leaf-line-table-generation

### 1. Context
- Why: neither backend attaches source positions to instructions or
  emits any DWARF section today — confirmed via this plan's own
  Decision-log research; there is no line-table generation code
  anywhere in this workspace.
- **Blocked on: (a) plan 16 settling which backend this leaf targets,
  and (b) plan 22 (sema diagnostic spans) having landed, since this leaf
  reuses its `Spanned<T>` byte offsets rather than re-deriving spans.**
  This leaf's Acceptance Criteria below describe both backend variants;
  only one executes, once (a) is known.
- Target state (Path A / Cranelift): every codegen'd Cranelift
  instruction gets a `SourceLoc` derived from the enclosing
  `Spanned<Expr>`/`Spanned<Stmt>`'s byte-offset span (plan 22),
  converted to a 1-based source line via a newline count over the
  original source text; after codegen, a `gimli::write::LineProgram` is
  built from the instruction→line mapping and written into the object
  file's `.debug_line`/`.debug_info`/`.debug_abbrev` sections via
  `object`'s section API.
- Target state (Path B / LLVM): every `inkwell` instruction-builder call
  is preceded by `builder.set_current_debug_location(...)` built from
  the same `Spanned<T>` byte-offset → line conversion; `inkwell`'s own
  object emission produces correct DWARF with no further hand-written
  section-writing code.

### 2. Acceptance Criteria
1. Compiling this plan's worked `add`/`sum` example produces an object
   file whose `.debug_line` section, decoded (via `objdump
   --dwarf=decodedline` or `llvm-dwarfdump --debug-line`), maps the
   instructions implementing `sum: Int64 = a + b` to the real source
   line number of that statement (verified against the source string's
   own line count, not asserted by inspection).
2. Whichever backend variant is *not* chosen is left as a documented,
   named, unimplemented Decision-log alternative — not silently deleted
   from this plan's record once a choice is made.
3. Regression: every existing codegen test for the chosen backend
   continues to pass unmodified — attaching debug info must not change
   any compiled program's actual behavior or output.

### 3. File & Module Structure
- **Modify (Path A):** `crates/emerald-codegen/src/lib.rs`, `crates/
  emerald-codegen/Cargo.toml` (adds `gimli`)
- **Modify (Path B):** whichever crate hosts the settled LLVM backend
  (`crates/emerald-codegen-llvm/src/lib.rs` or a consolidated `crates/
  emerald-codegen/src/lib.rs`, depending on plan 16's actual landed
  shape — verify the real crate layout at execution time rather than
  assuming either this plan's Decision log or plan 16's original
  proposal is still current)

### 4. Quality Gates
| Gate | Command | Pass | Witness level |
|------|---------|------|---------------|
| Build | `cargo build -p <settled codegen crate>` | clean | agent-claimed-locally |
| Line-table decode | `objdump --dwarf=decodedline <object file>` (or `llvm-dwarfdump --debug-line`) | real, correct source-line mapping present | agent-claimed-locally |
| Workspace | `cargo test --workspace` | all pass, no behavior change | agent-claimed-locally |

## Leaf: leaf-debugger-verification

### 1. Context
- Why: a `.debug_line` section existing and decoding to plausible-
  looking line numbers (leaf 2's own gate) proves the data is *present*
  and *well-formed* — it doesn't prove a real debugger can actually use
  it to stop execution at the right place. This leaf is the "prove it
  end-to-end" step every other plan in this project insists on.
- Target state: a scripted, non-interactive debugger session — e.g.
  `gdb -batch -ex 'break add.em:2' -ex run -ex 'info line' -q
  ./add_binary` (or the `lldb` equivalent) — run against the compiled,
  linked binary from this plan's worked example.

### 2. Acceptance Criteria
1. The scripted session's output shows the breakpoint resolved to the
   real source file and line number of `sum: Int64 = a + b` (not "no
   line number information available," the failure mode of a compiled
   program with no debug info at all — this is the concrete negative
   case this plan starts from).
2. Continuing execution (`run`/`continue`) actually stops at that
   breakpoint before the program exits — a real, observed program-halt,
   not just a resolved breakpoint address that's never hit.
3. If neither `gdb` nor `lldb` is actually available wherever this leaf
   executes (see Decision log — unverified in this sandbox due to a
   shell policy block, not confirmed absent), fall back to the
   `objdump`/`llvm-dwarfdump` line-table-decode proof from leaf 2 as the
   acceptance mechanism instead, and disclose plainly that the
   debugger-level proof is deferred to an environment where one is
   confirmed present — do not claim AC1/AC2 passed without a real
   debugger session behind them.

### 3. File & Module Structure
- **Create:** a small scripted debugger-session file (e.g. `crates/
  emerald-cli/tests/debug_info.rs` invoking `gdb -batch`/`lldb` as a
  subprocess, `#[ignore]`d the same way plan 15's benchmark runner is,
  since it depends on an external debugger binary being present)

### 4. Quality Gates
| Gate | Command | Pass | Witness level |
|------|---------|------|---------------|
| Debugger session | `cargo test --release -p emerald-cli -- --ignored --nocapture debug_info` | breakpoint resolves and hits at the real source line (or the disclosed line-table-decode fallback, if no debugger is available) | agent-claimed-locally |

## Out of scope / deferred
- Variable and type debug info (DWARF variable/type DIEs, per-variable
  location expressions) — see Decision log; a substantially larger,
  separate future increment.
- Optimized-code line-table correctness under a future instruction-
  reordering optimization pass — none exists today; a one-line forward
  disclosure for whoever adds one, not a problem this plan solves.
- Windows PDB / macOS dSYM debug formats — Linux DWARF/ELF only, matching
  plan 15's own stated target.
- Picking which of Path A/Path B this plan actually implements — that's
  plan 16's decision to make, not this plan's; this plan is ready to
  execute either the moment that's known.
- Verifying `gdb`/`lldb` presence in any particular execution
  environment — explicitly the executing plan's job, not assumed here
  (see Decision log's disclosed sandbox limitation).
