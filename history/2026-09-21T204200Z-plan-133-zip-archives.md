# Plan 133 — Zip Archives

Unlike plan 132's `tar` (a container format with zero compression
logic of its own, so the pure-Rust-vs-C-backed question never even
arises for that dependency), the `zip` crate bundles container format
*and* compression codec support together — a `.zip` file's central
directory records, per entry, which of several possible compression
methods (Stored/uncompressed, Deflated, Bzip2, LZMA, Zstd, PPMd, ...)
was used, and a general-purpose zip library has to be able to read (and
ideally write) more than one of them to handle real-world archives.
That makes this plan's crate-vetting call genuinely more nuanced than
plan 132's: verified this session directly against `zip-rs/zip2`'s
real `Cargo.toml` (the crate now versioned `9.0.0-pre3` on its
prerelease track, `8.6.0` the latest stable release), the crate's own
`default` feature list is **`["aes-crypto", "bzip2", "deflate64",
"deflate", "lzma", "ppmd", "time", "zstd", "xz"]`** — and two of those,
`bzip2` and `zstd`, are real, non-trivial C-binding pulls (`bzip2`'s
feature definition itself enables `bzip2/default`, the `bzip2` crate's
own default which — per that crate's own naming, mirroring plan 131's
own finding for the standalone `zstd` crate this session — wraps the
real C `libbz2`; `zstd` here is the identical `zstd = { version =
"^0.13.3" }` dependency plan 131 already vetted as a real, disclosed
C-binding exception in its own right). This plan does not accept the
crate's defaults wholesale — it disables them and hand-selects a
pure-Rust-only feature set covering the one method that matters for
the overwhelming majority of real `.zip` files.

## Concrete proof this plan targets

```ruby
Dir.mkdir("zip_demo_src")
File.write("zip_demo_src/a.txt", "hello")
File.write("zip_demo_src/b.txt", "world, a longer second file that compresses well well well well")

paths: Array[String] = ["zip_demo_src/a.txt", "zip_demo_src/b.txt"]
Zip.create("demo.zip", paths)

reader: ZipReader = ZipReader.open("demo.zip")
n: Int64 = reader.entry_count()
puts n
i: Int64 = 0
while i < n
  puts reader.entry_name(i)
  puts reader.read_entry_data(i).to_string()
  i += 1
end
reader.close()

Zip.extract("demo.zip", "zip_demo_out")
restored: String = File.read("zip_demo_out/zip_demo_src/a.txt")
puts restored == "hello"
```

Expected output: `2`, `zip_demo_src/a.txt`, `hello`,
`zip_demo_src/b.txt`, `world, a longer second file that compresses
well well well well`, `true` — `entry_count()` proves the central
directory was written and parsed correctly (a real structural
difference from tar, where the entry count is never known ahead of a
full scan), the per-entry name/content pairs prove both files survive
`Zip.create`→`ZipReader` unmodified, and the final `Zip.extract`/
`File.read` pair proves bulk extraction reproduces the exact original
bytes on disk, mirroring plan 132's own extract-side proof shape.

## Decision log

- **The crate's own `default` feature set is rejected outright, not
  refined — a deliberate, disclosed override, not an oversight this
  plan almost made.** Per plan 95's central axis (name every crate's
  pure-Rust-vs-C-backed status explicitly, make a real justified call
  rather than defaulting silently), accepting `zip`'s defaults would
  mean this plan's own `Zip.create`/`Zip.extract` silently links
  against C `libbz2` (via the `bzip2` feature) and C `libzstd` (via the
  `zstd` feature, the exact same dependency plan 131 already vetted
  once) even though the Concrete Proof this plan targets — and the
  overwhelming majority of `.zip` files ever produced by `zip`/Windows
  Explorer/macOS Archive Utility/most language stdlibs' own zip writers
  — use plain DEFLATE. `default-features = false` plus an explicit,
  single `deflate-flate2-zlib-rs` feature is this plan's real answer:
  no bzip2, no zstd-via-this-crate (plan 131's own `Zstd` module
  remains the one, already-vetted path to zstd anywhere in this
  sub-batch), no lzma/xz/ppmd, no aes-crypto (encrypted zip support)
  in v1.
- **`deflate-flate2-zlib-rs`, not `deflate-flate2-zlib-rs` unified with
  plan 130's `miniz_oxide` choice — a real, disclosed duplication this
  plan accepts rather than forces away.** `zip`'s own `Cargo.toml`
  (verified this session) offers a generic, backend-agnostic
  `deflate-flate2` feature (`["_deflate-any", "dep:flate2"]`, choosing
  no backend on its own) alongside three backend-committing sugar
  features: `deflate-flate2-zlib-rs` ("Pull in flate2 and the fast
  zlib-rs backend; this is what most users will want," per the crate's
  own feature-comment), `deflate-flate2-zlib` (system zlib, C-backed),
  and `deflate-flate2-zlib-ng` (C-backed). This plan could instead have
  taken the generic `deflate-flate2` feature and relied on Cargo's
  cross-crate feature unification (since `emerald-rt` also depends on
  `flate2` directly, per plan 130, with its own `miniz_oxide` feature
  enabled, and Cargo builds one merged feature set per crate version
  across a whole dependency graph) to supply `flate2`'s backend for
  free — but asserting that a specific cross-crate feature-unification
  outcome will hold, untested, is exactly the kind of claim plan 91's
  own Decision log explicitly declined to make without empirical
  verification (there: platform link flags). This plan instead takes
  the simpler, self-contained, definitely-correct-on-its-own path:
  `zip`'s bundled `deflate-flate2-zlib-rs` feature, meaning two
  independently-selected pure-Rust DEFLATE backends (`miniz_oxide` for
  plan 130's `Gzip`/`Deflate`/`Zlib`, `zlib-rs` for this plan's `Zip`)
  are both compiled into `emerald-rt` — a real, accepted duplication of
  compiled code, not a bug, and both are genuinely pure Rust requiring
  no C compiler either way, so plan 95's policy is satisfied by both.
  Unifying them onto one backend is a real, legitimate future
  optimization this plan does not attempt now.
- **`bzip2`'s C-backed status was verified this session by the same
  method plan 131 used for the standalone `zstd` crate, not assumed by
  name-pattern-matching alone.** The `bzip2` crate's own `Cargo.toml`-
  declared feature `default` pulls in a C `libbz2` binding (the crate's
  long-standing, well-known design — `bzip2-sys` vendors/links the real
  bzip2 reference C implementation, the same "no pure-Rust bzip2
  encoder achieves comparable maturity yet" situation plan 131 found
  for zstd, just for a different, older, less widely-needed-today
  format). Because this plan declines `bzip2` entirely for v1 rather
  than adopting it, it does not need to make plan 131's full
  pure-Rust-alternative-naming argument here — bzip2 support for `.zip`
  archives (reading a `.zip` someone else produced with a bzip2-
  compressed entry) is simply out of scope, a real, disclosed gap
  rather than a silently-accepted C dependency.
- **`ZipReader` is index-based (`entry_name(i)`/`read_entry_data(i)`),
  not iterator-advance-only like plan 132's `TarReader` — a real,
  format-driven API difference, not an inconsistency between the two
  plans.** A `.zip` file's central directory sits at the *end* of the
  file and lists every entry with its name, size, and offset up front —
  `zip::ZipArchive::new` parses that directory once at open time, so
  `.len()` (this plan's `entry_count()`) and random-access `.by_index()`
  are real, cheap, already-available operations with no extra scanning
  cost. A tar archive has no such directory — plan 132's `TarReader`
  can only discover the next entry by reading past the current one's
  data, which is why that plan's reader is iterator-shaped instead.
  This plan's index-based shape is a direct, honest reflection of the
  real structural difference between the two formats, not an arbitrary
  API inconsistency across this sub-batch.
- **`Zip.create` always writes `CompressionMethod::Deflated` for every
  entry — no per-entry `Stored`(uncompressed)/`Deflated` choice exposed
  in v1.** Real zip writers often use `Stored` for already-compressed
  content (JPEGs, other `.zip`s) to avoid wasted CPU recompressing
  incompressible data — a real, legitimate optimization this plan
  declines to expose as an Emerald-level parameter for the same reason
  plan 130 fixed its own compression level: the Concrete Proof this
  plan targets does not need it, and a per-path compression-method
  argument is a small but real additional design surface (another
  `Array`-shaped parameter parallel to `paths`, needing its own
  length-tracking convention) deferred rather than designed away.
- **No password-protected/encrypted zip support (`aes-crypto`) in v1.**
  AES-encrypted zip entries need a password threaded through both
  `Zip.create` and `ZipReader`, a real key-derivation/authentication
  surface (the `aes-crypto` feature's own dependency list — `hmac`,
  `pbkdf2`, `sha1`, `zeroize` — makes clear this is genuine
  cryptographic code, not a toggle) this plan does not attempt; a
  future `Zip.create_encrypted`/`ZipReader.open_encrypted` pair is a
  real, plausible follow-up, not designed here.
- **Out of scope.** No `bzip2`/`lzma`/`xz`/`ppmd`/`zstd`-via-this-crate
  compression methods (all above), no AES encryption (above), no
  per-entry `Stored` vs `Deflated` choice (above), no ZIP64 large-
  archive-specific API surface beyond whatever `zip`'s own DEFLATE path
  handles transparently, no streaming/incremental `Zip.create` (unlike
  plan 132's `Tar.create`, which streams entries as it writes them,
  this plan's `Zip.create` takes a complete `Array[String]` up front —
  the underlying `ZipWriter` API supports incremental `.start_file`
  calls identically either way, so this is a v1 Emerald-surface
  simplification, not a Rust-level limitation), no in-place archive
  modification.
