# Plan 127 — INI Configuration Files

`rust-ini` (owned by `zonyitoo`, 45 contributors, current release 0.21.3
published 2025-08-30, 8.06M downloads/month, used by 856 crates — 255
directly — verified this session via lib.rs) is the actively maintained,
dominant INI-parsing crate for Rust, not a name to disambiguate from a
competitor: lib.rs's own download and dependent-crate counts show no
comparably adopted alternative under the `ini` keyword. Its crates.io
package name is `rust-ini`; the import/library name is `ini`
(`use ini::Ini;`) — a real, easy-to-get-wrong naming split this plan
records explicitly rather than leaving implicit.

INI's own shape does not need a new dynamic-value ADT the way JSON, XML,
or HCL do — it is already, exactly, a two-level string map (section name
-> key -> value, plus an optional no-section prefix), representable
entirely in Emerald's already-shipped types with zero new type surface.
This plan deliberately does not attempt to marshal that whole nested
structure across the FFI boundary in one call; instead it exposes an
index-and-count accessor API over an opaque handle, the same idiom plan
45 already established for `ARGV`/`.split_count` and this batch's own
plan 122 reuses for `find_all_count`/`split_count` — proven, low-risk,
and requiring no new marshaling machinery.

## Concrete proof this plan targets

```ruby
doc: Result[IniDocument, String] = Ini.parse("[server]\nhost=localhost\nport=8080\n")

case doc do
  when Ok(d) do
    host: Option[String] = d.get("server", "host")
    match host do
      Some(h) do
        puts h
      end
      None do
        puts "no host"
      end
    end

    port: Option[String] = d.get("server", "port")
    match port do
      Some(p) do
        puts p
      end
      None do
        puts "no port"
      end
    end

    puts d.key_count("server")
  end
  when Err(msg) do
    puts msg
  end
end
```

Expected output: `localhost`, `8080`, `2` — both `[server]` keys read
back by name, and `key_count` confirming exactly two keys were parsed
into that section.

## Decision log

- **No new ADT for INI's shape — a genuine, disclosed simplification
  relative to JSON/XML/HCL, not an oversight.** Plan 118's `JsonValue`
  and plan 124's `XmlNode` both exist because their formats are
  recursive and heterogeneously typed. INI is neither: a value is always
  a string, and nesting stops at exactly one level (section -> key).
  Nothing in this plan reaches for plan 52's `enum` mechanism at all.
- **The accessor API is index/count-based, not a single call returning
  a nested `Hash[String, Hash[String, String]]`.** Marshaling a
  variable-shaped nested map across the FFI boundary in one call would
  need either a new, format-specific serialization scheme invented just
  for this plan, or reuse of plan 125's `JsonValue`-via-bincode
  machinery for a value this simple — both heavier than the problem
  warrants. The chosen accessor shape needs no new FFI convention beyond
  what plan 45 (`ARGV`, `.split_count`) already proved works.
- **Duplicate keys within one section are not exposed as a multimap.**
  `rust-ini` depends on `ordered-multimap` internally and can represent
  repeated keys faithfully; this plan's `.get` follows the crate's own
  last-value-wins default lookup behavior rather than exposing the
  richer multimap iteration, since no worked use case in this batch
  needs repeated keys.
- **Parse/write failure is `Result[T, String]` (plan 53), matching every
  other fallible-parse plan in this batch.**
- **Out of scope.** Comment preservation on round-trip write (comments
  are discarded on parse, matching the crate's own default behavior);
  the crate's optional `case-insensitive`, `brackets-in-section-names`,
  and `inline-comment` Cargo features (none enabled — v1 uses the
  crate's plain default configuration); INI dialect extensions some
  tools add (arrays via repeated keys with `[]` suffixes, `${VAR}`
  interpolation) — none are part of the base format this crate parses.
