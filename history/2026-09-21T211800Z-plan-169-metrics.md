# Plan 169 — Metrics

This is the second of eight sibling plans (168-175) in the 91-191
batch. Unlike plan 168 (structured logging), which every later plan in
this batch benefits from immediately, this plan is genuinely
stretch-tier: a counter an Emerald program increments is inert until
something reads it back, and v1 gives that "something" no transport of
its own — see the Decision log for exactly what this plan does and does
not close that gap with. It is included in this batch because metrics
is a real, common production need once an Emerald service exists, not
because every program written in this language needs it.

## Concrete proof this plan targets

```ruby
Metrics.counter_inc("requests_total")
Metrics.counter_inc("requests_total")
Metrics.counter_add("bytes_sent", 4096)
Metrics.gauge_set("queue_depth", 3.0)

text: String = Metrics.render_prometheus()
puts text
```

Expected output (sorted by metric name, exact real Prometheus text
exposition format for the two metric kinds this plan implements):

```
# TYPE bytes_sent counter
bytes_sent 4096
# TYPE queue_depth gauge
queue_depth 3
# TYPE requests_total counter
requests_total 2
```

This string is valid input to `promtool check metrics` or any real
Prometheus scrape parser — the proof is not that Emerald printed
plausible-looking text, but that a program with no HTTP server of any
kind can still produce output byte-for-byte acceptable to the actual
Prometheus text format, ready for a later plan to serve or a cron job
to write to a `node_exporter`-style textfile collector directory.

## Decision log

- **`metrics` is the right facade crate, verified today.** `docs.rs`
  shows `metrics` at `0.24.6`, published 13 July 2026, owned by
  `LucioFranco`/`tobz` under the `metrics-rs` GitHub organization,
  MIT-licensed, with exactly one non-dev dependency (`portable-atomic`,
  pure Rust) plus a vendored `rapidhash`. Its own documentation states
  its role precisely: it is "a lightweight metrics facade" — macros and
  a `Recorder` trait, no storage or export logic of its own. That is
  exactly the shape this plan needs: Emerald's own `emerald-rt` crate
  supplies the one real `Recorder` implementation, rather than this
  plan depending on and configuring someone else's.
- **Stretch-tier, stated plainly, not hedged.** A counter that only
  ever accumulates inside one process's memory, with no scrape
  endpoint and no push path, has produced nothing an operator can see.
  This plan's own `render_prometheus` closes exactly the rendering
  half of that gap — the text format is real and correct — but leaves
  the transport half (an HTTP `/metrics` endpoint, a
  `node_exporter`-style textfile-collector file drop) to whichever
  later plan builds Emerald's first HTTP server or reuses plan 144's
  file-write primitives on a timer. Programs that never call any
  `Metrics.*` function pay nothing (the global recorder is installed
  lazily by `emerald_rt_metrics_init`, never at process startup
  unconditionally).
- **No dimensional labels in v1 — a real, disclosed reduction of what
  the `metrics` crate's own `Key` type actually supports.** Real
  `metrics::Key`s carry a name plus an ordered set of label pairs
  (`counter!("requests_total", "method" => "GET")`), and Prometheus's
  own data model is built around exactly that dimensionality. This
  plan's `Metrics.counter_inc(name)` takes a bare `String` and nothing
  else — the `Recorder` implementation keys its internal maps on
  `Key::name()` alone, silently collapsing any labels a future version
  might add into one series. This is a genuine, load-bearing scope
  cut, not an oversight: a label-carrying API needs a dynamic
  key-value payload at the call site with exactly the same "how does
  an arbitrary-arity set of pairs cross the FFI boundary" problem plan
  168 already solved once with `LogFields` — the smaller, honest move
  here is deferring that machinery to a v2 that reuses `LogFields`'
  create/set/consume pattern for label sets, rather than duplicating
  or half-building it now for a stretch-tier plan.
- **Histograms are registered but not rendered in v1.** `metrics`'s
  `Recorder::register_histogram` must return a working `Handle` (the
  trait requires it; declining to implement it at all would make any
  Emerald program's future `Metrics.histogram_record` call panic
  inside `emerald-rt` rather than compile-error, which is worse). This
  plan implements that method honestly — a real `Handle` is returned
  and recorded values are genuinely stored — but `render_prometheus`
  never reads them back, and no `Metrics.histogram_record` Emerald
  intrinsic is added in this plan at all. The reason is Prometheus's
  own histogram representation: a real histogram in the text exposition
  format needs explicit bucket boundaries (`le=` label pairs) chosen in
  advance, which is real design surface (what buckets? per-metric or
  global default? configurable from Emerald source?) this stretch-tier
  plan declines to open, rather than shipping a bucket scheme with no
  real evidence it fits any actual v1 caller's needs.
- **The exporter question the batch brief poses — "needs an exporter
  backend to actually be consumed by anything" — is answered by
  declining the off-the-shelf one, not by adopting it.**
  `metrics-exporter-prometheus` (verified: `0.18.3`, 11 July 2026, same
  `metrics-rs` organization, dual MIT/Apache-2.0) is real, maintained,
  and would be the obvious default choice — except its own dependency
  list (checked this session) pulls `hyper ^1.8` and `hyper-rustls` to
  actually serve the `/metrics` HTTP endpoint itself, which needs an
  async runtime this project does not have: plan 91's own Out of scope
  explicitly defers "any async runtime of any kind" to plan 94, and
  Emerald's driver today links no `tokio`/`async-std` runtime at all.
  Pulling an async HTTP server transitively into `emerald-rt` for one
  stretch-tier metrics plan, ahead of plan 94's own decision about how
  Emerald does async at all, is a heavier commitment than this plan's
  actual value justifies. The hand-rolled `render_prometheus` — pure
  synchronous string building, zero new dependencies beyond `metrics`
  itself — is the "minimal text-exposition-format exporter" the
  brief explicitly asks for, and it composes with whatever HTTP or
  file-write mechanism the project eventually gets, rather than
  assuming one.
- **The global recorder reuses plan 168's exact install-once idiom,
  not a new one.** `metrics::set_global_recorder` (verified real
  against `docs.rs`'s function listing this session), like
  `tracing::subscriber::set_global_default`, is a true process-wide
  singleton settable exactly once — the crate's own docs state "the
  metrics system may only be initialized once." `emerald_rt_metrics_
  init`'s `OnceLock`-guarded wrapper, returning `-1` on a redundant
  call instead of propagating a panic, is the identical shape plan
  168's `Log.configure` already ships; this plan does not invent a
  second idempotency convention for what is structurally the same
  problem.
- **Gauge storage as bit-cast `f64` in an `AtomicU64` is a real,
  correct, lock-free technique, not a hack disclosed apologetically.**
  `f64::to_bits`/`f64::from_bits` round-trip every finite (and, for
  that matter, every NaN/infinite) `f64` value exactly, and
  `AtomicU64::store`/`load` give `gauge_set` and a future `gauge_add`
  atomicity without a `Mutex`, matching the lock-free spirit of
  `metrics`'s own `AtomicStorage` pattern (the same technique
  `metrics-util`, the crate `metrics-exporter-prometheus` itself
  depends on, uses internally) without adding `metrics-util` as a
  dependency for a v1 this small.
- **FFI/ABI notes.** Plan 92's general convention (`catch_unwind` at
  every boundary, `i64` status returns) governs every function here;
  its binary-safe `(ptr, len)` buffer convention is not needed — every
  value crossing this boundary is a plain null-terminated `String`
  (plan 59), an `Int64`, or an `f64`, and `render_prometheus`'s one
  returned buffer is a plain `CString`-shaped pointer, identical in
  kind to any other Emerald-`String`-producing runtime call already in
  `emerald_runtime.c` today.
- **Out of scope.** Dimensional labels (see above — a real v2, not
  this plan), histogram/summary rendering with real bucket or quantile
  output, any push-gateway support, any `# HELP` description text (no
  `Metrics.describe_*` intrinsic is added), any built-in HTTP scrape
  server, and any automatic periodic export — `render_prometheus` is
  purely synchronous, called on demand, and returns whatever the
  counters/gauges currently hold at the instant of the call.
