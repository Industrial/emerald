# Plan 11 — Exceptions

This is `exceptions`, row `11` of
[`plan-of-plans`](../../history/2026-09-08T174011Z-plan-of-plans.md),
implementing inception §19's exception-model questions as resolved in
`spec/SEMANTICS.md` §7: exceptions are dynamically typed but statically
declared at `rescue` sites, `raise` isn't arity/type-restricted beyond
ordinary call type checking, and — SEMANTICS.md §7.3 — "exceptions are
implemented using native unwinding." Inception/GRAMMAR.md give no single
worked example; this plan's concrete proof, self-designed per the
established practice from plans 07–10, is:

```ruby
class MyError
  code: Int64

  def code -> Int64
    @code
  end
end

def risky(x: Int64) -> Int64
  if x > 100
    raise MyError.new(99)
  end
  return x
end

begin
  puts risky(999)
rescue MyError => e
  puts e.code
end
```

Expected output: `99`.

(Two corrections made while implementing `leaf-ast-exceptions`, before any
sema/codegen work started: `x < 0`/`risky(-1)` don't parse — this
grammar has no unary minus or negative-literal syntax at all, only
`[0-9]+` — so the condition became `x > 100`/`risky(999)`. And `e.code`
needs an explicit `code` accessor method on `MyError`; Ruby-like dot
syntax is always a method call here, never implicit public field access
— there's no `attr_reader`-style sugar, matching real Ruby's own rule
that `obj.field` only works if `field` is an actual defined method.)

## Decision log

- **This plan does NOT implement true native unwinding** (DWARF call-frame
  information + a personality function + landing pads, the mechanism
  `SEMANTICS.md` §7.3 actually calls for, matching how C++/Rust exceptions
  work). That is a substantial, dedicated systems-programming undertaking
  — hand-authoring unwind-table generation and a personality function on
  top of Cranelift is bigger than every other plan in this project
  combined — and isn't achievable at this plan's scope. Instead, this
  plan implements a **setjmp/longjmp-based handler stack**: a real,
  working, historically-used non-local-control-transfer mechanism (early
  Objective-C and several Scheme implementations used exactly this for
  their first exception support), proving `raise`/`rescue`'s *semantics*
  — dynamic raise, statically-typed catch, stack unwinding back to the
  handler — genuinely end-to-end, while being honest that the
  *mechanism* is a real, disclosed deviation from the spec's stated
  preference. Migrating to true DWARF-unwind-based exceptions is future
  work, tracked here rather than silently substituted.
- **No class inheritance exists in this compiler yet** (plan 08's
  `ClassDef` has no superclass field — confirmed this session). So
  `rescue ExceptionType => e` matching is exact-type equality, not
  subtype matching — which is not a scope cut at all, just what "no
  inheritance" already implies. Each class gets a stable integer "class
  tag" (assignment order in `program.items`) instead of a string/RTTI
  scheme — simpler than emitting string constants into the object file's
  data section (which this codegen has never needed before), and exact
  enough since there's no subtyping to match against anyway.
- **`raise` only accepts a direct `ClassName.new(args)` expression** —
  not a variable holding a previously-constructed exception instance.
  Mirrors `Expr::New`'s own "class name must be statically visible"
  shape; the raise site's class tag has to be known at codegen time to
  pass to the runtime's `emerald_raise`, and this is the only exception
  construction shape plan 08 already makes trivially available.
- **Single `rescue` clause, no `ensure`, no bare catch-all `rescue`, no
  re-`raise` syntax.** The concrete proof only needs one typed handler;
  multiple `rescue` clauses / `ensure` / bare re-raise are additive
  grammar-level extensions of the same underlying mechanism, not
  architectural blockers, and aren't required to prove `raise`/`rescue`
  works.
- **`rescue`'s bound variable (`e`) is inserted into the same flat `env`/
  `vars` as everything else** — consistent with this compiler's existing
  "no block scoping" decision (plan 07), the same way an `if`/`while`
  body's `Let`s already flow into the surrounding scope. Not a new
  limitation specific to exceptions.
- **A caught exception whose tag doesn't match the `rescue` clause
  re-raises to the next-outer handler** (or, with none left, the runtime
  prints an "uncaught exception" message and exits) — this is genuinely
  correct behavior given no subtyping exists, not a shortcut; it's
  exercised structurally by the handler-stack design even though this
  plan's own concrete proof only has one exception class to test with.

## Leaf: leaf-ast-exceptions

### 1. Context
- Why: no AST shape exists for `raise` or `begin...rescue...end`.
- Current state: `Stmt` has no exception-control variants (verified this
  session).
- Target state: `Stmt::Raise(Expr)`; `Stmt::Begin { body: Vec<Stmt>,
  rescue_type: String, rescue_var: String, rescue_body: Vec<Stmt> }`;
  grammar productions `"raise" Expr` and `"begin" Stmt* "rescue" Ident
  "=>" Ident Stmt* "end"`. `raise`/`begin`/`rescue` become reserved
  keywords (same LALR(1) reason `puts`/`new`/`Array`/`Proc` were

3. This plan's full example parses into the expected `Stmt::Begin` shape
   (`rescue_type == "MyError"`, `rescue_var == "e"`).
4. Regression: every prior plan's example still parses identically.

## Leaf: leaf-sema-exceptions

### 1. Context
- Why: no type-checking exists for `raise`/`begin...rescue`.
- Target state: `Stmt::Raise(e)` requires `infer_expr_type(e)` to be
  `Type::Class(_)`; `Stmt::Begin` type-checks `body` normally, resolves
  `rescue_type` (must name a class), binds `rescue_var` at that type in
  `env`, then type-checks `rescue_body`.

### 2. Acceptance Criteria
1. This plan's full example type-checks `Ok(())`.
2. `raise 5` (not a class instance) is rejected with a diagnostic.
3. `rescue Int64 => e` (rescue naming a non-class type) is rejected with
   a diagnostic.
4. Inside `rescue MyError => e`, `e.code` resolves against `MyError`'s
   field — i.e. `e`'s bound type really is usable, not just accepted.

## Leaf: leaf-codegen-exceptions

### 1. Context
- Why: nothing compiles `raise`/`begin...rescue` to machine code, and no
  handler-stack runtime support exists yet.
- Target state: `runtime/emerald_runtime.c` gains a `setjmp`/`longjmp`
  handler stack (`emerald_push_handler`/`emerald_handler_jmpbuf`/
  `emerald_pop_handler`/`emerald_raise`/`emerald_handler_tag`/
  `emerald_handler_exception_ptr`); `Stmt::Begin` codegen pushes a
  handler, calls libc `setjmp` *directly* in the generated function (it
  can't be wrapped — `longjmp` must target a `setjmp` call site in a
  still-live stack frame), branches on the result into the try-body or
  the landing pad, and the landing pad compares the caught tag against
  the `rescue` clause's class tag (matching → bind `e`, run
  `rescue_body`; not matching → re-raise to the next handler).
  `Stmt::Raise(New(class_name, args))` builds the exception instance
  exactly like an ordinary `Expr::New`, then calls `emerald_raise(tag,
  ptr)` instead of falling through to normal control flow.

### 2. Acceptance Criteria
1. This plan's full example, compiled, linked, and run, prints `99\n` —
   real executed proof that raise, the setjmp/longjmp unwind, and the
   rescue-site field read on the caught exception all work together.
2. An unsupported shape (`raise` on anything but a direct `.new(...)`
   call) defensively returns a descriptive `Err`, not a panic.

### 3. File & Module Structure
- **Modify:** `crates/emerald-codegen/src/lib.rs`,
  `runtime/emerald_runtime.c`

### 4. Diagrams
```mermaid
sequenceDiagram
    participant Main as main()
    participant RT as runtime (setjmp/longjmp)
    participant Risky as risky(-1)
    Main->>RT: emerald_push_handler() -> handler
    Main->>RT: setjmp(jmpbuf) == 0 (first pass)
    Main->>Risky: call risky(-1)
    Risky->>Risky: x < 0 -> build MyError.new(99)
    Risky->>RT: emerald_raise(tag=MyError, ptr)
    RT-->>Main: longjmp back to setjmp site (returns 1)
    Main->>RT: emerald_handler_tag() == MyError's tag? yes
    Main->>Main: bind e = exception ptr; puts e.code (99)
```

### 6. Risks & Rollback
- `setjmp` must be called directly by Cranelift-generated code (not
  wrapped in a runtime C helper) — verified feasible since Cranelift
  already emits ordinary System V AMD64 `call` instructions
  interoperable with libc (the same mechanism every existing runtime
  call already uses), and the `setjmp` call site and its result check
  live in the same generated function, satisfying the C standard's
  usage restriction.
