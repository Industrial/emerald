# Plan 59 — C Foreign Function Interface

This is plan 59 of the 58-64 theoretical-maximum batch — seven independent
sibling plans, each implementing one piece of a follow-up debate's answer
to a single question asked deliberately ignoring maturity/ecosystem/
stability: what is Emerald's theoretical technical ceiling, measured
against C/C++/Rust/Python/Ruby/TypeScript/Go/Haskell/Elixir combined? Like
every other post-v1 batch in this repository (28-35, 36-47, 48-57), this
is not a row in [`plan-of-plans`](../../history/2026-09-08T174011Z-plan-of-plans.md)
and does not edit it or any other plan file. The other six siblings in
58-64 are authored in parallel this session and are not itemized here.

**This plan is the one deliberate, explicitly-fenced exception to
"everything else is statically safe."** Every other plan in this
repository, and every one of Emerald's locked identity constraints (no
`method_missing`/`eval`/`send`/reflection, no mixins/open classes/
monkey-patching, no dynamic/virtual dispatch or vtables, no tracing
garbage collector, no runtime reflection), exists so that ordinary
Emerald code can never crash, corrupt memory, or misbehave in a way the
type checker hasn't already ruled out at compile time. Foreign Function
Interface breaks that promise on purpose, at one syntactically marked
boundary, for a genuine and irreducible reason: calling into C means
calling code the Emerald compiler has never seen and cannot check — an
`extern "C"` declaration is a promise the *programmer* makes about a
function's real signature, not a fact the compiler verifies. State this
plainly, here, not buried in a Decision log bullet: **if a declared
`extern "C"` signature doesn't match the real C function's actual
signature, that is genuine undefined behavior** — the exact class of bug
every other design decision in this project exists to make unreachable.
This plan fences that risk behind a single, unavoidable, visually loud
syntactic marker (`unsafe extern "C" { ... }`, see Decision log) rather
than pretending the risk doesn't exist or letting it hide inside
ordinary-looking code.

Depends on: plan 06 (`2026-09-08T182056Z-plan-06-milestone1-codegen.md` —
the original codegen this plan's own core technical claim rests on), plan
45 (`2026-09-09T111000Z-plan-45-stdlib-strings-and-io.md` — `String`'s
real runtime representation, verified directly against real source this
session, not assumed), plan 46
(`2026-09-09T112000Z-plan-46-package-manager-and-build.md` — the real,
already-shipped `emerald.toml` manifest shape this plan's `[ffi]` table
extends).

Concrete proof this plan targets — three real libc functions, zero
third-party libraries, deterministic on any target:

```ruby
unsafe extern "C" {
  fn llabs(x: Int64): Int64
  fn strlen(s: String): Int64
  fn strstr(haystack: String, needle: String): CString
}

x: Int64 = llabs(-42)
puts x

n: Int64 = strlen("hello")
puts n

found: String? = String.from_cstring(strstr("hello world", "world"))
found ||= "not found"
puts found

missing: String? = String.from_cstring(strstr("hello world", "xyz"))
missing ||= "not found"
puts missing
```

Expected output, compiled, linked (plain `cc`, no `emerald.toml` `[ffi]`
table, no extra `-l` flags — libc is always linked): `42`, `5`, `world`,
`not found`. `llabs(-42)` proves a scalar `Int64` round-trip with zero
marshaling code; `strlen("hello")` proves an Emerald `String` value
passed directly to a real C function expecting `const char*` with zero
conversion, and its `size_t` return reinterpreted as `Int64`; `strstr`'s
two calls prove `CString`/`String.from_cstring` on both the found and
not-found (real `NULL`) paths, defaulted through plan 43's own real `||=`
mechanism rather than dereferencing a null pointer.

## Decision log

- **This plan invents no new FFI mechanism — it generalizes one the
  compiler already runs, unexposed to users, on every single build.**
  Verified this session directly against `crates/emerald-codegen/src/
  lib.rs`: `compile_to_object_impl` declares `emerald_alloc`,
  `emerald_print_i64`, `emerald_string_concat`, `emerald_region_create`,
  and roughly two dozen other real C functions from `runtime/
  emerald_runtime.c` (lines 10631-10790) with the exact same three-line
  shape every time — e.g. `module.add_function("emerald_alloc",
  ptr_ty.fn_type(&[i64_ty.into()], false), Some(Linkage::External))` —
  and then calls each one with an ordinary `builder.build_call`, the
  identical mechanism `declare_exception_runtime_funcs` (L2112) and
  `declare_actor_runtime_funcs` use for their own runtime symbols. This
  is, structurally, already C FFI: an LLVM `Linkage::External` function
  declaration resolved at link time against a real, separately compiled
  C translation unit. This plan's entire job is generalizing that one
  fixed, hardcoded, compiler-authored list into an arbitrary,
  user-named, source-declared one — not designing a new interop layer
  from scratch.
- **No custom calling convention exists anywhere in this codegen, so
  there is none to design here either.** Verified this session: zero
  matches for `call_convention`/`CallConv`/`set_call_convention` across
  `emerald-codegen/src/lib.rs`. Every one of the ~30 existing runtime
  declarations above rides inkwell/LLVM's implicit default — the
  platform C calling convention — already. `Int64`/`Float64` therefore
  map directly onto C's `int64_t`/`double` (or any C integer/floating
  type of the same real width) with zero conversion code, the same way
  every existing runtime call already gets this for free.
- **The real, implemented `Type` enum has no fixed-width integers
  narrower than `Int64` — `TYPE_SYSTEM.md` §2's table is aspirational,
  not built.** Verified this session against `emerald-sema/src/lib.rs`'s
  actual `Type` enum (`Int64, Float64, String, Boolean, Void, Symbol,
  Nil, Class, Array, Hash, Tuple, Enum, Result, Supervisor, Pair` — no
  `Int8`/`Int16`/`Int32`, no `UInt*`, no `Float32`), even though
  `TYPE_SYSTEM.md` §2 lists all eight fixed-width integer types and
  `Float32` in its primitive-types table. This plan's extern-signature
  type allow-list is therefore necessarily `{Int64, Float64, String,
  CString, Void (return-only)}` — nothing narrower exists to marshal
  into. This is a real, deliberate deviation from the task's own
  suggested worked example (`extern "C" fn abs(x: Int32): Int32`):
  `abs`'s real C signature takes a 32-bit `int`, which Emerald has no
  type to represent honestly today, so the worked proof above uses
  `llabs`/`strlen`/`strstr` instead — three real libc functions whose
  actual C signatures are genuinely 64-bit (`long long`) or
  pointer-typed, both widths Emerald's real type system already
  represents exactly. Adding narrower integer widths as real,
  checkable `Type` variants is a substantial, separate follow-up this
  plan does not fold in as a side effect.
- **`Boolean` is declined as an extern-signature type in v1 — a real,
  concrete ABI mismatch, not a hedge.** Verified this session:
  `emerald-codegen/src/lib.rs`'s `ValKind` doc comment states plainly
  that `Bool` "labels a `Expr::Compare`/`&&`/`||`/`!` result, or a real
  declared `Boolean`-typed value... both share the same `i1` storage" —
  Emerald's `Boolean` is a bare LLVM `i1`. A real C `bool`/`_Bool`
  parameter, as Clang itself lowers it, occupies a full byte (`i8`) at
  the ABI boundary, not `i1` — confirmed by this codegen's *own*
  existing practice: `emerald_bool_to_string`'s declaration comment
  states it "takes a plain `long long`, not a C `_Bool`/`i1`... codegen
  zero-extends the `i1` value before calling it," precisely because
  handing a bare `i1` across a real external-call boundary is already
  known, inside this codebase, not to be safe. This plan doesn't invent
  a new marshaling rule to bridge `i1` to a real `_Bool`'s `i8` ABI
  representation — `Boolean` simply isn't in the allow-list; a C API
  that takes a boolean flag is declared with `Int64` instead (many real
  C APIs — including SQLite's own — already use a plain `int` for this,
  so this is not a hypothetical workaround).
- **A declared-width mismatch is genuine undefined behavior, and here is
  the concrete mechanism, not just the abstract warning.** If an
  extern's declared return type is narrower or wider than the real C
  function's actual return width, the *caller* (Emerald) reads a full
  register-width value back, but the *callee* (real, separately
  compiled C code) only ever wrote the low bits its own true return
  type promises — the remaining high bits hold whatever garbage was
  already in that register, silently corrupting the value Emerald
  treats as a full `Int64`. An argument-width mismatch is comparatively
  more forgiving on some ABIs (a callee that only reads its own
  narrower declared width simply ignores extra high bits a caller
  over-supplied) but this is an ABI implementation detail, never a
  language guarantee — this plan does not rely on it, and states this
  asymmetry explicitly rather than leaving "just get the signature
  right" as an unexplained rule.
- **`String` needs no byte-level conversion to cross the FFI boundary —
  a genuinely more favorable finding than "likely needs
  `.to_cstring()`," verified directly, not assumed.** Read in full this
  session: `runtime/emerald_runtime.c`'s `emerald_alloc` (L63-66) is a
  bare `malloc` wrapper, and `emerald_string_length` (L331-333) is
  `return (long long) strlen(s);` — proof `String` carries **no length
  header at all**; it is a plain, `malloc`-backed, null-terminated
  buffer. `emerald-codegen/src/lib.rs`'s own `ValKind` doc comment
  confirms this at the type level: `Str` is "a pointer to a
  null-terminated UTF-8 buffer." This is bit-for-bit identical to C's
  own `char*`/`const char*` convention — an Emerald `String` value
  passed as an extern parameter needs zero conversion, no wrapper
  function, nothing; `strlen("hello")` in this plan's own worked proof
  is the executed proof of exactly that.
- **The real friction is trust and lifetime, not bytes — which is why
  an explicit `CString`/`String.from_cstring` conversion pair still
  exists on the return side, for a different reason than originally
  guessed.** A pointer a C function *hands back* carries none of the
  guarantees Emerald's type checker can verify: is it actually
  null-terminated, actually valid UTF-8, still alive by the time
  Emerald touches it? None of that is checkable from the declaration
  alone. `Type::CString` is a new, deliberately inert reference type
  (sema-only distinction, `emerald-codegen` stores it identically to
  `ValKind::Str` — same bare pointer, no new runtime representation) —
  no `String` method (`.upcase`, `.length`, ...) dispatches on it at
  all. The only two ways to move between `String` and `CString` are two
  new intrinsics reusing plan 45's own stated mechanism verbatim (its
  overview line: "every one a compiler-known intrinsic dispatched by
  receiver storage kind or reserved namespace name, the exact mechanism
  `puts` already uses"): `String.to_cstring(self): CString` (a
  zero-argument method intrinsic, same dispatch path as `.upcase`) and
  `String.from_cstring(ptr: CString): String?` (a reserved-namespace
  static call, same dispatch path as plan 45's own `File.read`). This
  keeps the FFI trust boundary visible at every *use* site that
  consumes a raw C pointer, not only at the (possibly distant)
  `unsafe extern "C" { ... }` declaration site — directly satisfying
  this plan's own "visually loud" requirement (see below) a second,
  independent way.
- **`String.from_cstring` compiles to zero LLVM instructions — a real,
  unplanned convergence between this plan and plan 43's actual, already-
  shipped nullable-type design.** Verified this session against plan
  43's own Decision log: nullable reference types (`String?` included)
  "both [are] backed by an LLVM `ptr` — which has a spare bit pattern
  (`null`) to spend on nilness for free." A C function's real `NULL`
  return and Emerald's own runtime representation of `nil` for a
  nullable reference type are, it turns out, bit-for-bit the same
  value. `String.from_cstring` therefore does not check, branch, or
  copy anything at the LLVM level — it is a pure, compile-time type
  relabeling from `CString` to `String?`, and this plan's own worked
  proof's `strstr(..., "xyz")` (a real `NULL` return) flowing straight
  into `||= "not found"` (plan 43's actual mechanism) without a crash
  is the executed proof of that convergence, not merely an assertion
  of it. `String.to_cstring` is the cheaper, total (never-nil) reverse
  direction — an Emerald `String` is already guaranteed non-null,
  NUL-terminated, real UTF-8, so nothing needs checking going out.
- **The `unsafe extern "C" { ... }` block is a mandatory, grammar-level
  marker — not a sema convention that a future change could quietly
  weaken.** Verified this session: zero matches for `"unsafe"` or
  `"extern"` as literal tokens anywhere in `grammar.lalrpop` today —
  both keywords are free to introduce with no collision. This plan
  adopts Rust's own real `extern "C" { ... }` block syntax directly
  (the same "reuse a well-understood existing convention rather than
  inventing a new one" posture plan 46 already used for TOML and
  Cargo's exact-pin lockfile shape), prefixed with a mandatory
  `unsafe` keyword that exists in this grammar *for no other purpose* —
  it is Emerald's only reserved word that admits an escape from static
  safety. Requiring it at the grammar level (a bare `extern "C" { ... }`
  with no `unsafe` is a genuine parse error, not merely a lint) means
  the risk marker cannot be silently dropped the way a sema-only check
  or a doc comment could be — a real, unforgeable structural fence, not
  a convention.
- **Linking a named external C library reuses `emerald-driver`'s real,
  already-shipped `link` function, extended additively.** Verified this
  session, read in full: `crates/emerald-driver/src/lib.rs`'s `link`
  (L111-134) — the parse→check→codegen→link pipeline plan 06 first
  built directly inside `emerald-cli`, later extracted into its own
  crate specifically so a second caller could reuse it (plan 17's
  `leaf-driver-extraction`, its own stated purpose: "the second caller
  plan 06 said would justify it" — `emerald-mcp`'s `compile_and_run`
  tool is exactly that second caller, and inherits this plan's linking
  capability automatically once it lands, with no `emerald-mcp` change
  needed) — invokes `Command::new("cc").arg("-no-pie").arg(&obj_path)
  .arg(&runtime_archive_path).arg("-o").arg(&output_path)` today, with
  no way to add any further linker argument. This plan's manifest-driven
  library list becomes one `-l<name>` argument per declared entry,
  positioned after the object/runtime-archive arguments and before
  `-o` — ordinary `cc`/`ld` link-order convention (a library must be
  listed after the objects that reference its symbols).
- **`emerald.toml` gains `[ffi] link = [...]`, additive and
  `#[serde(default)]`-guarded against the real, already-shipped
  manifest shape — zero regression to any existing manifest.** Read in
  full this session: `crates/emerald-cli/src/manifest.rs`'s real
  `Manifest { package: PackageMeta, dependencies: BTreeMap<String,
  DependencySpec> }` and `RawManifest { package, #[serde(default)]
  dependencies }` already establish the exact precedent this plan
  follows: a new `FfiSpec { link: Vec<String> }` field on both,
  `#[serde(default)]`-guarded so every `emerald.toml` written before
  this plan (none of which has an `[ffi]` table) keeps parsing to an
  empty `link: vec![]`, identical to today's behavior. `-l`-prefixing
  happens at the linker-argument-building step, not in the manifest
  itself — `link = ["sqlite3"]`, not `link = ["-lsqlite3"]`, matching
  Cargo's own `cargo:rustc-link-lib` naming convention rather than
  requiring the raw linker flag spelling in source.
- **Explicitly declined, stated directly rather than silently
  narrowed:** (1) **C++ FFI** — name mangling, vtables, templates are a
  separate, substantially harder problem than a flat C ABI; nothing
  here reaches for it. (2) **Automatic C-header-parsing/binding
  generation** (a bindgen-style tool) — v1 requires a hand-written
  `extern "C"` declaration matching the real signature exactly; the
  UB-if-wrong risk this plan states so plainly is the direct reason a
  human, not a heuristic header parser, writes it. (3) **Struct/
  aggregate-by-value marshaling, array marshaling, and C-calling-back-
  into-Emerald (function-pointer) support** — none of this plan's
  scalar+`String`+`CString` allow-list touches any of these; a real C
  API needing them (an `sqlite3**` out-parameter, a `struct stat*`, a
  progress-callback function pointer) cannot be declared in v1 at all.
  This is a genuine, disclosed limitation, not an oversight — it is
  exactly why the SQLite example below is a documented stretch, not
  this plan's required proof.

## Leaf: leaf-extern-declaration

### 1. Context
- Why: nothing in this compiler lets a user *name* an external C
  function today — only the compiler's own fixed, hardcoded runtime
  symbol list can be declared and called (see Decision log). This leaf
  generalizes that exact mechanism to arbitrary user-named symbols.
- Target state: `crates/emerald-parser/src/ast.rs` gains `ExternFn {
  name: String, params: Vec<Param>, return_type: String }` and
  `ExternBlock { abi: String, fns: Vec<ExternFn> }`, plus `Item::Extern
  (ExternBlock)`. `grammar.lalrpop` gains `"unsafe" "extern"
  <abi:StringLitTok> "{" <fns:ExternFnDecl*> "}"`, where each
  `ExternFnDecl` is `"fn" <name:Ident> "(" <params:Params> ")" ":"
  <ret:TypeName>` — reusing the existing, shared `Params`/`Param`
  production (the same one class fields already reuse, per plan 39's
  own citation) verbatim, and deliberately using `:` rather than `def`'s
  `->` so an extern declaration is visually distinct from an ordinary
  function signature at a glance, not just via the `unsafe extern`
  prefix. `emerald-sema` decodes the `abi` literal and rejects anything
  but exactly `"C"` with a diagnostic naming the unsupported ABI (the
  explicit C++ decline from the Decision log); a new narrow
  `resolve_extern_type` accepts only `Int64`/`Float64`/`String`/
  `CString` for parameters, the same four plus `Void` for return types,
  rejecting anything else (`Boolean`, any `Class`, `Array[_]`,
  `Hash[_,_]`, `Symbol`, `Tuple`, ...) with a diagnostic naming the
  offending type and position. Each `ExternFn` is registered into the
  same top-level function-name registry `function_signature()`
  populates for ordinary `def` functions (plan 39's `FunctionSig`) —
  no new call-expression AST is needed; `abs(x)`-style calls resolve
  through the existing `Expr::Call` path unchanged. `emerald-codegen`
  gains a pre-pass (mirroring plan 32's ClassDef-collection-before-
  methods-build precedent) that declares every extern fn via
  `module.add_function(name, marshaled_fn_type, Some(Linkage::
  External))` — the literal generalization of the runtime's own
  declarations at L10631-10790 — into a new `ctx.extern_func_ids` table;
  `Expr::Call` codegen's existing `ctx.user_func_ids` lookup gains a
  fallback into this table, calling `build_call` exactly as every
  existing runtime helper call site already does.

### 2. Acceptance Criteria
1. `unsafe extern "C" { fn llabs(x: Int64): Int64 fn strlen(s: String):
   Int64 }` parses to `Item::Extern(ExternBlock { abi: "C".into(), fns:
   [...] })` with both `ExternFn`s populated correctly.
2. The same declaration without the leading `unsafe` keyword (bare
   `extern "C" { ... }`) is a real parse error — the marker is
   grammar-mandatory, not sema-optional.
3. An extern fn declared with an unsupported parameter or return type
   (`Boolean`, a user `Class`, `Array[Int64]`) is rejected with a
   diagnostic naming the offending type — not a silent pass-through and
   not a panic.
4. An extern block whose ABI literal isn't exactly `"C"` (e.g. `"C++"`)
   is rejected with a diagnostic — the explicit decline from the
   Decision log, verified as a real compile error, not an assumption.
5. This plan's own worked proof's `llabs`/`strlen` portion — compiled,
   linked with plain `cc` (no `[ffi]` table, no extra `-l` flags), and
   run — prints `42` then `5`.
6. Regression: every prior plan's example still parses, type-checks,
   and compiles identically — this leaf only adds one new `Item`
   alternative and one new `Expr::Call` codegen fallback.

## Leaf: leaf-string-marshaling

### 1. Context
- Why: `String`'s own representation needs no conversion to cross the
  FFI boundary as an *argument* (see Decision log — verified, not
  assumed), but a pointer *returned* by a real C function carries no
  checkable NUL-termination/UTF-8-validity/liveness guarantee — a real,
  disclosed trust gap this leaf fences explicitly, at every use site.
- Target state: `emerald-sema` gains `Type::CString` — an opaque
  reference type with no methods of its own, resolvable only via
  `resolve_extern_type` (leaf-extern-declaration) and two new
  intrinsics reusing plan 45's compiler-known-intrinsic dispatch
  mechanism verbatim: `String.to_cstring(self): CString` (zero-argument
  method intrinsic, same dispatch path as `.upcase`/`.length`) and
  `String.from_cstring(ptr: CString): String?` (reserved-namespace
  static call, same dispatch path as `File.read`), where `String?`
  reuses plan 43's real, already-shipped `Type::Nullable(Box<Type>)`.
  `emerald-codegen` stores a `CString` value identically to
  `ValKind::Str` (a bare pointer) — both intrinsics compile to a pure
  type-level relabeling with zero emitted instructions, per the
  Decision log's null-representation convergence with plan 43.

### 2. Acceptance Criteria
1. `s.to_cstring()` on a `String`-typed `s` type-checks to `CString`;
   the emitted LLVM IR for the call site contains no new instruction
   beyond whatever already produced `s`'s pointer value (verified
   directly against the emitted IR, not assumed from the design).
2. `String.from_cstring(ptr)` where `ptr: CString` type-checks to
   `String?`; calling any `String`-only method directly on the
   un-narrowed result (`String.from_cstring(ptr).length`) is rejected
   the same way plan 43 already rejects a direct method call on any
   other `T?` receiver.
3. `String.from_cstring` called on a value that isn't `CString` (e.g. a
   bare `Int64`) is a real diagnostic, not a panic.
4. This plan's own worked proof's `strstr` portion — both calls piped
   through `String.from_cstring` and defaulted via plan 43's real `||=`
   — compiled, linked, and run, prints `world` then `not found`: the
   last two lines of the plan's full four-line worked example (`42`,
   `5`, `world`, `not found`), with this leaf specifically responsible
   for both being correct on the found and the real-`NULL` path.
5. Regression: plan 43's own Greeter/`&.`/`||=` proof and plan 45's
   stdlib String-intrinsic examples still compile and behave
   identically — this leaf adds two new intrinsics and one new opaque
   type, touching no existing dispatch arm.

## Leaf: leaf-manifest-linking

### 1. Context
- Why: today's `link` function (`emerald-driver/src/lib.rs`) has no way
  to add any linker argument beyond the object file and the embedded
  runtime archive — a real extern declaration that needs a named
  third-party C library (SQLite, say) would parse, type-check, and
  compile to a valid object file, then fail at the final `cc` step with
  an unresolved-symbol error and no way in `emerald.toml` to fix it.
- Target state: `crates/emerald-cli/src/manifest.rs` gains `FfiSpec {
  pub link: Vec<String> }` and a `#[serde(default)] pub ffi: FfiSpec`
  field on both `Manifest` and `RawManifest`, mirroring
  `RawManifest.dependencies`'s own existing `#[serde(default)]`
  precedent exactly. `emerald-driver/src/lib.rs`'s `link` becomes a
  thin wrapper over a new `link_with_libs(obj_path, output_path,
  extra_libs: &[String])` (matching this same file's own established
  "old entry point becomes a thin wrapper over the new one" pattern,
  already used for `link_stage`/`link` itself per plan 48's Decision
  log), which appends one `-l<name>` `Command` argument per
  `extra_libs` entry, positioned after `&runtime_archive_path` and
  before `"-o"`. `emerald-cli`'s `cmd_build` (already loads `Manifest`
  today) threads `manifest.ffi.link` into this new parameter.

### 2. Acceptance Criteria
1. `emerald.toml` with `[ffi]\nlink = ["sqlite3", "m"]` parses to
   `Manifest.ffi.link == vec!["sqlite3", "m"]`; a manifest with no
   `[ffi]` table at all parses to `Manifest.ffi.link == vec![]` — zero
   regression against every existing plan-46 manifest fixture (path
   dependency, git dependency, missing-entry-default tests all still
   pass unchanged).
2. `link_with_libs(obj, out, &["sqlite3".to_string()])`'s constructed
   `Command` argument list contains `-lsqlite3`, positioned after the
   object/runtime-archive arguments and before `-o` — asserted directly
   against the built argument vector, not by requiring `sqlite3`
   actually be installed on the machine running this gate.
3. `link_with_libs(obj, out, &[])` (what every pre-existing call site
   becomes) produces byte-for-byte the same argument list `link`
   already produced before this leaf — an asserted no-regression proof,
   not an assumption.
4. **Documented, non-gating stretch example** (not required for this
   leaf's own quality gate — kept out of the required acceptance
   criteria precisely so this plan's own gate never depends on what
   happens to be installed on a given machine): a two-file package
   whose `emerald.toml` sets `[ffi]\nlink = ["sqlite3"]`, declaring
   `unsafe extern "C" { fn sqlite3_libversion(): CString }` and printing
   the real linked library's version string via
   `String.from_cstring(sqlite3_libversion())` on a machine with
   `libsqlite3` installed.

## Out of scope / deferred
- C++ FFI (name mangling, vtables, templates) — a separate, much harder
  problem; see Decision log.
- Automatic C-header-parsing/binding generation (bindgen-style) — v1
  requires a hand-written `extern "C"` declaration matching the real
  signature exactly; the disclosed UB-if-wrong risk is the direct
  reason a human writes it, not a header parser.
- `Boolean` as an extern parameter/return type — a real `i1`-vs-C-
  `_Bool`/`i8` ABI mismatch this plan does not build a marshaling rule
  for; see Decision log.
- Narrower integer widths (`Int8`/`Int16`/`Int32`, `UInt8`-`UInt64`,
  `Float32`) as extern types — `TYPE_SYSTEM.md` §2 lists them
  aspirationally; the real `Type` enum has no such variants today; a
  genuinely separate, larger follow-up plan.
- Struct/aggregate-by-value marshaling, array marshaling across the FFI
  boundary, and C-calling-back-into-Emerald function pointers — none of
  this plan's scalar+`String`+`CString` allow-list reaches any of these.
- A general opaque raw-pointer/handle type for C APIs needing one (e.g.
  `sqlite3**`) — `CString` is narrowly scoped to `char*`-shaped values
  only, not a general `void*` escape hatch.
- `emerald.lock`/dependency-resolution changes — this plan only reads
  an additional `[ffi]` table at link time; no new resolution semantics.
- Keyword arguments, default parameters, or splat on extern fn
  declarations — plain positional calls only, matching plan 39's own
  scoping precedent for what a signature-completeness feature does and
  doesn't need to prove.
