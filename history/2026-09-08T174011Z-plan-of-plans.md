### Batch: closing the gap to ~45% (plans 36-47)

A prior analysis measured plans 01-35's shipped/target surface at
roughly 10-15% of standard Ruby's language-and-stdlib surface, and set
a strategic ceiling: close every further gap that is compatible with
Emerald's identity (no `method_missing`/`eval`/`send`/reflection, no
mixins/open classes/monkey-patching, no dynamic/virtual dispatch or
vtables, no tracing garbage collector, no runtime reflection), decline
the rest permanently. These twelve independent sibling plans — same
posture as the 28-35 batch — are that closing set, authored together in
one pass. All twelve are `planned` (authored, none executed yet).

One cross-plan inconsistency surfaced during authoring and was
corrected in place rather than left to rot: plan 42 was drafted assuming
plan 37 would deliver a first-class `Range` value; plan 37, once
actually authored, deliberately declined that (`..`/`...` are
grammar-restricted to a `for...in` scrutinee only, no standalone
`Range` value or type). Plan 42 now carries an explicit
"Post-authoring correction" note superseding its own stale `Range`-as-
`Iterable` references; its `Range.each` acceptance criterion is void.

### Batch: implementing "Beyond the Ceiling" in full (plans 48-57)

After the 36-47 batch was planned, a follow-up analysis ("Beyond the
Ceiling") proposed two further, independent tracks: pure compiler-
implementation improvements that touch no language semantics, and an
actor-model concurrency pillar (BEAM/Pony-inspired) plus algebraic data
types and a `Result[T,E]` error channel. A candidate third idea —
an Effect.ts/id_effect-style `Effect<A, E, R>` type with a built-in
dependency-injection channel — was debated and explicitly rejected: it
would need generic *data types* (plan 41 gives only generic functions),
composition sugar (do-notation/generators, a permanent non-goal here),
a fiber-based concurrency runtime competing with the actor pillar
below, and structural/intersection or variance typing this project has
none of. The user committed to building everything in "Beyond the
Ceiling," and nothing beyond it. These ten plans are that build,
authored together in one pass, same posture as the 28-35 and 36-47
batches. All ten are `planned`.

Sequencing note: 48-51 (implementation) are independent of each other
and of 52-57. 52 (ADTs) and 53 (Result) are a pair — 53 deliberately
does NOT use 52's user-facing `enum` mechanism (which explicitly
declines generic types), instead giving `Result[T,E]` its own hardcoded
compiler-native representation, mirroring `Array[T]`/`Hash[K,V]`/
`Pair[K,V]`. 54→55→56→57 is a strict, deliberately staged concurrency
chain (isolated heaps → real async dispatch → compile-time message
safety → supervision) — each stage is independently provable before
the next adds complexity on top; do not treat 54-57 as parallel-
executable the way most other batches' rows are.

One cross-plan inconsistency surfaced during authoring and was
corrected in place: plan 54 was drafted against a guessed placeholder
runtime API for plan 51's arena mechanism (a single `emerald_arena_new
(capacity)` call) before plan 51's real file landed. Plan 51's actual,
shipped API is three functions (`emerald_region_create`, `emerald_
region_alloc`, `emerald_region_destroy`), with the region handle
retained separately from the allocated pointer. Plan 54 now carries an
explicit "Post-authoring correction" note giving the real call
sequence; its own acceptance criteria are unchanged in substance.
