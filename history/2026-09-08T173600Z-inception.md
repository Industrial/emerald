# Emerald Language — Project Handoff / Bootstrap Specification

**Status:** Initial project brief  
**Language:** Emerald  
**Compiler implementation language:** Rust  
**Primary objective:** Build a statically typed, ahead-of-time compiled language derived from Ruby's syntax and programming model, with native-code performance as the target.

---

## 1. Mission

Emerald is a new programming language derived from Ruby.

The goal is **not** to make existing Ruby faster, and Emerald is **not** intended to preserve Ruby's dynamic execution model.

Instead:

> Emerald should retain as much of Ruby's syntax, readability, object-oriented model, and programming ergonomics as possible while imposing a fully static language semantics suitable for ahead-of-time native compilation.

The project deliberately chooses a **100% static model** rather than gradual typing or a Ruby-compatible dynamic fallback.

This is an intentional scope reduction.

We want the compiler to be substantially simpler than CRuby/JRuby/TruffleRuby and to have semantics that permit aggressive optimization.

---

## 2. Core Design Philosophy

### 2.1 Ruby is the starting point

The initial language design should begin from Ruby's grammar/specification rather than from Rust, Java, C++, or another language.

Ruby syntax is the source of truth for the *surface language*.

Useful references include:

- Ruby's current syntax documentation:
  https://docs.ruby-lang.org/en/master/syntax_rdoc.html
- Ruby's historical pseudo-BNF:
  https://ruby-doc.org/docs/ruby-doc-bundle/Manual/man-1.4/yacc.html

The current Ruby documentation describes syntax across literals, assignment, control expressions, pattern matching, methods, method calls, classes/modules, exceptions, precedence, refinements, and operators.

The old pseudo-BNF is useful as a grammar starting point, but it is explicitly described as pseudo-BNF and points to Ruby's `parse.y` for greater detail.

### 2.2 Do not turn Emerald into Rust with Ruby syntax

Rust concepts should not be imported merely because they are fashionable or useful.

We should first ask:

> What is the smallest semantic modification to Ruby that gives us a clean, statically typed, native-compiled language?

Only introduce concepts when the Emerald language itself requires them.

### 2.3 No gradual/dynamic mode

Emerald does not have:

- `dynamic` variables
- runtime type inference as a semantic fallback
- `eval`
- monkey patching
- runtime method creation
- `method_missing`
- runtime alteration of class definitions
- reflective mutation of program structure

These are not deferred features. They are outside the intended core language unless a future design decision explicitly reintroduces them.

---

# 3. Primary Goal

A valid Emerald program should be statically analyzable before code generation.

The compiler should be able to determine:

- every variable's type
- every method's parameter types
- every method's return type
- class relationships
- field types
- method availability
- operator meaning
- valid conversions
- control-flow correctness
- all compile-time errors

The generated program should be native code.

The language should not require:

- a bytecode VM
- an interpreter
- a JIT
- dynamic dispatch machinery where static dispatch is possible
- mandatory garbage collection for primitive/value operations

The compiler may use runtime support where the language semantics genuinely require it, but the static language itself should not depend on Ruby's dynamic runtime.

---

# 4. First Principle: Define Emerald Before Implementing Emerald

Do not let the first compiler implementation accidentally become the language specification.

Create and maintain these documents:

```text
SPEC.md
GRAMMAR.md
TYPE_SYSTEM.md
SEMANTICS.md
RUNTIME.md
COMPILER.md
```

The compiler must implement these documents.

If implementation and specification disagree, update the specification deliberately rather than silently changing the language.

The first Emerald version should target a deliberately small but useful subset.

- constants
- instance variables

- strings

- blocks

- `eval`

- runtime method definition

- dynamic constant definition
- dynamic instance-variable definition
- arbitrary reflection

Do not create complicated replacements for these features merely to preserve Ruby compatibility.

# 6. Static Typing

Emerald is statically typed.

Initial declarations should be explicit.

Example:

```ruby
def add(a: Int64, b: Int64) -> Int64
  a + b
end
```

and:

```ruby
class Point
  x: Float64
  y: Float64

  def initialize(x: Float64, y: Float64) -> Void
    @x = x
    @y = y
  end

  def distance_from_origin -> Float64
    Math.sqrt(@x * @x + @y * @y)
  end
end
```

Type inference may be introduced later as a compiler convenience.

Inference must not weaken the static semantics.

---

# 7. Initial Type Universe

Start small.

Candidate primitive/value types:

```text
Boolean
Int8
Int16
Int32
Int64
UInt8
UInt16
UInt32
UInt64
Float32
Float64
String
Symbol
Nil
Void
```

Containers:

```text
Array[T]
Hash[K, V]
```

User-defined:

```text
class Foo
struct Foo
```

Do not automatically assume that Ruby's arbitrary-precision `Integer` semantics should be preserved.

This is a design question to resolve explicitly.

A likely initial choice is to provide machine integer types such as `Int64`, while deciding separately whether Emerald's `Integer` should mean arbitrary precision or a machine integer.

Do not make this decision accidentally through the implementation.

---

# 8. Ruby Object Model

Preserve Ruby's object-oriented model where practical.

Example:

```ruby
class Animal
  def speak -> String
    "..."
  end
end

class Dog < Animal
  def speak -> String
    "woof"
  end
end
```

Inheritance should be statically known.

A method call such as:

```ruby
animal.speak
```

must have a statically known method contract.

Virtual dispatch may still exist for ordinary inheritance, but the compiler should know the receiver's static type and method signature.

Later optimization can perform:

- devirtualization
- inlining
- constant propagation
- dead dispatch elimination

---

# 9. No Duck Typing in v1

Do not attempt to preserve Ruby's implicit duck typing.

This:

```ruby
def print_name(x)
  puts x.name
end
```

is insufficiently specified for Emerald v1.

Instead:

```ruby
def print_name(x: Person) -> Void
  puts x.name
end
```

If structural typing or interfaces/protocols become necessary later, design them deliberately.

Do not import Rust traits or Java interfaces simply because they solve this problem.

---

# 10. Arrays and Collections

Ruby arrays are heterogeneous and dynamically typed.

Emerald arrays should be statically parameterized:

```ruby
Array[Int64]
Array[String]
Array[Float64]
Array[Person]
```

This permits the compiler to choose an appropriate representation.

For example:

```ruby
numbers: Array[Int64]
```

should permit contiguous machine-integer storage rather than requiring Ruby-style boxed objects.

Representation is an implementation detail governed by the static semantics, but performance-sensitive primitive collections should have a path to unboxed/native representation.

---

# 11. Numeric Performance

This is one of Emerald's primary motivations.

Given:

```ruby
def sum_squares(xs: Array[Int64]) -> Int64
  total: Int64 = 0

  for x in xs
    total += x * x
  end

  total
end
```

the compiler should be able to produce ordinary machine arithmetic without:

- Ruby object boxing
- dynamic method lookup
- runtime numeric type checks
- interpreter dispatch

The eventual optimizer should be free to apply:

- inlining
- loop optimization
- constant propagation
- strength reduction
- vectorization
- target-specific optimization

The language itself does not promise a particular speedup such as "1000×". The language promises semantics that permit native optimization.

---

# 12. Memory Model

Do not design a complicated ownership/borrowing system for v1.

First determine what Ruby-like static semantics require.

Initial implementation may use a conventional managed runtime for reference objects while keeping primitive/value operations unboxed.

Later, if profiling demonstrates that allocation/GC is a major bottleneck, investigate:

- stack allocation
- escape analysis
- arenas
- reference counting
- ownership analysis
- region allocation

Do not add Rust's ownership system preemptively.

---

# 13. Compiler Architecture

The compiler should be written entirely in Rust.

Recommended initial architecture:

```text
Emerald source
      |
      v
Lexer
      |
      v
Tokens
      |
      v
Parser
      |
      v
Concrete / lossless syntax representation
      |
      v
AST / HIR
      |
      v
Name resolution
      |
      v
Type checking
      |
      v
Typed IR
      |
      v
Optimization
      |
      v
Native code generation
      |
      v
Executable / object file
```

Do not build a VM unless a future requirement proves one necessary.

# 14. Rust Ecosystem Research

The compiler should reuse mature Rust infrastructure rather than reinventing common compiler tooling.

## 14.1 Parsing

Two strong candidates are:

### LALRPOP

LALRPOP is an LR(1) parser generator for Rust and is particularly appropriate if the Emerald grammar is maintained in a formal grammar file.

https://github.com/lalrpop/lalrpop

This is attractive because the project explicitly wants the Ruby BNF/grammar to be the starting point.

### Chumsky

Chumsky is a parser-combinator library designed for expressive, high-performance parsers and includes error recovery and zero-copy parsing facilities.

https://docs.rs/chumsky/

Do a small prototype with both before committing.

Do not decide based solely on popularity.

## 14.2 Lexing

Investigate `logos`.

Logos generates deterministic lexers and is designed specifically for fast Rust lexing.

https://docs.rs/logos/

A likely initial combination is:

```text
logos + LALRPOP
```

if the grammar fits that architecture well.

## 14.3 Syntax trees

Investigate `rowan`.

`rowan` provides generic lossless syntax trees and is used in the Rust tooling ecosystem.

https://docs.rs/rowan/

A lossless syntax tree is particularly useful if Emerald eventually wants excellent tooling, formatting, IDE support, and precise diagnostics.

Do not introduce it solely for theoretical purity. Prototype the parser architecture first.

## 14.4 Diagnostics

Investigate `miette`.

`miette` provides diagnostic protocols and human-friendly source diagnostics, including labeled spans and source-code rendering.

https://docs.rs/miette/

Alternative: Ariadne.

The compiler should eventually produce diagnostics of roughly this quality:

```text
error[E0007]: type mismatch

  --> example.em:4:12
   |
 4 |   x + "hello"
   |       ^^^^^^^ expected Int64, found String
   |
   = help: both operands of `+` must have compatible types
```

Diagnostics are a first-class compiler feature, not an afterthought.

## 14.5 Incremental compilation

Investigate `salsa`.

Salsa provides incremental, on-demand computation with memoized tracked functions and dependency tracking.

https://docs.rs/salsa/

It may be useful for:

- parsing
- name resolution
- type checking
- module dependency analysis
- IDE support

Do not add Salsa to the first hello-world compiler unless it materially simplifies the architecture.

## 14.6 Code generation

Investigate both LLVM and Cranelift.

### LLVM / Inkwell

Inkwell provides Rust bindings/wrappers around LLVM and is explicitly aimed at helping users write programming languages.

https://docs.rs/inkwell/

Current research shows Inkwell 0.10.0 and LLVM 22 bindings are available in the current ecosystem.

### Cranelift

Cranelift is a mature native code generation backend in the Bytecode Alliance ecosystem.

https://docs.rs/cranelift/

The current stable `cranelift` umbrella crate is 0.135.1, with a 0.136.0 release candidate also visible.

### Initial recommendation

Prototype Emerald code generation with **Cranelift first** if rapid implementation is the priority.

Evaluate **LLVM/Inkwell** if we need LLVM's broader optimization infrastructure or target ecosystem.

Do not commit permanently until a minimal Emerald benchmark has been compiled through both.

# 15. id_effect

The project owner has written `id_effect`.

It should be considered an available Rust dependency and architectural tool rather than something to replace.

Current published documentation describes `id_effect` as providing an interpreter-style `Effect<A, E, R>` abstraction, piping, capability/dependency-injection facilities, scheduling, streams, and related infrastructure.

Current documentation:

https://docs.rs/id_effect/

Current crates.io/docs.rs research shows active releases in 2026; the current documentation page is for the 0.4.x line.

The project should use `id_effect` where it genuinely improves compiler architecture, particularly for:

- compiler pipeline orchestration
- explicit effects
- dependency/context wiring
- diagnostics accumulation
- filesystem/toolchain effects
- build orchestration
- test infrastructure

Do not force every compiler function through `Effect`.

Use it where its abstraction makes the architecture clearer.

# 17. First Compiler Milestone

Do not attempt the full Ruby grammar initially.

The first executable milestone is:

```ruby
def add(a: Int64, b: Int64) -> Int64
  a + b
end

puts add(20, 22)
```

Emerald should:

1. tokenize the source
2. parse it
3. build syntax/AST representation
4. resolve `add`
5. type-check the parameters
6. type-check `a + b`
7. determine the return type
8. generate native code
9. link an executable
10. execute and print:

```text
42
```

This is the first vertical slice.

After that, add:

```ruby
x: Int64 = 10

if x > 5
  puts x
end
```

Then:

```ruby
class Point
  x: Float64
  y: Float64

  def initialize(x: Float64, y: Float64) -> Void
    @x = x
    @y = y
  end

  def sum -> Float64
    @x + @y
  end
end

p = Point.new(2.0, 3.0)
puts p.sum
```

Only after these work should the compiler expand toward the broader Ruby grammar.

# 18. Grammar Strategy

The Ruby grammar should be imported and normalized into an Emerald grammar rather than manually reinvented from memory.

Use the Ruby grammar as the inventory of syntax.

For every grammar production:

```text
KEEP
MODIFY
REMOVE
```

Record the decision and reason.

Example:

```text
Ruby:
    CALL
        -> FUNCTION
        -> COMMAND
        -> PRIMARY "." OPERATION CALL_ARGS

Emerald:
    CALL
        -> FUNCTION
        -> PRIMARY "." METHOD_CALL
```

The semantic difference should be documented separately.

Do not overload the grammar with type-system semantics.

# 19. Important Semantic Decisions to Resolve Early

The next AI/developer should explicitly investigate and settle these questions:

### Variables
- Are local variables mutable by default?
- Are constants truly immutable?
- Can variables change type after initialization? (Recommended: no.)

### Nil
- Is `nil` represented by a `Nil` type?
- Is `Nil` assignable to arbitrary reference types?
- Do we need nullable types?

### Methods
- Are methods overloaded?
- Is method resolution purely name + arity + static receiver type?
- Are keyword arguments retained?
- Are default arguments retained?

### Classes
- Are fields declared explicitly?
- Are undeclared instance variables illegal?
- Is multiple inheritance forbidden?
- Are modules mixins, namespaces, or both?

### Blocks
- Are blocks closures?
- Can blocks escape their defining scope?
- Are block parameter types inferred?
- Are closures heap allocated only when necessary?

### Arrays
- Are arrays mutable?
- Is `Array[T]` homogeneous?
- Are primitive arrays packed/unboxed?

### Exceptions
- Are exceptions dynamically typed but statically declared?
- Or is `raise` unrestricted?
- Are exceptions implemented using native unwinding?

### Numeric types
- Is `Integer` arbitrary precision?
- What is the default integer literal type?
- How do numeric conversions work?

### Strings
- UTF-8?
- Mutable or immutable?
- `String` versus byte arrays?

### Modules
- What Ruby module behavior survives?
- Is `include` retained?
- Is `extend` retained?
- Can modules define fields?

These decisions belong in `SEMANTICS.md`, not scattered throughout compiler code.

# 21. Performance Philosophy

Do not optimize the compiler before there is a working compiler.

The initial performance target is not "1000× Ruby."

The initial target is:

> Emerald's generated machine code should be capable of approaching ordinary optimized native code for statically typed workloads.

Benchmarks should eventually compare:

```text
Emerald
Rust
C
C++
Ruby
```

using equivalent algorithms and data representations.

Useful first benchmarks:

- integer summation
- sum of squares
- Fibonacci
- matrix multiplication
- array traversal
- string processing
- object allocation
- method dispatch
- recursive calls

Report both:

```text
runtime
binary size
compile time
memory usage
```

# 22. Engineering Rules

1. Keep the language specification ahead of the implementation.
2. Prefer deleting dynamic Ruby features over reproducing them with runtime machinery.
3. Reuse mature Rust crates.
4. Do not import another language's type system wholesale.
5. Keep compiler phases explicit.
6. Make errors excellent from the beginning.
7. Test every semantic rule.
8. Benchmark generated code against equivalent native implementations.
9. Avoid premature optimization in the compiler itself.
10. Keep the initial compiler small enough that one person can understand the entire pipeline.

# 25. Immediate Task for the Next AI

Do not jump straight into implementing the entire compiler.

Start by producing:

## A. `GRAMMAR.md`

Take the Ruby grammar as the starting point and produce a first Emerald grammar.

For every major Ruby grammar feature, mark:

```text
KEEP
MODIFY
REMOVE
UNDECIDED
```

Do not silently invent syntax.

## B. `SEMANTICS.md`

Define the static meaning of the first Emerald constructs.

## C. `TYPE_SYSTEM.md`

Define the initial primitive, class, collection, and function types.

## D. Parser prototype

Build the smallest parser capable of parsing:

```ruby
def add(a: Int64, b: Int64) -> Int64
  a + b
end
```

## E. Type checker

Make the compiler reject:

```ruby
def add(a: Int64, b: String) -> Int64
  a + b
end
```

with a useful diagnostic.

## F. Native code generation

Compile:

```ruby
def add(a: Int64, b: Int64) -> Int64
  a + b
end

puts add(20, 22)
```

to a native executable.

That is the first definition of "Emerald works."

# 26. Final Constraint

The project should remain small.

If a proposed feature causes a large runtime, complicated compiler subsystem, or substantial semantic machinery, stop and ask:

> Is this actually necessary to preserve Ruby's core character?

If not, remove it.

Emerald succeeds by making a decisive trade:

**Ruby's expressive surface and programming feel in exchange for static semantics and native compilation.**

The project should optimize for clarity, implementability, and native performance—not for compatibility with every behavior Ruby permits.
