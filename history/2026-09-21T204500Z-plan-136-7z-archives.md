# Plan 136 — 7-Zip Archive Support

This plan is explicitly the lowest-priority member of the 130-136
sub-batch, stated here rather than left implicit: 7z is a real,
still-used format (7-Zip itself remains popular on Windows, and 7z
archives show up in software-distribution and some backup-tooling
contexts), but it is far less common in the kind of programs an
Emerald user is likely to write than `.tar`/`.tar.gz` (plan 132,
Unix-world default) or `.zip` (plan 133, cross-platform default) —
this plan exists for completeness of this batch's compression/archive
coverage, not because 7z support is load-bearing for Emerald's own
strategic goals the way, say, plan 133's `Zip` plausibly is. Given that
framing, this plan's own honest job is verifying — not assuming — that
today's best available Rust 7z crate is actually solid enough to build
on, and reporting the real finding plainly either way.

## Concrete proof this plan targets

```ruby
Dir.mkdir("sevenz_demo_src")
File.write("sevenz_demo_src/a.txt", "hello")
File.write("sevenz_demo_src/b.txt", "world, a longer second file")

paths: Array[String] = ["sevenz_demo_src/a.txt", "sevenz_demo_src/b.txt"]
SevenZip.create("demo.7z", paths)

reader: SevenZipReader = SevenZipReader.open("demo.7z")
n: Int64 = reader.entry_count()
puts n
i: Int64 = 0
while i < n
  puts reader.entry_name(i)
  puts reader.read_entry_data(i).to_string()
  i += 1
end
reader.close()

SevenZip.extract("demo.7z", "sevenz_demo_out")
restored: String = File.read("sevenz_demo_out/sevenz_demo_src/a.txt")
puts restored == "hello"
```

Expected output: `2`, `sevenz_demo_src/a.txt`, `hello`,
`sevenz_demo_src/b.txt`, `world, a longer second file`, `true` —
structurally the identical create/list/extract proof shape plan 133
used for `.zip`, since 7z's own real header/central-directory-style
structure supports the same up-front `entry_count()` plan 133's `.zip`
does (see Decision log).

## Decision log

- **The crate to depend on is the *fork*, `sevenz-rust2`, not the
  name-obvious original `sevenz-rust` — verified directly, not assumed
  from either crate's name alone, and this is the single most
  important finding of this plan's research.** Read this session, in
  full, from `hasenbanck/sevenz-rust2`'s current README: "This is a
  fork of the original, unmaintained sevenz-rust crate to continue the
  development and maintenance." The fork's own GitHub repository
  metadata (fetched this session) shows a `pushed_at` timestamp of
  2026-09-18 — one day before this session — 117 stargazers, 31 forks,
  actively open issues; the original `dyz1990/sevenz-rust` repository
  path no longer resolves the same way on GitHub's API as of this
  session's check, consistent with the fork's own "unmaintained"
  characterization of it. Per plan 95's policy (name the real, current,
  best-maintained option explicitly, don't default to whichever name
  sounds canonical), this plan names `sevenz-rust2` as the dependency,
  not `sevenz-rust`.
- **The honest maturity finding is materially better than the task's
  own initial \"lower-priority/stretch-tier, possibly immature or
  narrowly-scoped\" framing predicted — stated plainly rather than
  either overselling or reflexively repeating that framing unchecked.**
  `sevenz-rust2`'s own README (read this session) documents a real
  codec support matrix: COPY, LZMA, LZMA2, BZIP2, and PPMD support both
  decompression *and* compression unconditionally; BROTLI, DEFLATE,
  LZ4, and ZSTD support both directions too, gated behind optional
  Cargo features. It supports AES-encrypted archives (`decompress_
  file_with_password`/`compress_to_path_encrypted`), solid compression,
  and configurable per-content encoder methods (`ArchiveWriter::set_
  content_methods`) — genuinely more complete, on both the read *and*
  write side, than this plan's own original stretch-tier framing
  assumed going in. This plan's v1 scope (below) is nonetheless kept
  deliberately narrow — not because the crate can't do more, but
  because this plan's own priority tier doesn't justify building out
  every codec/encryption combination the crate makes available.
- **v1 codec scope is COPY/LZMA/LZMA2/BZIP2/PPMD only — the crate's own
  always-available set, with `default-features = false` explicitly
  declining BROTLI/DEFLATE/LZ4/ZSTD.** Those four optional codecs are
  real, but each would mean either a second, independent binding to a
  format this sub-batch already vets elsewhere (plan 130's `flate2` for
  DEFLATE, plan 131's `zstd` for ZSTD, plan 134's `lz4_flex` for LZ4,
  plan 135's `brotli` crate for BROTLI) or accepting whatever pure-Rust-
  vs-C-backed implementation `sevenz-rust2` itself chooses for each —
  a real, separate vetting question this stretch-tier plan declines to
  chase down four times over. A 7z archive using one of those four
  methods (produced by real 7-Zip itself, which supports all of them)
  would fail to extract under this plan's v1 feature set — a real,
  disclosed gap, not silent data loss (the crate surfaces a real
  unsupported-codec error, per plan 92's convention).
- **No AES encryption support in v1** — matching plan 133's identical
  call for `.zip`'s own `aes-crypto` feature, for the same reason:
  `sevenz-rust2`'s encrypted-archive API needs a password threaded
  through both create and extract call sites, real cryptographic
  surface this stretch-tier plan does not build out for its first
  landing.
- **`SevenZipReader` is index-based, mirroring plan 133's `ZipReader`
  rather than plan 132's iterator-shaped `TarReader` — a real,
  format-driven choice, not an arbitrary pick.** 7z's own container
  format (like zip's, unlike tar's) stores a structured header
  describing every entry before the compressed content streams begin,
  so `sevenz_rust2::ArchiveReader`'s own real API exposes entries as an
  enumerable, indexable collection rather than requiring sequential
  advancement through the compressed stream to discover each one — the
  same structural reason plan 133 gave for `ZipReader`'s own shape,
  applied here because it is true of this format too, not copied
  reflexively.
- **`leaf-create-archive`/`leaf-rust-tests-and-proof-example` both
  state an explicit fallback (read-only v1, using a checked-in fixture
  `.7z`) rather than asserting the create-side API will land exactly as
  drafted — a real, disclosed uncertainty this plan does not paper
  over.** This plan's own research verified `sevenz_rust2::decompress_
  file`'s real, simple signature directly from the crate's current
  README, but the *write* side's exact ergonomics against this batch's
  `Array[String]`-of-explicit-paths convention (as opposed to the
  crate's own directory-tree-oriented `compress_to_path`/`push_source_
  path` helpers, which the README's own worked examples show operating
  on a whole source *directory*, not an explicit file list the way
  plan 132's/133's `Array[String]` convention does) was not fully
  proven against real compiled Rust this session. Stating this
  uncertainty explicitly, with a real fallback plan (read-only v1,
  matching this plan's own "far less commonly needed" priority framing
  honestly), follows plan 91's own precedent of marking a genuinely
  unverified detail as such rather than asserting a confident design
  that EXECUTE might then have to walk back.
- **Out of scope.** BROTLI/DEFLATE/LZ4/ZSTD codec support (above), AES
  encryption (above), solid-archive-specific tuning, dictionary/
  training data, WASM target support (the crate's own README documents
  a real, separate `default_wasm` feature set this plan does not
  adopt), and — if `leaf-create-archive`'s fallback triggers — archive
  creation of any kind, deferred to a future plan revision once the
  crate's write-side API is verified against real compiled code rather
  than README examples alone.
