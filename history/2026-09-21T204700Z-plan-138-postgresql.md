# Plan 138 — PostgreSQL

Postgres is the plan-95 pure-Rust-first policy working exactly as
intended, not an exception to it. Postgres's client/server wire protocol
(the "frontend/backend protocol," major version 3) is a public,
documented specification — a Postgres client never needs to link
`libpq` or any other C code to speak it correctly, only to implement the
message framing and authentication handshake the spec describes. The
`rust-postgres` project (`tokio-postgres` plus its synchronous wrapper
`postgres`) is exactly that: a from-scratch Rust implementation of the
protocol, checked this session — `tokio-postgres` `0.7.18` (Jun 2026),
MIT/Apache dual-licensed, 6.1M downloads/month, depended on directly or
transitively by 1,592 crates, maintained by Steven Fackler (the original
`rust-postgres` author) and Paolo Barbolini with 96 contributors. No C
toolchain, no bundled or system Postgres client library, nothing plan
137's SQLite exception had to accept. This plan wraps the synchronous
`postgres` crate specifically (not `tokio-postgres` directly) — `postgres`
is `tokio-postgres` with a dedicated background Tokio runtime already
built in, blocking the calling thread per call, which is precisely the
async-to-sync bridging shape plan 94 sets as this project's general
convention for wrapping async-native Rust database crates. This plan
gets that bridge for free by choosing the crate that already built it,
rather than re-deriving it against raw `tokio-postgres`.

## Concrete proof this plan targets

```ruby
conn: Int64 = Postgres.connect("host=localhost user=postgres dbname=emerald_demo")
Postgres.execute_direct(conn, "CREATE TABLE IF NOT EXISTS users (id SERIAL PRIMARY KEY, name TEXT NOT NULL, age INTEGER NOT NULL)")

insert: Int64 = Postgres.prepare(conn, "INSERT INTO users (name, age) VALUES ($1, $2)")
Postgres.bind_string(insert, 1, "Ada")
Postgres.bind_int64(insert, 2, 30)
Postgres.execute(insert)

select: Int64 = Postgres.prepare(conn, "SELECT name, age FROM users WHERE age > $1")
Postgres.bind_int64(select, 1, 18)
cursor: Int64 = Postgres.query(select)
while Postgres.step(cursor)
  name: String = Postgres.column_string(cursor, 0)
  age: Int64 = Postgres.column_int64(cursor, 1)
  puts name
  puts age
end
Postgres.close(conn)
```

Expected output: `Ada` then `30` — a row inserted through `$1`/`$2` bound
parameters (never a formatted SQL string) and read back through a
parameterized, comparison-filtered `SELECT`. Running this example for
real requires a reachable Postgres server (see the testing leaf below for
how CI provides one) — it is not, unlike plan 137's in-memory SQLite
proof, runnable with zero external state.

## Decision log

- **This is the batch's clean pure-Rust case, verified rather than
  assumed — the direct contrast plan 95's crate-vetting policy exists to
  draw.** Postgres's wire protocol needs no C engine linked into the
  process the way SQLite's file format does (plan 137) — a client only
  ever exchanges protocol messages over a socket with a server process
  running elsewhere. `tokio-postgres`'s own `lib.rs` package listing
  shows no C source at all (12K SLoC, entirely Rust), confirming the
  implementation is native end to end, not a Rust wrapper around a
  vendored `libpq`.
- **Parameterized queries are the only path that exists, mirroring plan
  137's posture exactly.** Postgres's native placeholder syntax is
  numbered (`$1`, `$2`, ...), not positional `?` — `Postgres.bind_*`
  writes into an owned parameter buffer keyed by that same numbering,
  applied through `postgres_types::ToSql` at `execute`/`query` time.
  `Postgres.execute_direct(conn, sql)` exists only for parameter-free DDL
  (matching plan 137's `execute_direct`), and no function in this surface
  accepts a SQL string with a caller-supplied value already interpolated
  into it.
- **The statement/cursor handle model reuses plan 137's buffered
  convention deliberately, for calling-convention uniformity — not
  because `postgres`'s own types force it.** `tokio_postgres::Statement`
  is in fact an owned, `'static`, cheaply-cloneable handle (an `Arc`-
  backed reference to server-side prepared-statement state), unlike
  `rusqlite::Statement<'conn>` — Postgres's Rust client does not have
  plan 137's self-referential-lifetime problem at all. This plan still
  stores only owned SQL text and a parameter buffer at `prepare` time,
  and still eagerly materializes every row into an owned `Vec<Vec<
  PgValue>>` at `query` time, so that plan 92's calling convention can
  describe one statement/cursor lifecycle shared by every SQL driver in
  this batch (137, 138, 139) instead of three subtly different per-
  driver contracts. Caching the real `tokio_postgres::Statement` across
  calls (avoiding a live server-side re-parse on every `execute`/`query`)
  is a real, available optimization this plan defers — see Not yet
  decided.
- **Type mapping is a real, disclosed narrowing — Postgres has dozens of
  column types, Emerald's `Type` enum has five relevant members
  (`Int64`, `Float64`, `String`, `Boolean`, plus `Array`/`Hash` for
  collections, none of them usable here — see next bullet).** The
  mapping this plan commits to: every Postgres integer width (`smallint`/
  `integer`/`bigint`) widens to `Int64`; `real`/`double precision`
  narrow to `Float64` directly; `numeric`/`decimal` also map to
  `Float64`, a disclosed, real precision loss (Postgres's arbitrary-
  precision decimal narrowed to an IEEE-754 double) — a caller needing
  exact decimal semantics must round or cast Postgres-side, this plan
  does not add a decimal type to carry it losslessly; `text`/`varchar`/
  `char`/`bpchar`/`name`/`uuid`/`date`/`time`/`timestamp`/`timestamptz`/
  `interval` all stringify to `String` (Postgres's own text-output
  format for each type, via `ToSql`/`FromSql`'s text-mode conversion) —
  Emerald has no `Date`/`Time` type as of this plan, so a timestamp
  column's timezone/precision information survives only as much as its
  string rendering carries it; `boolean` maps directly to `Boolean`;
  `json`/`jsonb` route through plan 118's dynamic JSON value type,
  whatever shape that plan settles on (a genuine forward reference — plan
  118 is authored in parallel this batch).
- **Postgres array columns (`integer[]`, `text[]`, ...) are declined,
  not silently coerced — the same `Array[T]`-has-no-runtime-length wall
  plan 45 already documented, hit from a new direction.** `emerald-
  codegen`'s `Array[T]` representation carries no length metadata (plan
  45's own finding, verified against `build_array_lit`'s doc comment);
  a Postgres array column's element count is only known at query time,
  so there is no honest way to materialize it into an `Array[T]` this
  compiler's existing `for`-`in`/indexing machinery could safely consume.
  Rather than inventing a parallel `Hash[Int64, T]`-indexed encoding
  (which plan 140's Redis list mapping does adopt, see that plan's own
  Decision log for why the tradeoff reads differently for Redis), this
  plan simply declines array-typed columns: `column_string`/`column_
  int64`/etc. on an array-typed column is a plan-93 error naming the
  column's real Postgres type, and the documented workaround is
  `unnest()`-ing the array in the SQL query itself so each element
  arrives as its own scalar row — a real SQL idiom, not a workaround
  invented for this plan.
- **`bytea` is out of scope for the same reason plan 137 declined
  `BLOB`.** No `Bytes`/`Blob` type exists in Emerald's real `Type` enum
  (verified, plan 59); `column_string` on a `bytea` column is a plan-93
  error rather than a silently-invalid-UTF-8 `String`. Both this plan
  and plan 137 wait on the same future cross-cutting `Bytes` type,
  should one land.
- **TLS is out of scope for v1 — `postgres::NoTls` is the only connector
  this plan wires up, a real and disclosed limitation, not an oversight
  left unstated.** `tokio-postgres` requires an explicit `TlsConnector`
  implementation (`postgres-native-tls` or `postgres-openssl`/`tokio-
  postgres-rustls`) to speak `sslmode=require`/`verify-full` — none of
  those crates is pulled in by this plan. `Postgres.connect` therefore
  only reaches a server accepting plaintext connections (a local
  database, or one reached over an already-trusted network/tunnel). A
  later plan pairing this driver with a TLS crate (the same kind of
  work plan 100/106's HTTP-client plans would need for HTTPS) is the
  honest place to add `sslmode=require` support — not silently assumed
  to already work here.
- **Out of scope.** Connection pooling (one `Postgres.connect` call is
  one dedicated `postgres::Client`; no pool multiplexes several
  `.query()` callers over shared connections — a cross-driver concern,
  not this plan's), `LISTEN`/`NOTIFY` and the `COPY` protocol (both real,
  substantial `tokio-postgres` features this plan's scalar query/execute
  surface doesn't reach), migrations, and any row-to-class-instance
  mapping or query-builder layer — this is a driver, not an ORM.
