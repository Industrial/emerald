# Plan 186 — WebAuthn/FIDO2 (Stretch)

**This plan is explicitly stretch-tier — flagged plainly here, not
discovered halfway through.** WebAuthn is a genuinely more involved
protocol than nearly anything else in this batch: a *ceremony* (not a
single request) with a browser-generated challenge, a hardware
authenticator's signed attestation or assertion response, origin and
relying-party-ID binding checks that exist specifically to defeat
phishing, and — in the full W3C spec — a whole taxonomy of attestation
statement formats (`packed`, `fido-u2f`, `android-key`,
`android-safetynet`, `tpm`, `apple`, `none`) each with its own
certificate-chain-verification logic. `webauthn-rs` implements all of
that faithfully because a real relying-party server must be able to.
This plan does not attempt to expose all of it. It scopes v1 to
exactly the path `webauthn-rs`'s own tutorial recommends as the modern
default — **passkeys**, `attestation = none` (no attestation-chain
verification, the browser/authenticator's own default and the shape
every "sign up with a passkey" flow on the modern web actually uses) —
and defers the advanced attestation-format-specific verification paths
named above entirely. A caller who genuinely needs enterprise-grade
attestation policy (e.g. "only accept credentials from this specific
YubiKey model batch") is not served by this plan's v1 surface.

Depends on: plan 91 (`emerald-rt` archive), plan 92 (`catch_unwind`
convention, `NativeError`, `Result[T,E]` helpers), plan 93 (opaque-
handle resource model — `WebauthnRp`, `RegistrationChallenge`,
`AuthenticationChallenge`, `PasskeyCredential` are all handle-carrying
resources), plan 95 (crate-vetting policy and checklist), and plan 100
(cited for architectural completeness, not code reuse: a real WebAuthn
relying party is normally embedded inside an HTTP server that serves
the challenge JSON to a browser and receives the response JSON back —
this plan provides the ceremony logic; wiring it to an actual HTTP
server built on plan 100 is application code, not this plan's own
scope, see Out of scope).

## Concrete proof this plan targets

Using `webauthn-rs`'s own virtual-authenticator test support (or an
equivalent fixed fixture pair) to stand in for a real browser/security
key, so the proof is fully deterministic in CI:

```ruby
rp: WebauthnRp = WebauthnRp.new("localhost", "http://localhost:8080", "Emerald Test RP")

reg_challenge: RegistrationChallenge = rp.start_registration(
  "11111111-1111-1111-1111-111111111111",
  "alice",
  "Alice Example"
)
challenge_json: String = reg_challenge.challenge_json()
puts challenge_json.length > 0

synthetic_response: String = simulate_authenticator_registration(challenge_json)
reg_result: Result[PasskeyCredential, String] = rp.finish_registration(reg_challenge, synthetic_response)

case reg_result
when Ok(credential)
  puts "registered"

  auth_credentials: Array[PasskeyCredential] = [credential]
  auth_challenge: AuthenticationChallenge = rp.start_authentication(auth_credentials, 1)
  auth_json: String = auth_challenge.authentication_challenge_json()
  synthetic_auth_response: String = simulate_authenticator_authentication(auth_json)

  auth_result: Result[Boolean, String] = rp.finish_authentication(auth_challenge, synthetic_auth_response)
  case auth_result
  when Ok(ok)
    puts ok
  when Err(msg)
    puts msg
  end
when Err(msg)
  puts msg
end
```

(`simulate_authenticator_registration`/`simulate_authenticator_
authentication` stand in for the test harness's virtual-authenticator
fixture generator, not real Emerald-callable functions this plan ships
— the actual test lives in `emerald-rt`'s own `#[test]` suite, driving
`webauthn-rs` directly on the Rust side to produce the fixture JSON a
real browser's `navigator.credentials.create()`/`.get()` would return,
per `leaf-example-and-gate`.) Expected output: `true` (a non-empty
challenge JSON was produced), `registered`, then `true` (the
authentication ceremony verifies against the just-registered
credential).

## Decision log

- **Passkeys, not the lower-level generic-credential API — `webauthn-
  rs`'s own recommended entry point, not this plan's invention.**
  Verified against `webauthn-rs` 0.5.5's own published documentation
  (docs.rs, this session): the crate exposes both a lower-level, more
  configurable `Webauthn::start_securitykey_registration`/generic
  credential path and a higher-level, opinionated `start_passkey_
  registration`/`Passkey` path the crate's own tutorial recommends as
  "what is a 'Passkey'?" — synced, discoverable, multi-device
  credentials, the shape virtually every modern "create a passkey"
  browser prompt produces by default. This plan wraps the passkey path
  specifically because it is both the simpler API surface and the one
  that matches what a caller integrating with real, current browsers
  will actually encounter.
- **`attestation = none` (the default) — no attestation-chain
  verification in v1, named explicitly rather than silently
  implied.** WebAuthn attestation lets a relying party cryptographically
  verify *what kind* of authenticator generated a credential (a
  specific hardware security key model, a platform authenticator, etc.)
  via a certificate chain back to a manufacturer root. Verifying that
  chain correctly requires maintaining or fetching a trust-anchor set
  (the FIDO Metadata Service, or per-vendor root certificates) — real,
  substantial, separately-scoped infrastructure this plan does not
  build. `webauthn-rs`'s own default behavior already tolerates `none`
  attestation (the overwhelming majority of real passkey flows use it,
  since most consumer browsers do not send a verifiable attestation
  statement by default for privacy reasons), so this plan's v1 simply
  does not ask for more than the crate's own default already checks
  (challenge freshness, origin binding, relying-party-ID binding,
  signature validity) — real security guarantees, just not the
  additional, optional attestation-provenance layer.
- **Credential storage is entirely the caller's responsibility — this
  module holds no database.** `PasskeyCredential.to_json`/`from_json`
  exist specifically so an Emerald application can persist a registered
  credential itself (a real SQL/KV store, a flat file — whatever that
  application already uses) between the registration ceremony and every
  future authentication ceremony. `WebauthnRp` itself is stateless
  across ceremonies beyond its own fixed relying-party configuration;
  it does not remember which users have which credentials. This mirrors
  plan 185's identical split for OAuth2 session/state storage, for the
  same reason: a crate wrapper inside `emerald-rt` has no legitimate
  place to keep a caller's durable user data, and inventing one would
  make this module a de facto (and unreviewed, unvetted-as-a-database)
  persistence layer.
- **The ephemeral per-ceremony state (`PasskeyRegistration`/
  `PasskeyAuthentication`) gets its own opaque handle, exactly like
  plan 185's PKCE verifier — the same structural reason, restated for
  this plan's own ceremony shape.** `webauthn-rs`'s own API returns
  this state from `start_*` and requires the *exact same* value back
  at `finish_*` — it is not reconstructible from the challenge JSON
  alone (it includes server-generated randomness the client never
  sees). A real deployment would serialize this state into a signed,
  short-lived session token spanning the two ceremony legs — this
  plan's own `RegistrationChallenge`/`AuthenticationChallenge` handle
  types are the in-process stand-in for that, with the same caveat
  plan 185 names for its own auth-request handle: a caller whose two
  ceremony legs cross a process boundary (a load-balanced web server,
  say) must serialize this state itself, which is why `webauthn-rs`'s
  own registration/authentication-state types are already `serde`-
  serializable — a future leaf could expose that serialization surface
  directly if a real caller needs it, not attempted in this plan's v1.
- **`webauthn-rs`, verified current this session.** Version 0.5.5,
  published 12 July 2026, maintained by the Kanidm project team
  (`Firstyear`/`yaleman`/`micolous`) under the MPL-2.0 license — note
  the license explicitly, since it differs from the MIT/Apache-2.0 dual
  license most other crates in this batch use; plan 95's crate-vetting
  ledger should record this as a real, disclosed license variance to
  check against the project's own license-compatibility policy, not
  silently assumed identical to every other dependency.
- **Out of scope.** Non-passkey security-key-specific ceremonies
  (`start_securitykey_registration` and its user-verification-optional
  variants) — a real, different API surface `webauthn-rs` exposes,
  deferred entirely. Attestation-format-specific verification beyond
  `none` (`packed`/`fido-u2f`/`android-key`/`android-safetynet`/`tpm`/
  `apple`) — named explicitly above, not attempted. The FIDO Metadata
  Service integration needed to make attestation verification actually
  useful in practice — a separate, substantial trust-anchor-management
  feature. Any browser-side JavaScript, HTML, or HTTP server wiring —
  this plan hands back and consumes JSON strings only; serving them to
  a real browser via plan 100's HTTP client/server surface is
  application code this plan does not write or ship. Conditional UI /
  username-autocompletion support (a `webauthn-rs`-documented, real,
  separate browser-integration feature) — not exposed.
