# Plan 134 — LZ4 Compression

LZ4 exists in this sub-batch for a genuinely different reason than
gzip/deflate/zlib (plan 130) or zstd (plan 131): it is not chasing
compression ratio at all. LZ4's whole design premise — verified against
its real behavior this session via `lz4_flex`'s own published
benchmarks — trades ratio for raw throughput: on the maintainer's own
10MB "dickens" benchmark corpus, `lz4_flex`'s safe build compresses at
259 MiB/s and decompresses at 2338 MiB/s, an order of magnitude faster
than either plan 130's DEFLATE or plan 131's zstd would manage on
comparable hardware, at a correspondingly worse compression ratio
(0.6372 vs zstd's typically-tighter output at equivalent effort). The
real use case this format serves is fast in-memory or over-the-wire
compression where CPU time is the scarce resource and a somewhat larger
payload is an acceptable trade — the opposite end of the tradeoff plan
131's `Zstd` occupies, and this plan states that contrast explicitly
rather than presenting `Lz4` as "gzip but different."

## Concrete proof this plan targets

```ruby
original: Bytes = "the quick brown fox jumps over the lazy dog, the quick brown fox jumps over the lazy dog".to_bytes()
compressed: Bytes = Lz4.compress(original)
puts compressed.length < original.length
restored: Bytes = Lz4.decompress(compressed)
puts restored == original

empty: Bytes = "".to_bytes()
puts Lz4.decompress(Lz4.compress(empty)) == empty
```

Expected output: `true`, `true`, `true` — the same round-trip shape as
plans 130/131 (real compression happened, real decompression recovers
the exact original bytes), plus an explicit zero-length-input edge
case, since `compress_prepend_size`/`decompress_size_prepended`'s own
size-header convention is exactly the kind of mechanism a length-zero
input could plausibly break if implemented carelessly — this plan's own
Rust-side `#[test]` suite (`leaf-rust-tests-and-proof-example`) checks
this same case directly against the real crate, not only through the
compiled Emerald proof.

## Decision log

- **`lz4_flex` is pure Rust, verified directly, not inferred from the
  absence of a `-sys` crate in its name.** Read this session, in full,
  from `PSeitz/lz4_flex`'s real `README.md`: "Fastest LZ4 implementation
  in Rust... Originally based on redox-os' lz4 compression, but now a
  complete rewrite." Its own benchmark section explicitly compares
  itself against `lzzz` — labeled in the same README as "the c version
  via rust bindings" (`crates.io/crates/lzzzz`) — as a *competing,
  separate* crate, not a dependency of `lz4_flex` itself; `lz4_flex`
  beats or closely matches that C-bound competitor's own numbers on the
  maintainer's own hardware (e.g. 259 vs 324 MiB/s compression, but
  2338 vs 2759 MiB/s decompression on the 10MB corpus — genuinely
  competitive, not merely "acceptable for a pure-Rust fallback"). Per
  plan 95's policy, this is an easy, clean pure-Rust call precisely
  because the pure-Rust option is not a compromise here — it is
  reported by its own author to be the fastest LZ4 implementation in
  the Rust ecosystem, C-bound competitors included.
- **The older `lz4` crate is the real C-backed alternative this plan
  explicitly declines, named for the same reason plan 131 named
  `zstd`.** `crates.io/crates/lz4` (distinct from `lz4_flex`) wraps
  `liblz4` via `lz4-sys`, the original and — for years — the only
  well-known Rust LZ4 binding. `lz4_flex`'s own README frames itself as
  the newer, from-scratch, benchmark-competitive replacement rather
  than a "good enough" pure-Rust stand-in for that older binding. This
  plan picks `lz4_flex` deliberately over `lz4` — the direct pure-Rust-
  preferred call plan 95's policy asks every plan in this batch to make
  explicitly, here backed by real, checkable throughput numbers rather
  than a policy default alone.
- **`safe-encode`/`safe-decode` are kept enabled, not dropped for the
  `unsafe`/faster path — a deliberate conservatism matching plan 130's
  own `miniz_oxide`-over-`zlib-rs` choice.** `lz4_flex`'s README states
  plainly: with the default `safe-encode`/`safe-decode` features,
  "Compression and decompression uses no unsafe." Disabling them (`--no-
  default-features --features alloc`, per the crate's own documented
  "Performance" configuration) trades a real, measured throughput gain
  — the crate's own benchmark table shows roughly 25-35% faster
  compression with `unsafe` enabled (1615 vs 1272 MiB/s on the 66KB
  JSON corpus) — for `unsafe` Rust code inside `emerald-rt`'s
  dependency graph. Given `Lz4`'s whole value proposition is already
  "fast enough for CPU-bound hot paths," and the safe build is already
  an order of magnitude faster than plan 130's/131's alternatives at
  their own tasks, this plan does not spend that additional `unsafe`
  risk for a further 25-35% here — the same reasoning, applied
  consistently, that picked `miniz_oxide` over `zlib-rs` for plan 130.
  A future `Lz4.compress_unchecked`-style opt-in fast path is a
  plausible, disclosed follow-up, not built here.
- **Two distinct on-disk shapes exist inside this one crate — block
  format (one-shot API) and frame format (streaming API) — and this
  plan uses both deliberately rather than picking one for everything.**
  `lz4_flex`'s own README is explicit that the block format "is only
  valid for smaller data chunks as [it] is de/compressed in memory,"
  while "For larger data use the frame format, which consists of
  multiple blocks." This plan's one-shot `Lz4.compress`/`Lz4.decompress`
  uses the block format (`compress_prepend_size`/
  `decompress_size_prepended`, the crate's own documented pairing,
  self-describing length with zero extra Emerald-level bookkeeping);
  its streaming `Lz4Writer`/`Lz4Reader` uses the frame format
  (`lz4_flex::frame::{FrameEncoder,FrameDecoder}`) specifically because
  the block format's own documented "compressed in memory" limitation
  makes it structurally unsuitable for the same large-payload streaming
  case plan 93's handle model exists to serve. A block-format buffer
  fed to the frame-format decoder (or vice versa) fails to parse — a
  real, expected, plan-92-surfaced error, not a silent misread, since
  the two formats' magic bytes/framing differ entirely.
- **No `no_std`/no-allocator build variant exposed in v1, despite
  `lz4_flex` genuinely supporting one.** The crate's README documents
  real `no_std` support for the block format (with a further
  no-allocator mode for embedded targets) — not relevant to
  `emerald-rt`'s own build, which already links against Rust's full
  standard library (plan 91's own `emerald-rt` crate has no `no_std`
  aspirations; `runtime/emerald_runtime.c` itself assumes a hosted
  libc environment). This is named here only so a reader does not
  mistake its omission for an oversight — it is a real capability this
  plan's own target environment has no use for.
- **No LZ4HC (high-compression mode) surface in v1.** The real LZ4
  ecosystem includes an "HC" (high compression) variant trading
  compression speed for a better ratio, closer to (but still below)
  zstd's territory — `lz4_flex`'s own roadmap lists "High compression"
  under its own stated `TODO`, meaning the crate itself does not yet
  offer it as of the version this plan pins. There is nothing to bind
  to even if this plan wanted to; `Lz4.compress` uses the crate's one
  real, available compression path.
- **Out of scope.** No LZ4HC (above, genuinely unavailable upstream as
  of this session), no `no_std` build variant (above, not applicable to
  this target), no unsafe/`checked-decode`-toggle fast path (above,
  deliberately declined), no dictionary support, no multi-threaded
  compression. `.tar.lz4` composition, if ever wanted, follows plan
  132's established `Tar`-plus-compression-format layering exactly —
  not built here.
