# Plan 185 — OAuth2 Client Flow

"Log in with Google" / "Log in with GitHub" is the authorization-code
grant: a program redirects a user's browser to a provider's login page,
the provider redirects back with a short-lived authorization code, and
the program exchanges that code — server-to-server, over a request the
user's browser never sees — for an access token. This plan wraps
`oauth2-rs`, the standard, strongly-typed Rust implementation of RFC
6749's authorization-code grant plus RFC 7636's PKCE extension, as an
`OAuth2Client` resource type built on this batch's own plan 100 (HTTP
transport for the token-exchange call) and plan 113 (CSPRNG for the
state token and PKCE verifier — both must be unguessable, and both are
exactly the kind of value this project's blessed randomness source, not
an ad hoc seed, must produce).

Depends on: plan 91 (`emerald-rt` archive), plan 92 (`catch_unwind`
convention, `NativeError`, `Result[T,E]` construction helpers for the
token-exchange failure path), plan 93 (opaque-handle resource model for
`OAuth2Client`/`OAuth2AuthRequest`/`OAuth2Token`), plan 95 (crate-vetting
policy and checklist), plan 100 (the `ureq`-backed HTTP transport
`oauth2-rs`'s own synchronous client feature rides on for the real
token-endpoint network call), and plan 113 (CSPRNG — `oauth2-rs`'s own
`CsrfToken::new_random`/`PkceCodeChallenge::new_random_sha256` calls
depend on a real, unpredictable randomness source under the hood, the
same project-wide blessed source plan 113 establishes, not a second,
independently-chosen RNG).

## Concrete proof this plan targets

Against a fixed local mock token endpoint (started by the test harness
itself, listening on a fixed port, returning a canned JSON access-token
response for one specific, expected authorization code and a 400 error
for any other):

```ruby
client: OAuth2Client = OAuth2Client.new(
  "test-client-id",
  "test-client-secret",
  "http://127.0.0.1:9931/authorize",
  "http://127.0.0.1:9931/token",
  "http://127.0.0.1:8080/callback"
)

scopes: Array[String] = ["profile", "email"]
auth_request: OAuth2AuthRequest = client.begin_auth(scopes, 2)

url: String = auth_request.authorization_url()
puts url

state: String = auth_request.state()
puts state.length > 0

exchange_result: Result[OAuth2Token, String] = client.exchange_code(auth_request, "fixed-test-code")

case exchange_result
when Ok(token)
  puts token.access_token()
when Err(msg)
  puts msg
end
```

Expected output: a real `authorization_url` string beginning
`http://127.0.0.1:9931/authorize?response_type=code&client_id=test-client-id&...`
and containing real `code_challenge`/`code_challenge_method=S256`/
`state` query parameters (proving PKCE and CSRF-state were genuinely
attached, not merely claimed); `true` (the generated state string is
non-empty); and the mock server's own fixed access-token literal (e.g.
`mock-access-token-12345`) from the `Ok` branch — a real, working proof
that a PKCE-paired authorization URL was built and that the matching
verifier was later presented correctly at token-exchange time, since
the mock server itself can be configured to reject the exchange if the
`code_verifier` it receives doesn't hash (SHA256, base64url) to the
`code_challenge` it saw in the authorization step.

## Decision log

- **PKCE is structural, not optional — the plan's central security
  requirement, enforced by API shape rather than by convention.** The
  authorization-code-interception attack PKCE (RFC 7636) exists to stop
  is concrete and well-documented: a public client (one that cannot keep
  a secret confidential — and any client embedding a secret directly in
  distributed Emerald source, as this plan's own `client_secret`
  parameter technically allows, should still be treated as one for this
  purpose) has its redirect intercepted by a malicious app on the same
  device, which steals the authorization code and exchanges it itself
  before the legitimate client can. PKCE closes this by binding the
  authorization request to a verifier only the legitimate client ever
  held, checked at token-exchange time. `begin_auth` is this module's
  *only* authorization-URL-building function, and it has no parameter
  or code path that skips generating and attaching a PKCE challenge —
  a caller cannot construct a non-PKCE authorization request through
  this API even by accident. This is a deliberate, stronger stance than
  "PKCE available, recommended" — it states plainly, as the task
  driving this plan requires, that PKCE is not an afterthought here.
- **`oauth2-rs`, verified current and HTTP-client-agnostic this
  session.** Version 5.0.0, published 7 August 2026, by a single
  long-standing maintainer (`ramosbugs`) — its own `Cargo.toml`
  (checked via docs.rs) lists `reqwest`, `ureq`, and `curl` all as
  *optional* dependencies behind separate feature flags, confirming the
  crate's core token-exchange logic is transport-agnostic; only the
  convenience synchronous-client wrapper this plan actually uses pulls
  in one of them. Pinning to the `ureq`-backed feature keeps this
  module's transport identical to plan 100's own HTTP client choice,
  rather than pulling a second HTTP stack (`reqwest`) into the archive
  for OAuth2's sake alone.
- **The state/CSRF token is returned to the caller, not stored by this
  module — session-storage is explicitly the caller's job.** A real
  web application's OAuth2 flow spans two separate HTTP requests to
  *that application* (the redirect-out, and the provider's later
  callback), typically seconds to minutes apart and often hitting a
  different server process/thread/replica in a load-balanced
  deployment. This module has no concept of an HTTP session and cannot
  safely assume the same `OAuth2AuthRequest` handle (a Rust-side,
  single-process, in-memory resource per plan 93's own handle model)
  is still alive or even in the same process by the time the callback
  arrives. `.state()` and, when needed, the raw PKCE verifier string
  are exposed as plain `String` values specifically so a real
  application can persist them itself (a session cookie, a server-side
  session store, a signed short-lived token) across that gap — this
  plan does not attempt to solve cross-request state persistence, which
  is an application-architecture concern outside any one crate wrapper.
- **`client_secret` is a required, non-optional constructor argument in
  v1 — the confidential-client shape only, not the public-client
  (no-secret) variant `oauth2-rs` also supports.** Most real Emerald
  programs using this module (a CLI tool, a desktop app, anything
  whose compiled binary a user runs locally) are, in OAuth2 terms,
  public clients that structurally *cannot* keep a secret confidential
  no matter what this API's type signature claims — embedding a secret
  in a distributed binary is not confidentiality. Exposing a secret-less
  constructor overload for that case is real, correct, additional
  scope this plan defers rather than rushes (seeAlso Not yet decided) —
  requiring a secret in v1 is the smaller, more conservative surface,
  even though it means a v1 caller with a genuinely public client must
  pass an empty string, a disclosed rough edge stated here rather than
  hidden.
- **Token refresh (`refresh_token` grant) is exposed as a field on
  `OAuth2Token`, not as a second grant-flow entry point.** `oauth2-rs`
  supports a full `.exchange_refresh_token()` flow; this plan's v1
  surfaces the refresh token *value* a successful exchange returns
  (`OAuth2Token.refresh_token(): Option[String]`) so a caller can persist
  it, but does not add a matching `OAuth2Client.refresh(...)` method to
  actually use it — deferred as a small, natural, separately-scoped
  follow-up once a real caller needs it, rather than speculative surface
  added to round out the type.
- **A failed token exchange is `Result`, not `NativeError` — the same
  expected-vs-unexpected-failure split plan 92 and plan 182 both already
  draw.** An authorization code being expired, already used, or
  rejected by the provider is a normal, anticipated outcome of a
  network protocol talking to a service outside this process's control
  — not a Rust-side bug. `exchange_code` therefore returns
  `Result[OAuth2Token, String]`, built via plan 92's own
  `emerald_rt_result_ok`/`emerald_rt_result_err` helpers, rather than
  raising.
- **Out of scope.** The OpenID Connect layer (ID tokens, `.well-known`
  discovery, JWT validation) — `oauth2-rs`'s own README explicitly
  points users wanting OIDC at the separate `openidconnect` crate built
  on top of it; this plan wraps the bare OAuth2 authorization-code
  grant only, not identity/authentication semantics on top of it.
  The implicit grant and resource-owner-password-credentials grant —
  both are legacy, actively discouraged-by-the-current OAuth2 Security
  Best Current Practice flows this plan deliberately does not surface,
  consistent with steering every caller toward the one flow (auth-code
  plus PKCE) that is actually recommended today. Token storage/
  persistence, automatic silent refresh, and any notion of a
  long-lived "logged in" session — all real application concerns this
  thin client wrapper does not attempt to own.
