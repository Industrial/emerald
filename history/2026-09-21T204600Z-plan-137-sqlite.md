# Plan 137 — SQLite

Every SQL-database plan in this batch (137, 138, 139) answers the same
question differently: how does Emerald reach a real database without
reimplementing one. Postgres and MySQL (plans 138, 139) get to answer it
the comfortable way — their wire protocols are public specifications with
mature, genuinely pure-Rust client implementations, so wrapping them adds
no C dependency at all. SQLite cannot answer it that way. SQLite is not a
server with a wire protocol; it is a C library that reads and writes a
file format directly, and the file format's only fully-conformant
implementation, then and now, is SQLite's own C source. This plan is
therefore this batch's one deliberate, expected exception to a
pure-Rust-first policy (plan 95) — and it earns that exception honestly,
by checking first whether the exception is still necessary.

Turso (the project formerly named `limbo`, renamed after its maintainers'
company) is a real, active attempt at exactly the pure-Rust SQLite
rewrite that would obsolete this plan's C dependency. It was checked
directly this session, not assumed away: as of 2026-09-11 its `turso`
crate on crates.io is at `0.8.0-pre.11` — a pre-release tag, seven
breaking changes recorded across its 127 published releases, no `1.0.0`
ever cut. Its own README, current as of this check, still pins its own
installation instructions to `turso = "0.4.3"` — an inconsistency between
the latest published version and the version the project's own docs tell
a new user to install, itself a signal of a project mid-churn rather than
settled. It is genuinely promising (100+ contributors, 175K downloads/
month and growing, an async-native Rust API, SQLite-file-format
compatibility as a stated design goal, optional cloud sync) — but
"promising and pre-1.0" is not "ready to be the one embedded-database
dependency this compiler's stdlib ships by default." `rusqlite`, by
contrast, checked the same session: `0.40.2` (Aug 2026), 74 releases, an
explicit `maintenance = { status = "actively-developed" }` badge in its
own `Cargo.toml`, 13M downloads/month, ranked `#1` in crates.io's
Database-interfaces category. This plan makes the real, checked call:
`rusqlite`, with its bundled C dependency disclosed and accepted, not
`turso`.

## Concrete proof this plan targets

```ruby
db: Int64 = Sqlite.open_memory()
Sqlite.execute_direct(db, "CREATE TABLE todos (id INTEGER PRIMARY KEY, title TEXT NOT NULL, done INTEGER NOT NULL)")

insert: Int64 = Sqlite.prepare(db, "INSERT INTO todos (title, done) VALUES (?, ?)")
Sqlite.bind_string(insert, 1, "write plan 137")
Sqlite.bind_int64(insert, 2, 0)
Sqlite.execute(insert)

select: Int64 = Sqlite.prepare(db, "SELECT id, title FROM todos WHERE done = ?")
Sqlite.bind_int64(select, 1, 0)
cursor: Int64 = Sqlite.query(select)
while Sqlite.step(cursor)
  id: Int64 = Sqlite.column_int64(cursor, 0)
  title: String = Sqlite.column_string(cursor, 1)
  puts id
  puts title
end
Sqlite.close(db)
```

Expected output: `1` then `write plan 137` — an in-memory database
created, a row inserted through a bound parameter (never a formatted
string), and read back through a prepared, bound `SELECT`, proving the
parameterized-only path round-trips correctly end to end with no file
left behind on disk.

## Decision log

- **`rusqlite`'s C dependency is bundled, not system-linked — a real,
  disclosed choice about which kind of C dependency this plan accepts.**
  Built with `features = ["bundled"]`, `libsqlite3-sys` compiles its own
  vendored SQLite amalgamation (`lib.rs`'s language breakdown for
  `rusqlite` shows 353K SLoC of C alongside 41K SLoC of Rust — the
  amalgamation itself) via `cc` at `emerald-rt`'s own build time, the
  same mechanism plan 91's `build.rs` already uses to compile `runtime/
  emerald_runtime.c`. No system `libsqlite3` package is required on the
  build machine or the end user's machine; this is a third C artifact
  compiled and statically linked into the same final binary plan 91
  already established two archives for (the hand-written C runtime, the
  Rust `emerald-rt` archive) — except this one arrives as an ordinary
  transitive Cargo dependency of `emerald-rt`, needing no new linking
  mechanism beyond what plan 91 already built.
- **Parameterized queries are the only path that exists — not merely the
  only one documented.** Every Emerald-facing function that can carry a
  caller-supplied value (`bind_string`/`bind_int64`/`bind_float64`/
  `bind_null`) writes into `rusqlite`'s own `?`-positional parameter
  slots (`Statement::raw_bind_parameter` under the hood), never into the
  SQL text itself. There is no `Sqlite.execute_direct(conn, sql_with_
  values)` overload that accepts anything but a literal string — the one
  `execute_direct` in this surface exists solely for parameter-free DDL
  (`CREATE TABLE`, `CREATE INDEX`) and is documented as such; nothing
  stops a caller from building an injection-vulnerable string in Emerald
  and passing it to `execute_direct` (there is no taint-tracking system
  in this compiler to catch that, an honest limitation, not a silent
  one), but every actual *value* — anything read from user input, a
  network request, a file — has no route into a query except through
  `bind_*`, which is the meaningful guarantee: the unsafe path requires
  actively misusing a DDL-only function, not the natural way to write a
  parameterized query.
- **A prepared statement holds no live `rusqlite::Statement` across FFI
  calls — a real Rust lifetime problem this plan resolves by buffering,
  not by fighting the borrow checker.** `rusqlite::Statement<'conn>`
  borrows its parent `Connection` for its own lifetime; if `Sqlite.
  prepare` tried to store a real `Statement` in a handle registry
  separate from its `Connection`'s own registry, the two would form a
  self-referential structure no safe Rust type can express without
  `unsafe` lifetime extension — sound only if something enforces that
  the statement is always dropped before its connection, which nothing
  in a plain handle-registry model does automatically. This plan avoids
  the problem instead of papering over it: `Sqlite.prepare` stores only
  owned data (the SQL text, an empty parameter buffer) with no
  `rusqlite` object at all; `Sqlite.execute`/`Sqlite.query` are the only
  two functions that ever call `conn.prepare(&sql)`, and they do so,
  bind, run, and — for `query` — eagerly drain every row into an owned
  `Vec<Vec<SqliteValue>>` (`SqliteValue` an internal enum of owned
  `String`/`i64`/`f64`/null, never a borrowed `&str`), all within that
  one function body, before the borrow ever has to survive a return.
  `Sqlite.step`/`Sqlite.column_*` afterward only ever touch that
  already-materialized, ordinary owned buffer through a cursor handle.
- **This is a disclosed, whole-result-set buffering strategy, not true
  streaming — a real limitation, stated plainly rather than implied
  away.** A `SELECT` returning a very large result set is pulled
  entirely into memory at `Sqlite.query` time, not row-by-row as
  `Sqlite.step` is called. This mirrors plan 45's own disclosed
  `.split`/`.split_count` two-full-scan inefficiency in spirit — an
  accepted, stated simplification chosen because it makes the FFI
  lifetime story sound with zero `unsafe`, not because streaming is
  impossible in principle. A later plan could add a true incremental
  cursor (holding a `rusqlite::Statement` behind an `unsafe`-justified
  lifetime extension, with `Sqlite.close` refusing to run while any
  cursor referencing it is still open) if a workload's memory profile
  ever demands it; this plan does not build that.
- **Result columns marshal through the same three scalar Rust FFI types
  plan 92 fixes for every domain plan — `Int64`, `Float64`, `String` —
  with SQLite's own dynamic column typing collapsed onto them.** SQLite
  columns are not statically typed (a `TEXT`-declared column can still
  hold an integer at the storage-engine level, SQLite's own well-known
  "type affinity" behavior); `Sqlite.column_int64`/`column_string`/
  `column_float64` therefore each perform `rusqlite`'s own `ValueRef`-
  to-requested-type coercion (`rusqlite::types::FromSql`) rather than
  asserting the column's declared type matches, erroring through plan
  93's error convention on a genuine coercion failure (e.g. calling
  `column_int64` on a column holding non-numeric text) instead of
  silently returning garbage or panicking across the FFI boundary.
- **Blob (`BLOB`) columns are out of scope for v1 — the same missing-
  `Bytes`-type gap plan 59 already found for C FFI's return-side trust
  boundary, now hit from the database-column direction instead.**
  Emerald's real `Type` enum (verified against `emerald-sema`'s actual
  definition, plan 59) has no byte-buffer type — `String` is defined as
  UTF-8, and a `BLOB` column's bytes are not guaranteed valid UTF-8 at
  all. `column_string` called on a `BLOB` column is a plan-93 error, not
  a silent, possibly-invalid UTF-8 `String`. A real `Bytes`/`Blob`
  Emerald type is a separate, cross-cutting language feature (every
  binary-data-producing plan in this batch would want it) this plan
  does not introduce as a side effect.
- **Transactions are exposed as three thin statement-shaped calls, not a
  new control-flow construct.** `Sqlite.begin(conn)`, `Sqlite.commit
  (conn)`, `Sqlite.rollback(conn)` each issue the corresponding literal
  SQL (`BEGIN`/`COMMIT`/`ROLLBACK`) through the connection directly —
  SQLite itself defines transaction control as ordinary SQL statements,
  so there is no `rusqlite`-specific transaction object to wrap, and no
  new Emerald grammar (a `do`/`end`-scoped transaction block, `rusqlite`
  own `Connection::transaction()` RAII guard) is attempted; that RAII
  auto-rollback-on-drop guarantee has no analogue at an opaque-`Int64`-
  handle FFI boundary in the first place — a dropped Rust guard has no
  way to observe that the corresponding Emerald handle was abandoned
  without an explicit `.rollback()` call. A caller that opens a
  transaction and never calls `.commit()`/`.rollback()` leaves it open
  until `.close()` — the same disclosed always-your-responsibility
  posture plan 93 establishes for every handle in this batch.
- **Out of scope.** Connection pooling (a single `Sqlite.open` call is
  one dedicated `rusqlite::Connection`; nothing multiplexes several
  callers over a shared pool — a distinct, general concern plan 93 or a
  future plan owns for every driver in this batch, not this one), a
  query builder or any ORM-level mapping from rows to Emerald class
  instances (this is a driver — raw SQL text in, typed columns out — not
  an ORM), SQLite extensions/virtual tables/FTS5 (a real, large surface
  `rusqlite`'s own `vtab`/`csvtab` features expose, deliberately not
  wrapped here), and a true incremental result cursor (see above). The
  bundled `libsqlite3-sys` version is pinned by `rusqlite`'s own
  `Cargo.lock` entry, not independently tracked by this plan — a SQLite
  CVE fix arrives by bumping `rusqlite`, not by this plan's own code.
