# Plan 126 — Protocol Buffers

Every other plan in this 91-191 batch wraps one fixed, closed Rust API
surface into `emerald-rt` — the single static archive plan 91 built,
compiled once when Emerald itself is built, and linked unmodified into
every user program thereafter. That works because `regex`, `base64`,
`quick-xml`, `bincode`/`rmp-serde` all operate on data whose *shape* is
either fully dynamic (a `JsonValue`-style tree) or fully fixed (a byte
buffer, a UTF-8 string) — nothing about calling `Regex.compile` needs
Emerald's compiler to have known, at its own build time, anything about
the *caller's* eventual regex pattern.

Protobuf breaks this assumption structurally, not incidentally. A
`.proto` message's wire encoding is field-number-and-type-driven — field
1 might be a `string`, field 2 a `sint32`, and nothing in the byte stream
itself says so; a decoder needs the schema to make sense of the bytes at
all. This is the opposite of JSON/XML/MessagePack, which are
self-describing (a `JsonValue`-shaped dynamic tree can represent *any*
document those formats can produce, with no schema needed up front).
There is no way to write one fixed `Protobuf.decode(data: Bytes):
Result[JsonValue, String]` function the way plan 125 did for bincode/
MessagePack, because a `JsonValue` walker has no way to know field 2's
*type* without the `.proto` file — `prost` itself doesn't attempt this
either; every one of its own generated types is schema-specific, code
generated from the `.proto` file at *its* caller's own build time via
`prost-build`, which is exactly the shape of tool this plan must build
an Emerald-facing equivalent of, not merely a library this plan can wrap
in `emerald-rt`.

`prost` (`tokio-rs/prost`, current release 0.14.4, published 2026-08-30 —
verified this session via docs.rs) is the chosen implementation, with one
honest caveat disclosed up front rather than glossed over: its own
crate-level documentation carries a "passively-maintained" badge, and its
own Contributing section states plainly, "The current maintainer is not
contributing new features and doesn't have the time to review new
features. Bug fixes and small improvements are welcome... security fixes
will be released as soon as possible," further noting the maintainer
"expects the official `protobuf` project to release their rust library
soon." This is a materially different risk profile than `regex` or
`base64` (both under very active, well-resourced stewardship) but a
meaningfully better one than plan 125's `bincode` finding (there,
development has fully ceased; here, security fixes and small patches
still flow, and MSRV policy is actively maintained — current MSRV 1.85 as
of the 0.14.4 release). `prost` remains the right choice for this plan:
it is the dominant, most widely used pure-Rust Protobuf implementation
(dependency of choice across the Rust gRPC/data-infrastructure
ecosystem), and no small-message-subset need this plan has depends on
features only an actively-feature-developed fork would provide.

## Concrete proof this plan targets

Given `examples/person.proto`:

```protobuf
syntax = "proto3";
package tutorial;

message Person {
  string name = 1;
  int32 id = 2;
  string email = 3;
}
```

running `emerald proto generate examples/person.proto -o examples/person.em`
generates (the target shape this plan's codegen leaf must produce):

```ruby
class Person
  @name: String
  @id: Int64
  @email: String
end
```

and the following program, using the generated class plus its two
compiler-attached FFI-backed methods:

```ruby
p: Person = Person.new("Ada", 1815, "ada@example.com")
bytes: Bytes = p.to_protobuf
restored: Result[Person, String] = Person.from_protobuf(bytes)
case restored do
  when Ok(p2) do
    puts p2.name
    puts p2.id
    puts p2.email
  end
  when Err(msg) do
    puts msg
  end
end
```

Expected output: `Ada`, `1815`, `ada@example.com` — a genuine protobuf
wire round-trip (`p.to_protobuf` produces the real, standard Protobuf
binary encoding for `Person`, byte-identical to what `protoc --encode`
against the same `.proto` file would produce for the same field values,
not an Emerald-private format).

## Decision log

- **This plan is a build-time codegen tool plus a per-project third
  archive, not a stdlib wrap — stated plainly rather than minimized.**
  Every leaf above exists because of this one structural fact. The task
  this batch works from asks for "a real, considered approach... an
  `emerald` CLI subcommand that consumes a `.proto` file and emits
  Emerald class definitions, analogous to `prost-build`'s own role" —
  this plan is exactly that, and no smaller design was found that avoids
  needing both a codegen step *and* a second, per-project compiled
  artifact. A "just decode into `JsonValue` generically" design (the
  shape every sibling plan uses) was considered and rejected above:
  Protobuf's non-self-describing wire format makes it structurally
  impossible without the schema in hand.
- **A `prost_reflect`-based generic/dynamic-value alternative was
  considered and declined for v1, not overlooked.** `prost_reflect`
  exists and can decode arbitrary protobuf bytes against a runtime-
  supplied `FileDescriptorSet` into its own dynamic `prost_reflect::
  Value` — avoiding per-schema Rust codegen entirely, and unifying this
  plan with the rest of the batch's "dynamic tree" strategy. It was
  declined because it re-derives a *third* dynamic-value mapping
  (`prost_reflect::Value`'s own field-number/name and `oneof` handling
  differs from both `JsonValue` and `XmlNode`) for real costs
  (reflection-based decode is slower, loses `prost`'s derive-based fast
  path, and still needs the same `.proto`-to-Emerald-type field mapping
  this plan's codegen leaf already has to solve for the class-generation
  approach) without avoiding the schema problem, only relocating it from
  compile time to a runtime `FileDescriptorSet` argument. Generated
  Emerald `class` definitions — real, named, statically typed fields the
  programmer can see and the type checker can check — is the more
  Emerald-idiomatic answer and the one actually requested.
- **Field-order, not field-name or field-number, is the marshaling
  contract between the generated Rust shim and the generated Emerald
  class — the mechanism that makes this tractable without runtime
  reflection on either side.** Because both the Emerald `class` and its
  backing Rust `prost::Message` struct are generated from the same
  `DescriptorProto` in the same codegen pass, they can be generated in
  lockstep with identical field order — the `to_protobuf`/`from_protobuf`
  shim functions are positional (`extern "C" fn person_to_protobuf(name:
  *const c_char, id: i64, email: *const c_char, out_ptr: *mut *mut u8,
  out_len: *mut i64) -> i64`-shaped, following plan 92's `(ptr,len)`
  `Bytes` convention for the output), never needing a field-name lookup
  or any structural reflection on the Emerald side, which does not
  exist. This is the same "the compiler controls both ends of the call"
  reasoning plan 122 used for its Boolean-return-widening decision,
  applied here to an entire struct's worth of fields at once.
- **`uint64`/`fixed64`/`sfixed64` fields are a real, disclosed precision/
  sign hazard, reusing plan 59's own already-verified Type-enum finding
  rather than inventing a new limitation.** Emerald's `Type` enum has no
  unsigned integer variant (plan 59, re-verified unchanged through plan
  91). A `uint64` field whose true value exceeds `i64::MAX` reinterprets,
  bit-for-bit, as a negative `Int64` — the exact same "declared-width/
  signedness mismatch is genuine, disclosed, not-silently-ignored
  undefined behavior" posture plan 59's own Decision log takes for
  narrower-than-expected extern signatures, applied here to a
  never-narrower but sign-reinterpreted case instead.
- **`oneof` and `map` fields are out of scope for v1's field-mapping
  table, not silently mis-mapped.** A `oneof` needs its own closed sum
  type per declared `oneof` name (plan 52's `enum` mechanism could model
  it, payload-carrying variants and all, but the codegen leaf would need
  real additional logic this plan does not yet design); a `map<K,V>`
  field needs `Hash[K,V]` construction across the FFI boundary, which
  the codegen's positional-field-shim strategy above does not yet cover
  for a variable-length keyed collection. The generator emits a
  compile-time error naming the unsupported field and its message,
  rather than silently dropping or mis-typing it.
- **Well-known types (`google.protobuf.Timestamp`, `Duration`, `Any`,
  `Struct`, wrapper types) are out of scope for v1** — each has its own
  real, non-obvious canonical mapping (e.g. `Any` needs Protobuf's own
  type-URL-based dynamic dispatch, which reopens the same schema-at-
  runtime problem this plan's whole architecture exists to avoid) that
  deserves its own follow-up rather than a rushed default here.
- **gRPC services are entirely out of scope.** `prost` itself generates
  no service/RPC code (that is `tonic`'s job in the Rust ecosystem, a
  separate crate this plan does not pull in) — this plan is message
  serialization only, matching the task's own framing of this batch as
  data-format plans, not a networking/RPC batch.
- **Out of scope, restated plainly.** Full `.proto` language coverage
  (imports across multiple files, custom options, extensions — proto2's
  legacy extension mechanism); `protoc` bundling (per `prost-build`'s
  own v0.11+ policy, `protoc` must already be installed and on `PATH` —
  this plan does not vendor or build it); regenerating Emerald source in
  place on every build automatically (v1 is an explicit, user-invoked
  `emerald proto generate` step, checked into version control like any
  other generated source, not a hidden build.rs step run on every
  compile).
