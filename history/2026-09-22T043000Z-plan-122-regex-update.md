## One representational choice: `Regex` is a compiler-synthesized `Int64` newtype, not `Type::Class("Regex")`

The original plan's own text describes `Regex` as "a new
`Type::Class(\"Regex\")`-shaped opaque resource handle." This session
implemented it instead as a compiler-synthesized `Int64` newtype — the
exact same zero-cost shape `NativeHandle` (plan 93) and `LogFields`
(plan 168) already use, both landed earlier this same session. This is
a real, deliberate consistency choice, not a deviation from the
plan's own intent: the plan's own text elsewhere says plainly "this
plan assumes plan 93's contract supplies *some* opaque handle
wrapper... if plan 93 lands with a materially different shape, this
plan's handle plumbing... is what would need to change" — plan 93 DID
land (earlier this session) with exactly this newtype shape, and this
plan follows it rather than introduing a second, competing resource-
handle representation. Every one of `Regex`'s nine instance methods is
carved out of the ordinary newtype `.value`-only restriction (the
identical mechanism `LogFields#set` already established, just with
nine methods instead of one), in both `emerald-sema` and
`emerald-codegen`.

## Three real, disclosed corrections found while writing the example (none `Regex`-specific)

1. **`case`/`when`/`else` don't exist** (plan 71) — the same correction
   every other example this session needed. Real syntax: `match X do
   Ok(v) do ... end Err(e) do ... end end`.
2. **This lexer's string-literal regex admits only `\"`/`\n` as escape
   sequences** — `crates/emerald-parser/src/ast.rs`'s own `decode_
   string_lit` doc comment states this plainly, and verified directly:
   writing `"(\\d{4})-..."` (the plan's own Concrete Proof pattern,
   after Rust-string double-escaping) is a genuine lexer-level parse
   error (`Invalid token`), not merely undecoded. This is a real,
   pre-existing, `Regex`-independent limitation on what ANY regex
   pattern (or any string needing a literal backslash at all) can look
   like as an Emerald string literal today. Worked around by using the
   equivalent POSIX bracket-expression form (`[0-9]`) instead of `\d` —
   semantically identical to the crate, syntactically legal here.
3. **`puts` accepts only `Int64`/`Float64`/`String`** (`emerald-sema`'s
   own `puts` arm, unchanged by this plan) — a bare `Boolean` argument
   (`puts re.is_match(...)`, the plan's own Concrete Proof) is rejected
   outright. String interpolation (`"#{...}"`), which DOES support
   `Boolean` (a separate, pre-existing check), is the real, current way
   to print one — worked around by binding the result to a `Boolean`
   local first, then interpolating it.
