# Plan 128 — HCL (HashiCorp Configuration Language) Parsing

Flagged plainly, in the overview and here: HCL is a niche format relative
to everything else in this batch. It matters to a specific, real
audience (anyone generating or consuming Terraform/Nomad/Packer
configuration, or building HCL-based tooling of their own) and is
essentially unused outside the HashiCorp ecosystem and its immediate
orbit. This plan exists for the "kitchen sink" mandate's own sake — full
completeness of the batch's data-format coverage — not because any other
plan in this batch, or Emerald's own toolchain, needs HCL support to
function.

`hcl-rs` (`martinohmann/hcl-rs`, current release 0.19.8 published
2026-08-09, MIT/Apache-2.0, 13 contributors, 270K downloads/month, used
by 131 crates (77 directly) — verified this session via lib.rs) is a
real, single-primary-maintainer project, honestly reported rather than
inflated: its release cadence is genuinely active (0.19.4 in October
2025, 0.19.6 in February 2026, 0.19.7 in April 2026, 0.19.8 in August
2026 — a steady few-months-apart cadence, not a stalled project), and it
holds `#51` in lib.rs's own Encoding category — a real, working, current
crate, just a much smaller one by every adoption metric than `regex`
(91.8M downloads/week) or `base64` (126.4M downloads/week). This plan
reports that difference plainly rather than describing `hcl-rs` in the
same terms as this batch's larger dependencies.

The one genuinely interesting technical finding, verified directly
against `hcl-rs`'s own published README this session: its dynamic
deserialization mode targets `serde_json::Value` directly, by design —
the README's own worked example imports `serde_json::{json, Value}` and
calls `hcl::from_str::<Value>(input)`, per its own stated goal of
"Deserialize arbitrary HCL according to the HCL JSON Specification."
HCL's own project (hashicorp/hcl) publishes a formal JSON mapping
specification precisely so a JSON-shaped consumer can read HCL without
its own bespoke value type — `hcl-rs` implements that specification
directly, rather than inventing its own dynamic-value shape the way,
say, `quick-xml` has no equivalent built-in DOM mode (plan 124 has to
build XML's tree mode itself). This plan therefore needs no new Rust
glue code beyond a `serde_json::Value -> JsonValue` conversion (plan 118
already owns the reverse of this conversion for its own JSON decode
path, so this is likely a direct reuse, not new logic) — the smallest
implementation footprint of any parsing plan in this batch, a direct
consequence of `hcl-rs`'s own upstream design choice rather than an
Emerald-specific optimization.

## Concrete proof this plan targets

```ruby
hcl_src: String = "some_attr = {\n  foo = [1, 2]\n  bar = true\n}\n\nsome_block \"some_block_label\" {\n  attr = \"value\"\n}\n"

parsed: Result[JsonValue, String] = Hcl.parse(hcl_src)
case parsed do
  when Ok(v) do
    match v do
      Obj(fields) do
        puts fields.get("some_attr").is_some
        puts fields.get("some_block").is_some
      end
      _ do
        puts "unexpected shape"
      end
    end
  end
  when Err(msg) do
    puts msg
  end
end
```

Expected output: `true`, `true` — both top-level keys (`some_attr`, an
inline object with a list and a boolean; `some_block`, a labeled block
flattened per the HCL JSON specification into a nested object keyed by
its label) present in the parsed `JsonValue::Obj`, matching `hcl-rs`'s
own README example of the identical input verified against
`serde_json::json!` this session.

## Decision log

- **`JsonValue` (plan 118) is reused verbatim as this plan's return
  type, not merely "the same strategy" reapplied — a stronger, more
  literal reuse than plan 124's `XmlNode` (which is JSON-*shaped* but a
  distinct ADT for XML's own element/text tree) or plan 126's protobuf
  mapping (which needs schema-specific classes).** This is possible only
  because `hcl-rs` itself already targets `serde_json::Value` for its
  dynamic mode — HCL's own JSON specification defines a real,
  standardized mapping from HCL's block/label/attribute/expression
  syntax onto plain JSON values, and `hcl-rs` implements exactly that
  spec, not an HCL-native value shape this plan would need to adapt.
- **The richer `hcl::Body`/`Block`/`Expression` typed AST, and HCL's own
  expression/template evaluation (`hcl::eval` — variable references,
  string interpolation, function calls inside `.tf`-style expressions),
  are both declined for v1.** The `Value`-based JSON-spec mode this plan
  uses is real, but not free of tradeoffs: block *labels* (e.g.
  `resource "aws_instance" "web" { ... }`, HCL's own defining feature
  for Terraform-style configuration) collapse into nested object keys
  under the JSON mapping rather than staying available as first-class,
  separately-typed label values the richer `Body`/`Block` API would
  preserve. This plan accepts that lossiness in exchange for reusing
  `JsonValue` wholesale; a future plan wanting genuine block-label
  fidelity or expression evaluation would need the richer, currently-
  out-of-scope `Body` API and its own dedicated Emerald-side type,
  closer in shape to plan 124's hand-built `XmlNode` than to this plan.
- **Parse failure is `Result[JsonValue, String]` (plan 53), matching
  every other fallible-parse plan in this batch.**
- **Serialization (Emerald value -> HCL text) is out of scope for v1 —
  parse direction only**, matching this plan's own minimal-footprint
  framing; `hcl-rs` supports it (`hcl::to_string`) but nothing in this
  batch's motivating use cases (reading existing Terraform/Nomad/Packer
  configuration) needs to emit HCL.
- **Out of scope.** The typed `Body`/`Block`/`Expression` AST mode;
  expression/template evaluation (`hcl::eval`, `Context::declare_var`);
  HCL serialization/writing; the crate's `perf` feature (a parser
  performance optimization, invisible at this plan's API surface).
