# Plan 110 — Standard Library: Symmetric AEAD Encryption

This is plan 110 of the 91-191 batch, the second of three cryptography
plans (109 hashing, 110 this plan, 111 asymmetric) built on plan 91's
`emerald-rt` mechanism. Unlike hashing, AEAD encryption has real secret
state (a key) and a real, extremely common failure mode (nonce reuse)
that has nothing to do with the underlying crate's correctness and
everything to do with how this plan's own API surface is shaped — so
where plan 109's Decision log is mostly about crate/type selection,
this plan's is mostly about the API-design choices that determine
whether a caller can misuse this safely at all.

Depends on: plan 91 (the `emerald-rt` crate and its
`catch_unwind`-at-every-boundary convention), plan 92 (FFI/ABI
Conventions, authored in parallel this session — the ptr+len buffer
convention `Bytes` surfaces, reused here unchanged), plan 93 (Resource
Handle & Lifetime Model, authored in parallel this session — the
mechanism `AeadKey`'s real free/zeroize-on-drop story is deferred to),
plan 95 (Crate-Vetting Policy, authored in parallel this session), plan
53 (`2026-09-09T123000Z-plan-53-result-type-and-error-propagation.md`
— the `Result[T, E]` type this plan's every fallible operation returns,
rather than plan 45's runtime-abort-on-failure precedent, a deliberate
divergence explained below), and plan 109
(`2026-09-22T000000Z-plan-109-crypto-hashing.md` — the `Bytes` type
this plan's plaintext/ciphertext/AAD/nonce values are all built on,
established there rather than redefined here).

## Concrete proof this plan targets

```ruby
key1: AeadKey = XChaCha20Poly1305.generate_key()
key2: AeadKey = XChaCha20Poly1305.generate_key()
plaintext: Bytes = "attack at dawn".to_bytes()
aad: Bytes = "".to_bytes()

sealed: Bytes = XChaCha20Poly1305.encrypt(key1, plaintext, aad).unwrap()

opened: Result[Bytes, AeadError] = XChaCha20Poly1305.decrypt(key1, sealed, aad)
puts opened.unwrap().to_s()

wrong_key: Result[Bytes, AeadError] = XChaCha20Poly1305.decrypt(key2, sealed, aad)
puts wrong_key.is_err()
```

Expected output:
```
attack at dawn
true
```

Unlike plan 109's hashing proof, `sealed`'s actual bytes are not
literally reproducible run-to-run — a fresh random nonce is generated
inside every `.encrypt` call, by design (see Decision log). What *is*
deterministic and what this proof actually checks: decrypting with the
correct key recovers the exact original plaintext, and decrypting with
a different, unrelated key fails closed (`Result::Err`, no partial or
garbage plaintext returned) every single time. The fixed-byte
correctness of the underlying primitive itself is what the RFC
8439/Wycheproof-vector `#[test]`s (see below) exist to prove instead.

## Decision log

- **Two RustCrypto AEAD crates, chosen for genuinely different
  hardware/performance profiles, not redundantly.** `aes-gcm` (0.11.1,
  Aug 21 2026) and `chacha20poly1305` (0.11.0, Jun 28 2026) are both
  RustCrypto, both pure Rust, both carry the identical security-notes
  paragraph in their own READMEs (verified this session): "designed to
  execute in constant time, either by relying on hardware intrinsics
  (i.e. AES-NI and CLMUL on x86/x86_64 [respectively AVX2 for ChaCha]),
  or using a portable implementation which is only constant time on
  processors which implement constant-time multiplication... not
  suitable for use on processors with a variable-time multiplication
  operation." AES-GCM's performance genuinely depends on AES-NI/CLMUL
  hardware acceleration being present (near-universal on modern
  server/desktop x86_64, absent on some embedded/microcontroller
  targets); ChaCha20-Poly1305 exists specifically because, per its own
  README, it's "notable for being simple and fast when implemented in
  pure software" — the right choice on hardware without AES
  acceleration. Offering both, rather than picking one, is a real
  hardware-portability decision, not indecision. Both crates received
  one security audit by NCC Group in 2020 (funded by MobileCoin), "with
  no significant findings" — verified via each crate's own README,
  which links the same archived audit PDF.
- **RUSTSEC-2023-0096 is real, and this plan avoids it by never calling
  the affected API shape — not by trusting the version pin alone.**
  Verified directly against the advisory: `aes_gcm::AeadInPlace::
  decrypt_in_place_detached` (and `AesGcm::decrypt_in_place_detached`)
  in versions `>=0.10.0, <0.10.3` expose the decrypted-but-unauthenticated
  plaintext in the caller's buffer even when tag verification fails —
  patched in `>=0.10.3`, and this plan's `0.11.1` pin is well past that.
  But version alone is not the whole story: this plan's `.decrypt`
  intrinsic is built on the crate's safe, `Vec`-returning `aead::Aead::
  decrypt` (not the in-place/detached variant at all), which per the
  advisory's own description was never affected in the first place —
  it only ever returns `Ok(plaintext)` or `Err`, with no buffer the
  caller could inspect on the error path. This plan's own `#[test]`
  suite reproduces the advisory's exact published PoC vector (Wycheproof
  test case 23: key `000102030405060708090a0b0c0d0e0f`, nonce
  `505152535455565758595a5b`, ciphertext `eb156d081ed6b6b55f4612f021d87b39`,
  bad tag `d9847dbc326a06e988c77ad3863e6083`) against this plan's own
  `.decrypt` wrapper and asserts `Err`, proving the avoidance
  empirically rather than only by API-shape argument.
- **Key material is `AeadKey`, never a bare `Bytes` — the concrete,
  statable design decision the task's own "never log or accidentally
  stringify a key" requirement demands.** Plan 109 gives `Bytes` a
  `.to_hex()` convenience specifically so hash digests are printable —
  exactly the method that would turn a raw key into a one-line
  `puts key.to_hex()` accident if key material were stored as plain
  `Bytes`. `AeadKey` is a second, distinct inert sema type (CString-
  shaped again, per plan 59's precedent, reused a third time in this
  batch) with no `.to_hex()`, no `.to_s()`, no method that produces a
  `String` or printable value from it at all — the only way to move
  data across the `AeadKey` boundary is `key_from_bytes`/`generate_key`
  going in, and `.encrypt`/`.decrypt` consuming it as an opaque
  parameter, never yielding it back out in inspectable form. This is
  the same category of decision plan 59 made for `CString`'s trust
  boundary, applied here to a *secrecy* boundary instead of a *trust*
  one.
- **Nonce management: automatic generation is the default, and the
  security tradeoff of that choice is stated plainly, not hidden behind
  "we handle it for you."** Both algorithms here use a standard 96-bit
  (12-byte) nonce. `.encrypt` generates a fresh one via `AeadCore::
  generate_nonce` (backed by the `getrandom` feature, i.e. the OS
  CSPRNG) on every call and prepends it to the returned `Bytes`
  (`nonce || ciphertext || tag`), so the common "encrypt once, decrypt
  once" case never requires the caller to manage a nonce at all. The
  real limit of this safety: NIST SP 800-38D's own guidance is that
  random 96-bit nonces under one AES-GCM key start to carry meaningful
  collision probability past roughly 2^32 encryptions under that key —
  this plan does not hide that ceiling, and recommends `XChaCha20Poly1305`
  (a 192-bit/24-byte nonce, large enough that random-nonce collision is
  not a practical concern at any realistic message volume) as the
  default choice for the auto-nonce path specifically because of this,
  reserving plain AES-256-GCM for throughput-sensitive, key-rotated, or
  hardware-AES-NI-available contexts.
- **The explicit-nonce escape hatch exists for real interop needs, and
  its danger is stated in the strongest terms this plan uses anywhere.**
  Some protocols mandate deterministic (e.g. counter-based) nonces for
  interop reasons outside this plan's control — `.encrypt_with_nonce`
  exists for exactly that, with full caller responsibility for
  uniqueness. The security implication is not symmetric between the two
  algorithms this plan wraps: for AES-GCM specifically, reusing a
  (key, nonce) pair doesn't just leak an XOR of two plaintexts the way a
  reused stream-cipher keystream would — it also leaks the GHASH
  authentication subkey, which lets an attacker forge *new*,
  never-encrypted messages that verify successfully under that key,
  going forward, not just recover the two colliding messages. This is a
  well-documented, GCM-specific consequence of its polynomial MAC
  construction, and this plan's own doc comments on `.encrypt_with_nonce`
  state it explicitly rather than leaving "don't reuse nonces" as an
  unexplained rule.
- **Fallible operations return `Result[T, E]`, a real, deliberate
  divergence from plan 45's file-I/O precedent, not an oversight of
  it.** Plan 45's `File.read`/`File.write` abort the process on error
  (`fprintf(stderr, ...); exit(1)`) because a missing file is, in that
  plan's own framing, closer to a configuration/environment problem than
  a routine branch a program is expected to handle. A tampered or
  corrupted ciphertext failing authentication is the opposite: it is
  the *expected*, routine, must-handle outcome of decrypting anything
  an AEAD scheme didn't produce and authenticate itself — exactly the
  case plan 53's `Result[T, E]`/`rescue` machinery exists for. `.encrypt`
  can fail only on a malformed key (already excluded by `AeadKey`'s
  construction-time validation) or an implausible >256GB plaintext (the
  RFC 8439 `P_MAX` ceiling, verified from RFC 8439 §2.8 directly:
  "P_MAX... is 274,877,906,880 bytes, or nearly 256 GB") — both real,
  both worth a `Result` rather than a hard abort.
- **`AeadKey`'s Rust-side `zeroize`-on-drop guarantee is real but not
  yet actually wired to anything on the Emerald side — a genuine,
  disclosed gap this plan does not paper over.** Both crates' `zeroize`
  feature (confirmed present in each crate's own dependency list this
  session) makes the underlying Rust key type zero its memory when
  Rust's `Drop::drop` actually runs. But per plan 59/51's own repeated
  finding, Emerald has no destructor/drop-glue on scope exit for any
  value today — an `AeadKey` handle is a boxed Rust value living behind
  an opaque pointer Emerald's own generated code never calls back into
  to free. If nothing frees it, `Drop::drop` never runs, `zeroize` never
  fires, and the key material sits, unzeroized, in leaked heap memory
  for the life of the process — the opposite of what enabling that
  feature was supposed to buy. This plan states the hazard rather than
  claiming the feature flag alone solves it; an explicit, plan-93-owned
  consuming-free operation on `AeadKey` is a hard prerequisite before
  this plan's `EXECUTE` phase, not an optional nicety (see Not yet
  decided).
- **This plan invents no new cryptographic construction.** Every
  encrypt/decrypt call is a direct, unmodified call into `aead::Aead::
  encrypt`/`decrypt` (or the `_with_nonce` sibling using the crate's own
  `AeadCore`-typed nonce parameter) — no custom padding, no home-grown
  key derivation, no alternate tag length or truncation. The
  `nonce || ciphertext || tag` framing this plan chooses for the
  auto-nonce path's returned `Bytes` is a packaging convention, not a
  cryptographic modification of either algorithm — libsodium's
  `crypto_secretbox_easy` and the `age` encryption format both use the
  identical nonce-prepended-to-ciphertext convention, for the same
  reason (the decrypting side needs the nonce and this avoids a second
  out-of-band channel to carry it).
- **Out of scope.** Streaming/chunked AEAD for plaintext too large to
  hold in memory at once (RustCrypto's own `aead-stream` crate — seen
  directly in `aes-gcm`'s own "Related" crate list this session — is
  the natural future dependency for this, built on whatever handle
  model plan 93 lands, not this plan); AES-GCM-SIV or AES-SIV
  (nonce-misuse-resistant variants — a real, different security
  property, a distinct future plan, not a drop-in replacement for the
  two algorithms named in this plan's scope); key derivation from a
  password (that's a KDF, out of scope for the same reason plan 109
  declined Argon2/scrypt); key wrapping/envelope encryption; any
  network/transport protocol (TLS, etc.) built on top of these
  primitives — this plan is the primitive layer only; constant-time
  comparison of anything (this plan's own operations never compare
  secret bytes directly in Emerald-visible code — tag verification
  happens entirely inside the audited crate — so plan 117's `subtle`
  crate isn't a direct dependency here the way it's foreshadowed in
  plan 109, but remains the answer if a future plan built on this one
  ever needs to compare `AeadKey`-adjacent secrets directly).

## Not yet decided (blocking EXECUTE)

1. `AeadKey`'s explicit free/consume mechanism is plan 93's call, not
   this plan's — until it lands, this plan cannot actually guarantee
   the `zeroize` feature's benefit reaches real key material, only that
   the feature is enabled. This is a hard EXECUTE blocker, not a
   deferred nicety, given the task's own "never log or accidentally
   leak a key" framing.
2. Whether `.encrypt`'s nonce-prepending convention should be a fixed,
   undocumented implementation detail or an explicitly-typed `Sealed`
   wrapper distinct from a bare `Bytes` (to stop a caller from, say,
   truncating the leading nonce bytes off before storing it) is left
   open — `Bytes` is used directly above for this plan's own proof
   simplicity, but a future revision may want the same
   accidental-misuse protection `AeadKey` itself gets.
