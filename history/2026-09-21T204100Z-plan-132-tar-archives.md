# Plan 132 — Tar Archives

Tar is the one format in this 130-136 sub-batch that does no
compression at all — it is a container format, a concatenation of
fixed-size (512-byte-aligned) headers and file contents, originally
designed (per its name, "tape archive") for streaming to sequential
magnetic tape. That single fact shapes this whole plan: the real
`tar`/GNU-`tar`/BSD-`tar` command-line tools never compress on their
own either, they shell out to (or pipe through) `gzip`/`bzip2`/`zstd`
and the resulting `.tar.gz`/`.tar.bz2`/`.tar.zst` is exactly a tar
stream fed through a *second*, independent compressor — and this plan
follows that precedent exactly rather than inventing an Emerald-native
"compressed archive" abstraction. The pure-Rust `tar` crate
(`alexcrichton/tar-rs`, the same `alexcrichton` GitHub account behind
`cc-rs` — already this project's own C-compilation dependency via
plan 91's `build.rs`) is, verified this session by reading its own
`README.md` and dependency list directly, a container-format-only
library with no compression code and no C code anywhere in its own
source tree.

## Concrete proof this plan targets

```ruby
Dir.mkdir("tar_demo_src")
File.write("tar_demo_src/a.txt", "hello")
File.write("tar_demo_src/b.txt", "world, a longer second file")

paths: Array[String] = ["tar_demo_src/a.txt", "tar_demo_src/b.txt"]
Tar.create("demo.tar", paths)

reader: TarReader = TarReader.open("demo.tar")
match reader.next_entry()
when Some(name1)
  puts name1
  puts reader.read_entry_data().to_string()
when None
  puts "unexpected end"
end

match reader.next_entry()
when Some(name2)
  puts name2
  puts reader.read_entry_data().to_string()
when None
  puts "unexpected end"
end

match reader.next_entry()
when Some(name3)
  puts name3
when None
  puts "end"
end
reader.close()

Tar.extract("demo.tar", "tar_demo_out")
restored: String = File.read("tar_demo_out/tar_demo_src/a.txt")
puts restored == "hello"
```

Expected output: `tar_demo_src/a.txt`, `hello`, `tar_demo_src/b.txt`,
`world, a longer second file`, `end` (the third `.next_entry()` call,
past the last real entry, resolves to `None` and proves iteration
genuinely terminates rather than looping or erroring), and `true` (bulk
`Tar.extract` recreates the same relative path structure `Tar.create`'s
input paths described, and `File.read` — plan 45's own existing
intrinsic — reads back the exact original bytes). `Dir.mkdir` is
assumed present as ordinary filesystem stdlib surface by this plan's
EXECUTE gate, not itself designed here; `Option[T]`/`Some`/`None`/
`match` reuse plan 73's real, already-shipped nullability model rather
than plan 43's older `T?` nullable-type syntax it replaced.

## Decision log

- **Zero C anywhere in this dependency's own graph — verified directly,
  not inferred from "it's a container format so it must be simple."**
  Read this session, in full: `alexcrichton/tar-rs`'s `README.md`
  describes it plainly as "A tar archive reading/writing library for
  Rust," `[dependencies] tar = "0.4"`, no build-dependency section, no
  `links = "..."` manifest key. Its two real runtime dependencies —
  `filetime` (preserving/restoring file modification times across
  archive/extract) and, only under the `xattr` feature this plan
  disables, `xattr` (POSIX extended attributes) — are themselves pure
  Rust crates that reach the OS through safe wrappers over
  platform-provided syscalls, not through any vendored or
  linked-against C library. Per plan 95's policy, this is the simplest
  possible call in the whole sub-batch: no C exception to justify, no
  competing pure-Rust alternative to weigh, because there is no
  incumbent C-backed option in wide Rust use to begin with — `tar-rs`
  has been the de facto standard Rust tar implementation for close to a
  decade (Cargo's own `.crate` package format is itself a `.tar.gz`,
  and `cargo` itself depends on this exact crate to read/write it).
- **`xattr` (POSIX extended attributes) is disabled for v1, a real,
  disclosed capability loss, not an oversight.** Extended attributes
  (e.g. macOS Finder tags, SELinux security contexts, arbitrary
  `user.*` namespaced key-value metadata some tools attach to files)
  are real data some archives carry, and disabling the feature means
  `Tar.create`/`TarReader` neither writes nor restores them. This plan
  declines the feature because it pulls in platform-specific syscall
  surface (`listxattr`/`getxattr`/`setxattr` and their BSD/macOS/Linux
  variants) this plan's own Concrete Proof has no way to exercise
  meaningfully, and because Emerald has no extended-attribute-typed
  stdlib surface today for `Tar` to hand such data to even if it were
  read — a real, separate, future feature, not a silent gap.
- **`.tar.gz`/`.tar.zst` are explicitly composition, not a feature this
  plan builds — `Tar` never links against `flate2` or `zstd` directly.**
  This is the load-bearing design decision of this whole plan: rather
  than `Tar.create_gz(...)`/`Tar.create_zst(...)` convenience methods
  duplicating plan 130's/131's compression logic inside `emerald-rt`'s
  `tar.rs` module, a `.tar.gz` is produced by calling `Tar.create` to
  get raw tar bytes (or, more precisely, streaming `tar::Builder`'s
  output directly into a `flate2::write::GzEncoder` at the Rust level —
  an internal implementation optimization this plan's Emerald-level API
  does not need to expose, since `Tar.create` writing straight to a
  `GzipWriter`-backed `std::io::Write` is exactly the same bytes either
  way) and then feeding that through `Gzip.compress`/`GzipWriter`. This
  keeps `emerald-rt`'s `tar.rs` module's only real dependency
  compression-format-agnostic, matches the real Unix tools' own
  `tar | gzip` pipeline precedent exactly, and means a future sixth
  compression format added to this batch composes with `Tar` for free,
  with zero change to this plan's own code.
- **`TarReader.next_entry()` returns `Option[String]`, not a
  richer `TarEntry` class with size/mtime/permission fields — a real,
  disclosed simplification, not the eventual complete surface.** A full
  tar header carries mode, uid/gid, mtime, and entry type (regular
  file, directory, symlink, ...) beyond just path and size; exposing
  all of that as a real Emerald value would mean either a new built-in
  struct-like return type (more machinery than this plan's own Concrete
  Proof needs) or a hand-rolled multi-field intrinsic return (real,
  working precedent exists — plan 39's tuple-returning functions — but
  adopting it here for six-plus fields is a larger design surface than
  \"list entries and read their bytes\" requires). `.entry_size()` is
  kept as a narrow, second call specifically because
  `.read_entry_data()`'s `Bytes` result already discloses length
  implicitly (`Bytes.length`, per plan 92) — it exists only so a caller
  who wants to skip large entries without reading their data can check
  size first, genuinely useful for a streaming reader in a way
  `Array[T]`'s `.split`/`.split_count` split never needed to justify
  twice.
- **`Tar.create`'s second argument is `Array[String]` of file paths,
  not directory paths with recursive walking.** `tar::Builder::append_
  dir_all` exists upstream and would let one call sweep an entire
  directory tree into an archive, but recursive directory walking
  brings in real decisions this plan declines to make now: does a
  symlink get followed or archived as a symlink entry? does a `.git/`
  or other dotfile directory get included by default? Emerald has no
  existing directory-walk stdlib intrinsic for this plan to build on
  (no `Dir.walk`/`Dir.entries` exists in any shipped plan verified this
  session), so `Tar.create` takes an explicit, caller-supplied
  `Array[String]` of exactly the paths to include — inheriting `Array[T]`'s
  own already-disclosed no-runtime-length representation (plan 45),
  hence `count: i64` being passed alongside the pointer array at the
  FFI boundary in `leaf-create-archive` rather than the extern function
  trying to discover the array's length itself.
- **Archive member order is caller order, not sorted — matching
  `tar::Builder::append_path`'s own real behavior (append in call
  order) rather than imposing a canonicalization this plan doesn't
  need.** A caller wanting deterministic, reproducible archive bytes
  (e.g. for a build system caching a `.tar.gz` by content hash) must
  sort `paths` itself before calling `Tar.create` — this plan does not
  sort on the caller's behalf, since a caller who deliberately wants a
  specific order (e.g. a manifest file first) would otherwise have that
  intent silently overridden.
- **Out of scope.** No recursive directory archiving (above), no
  extended attributes (above), no symlink-following policy choices
  beyond whatever `append_path`'s own default is, no sparse-file
  support, no PAX-format long-filename/long-link extensions beyond
  whatever `tar-rs` handles by default, no in-place archive
  modification (append-to-existing-archive) — `Tar.create` always
  writes a fresh archive. `.tar.gz`/`.tar.zst` convenience wrappers
  that internally do the `Tar`+`Gzip`/`Zstd` composition in one call
  are a real, plausible follow-up but not built here — this plan
  proves the composition works (`leaf-rust-tests-and-proof-example`'s
  `.tar.gz` test) without also building the sugar on top of it.
