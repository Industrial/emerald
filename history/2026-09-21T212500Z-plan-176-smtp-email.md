# Plan 176 — SMTP Email Client

`emerald-rt` (plan 91) exists specifically so stdlib expansion is written
against a real, vetted Rust crate instead of hand-rolled C; plan 92 fixed
the calling convention every export follows. This plan is the first of
this batch's six to actually land a third-party dependency (plans 96-175
land the others, authored in parallel) — `lettre`, wrapping SMTP send.
It is deliberately one of the simplest plans in this batch: no actor-
model tension to resolve (unlike plans 177-179, cite their own Decision
logs), no new marshaling convention beyond what plan 92 already
specifies for scalar strings, and a proof that needs no real network
access. The only genuinely new design work is choosing which of
`lettre`'s several transport/TLS/async configurations this project's
synchronous, `emerald_rt_fn!`-wrapped FFI convention actually wants.

## Concrete proof this plan targets

```ruby
client: SmtpClient = SmtpClient.connect("127.0.0.1", 2525, "testuser", "testpass")

email: Email = Email.new("sender@example.test", "receiver@example.test", "Hello", "Plain text body.")

result: Result[Void, String] = client.send(email)
case result
when Ok(_)
  puts "sent"
when Err(e)
  puts e
end
```

Expected output: `sent` — a real, deterministic proof that `SmtpClient.
connect` opens a TCP connection to the stub SMTP server started by this
plan's own test harness (`leaf-loopback-smtp-stub-and-proof`), that
`Email.new` and `.send` drive `lettre`'s real `SmtpTransport`/
`MessageBuilder` through a genuine (if canned-response) SMTP `EHLO`/
`AUTH LOGIN`/`MAIL FROM`/`RCPT TO`/`DATA`/`QUIT` conversation, and that
`transport.send(&message)`'s `Ok(_)` result crosses back into Emerald as
plan 92's real `Result[Void, String]` `Ok` variant — not a mocked
"pretend this worked" shortcut. No internet access, no real mail
delivery, and no timing dependency are involved anywhere in this proof,
the same "deterministic, dependent on nothing outside this repo's own
control" posture plan 91's FNV-1a proof established for correctness and
this plan re-establishes for reachability.

## Decision log

- **`lettre` 0.11, verified current and actively maintained this
  session, not assumed.** `lib.rs`'s real crate page: latest release
  `0.11.23` (3 Aug 2026), 2,507,121 downloads/month, used in 704
  dependent crates (459 directly), MIT-licensed, owned by a real,
  multi-person team (`amousset`, `paolobarbolini`, the `lettre` GitHub
  org) rather than a single unresponsive maintainer. Its own README
  states plainly what it does and does not do: "Multiple transport
  methods... Secure delivery with SMTP using encryption and
  authentication... Easy email builders... Async support" against
  "Lettre does not provide (for now): Email parsing" — this plan needs
  exactly the capabilities on the first list and none from the second
  (sending only, never parsing/receiving), a clean match with no
  scope-stretching required to justify the dependency.
- **Blocking `SmtpTransport`, not an async transport — no async runtime
  dependency enters `emerald-rt` at all in this plan.** `lettre`'s
  dependency list (verified via docs.rs, `lettre-0.11.23`) shows `tokio
  ^1`, `async-std ^1.8`, and `futures-*` all listed as *optional* —
  `smtp-transport` alone (this plan's chosen feature) pulls in none of
  them; the synchronous `SmtpTransport::send` call simply blocks the
  calling OS thread for the SMTP round trip, exactly like any other
  blocking libc call this project's native functions already make (a
  `read()`/`connect()` inside `runtime/emerald_runtime.c`'s own
  `emerald_tcp_connect`, verified present at `runtime/emerald_runtime.c`
  L1533-1551, blocks the calling thread identically, with no async
  machinery involved). Whether/how a *general* async-vs-blocking-native-
  call story should exist across the whole `emerald-rt` surface is
  plan 94's question, cited here, not re-litigated — this plan simply
  takes the narrowest, dependency-free option available today.
- **Under plan 55's "N actors over M OS threads" model, `.send`
  occupies its calling actor's one execution slot for the full SMTP
  round trip — a real, disclosed cost, not a new hazard.** A slow or
  unreachable SMTP relay ties up one worker thread for as long as
  `lettre`'s own connect/write timeouts allow, exactly as any other
  blocking native call already can (this is not a *new* category of
  risk this plan introduces — plan 55's scheduler already accepts that
  a synchronous native call runs to completion on whichever worker
  thread dequeued the message before that actor's mailbox is drained
  further). A bounded pool specifically for slow/blocking native calls,
  separate from the actor scheduler's own pool, is exactly the kind of
  thing plan 94 might one day add; this plan does not attempt it.
- **`SmtpClient` is an opaque resource handle, per plan 93, not a
  representable Emerald value.** A `lettre::transport::smtp::
  SmtpTransport` (an internally-pooled, potentially-TLS-wrapped TCP
  connection object) has no honest representation in Emerald's flat
  `Int64`/`Float64`/`String`/pointer `ValKind` world — it is kept
  server-side in `emerald-rt`'s resource registry (plan 93's own
  mechanism) behind a plain `i64` handle, the same pattern every other
  stateful native wrapper in this batch (a database connection, a
  compression stream) needs and plan 93 is defining generally. This
  plan is a real, disclosed *consumer* of plan 93's registry, not a
  second, parallel handle scheme invented locally.
- **TLS reuses plan 99's rustls trust story via `lettre`'s
  `rustls-tls` feature, not `native-tls`/OpenSSL.** `lettre`'s
  dependency list (verified) offers both `native-tls ^0.2.9` and
  `rustls ^0.23.18` + `rustls-native-certs`/`webpki-roots` as optional
  features — this plan takes `rustls-tls` specifically so the project's
  TLS trust-root/certificate-verification story lives in exactly one
  place (plan 99), never a second, OpenSSL-linked one that would need
  its own separate system-library vetting and platform build story.
  `SmtpClient.connect_tls` builds `lettre::transport::smtp::client::Tls::
  Wrapper` (implicit TLS, conventionally port 465) — the concrete proof
  above deliberately exercises only the plain `.connect` path, since
  proving a real TLS handshake against a loopback stub server would
  require the stub itself to terminate TLS, disproportionate machinery
  for this plan's own proof; `connect_tls`'s own correctness is left to
  a Rust-side `#[test]` against `lettre`'s own TLS transport
  construction (never a hand-verified handshake), per this plan's
  `leaf-smtp-client-native-functions`.
- **Attachment bytes are read on the Rust side via a plain filesystem
  path string, never through Emerald's own `File` API or plan 92's
  `(ptr, len)` binary-safe convention.** `Email.add_attachment(path:
  String)` stores the path as an ordinary Emerald `String` field;
  `emerald_rt_smtp_send` reads that path's real bytes itself
  (`std::fs::read`), builds a `lettre::message::Attachment` from them,
  and never crosses the raw bytes back across the FFI boundary at all —
  a deliberately narrower, simpler design than accepting a `Bytes`
  value from Emerald source directly, which plan 92's own Decision log
  already named as a real, disclosed gap ("a domain plan built on
  [the `(ptr, len)` convention] can *consume* arbitrary bytes a native
  call *produces*, but cannot yet accept an Emerald-source-literal
  `String` containing an embedded NUL byte"). Reading the attachment
  natively sidesteps that gap entirely for this plan's own proof, at
  the cost of attachments always coming from a real filesystem path,
  never from in-memory Emerald-constructed byte data — a real,
  disclosed narrowing, not an oversight.
- **A connection-setup failure (bad host, connection refused, auth
  rejected) becomes a `Result[Void, String]` `Err`, never a raised
  exception — a genuinely ordinary, expected outcome, unlike a Rust
  panic.** Reusing plan 92's own distinction directly: a caught Rust
  *panic* (a genuine bug — a `lettre` internal invariant violated,
  e.g.) becomes `NativeError` via `emerald_rt_fn!`, but `lettre::
  transport::smtp::Error` (an ordinary, expected `Result::Err` from a
  real network operation that can simply fail — wrong password, relay
  down) is mapped directly to `emerald_rt_result_err`, never allowed to
  panic-then-get-caught. This is the first domain plan to actually
  exercise plan 92's stated-but-until-now-hypothetical "when does a
  native failure become `Result::Err` vs. a raised exception" rule in
  a real, non-toy function.
- **Out of scope.** No IMAP/POP3 (receiving), no email parsing (`lettre`
  itself declines this, per its own README, quoted above), no mailing-
  list/bulk-queue send, no DKIM/SPF/message signing (a real, disclosed
  gap `lettre` itself does not fully own either), no async transport of
  any kind (see above — plan 94's territory if ever wanted), no retry/
  backoff policy beyond whatever `lettre`'s own transport does
  internally, and no `Bytes`-typed in-memory attachment content (see
  the attachment bullet above — filesystem-path attachments only).
