# Plan 121 — CSV

This is plan 121 of the 91-191 batch, sibling to plan 118 (JSON), 119
(TOML), and 120 (YAML), all three of which reuse plan 118's `JsonValue`
tagged union as their shared dynamic-value representation. **This plan
does not.** Crate: `csv` — verified this session against its own real,
current `lib.rs` crate page: version **1.4.0** (published Oct 17, 2025),
by `BurntSushi` (Andrew Gallant, the author of `ripgrep`), ranked **#6**
in the "Encoding" category, **17,880,981 downloads per month**, used
directly in 3,392 crates — the canonical, official, fast Rust CSV
reader/writer, with no serious competing choice for this plan's own
"vetted, widely-used" criterion.

CSV's real shape is fundamentally different from JSON/TOML/YAML's, and
this plan's whole API design follows from stating that difference
plainly rather than forcing a tree-shaped answer onto a table-shaped
problem. A JSON document's shape is discovered by walking it — an
object might contain an array might contain another object, arbitrarily
deep, and a consumer genuinely doesn't know what's at a given path
until it looks. A CSV document's shape is a flat table: rows, and
within each row, fields identified either by position (column 0, column
1, ...) or, if the caller treats the first row as a header, by one
shared field-name-per-column mapping applied identically to every other
row. There is no nesting, no per-row schema variation, no recursive
case where a "cell" might itself contain a whole sub-table — a CSV
field is always, unconditionally, a string (the crate's own core type,
`StringRecord`, is a `Vec<String>`-shaped record with no fancier per-
cell typing at all; numeric/boolean interpretation of a cell's text is
always a decision the *caller* makes afterward, never the parser).
Wrapping that in `JsonValue` (which has JSON's own genuinely nested
`JsonArray`/`JsonObject` variants available, whether or not a given CSV
document ever needs them) would suggest a false flexibility this
format never actually has — and would need every consumer to `case`/
`when`-narrow a `JsonArray(JsonArray(JsonString(...)))` shape down to
plain strings by hand, for a document that was never anything but a
flat table of strings to begin with. `Array[Array[String]]`/`Array[
Hash[String, String]]` say exactly what a CSV document is, directly, in
Emerald's own real, existing collection types — no new tagged union,
no new enum, nothing plan 118 needs to grow to accommodate this plan.

## Concrete proof this plan targets

```ruby
input: String = "name,role,notes\nAda,\"engineer, lead\",\"wrote ""the\nfirst"" program\"\nGrace,admiral,\n"

match Csv.parse(input) do
Ok(rows) do
  header: Array[String] = rows[0]
  puts header[1]

  second_row: Array[String] = rows[1]
  puts second_row[1]
  puts second_row[2]
end
Err(msg) do
  puts msg
end
end

match Csv.parse_with_headers(input) do
Ok(records) do
  first: Hash[String, String] = records[0]
  first.each do |pair|
    if pair.key == "role"
      puts pair.value
    end
  end
end
Err(msg) do
  puts msg
end
end
```

Expected output:
```
role
engineer, lead
wrote "the
first" program
engineer, lead
```
The three classic CSV edge cases this proof exercises directly: a
quoted field containing the delimiter itself (`"engineer, lead"` — the
comma inside the quotes is not a field boundary), a quoted field
containing a literal embedded newline (`"wrote ""the\nfirst""
program"` — RFC 4180-style CSV genuinely allows a newline inside a
quoted field, and this plan's `.parse` must not treat it as a row
boundary), and doubled-quote escaping (`""the""`/`""first""` inside the
outer quotes becomes a single literal `"` in the parsed field, not two,
not zero) — all three handled by the `csv` crate's own real, standard-
compliant parser, none of them hand-rolled by this plan. `Csv.
parse_with_headers`'s own second block proves the header-keyed path
independently, reading `role` back by name rather than position.

## Decision log

- **Two parse functions, not one — position-indexed is the default,
  header-keyed is the explicit opt-in, and both are offered rather than
  picking a single winner.** `Csv.parse` (`Array[Array[String]]`,
  header row included as ordinary row 0 if the document has one) is the
  narrower, more honest default: not every real CSV file has a header
  row at all (a plain data dump, a one-column list), and `Csv.parse`
  makes no assumption either way — it hands back exactly what's on
  disk, one `Array[String]` per line, positionally. `Csv.parse_with_
  headers` (`Array[Hash[String, String]]`) is the more convenient shape
  for the common case (a file whose first line genuinely is a header)
  but requires that assumption to be true, and consumes row 0 as the
  header rather than data — the two functions produce genuinely
  different, non-overlapping row counts on the identical input (`Csv.
  parse` on this plan's own three-line proof input returns 3 rows;
  `Csv.parse_with_headers` returns 2 records), which is exactly why
  both are named explicitly rather than one being an optional-argument
  variant of the other.
- **`Hash[String, String]` for `Csv.parse_with_headers`'s per-row
  shape — the same `Hash[K,V]` type plan 118 already established for
  `JsonObject`, and the same real, disclosed `[]`-indexing limitation
  applies here too, worked around the same way.** `crates/emerald-
  codegen/src/lib.rs`'s `build_hash_lookup`/`build_index` genuinely
  cannot index a `Hash[String, V]` with `[]` today (verified directly,
  full citation in plan 118's own Decision log — `key_val: IntValue`,
  `idx.into_int_value()` called unconditionally, a real reachable
  panic for a non-`Int64` key). This plan's own Concrete Proof above
  therefore reads a record's fields via `.each` (`Hash[K,V]`'s real,
  already-shipped Enumerable method, plan 70 — walks the flat pair
  buffer sequentially, never calls `into_int_value` on a key, so it
  works correctly regardless of key type) rather than `record["role"]`,
  exactly the same workaround plan 118 built `.get` for. This plan does
  not duplicate plan 118's `.get` mechanism for a plain `Hash[String,
  String]` (there is no `JsonValue`-style enum receiver here to gate an
  intrinsic on) — a future, general fix to `Hash[K,V]` `[]` indexing
  (out of scope for this plan, same as plan 118) would make `record[
  "role"]` work for free once it lands; until then, `.each` is this
  plan's own disclosed, correct path.
- **A short or long data row relative to the header, under `Csv.parse_
  with_headers`, is a real per-row `Err`-worthy condition this plan
  surfaces rather than silently padding or truncating.** The `csv`
  crate's own `Reader` has two real, documented postures here: `
  flexible(false)` (its own default) rejects a record whose field count
  doesn't match the header's via a real `csv::Error`; `flexible(true)`
  accepts any field count. This plan uses the crate's own default
  (`flexible(false)`) for `Csv.parse_with_headers` specifically — a row
  with fewer or more fields than the header genuinely can't build a
  complete, correct `Hash[String,String]` (which key does an extra
  trailing field belong to? which key is missing a value for a short
  row?), and returning a wrong-but-plausible-looking `Hash` would be a
  worse failure mode than a real `Err`. `Csv.parse` (the positional
  form) has no such problem — a short/long row is just a shorter/longer
  `Array[String]`, a fact the caller can already see by checking
  `.count`, so it uses `flexible(true)` instead and never rejects a
  row for its field count alone.
- **Dialect configuration: delimiter and quote character are
  configurable per the crate's own real `ReaderBuilder`/`WriterBuilder`
  API (`.delimiter(byte)`/`.quote(byte)`), but this plan's own v1
  surface fixes both to CSV's own RFC 4180 defaults (`,` and `"`) and
  does not expose them as Emerald-level parameters.** The `csv` crate
  itself supports arbitrary single-byte delimiters (tab-separated data,
  semicolon-delimited European-locale CSV, pipe-delimited data are all
  real, common variants a `ReaderBuilder::delimiter(b'\t')` call
  handles natively) and a configurable quote byte — this plan's
  `Csv.parse`/`Csv.parse_with_headers`/`Csv.write` intrinsics call
  `ReaderBuilder`/`WriterBuilder` with their own real, un-overridden
  defaults rather than adding a second parameter to every one of these
  functions' Emerald-level signatures for a dialect knob most callers
  never need. A `Csv.parse_with_delimiter(s: String, delim: String):
  Result[...]`-shaped follow-up is real, additive, disclosed future
  work — not attempted here, since this plan's own Concrete Proof (an
  ordinary comma-delimited file) doesn't need it and every dialect
  variant is a strictly separate entry point, not a change to this
  plan's own two functions' signatures.
- **`Csv.write`'s quoting is the crate's own `QuoteStyle::Necessary`
  default, not a hand-rolled "does this field contain a comma" check —
  a real, disclosed reason to trust the dependency rather than
  reimplement its core value proposition.** `csv::Writer` quotes a
  field only when required (it contains the delimiter, the quote
  character, a `\r`, or a `\n`) and doubles any embedded quote
  character per RFC 4180 automatically; this plan's `emerald_rt_csv_
  write` function passes `Array[Array[String]]`'s rows straight to
  `csv::Writer::write_record` one row at a time and lets the crate's
  own, already-battle-tested quoting logic decide — re-deriving that
  logic by hand (the exact kind of "when does a CSV field need
  quoting" edge-case surface `serde_json`/`toml`/`saphyr` all exist
  specifically to keep this batch's other plans from hand-rolling) is
  precisely what depending on a vetted crate instead of writing more
  C/Rust from scratch is supposed to avoid, restated concretely here.
- **No typed-row deserialization (`csv::Reader::deserialize`'s own
  `#[derive(Deserialize)] struct Record { ... }` path) — identical
  reasoning to plan 118/119/120, restated briefly rather than assumed
  silently inherited, since this plan's own row-shaped API surface is
  different enough from the other three that the connection isn't as
  immediately obvious as it is between three tree-shaped siblings.**
  Emerald has no macro/attribute/codegen-derive system; a user who
  wants `Person`-typed rows writes their own `def row_to_person(r:
  Hash[String,String]): Result[Person, String]` by hand against `Csv.
  parse_with_headers`'s own output, fully expressible today.
- **Line-ending handling: the crate's own default (`\r\n` and `\n` both
  accepted on read; `\n` written on write, matching what `csv`'s own
  `Terminator::CRLF`-vs-default choice already documents) is used
  unmodified — this plan does not add an Emerald-level line-ending
  parameter.** Real-world CSV interoperates across both conventions
  constantly (a file exported from a spreadsheet tool on one platform,
  consumed on another); the crate's own read-side leniency (RFC 4180
  formally specifies `\r\n`, but `csv`'s reader accepts a bare `\n` too,
  a real, deliberate compatibility choice on the crate's own part, not
  this plan's) means this plan inherits correct behavior for free by
  not overriding it.
- **Out of scope.** Dialect configuration beyond RFC 4180 defaults
  (delimiter/quote-character overrides — see above, real additive
  follow-up); typed/derive row deserialization; a streaming `CsvReader`
  resource handle that yields rows one at a time off an open `File`
  without materializing the whole `Array[Array[String]]`/`Array[Hash[
  String,String]]` in memory at once (a real, useful capability for a
  large file, genuinely different from this plan's own buffer-in,
  array-out `Csv.parse` — deferred to whatever handle/lifetime
  convention plan 93 establishes, the same posture plan 118 already
  took for a streaming JSON parser, not designed here); a general fix
  to `Hash[K,V]`'s `[]` indexing for non-`Int64` keys (plan 118's own
  scope cut, inherited unchanged); CSV writing directly to a `File`
  handle rather than returning a `String` (`Csv.write`'s own output can
  already be passed to `File.write`, plan 45's existing function — no
  new I/O path needed).

## Update (2026-09-22, EXECUTE)

Implemented exactly as designed, no scope reduction. `Csv.parse`/
`.parse_with_headers`/`.write` reuse `Array[String]`'s own real `[len: i64]
[elem: *const c_char]*n` buffer layout (`Env.keys`'s own established
construction pattern) and `Hash[String,V]`'s own real pair-buffer layout
(plan 118's `lower_object`, reused in shape, not code) directly — no
`JsonValue` tree, exactly per this plan's own central design decision.
`"Not yet decided" item 1` resolved: the crate's own default `csv::Error`
`Display` text is surfaced as-is, not extended with position information —
consistent with plan 118/119's own plain-`String`-message convention, and a
real per-plan decision left open by design, not settled batch-wide.

**Three real, previously-undisclosed codegen bugs found and fixed**, all in
`Stmt::MatchResult`'s own `Ok(v)`-binding machinery — never previously
exercised by a nested or compound `T`, since every prior plan's own
`Result[T, E]` used a flat `T` (`Bytes`, `HttpResponse`, `JsonValue`, plain
`String`):

1. `local_array_elem_types` was never populated for an `Array[T]`-typed
   `Ok(v)` binding at all — `Csv.parse`'s own `rows[0]` indexing failed
   outright with "cannot determine the element type." Fixed by mirroring the
   sibling enum-field-binding path's own already-correct handling.
2. The `"Result[T, E]"` string-splitting used a naive first-match
   `str::split_once(", ")` to separate `T` from `E` — a REAL, silent-
   corruption-shaped bug, not merely a missing feature: it breaks whenever
   `T` itself contains a nested multi-param generic (`Result[Hash[String,
   String], String]`, `.parse_with_headers`'s own real return type), finding
   the FIRST `", "` inside `Hash`'s own two type arguments rather than the
   real top-level split point, producing two garbled, unbalanced-bracket
   strings for `t_name`/`e_name` with no error raised at all. Fixed with a
   new `split_top_level_comma_space` bracket-depth-aware helper, applied
   here and to the two sibling `Hash[K, V]`/`Pair[K, V]` string parsers
   (`parse_hash_type`/`parse_pair_type`) sharing the identical bug.
3. `.each` on an `Ok(v)`-bound `Hash[K,V]` failed with "cannot determine the
   class of `v`" — `local_classes` was never populated for a compound,
   non-class/enum/newtype type string. Fixed narrowly for `Hash[`/`Pair[`
   prefixes only, deliberately NOT extended to `Array[` too: that broader
   fix was tried first and found to regress plain array indexing (`rows[0]`
   started reporting "unsupported method call `Array[Array[String]].[]`"),
   since indexing needs the receiver absent from `local_classes` to reach
   its own dedicated `local_array_elem_types`-keyed fast path rather than
   falling through to generic method-call dispatch — a real, disclosed
   near-miss, caught by testing the broader fix and finding it broke a
   passing case, not assumed safe.

**A fourth, genuinely separate architectural limitation found but
deliberately NOT fixed** (a real scope decision, not an oversight): the
`.each do |x| ... end` inline-block-to-Proc synthesis mechanism itself does
not work when nested inside a `match ... Ok(v) do ... end` body at all — a
`Proc`-typed argument reaches codegen as a raw, unresolved block-literal AST
node instead of an already-hoisted top-level name, hitting `call_named_proc`'s
own "enumerable Proc argument is not a plain local" internal-error path.
`examples/csv_demo.em` works around this the same way this session has
worked around every other real grammar/compiler gap: restructured, not
hidden — the `Hash` value is hoisted out to a `var` declared before the
`match` and assigned inside `Ok(records) do ... end`, with `.each` called
afterward at the top level, never nested. The underlying gap is named here,
explicitly, as real follow-up work outside this plan's own charter (fixing
the block-hoisting/synthesis mechanism itself is separate, substantial
compiler-architecture work), not chased to closure.
