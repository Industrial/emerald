# Plan 139 — MySQL

MySQL is this batch's second pure-Rust wire-protocol win, and it earns
that verification independently rather than by analogy to plan 138 —
Postgres and MySQL are different protocols implemented by different
Rust crates with a genuinely different relationship to async, and this
plan checks MySQL's own facts rather than assuming they mirror
Postgres's. `mysql` (crates.io, `28.0.2`, Sep 2026) is the synchronous
client from blackbeam's `rust-mysql-simple` repository — 80 stable
releases, MIT/Apache, 229K downloads/month, 228 dependent crates. Unlike
plan 138's `postgres` (a thin blocking wrapper spinning up a private
Tokio runtime around `tokio-postgres`'s async core), `mysql` is a
from-scratch, natively synchronous implementation — it shares MySQL's
row/value/protocol codec logic with the async `mysql_async` crate
through a common lower-level `mysql_common` crate, but `mysql` itself
never touches an async runtime. This is a real, useful distinction for
this project: plan 94's async-to-sync bridging convention, which plan
138 leans on for Postgres, has nothing to do here — MySQL's sync client
was synchronous natively, not bridged into being synchronous.

## Concrete proof this plan targets

```ruby
conn: Int64 = Mysql.connect("mysql://root@localhost:3306/emerald_demo")
Mysql.execute_direct(conn, "CREATE TABLE IF NOT EXISTS users (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(255) NOT NULL, active TINYINT(1) NOT NULL)")

insert: Int64 = Mysql.prepare(conn, "INSERT INTO users (name, active) VALUES (?, ?)")
Mysql.bind_string(insert, 1, "Grace")
Mysql.bind_boolean(insert, 2, true)
Mysql.execute(insert)

select: Int64 = Mysql.prepare(conn, "SELECT name, active FROM users WHERE active = ?")
Mysql.bind_boolean(select, 1, true)
cursor: Int64 = Mysql.query(select)
while Mysql.step(cursor)
  name: String = Mysql.column_string(cursor, 0)
  active: Boolean = Mysql.column_boolean(cursor, 1)
  puts name
  puts active
end
Mysql.close(conn)
```

Expected output: `Grace` then `true` — a row inserted through `?`-bound
parameters and read back through a bound, `TINYINT(1)`-as-`Boolean`
filtered `SELECT`. Like plan 138, this example needs a reachable MySQL
server to run for real; it is not self-contained the way plan 137's
in-memory SQLite proof is.

## Decision log

- **`mysql`'s independence from `mysql_async` at the runtime level is a
  real, checked fact, not an assumption carried over from plan 138's
  Postgres relationship — stated explicitly because a reader who just
  read plan 138 could reasonably expect the same shape here and would
  be wrong to.** Verified this session via `mysql`'s own crates.io
  listing (`28.0.2`, repository `blackbeam/rust-mysql-simple`, distinct
  from `mysql_async`'s `blackbeam/mysql_async` repository): `mysql` is
  its own client, not a wrapper generated by blocking on `mysql_async`'s
  futures. This plan therefore needs zero plan-94 bridging machinery —
  a genuine simplification relative to plan 138, disclosed here as a
  real difference rather than glossed as "the same pattern as Postgres."
- **Parameterized queries are the only path that exists, using MySQL's
  own `?` positional placeholder syntax — the same token plan 137's
  SQLite uses, distinct from plan 138's numbered `$1`/`$2`.** `Mysql.
  bind_*` writes into an owned buffer applied via `mysql::Params::
  Positional` at `execute`/`query` time; `Mysql.execute_direct(conn,
  sql)` exists only for parameter-free DDL, matching both sibling
  plans; no function anywhere in this surface accepts a caller-built SQL
  string carrying an interpolated value.
- **`TINYINT(1)` maps to `Boolean` — a real, MySQL-specific decision
  Postgres's driver never had to make, because Postgres has a native
  `boolean` type and MySQL does not.** MySQL represents boolean-like
  columns as `TINYINT(1)` by long-standing convention (the type itself
  is a numeric `TINYINT`; `BOOLEAN`/`BOOL` are recognized in `CREATE
  TABLE` syntax purely as aliases for `TINYINT(1)`, per MySQL's own
  documented behavior). This plan's `column_boolean`/`bind_boolean`
  therefore specifically target columns declared `TINYINT(1)` (checked
  via the result set's column-metadata length/flags, which `mysql`'s
  own `Column` type exposes) and treat zero as `false`, nonzero as
  `true`; any other `TINYINT` width, or a `TINYINT` not declared with
  display width `1`, stays `Int64` rather than silently becoming a
  `Boolean` — the ambiguity is resolved by looking at the real column
  metadata, not by guessing from a single query's data.
- **Unsigned `BIGINT` can overflow `Int64`, a real edge case Postgres's
  driver structurally cannot hit.** Postgres has no unsigned integer
  types at all; MySQL's `BIGINT UNSIGNED` ranges up to roughly 1.8×10^19,
  past `i64::MAX` (~9.2×10^18). `column_int64` on such a column raises a
  plan-93 error when the actual value exceeds `i64::MAX`, rather than
  silently reinterpreting the bit pattern as a negative `Int64` — a real
  correctness hazard this plan states plainly rather than treats as a
  hypothetical.
- **`SET`-typed columns return MySQL's own comma-joined text form, not a
  parsed collection — the same `Array[T]`-has-no-runtime-length reasoning
  plan 138 already applied to Postgres arrays, not re-derived here.**
  MySQL's `SET` type can hold multiple string labels from a fixed
  enumerated list simultaneously; `mysql` itself already surfaces a
  `SET` value as its serialized comma-separated string, which this plan
  keeps as-is (`String`) rather than splitting it into an `Array[String]`
  or `Hash[Int64, String]` — consistent with plan 138's decision to
  decline runtime-sized collection materialization from a SQL driver at
  all, for the same underlying `Array[T]` representation limit (plan
  45). A caller needing individual `SET` members can call Emerald's own
  `.split(",")` (plan 45) on the returned string.
- **`DECIMAL`/`NUMERIC` narrow to `Float64` with the identical disclosed
  precision loss plan 138 accepted for Postgres's `numeric`.** Both
  engines offer arbitrary-precision fixed-point storage Emerald's
  `Type` enum (verified, plan 59: no decimal/fixed-point member) cannot
  represent losslessly; this plan does not attempt a different, MySQL-
  specific answer to a problem that is identical in both drivers.
- **`BLOB`/`BINARY`/`VARBINARY` are out of scope — the third and last of
  this batch's three SQL drivers to hit the same missing-`Bytes`-type
  wall.** `column_string` on any binary-family column is a plan-93 error,
  matching plans 137 and 138 exactly, all three waiting on the same
  future cross-cutting `Bytes` type rather than each improvising a
  different workaround.
- **TLS is out of scope for v1, the same disclosed limitation plan 138
  states for Postgres.** `mysql` supports TLS behind its own optional
  `native-tls`/`rustls` Cargo features; this plan does not enable either,
  so `Mysql.connect` only reaches a server accepting plaintext
  connections. A future plan pairing this driver with a TLS crate is the
  honest place to add it.
- **Out of scope.** Connection pooling (`mysql::Pool` exists and this
  plan deliberately does not wrap it — one `Mysql.connect` is one
  dedicated `mysql::Conn`, matching plans 137/138's posture), MySQL's
  `LOAD DATA INFILE` and replication-protocol features, migrations, and
  any row-to-class-instance/query-builder layer — a driver, not an ORM.
