# Plan 175 — Audio Decoding

`symphonia` is a real, actively developed (release dated 2026-08-13 per
docs.rs, verified this session), pure-Rust, modular multimedia decoding
library — the same project a 2021 Reddit announcement (found this
session, "Symphonia v0.3: pure-Rust decoders for MP3, WAV, FLAC, AAC")
shows has years of continuous development behind its current 0.6.x
line. Wrapping it gives Emerald programs the ability to read real-world
audio files into raw samples with zero C dependency (no `libmp3lame`,
no `libFLAC`, no `libvorbis` linked) — flagged explicitly as
stretch-tier since audio decoding is a narrower-audience capability
than this batch's networking/crypto/data-format plans, but a genuine,
working one once shipped.

## Concrete proof this plan targets

```ruby
bytes: Bytes = File.read_bytes("examples/fixtures/tone.wav")
audio: AudioBuffer = Audio.decode(bytes)
puts audio.sample_rate
puts audio.channels
samples: Array[Float64] = audio.read_samples(100)
puts samples.length
```

Expected output: the fixture's real, known sample rate (e.g. `44100`),
channel count (e.g. `1`), and `100` — the exact number of samples
requested, decoded from real PCM data, not synthesized placeholder
values.

## Decision log

- **Decode-only is the correct v1 scope because symphonia itself has no
  encoder — this is not a self-imposed limitation, it is the actual
  shape of the underlying crate.** Verified this session via a real
  Rust-users-forum thread: a symphonia user states plainly "Symphonia
  works great as an audio decoder, however unfortunately it doesn't
  support encoding," using a separate crate (`video-rs`) for encoding
  needs. This plan does not attempt to work around that gap by adding a
  second encoding-capable crate — encoding is named explicitly as
  out-of-scope future work, not silently absent.
- **MPL-2.0 is a real, materially different license from every other
  crate this batch has selected, and is disclosed rather than treated
  as equivalent to MIT/Apache-2.0.** Verified via docs.rs. MPL-2.0 is
  weak-copyleft at the *file* level (modifications to MPL-licensed
  files must themselves stay MPL, but the license does not propagate to
  separate files/crates linking against it — unlike GPL). This does not
  block using symphonia in `emerald-rt` (a straightforward "use the
  crate as a dependency" case, not a "modify and redistribute its
  source" case), but plan 95's ledger records it as the one MPL entry
  in an otherwise MIT/Apache-2.0/BSD dependency tree, since a future
  reader auditing `DEPENDENCIES.md` for license compliance should not
  have to independently rediscover this.
- **Per-codec/per-container feature selection, not the crate's own
  blanket `all` feature, mirrors the same dead-code-elimination
  discipline plan 91 established for the C runtime.** symphonia is
  explicitly modular by design (verified via its own docs.rs feature-
  flag list: `symphonia-bundle-mp3`, `symphonia-codec-aac`, etc. are
  all separate, individually-optional crates) — an Emerald program that
  only ever calls `Audio.decode` on WAV files should not force-link
  MKV/CAF/AAC container-parsing code it never reaches, the same
  per-symbol pruning argument plan 91's `--gc-sections` decision and
  plan 122's regex-crate choice both already made for their own
  domains.
- **Opus is confirmed absent, and this is stated plainly rather than
  glossed over.** Checked this session against symphonia's own
  currently-listed optional codec dependencies (flac, mp3, aac, adpcm,
  alac, pcm, vorbis) — no Opus decoder crate appears among them. Some
  other language ecosystems' "batteries included" audio stacks do
  support Opus out of the box; this plan's real, disclosed gap is that
  Emerald's v1 audio support does not, until and unless a dedicated
  Opus decoder crate is vetted and added in a later, separate plan.
- **Decoded samples are exposed via a plan-93 handle with chunked
  `.read_samples(n)`, not one unbounded `Array[Float64]` returned in
  full — the same no-GC-heap-growth caution already raised for large
  buffered data elsewhere in this batch.** A multi-minute stereo audio
  file at a typical sample rate can produce tens of millions of raw
  samples; materializing that whole into one Emerald `Array` on a
  runtime with no garbage collector (per plan 91/93's own repeated
  finding) risks exactly the unbounded-growth failure mode plan 105's
  multipart-upload plan already named for large request bodies.
- **Out of scope.** Audio encoding (symphonia provides none, confirmed
  above), Opus decoding (a real, disclosed current gap), real-time
  playback/output-device integration (this plan decodes to samples in
  memory; routing those samples to actual speaker hardware is an
  unaddressed, separate problem — likely needing a crate like `cpal` in
  a future plan), and audio effects/DSP (resampling, filtering,
  mixing) are all explicitly not covered here.
