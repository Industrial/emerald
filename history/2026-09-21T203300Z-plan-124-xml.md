# Plan 124 — XML Parsing

`quick-xml` (current release 0.42.0, published 2026-08-22, MIT-licensed,
owned by `tafia`/`Mingun`/`dralley` on crates.io — verified this session
via docs.rs) is the standard pure-Rust XML choice: its own top-level
documentation states plainly that it "contains two modes of operation" —
a StAX-model streaming API (`Reader`/`Writer`, pull-based, the user
explicitly asks for the next event) for documents too large to hold
entirely in memory, and an optional `serialize` feature (gated behind
the `serialize` Cargo feature, `quick_xml::de`/`quick_xml::se`) for
struct-shaped serde deserialization. This plan uses neither serde
integration directly — Emerald has no `#[derive(Deserialize)]`-equivalent
mechanism to hang typed deserialization off of, the same real gap plan
126 (Protocol Buffers) has to design around at much greater length — and
instead builds a small tree-mode on top of the crate's own streaming
`Reader`, which is exactly how many languages' "parse XML to a DOM tree"
convenience APIs are implemented over a lower-level pull parser (roxmltree
does the same thing, purpose-built; this plan gets it "for free" as
~50 lines of Rust rather than a second crate dependency).

## Concrete proof this plan targets

```ruby
xml: String = "<library><book title=\"Dune\" author=\"Herbert\" /><book title=\"1984\" author=\"Orwell\" /></library>"

tree: Result[XmlNode, String] = Xml.parse(xml)
case tree do
  when Ok(root) do
    match root do
      Element(tag, attrs, children) do
        puts tag
        i: Int64 = 0
        while i < children.length do
          child: XmlNode = children[i]
          match child do
            Element(book_tag, book_attrs, _) do
              title: Option[String] = book_attrs.get("title")
              match title do
                Some(t) do
                  puts t
                end
                None do
                  puts "untitled"
                end
              end
            end
            Text(_) do
            end
          end
          i += 1
        end
      end
      Text(_) do
        puts "unexpected text root"
      end
    end
  end
  when Err(msg) do
    puts msg
  end
end

reader: XmlReader = Xml.reader_from_string(xml)
event: XmlEvent = reader.next_event
match event do
  StartElement(tag, _) do
    puts tag
  end
  EndElement(_) do
  end
  Text(_) do
  end
  Eof do
  end
end
```

Expected output, in order: `library` (the root element's tag, walked via
tree mode), `Dune`, `1984` (each `<book>`'s `title` attribute, read via
`Hash[String,String].get` and plan 73's `Option[String]`), then `library`
again (the streaming reader's very first event, a `StartElement` for the
root, proving both entry points parse the identical document
consistently).

## Decision log

- **Tree shape reuses plan 118's own dynamic-value answer rather than
  re-deriving one.** The task this batch works from names plan 118
  (JSON) as the place Emerald's real answer to "how does a dynamically-
  shaped parsed value map onto a static type system" was decided — a
  fixed ADT built on plan 52's `enum`/pattern-matching mechanism (plus
  plan 73's `Option[T]` and the already-shipped `Hash[K,V]`/`Array[T]`),
  not a dynamic `Any`/reflection type, which Emerald's whole design
  (no `method_missing`, no runtime reflection) forecloses anyway. `XmlNode`
  is that same strategy applied to XML's own two-shape tree (an element
  has a tag, attributes, and children; a text node is just a string) —
  simpler than JSON's six-variant `JsonValue` because XML's own grammar
  is simpler, not because a different strategy was chosen.
  `Hash[String, String]` (already-shipped, plan 9/25) is the attribute
  map — XML attributes are always string-valued, so there is no need for
  `JsonValue`'s richer nesting there.
- **`quick-xml` supplies no tree/DOM API of its own — this plan writes
  one, on top of the crate's own streaming `Reader`, entirely inside
  `emerald-rt`.** This is a real, disclosed scope difference from every
  other crate in this batch: `Xml.parse` is not a thin one-call wrapper
  around a library function, it is Emerald-authored Rust glue code (a
  recursive descent over `Reader::read_event_into`'s `Event` stream,
  building `XmlNode` values) that happens to use `quick-xml` for
  tokenization. This is the same shape of work plan 91's own
  `emerald_rt_fnv1a_hash` proof function is (real logic, zero-dependency
  algorithm) scaled up to a real dependency underneath it.
- **The streaming `XmlReader` handle needs plan 93's resource-handle
  model, for the same reason plan 122's `Regex` does** — a
  `quick_xml::reader::Reader<R>` holds a live cursor position and (for
  the file-backed constructor) an open file handle, both of which must
  be explicitly disposed rather than garbage-collected, since Emerald
  has no tracing GC (a locked identity constraint, restated in plan 59's
  own framing). Tree-mode sidesteps this entirely by never exposing a
  `Reader` to Emerald source at all — `Xml.parse` opens, fully drains,
  and closes its internal reader within one Rust-side call, returning
  only an owned `XmlNode` tree, which is why tree mode needs no handle
  disposal story of its own.
- **v1 is restricted to UTF-8 input — `quick-xml`'s `encoding` feature
  (non-ASCII-compatible encodings like UTF-16, detected via the XML
  declaration) is declined.** Emerald's own `String` is UTF-8 by
  definition (`spec/TYPE_SYSTEM.md` §9); accepting a UTF-16-encoded
  document would require transcoding before it could ever become an
  Emerald `String` at all, a real additional step this plan's two entry
  points don't attempt. A document with no `encoding=` declaration, or
  an explicit `encoding="UTF-8"`, is the overwhelmingly common real-world
  case and the only one v1 supports; anything else surfaces as a parse
  `Err`, not silent mojibake.
- **CDATA sections and ordinary text both collapse to `XmlNode::Text`/
  `XmlEvent::Text` — no separate CDATA variant.** Nothing downstream in
  this plan's own worked proof, or any plausible v1 consumer, needs to
  distinguish "text that happened to be CDATA-escaped" from "text that
  wasn't" — both represent the same logical string content once parsed.
  Comments and processing instructions are silently skipped by the
  tree-builder (never appear in `XmlNode`) and are not yet surfaced as
  their own `XmlEvent` variant in streaming mode either — see Out of
  scope.
- **Malformed input is `Result[XmlNode, String]`/`Result[XmlReader,
  String]` (plan 53), matching plan 122's and 123's identical reasoning:
  malformed XML arriving from a file or network payload is routine,
  expected, non-programmer-bug failure**, not `File.read`'s
  abort-on-error precedent (plan 45).
- **Out of scope.** XML namespaces and prefix resolution (`quick-xml`
  ships a separate `NsReader` for this; v1's plain `Reader` keeps
  qualified names as raw strings, e.g. `"ns:tag"`, unresolved); DTD/XML
  Schema validation; XPath or any query language over the tree; writing/
  serializing an `XmlNode` back out to XML text (`quick_xml::writer::
  Writer` — read-only in this plan); the `serialize` feature's serde
  integration (no Emerald-side derive mechanism exists to consume it);
  async streaming via the `async-tokio` feature (this batch has no
  async runtime yet — see the task's own note that a distinct plan
  covers that); comments/processing-instructions as distinct queryable
  nodes (currently silently dropped, not merely deferred rendering).
