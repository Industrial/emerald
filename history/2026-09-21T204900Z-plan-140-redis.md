# Plan 140 — Redis

Redis is the one database in this batch whose own value model needs no
real translation effort to reach Emerald's stdlib types. Every plan
covering a SQL database (137, 138, 139) had to build a real, disclosed
narrowing between a large, statically-typed column-type system and
Emerald's five-member scalar surface. Redis has no schema and no column
types at all — a key holds a string, a list of strings, a hash of
string fields to string values, or a set of strings, and every RESP
reply a command produces is one of: nil, an integer, a single bulk
string, or a *flat* array of the above — RESP arrays do not nest inside
Redis's own command replies in ordinary use (no built-in command returns
an array-of-arrays or an array-of-hashes). That flatness is the reason
this plan, alone in this batch, needs no dynamic, JSON-style value type
the way plan 118 does for genuinely arbitrary nested documents: each
Redis command's reply shape is fixed and known from the command itself
(`GET` always yields one nilable string, `LRANGE` always yields a flat
list of strings, `HGETALL` always yields flat field/value pairs), so
every function in this plan's surface can commit to one concrete,
statically-typed Emerald return type, not a dynamic value a caller has
to inspect at runtime.

`redis` (redis-rs) is also this batch's most straightforwardly mature
dependency, checked directly this session: `1.7.0` (Sep 2026), a real
`1.x` stable line (18 stable releases recorded on crates.io, not a
project still shipping `0.x`), BSD-3-Clause, maintained by Armin
Ronacher, Shachar Langbeheim, and the `redis-rs` organization, 9.19M
downloads/month, depended on by 2,322 crates. It implements RESP
natively — no C dependency — and ships both a synchronous `Connection`
type and an async `aio`/`MultiplexedConnection` pair; this plan uses the
synchronous one directly, needing none of plan 94's bridging machinery,
a third distinct posture from this batch's other database plans (plan
137's SQLite is never async to begin with; plan 138's Postgres driver
bridges an async core; plan 139's MySQL driver is natively synchronous
like this one, but for an unrelated reason — `mysql`'s own from-scratch
design, not a choice between two APIs on the same crate).

## Concrete proof this plan targets

```ruby
conn: Int64 = Redis.connect("redis://127.0.0.1:6379")
Redis.set(conn, "visits", "0")
Redis.incr(conn, "visits")
Redis.incr(conn, "visits")
count: String? = Redis.get(conn, "visits")
count ||= "0"
puts count

Redis.rpush(conn, "colors", "red")
Redis.rpush(conn, "colors", "green")
Redis.rpush(conn, "colors", "blue")
colors: Hash[Int64, String] = Redis.lrange(conn, "colors", 0, -1)
i: Int64 = 0
n: Int64 = Redis.llen(conn, "colors")
while i < n
  puts colors[i]
  i += 1
end
Redis.close(conn)
```

Expected output: `2`, then `red`, `green`, `blue` — a counter
incremented twice via `INCR` and read back through a nilable `GET`
(defaulted through plan 43's `||=`, never dereferencing a real miss),
and a list built with `RPUSH` and read back whole via `LRANGE`.

## Decision log

- **`redis-rs`'s crossing into a stable `1.x` line is a real, checked
  fact this plan leans on, not an assumption inherited from its
  popularity.** Verified this session against its crates.io release
  history: `1.7.0`, 18 stable releases, actively published as recently
  as 2026-09-05. Combined with its download volume and dependent-crate
  count, this is the least equivocal maturity case in this batch after
  Postgres's driver — no pre-1.0 caveat needed, unlike plan 137's Turso
  comparison.
- **List and set commands materialize into `Hash[Int64, String]`, not
  `Array[String]` — a deliberate reuse of `Hash`'s already-dynamic
  runtime behavior to sidestep `Array[T]`'s no-length-metadata wall
  (plan 45), the same underlying constraint plan 138 hit for Postgres
  array columns, resolved oppositely here for a stated, specific
  reason.** `Array[T]`'s representation (verified, plan 45: `build_
  array_lit`'s own doc comment) carries no runtime length, so a
  variable-length `LRANGE`/`SMEMBERS` reply cannot honestly become one
  without a companion count value the way `.split`/`.split_count`
  needed one. `Hash[K,V]`, by contrast, is already a genuinely dynamic,
  runtime-sized container in this compiler today (its existing "key not
  found" runtime abort, cited in plan 45's own Decision log, is only
  possible because `Hash` already supports arbitrary runtime population
  — unlike `Array[T]`, which only ever holds literal, compile-time-sized
  contents). Indexing a Redis list result by `Hash[Int64, String]` with
  integer keys `0..n-1` costs nothing new to build and reuses existing,
  working machinery. Plan 138 declined the equivalent move for Postgres
  arrays instead of adopting it, for a real, different reason: a
  Postgres array column is a comparatively rare relational-schema
  feature with a workable SQL-side escape hatch (`unnest()`); Redis's
  list/set commands are core, ubiquitous parts of exactly the command
  surface this plan exists to cover — declining them here would gut the
  plan's own stated scope in a way declining Postgres arrays does not
  gut plan 138's.
- **`Redis.get` returns `String?`, a real nilable type, because a cache
  miss is Redis's single most ordinary, expected outcome — not an
  error.** `redis::Value::Nil` maps directly to Emerald `nil` through
  plan 43's existing nullable-reference mechanism (the same zero-cost
  `ptr`-with-a-spare-null-bit-pattern relabeling plan 59's own
  `String.from_cstring` already uses) — no exception, no `Result`, just
  an ordinary nilable value a caller defaults with `||=` exactly as this
  plan's own Concrete Proof does.
- **Pub/sub needs its own, separate connection and its own handle
  registry — a real `redis-rs` API constraint, not an arbitrary design
  choice.** Calling `.as_pubsub()` on a `redis::Connection` consumes it,
  converting it permanently into subscribe-mode use; the same connection
  can no longer run ordinary `GET`/`SET`-style commands afterward. This
  plan's `Redis.subscribe` therefore opens a fresh connection internally
  rather than reusing the caller's existing command-connection handle,
  and stores it in a distinct pubsub-handle registry so plan 93's
  handle-closing discipline (a stale pubsub handle vs. a stale command
  connection) stays independently checkable for each.
- **`Redis.next_message` is a blocking poll, not a callback — this
  plan's whole surface is synchronous, and pub/sub does not get a
  special exception.** `PubSub::get_message` blocks the calling thread
  until a message arrives on a subscribed channel; Emerald source calls
  it in an ordinary loop. No async runtime, no event-loop integration,
  and no plan-94 bridging is introduced for this one feature even though
  pub/sub is the part of Redis's surface that most naturally suggests an
  event-driven design — that shape is deliberately not built here.
- **Command coverage is curated, not exhaustive — Redis's real command
  surface is close to 250 commands; this plan covers the common core the
  task brief names explicitly (GET/SET/expiry, list/hash/set operations,
  pub/sub) and stops there.** `MULTI`/`EXEC` transactions, Lua scripting
  (`EVAL`/`EVALSHA`), streams (`XADD`/`XREAD`), `SCAN`-family cursor
  iteration, and Redis Cluster/Sentinel topology-aware connection
  management are all real, substantial `redis-rs` features this plan
  does not wrap — each is closer in scope to its own plan than to a
  sub-bullet of this one.
- **TLS is out of scope for v1, the same disclosed limitation plans 138/
  139 state for their own drivers.** `redis-rs` supports TLS behind its
  own optional `tls-native-tls`/`tls-rustls` Cargo features; this plan
  enables neither, so `Redis.connect` only reaches a plaintext
  `redis://` endpoint, not `rediss://`.
- **Out of scope.** Connection pooling (one `Redis.connect` is one
  dedicated `redis::Connection`, matching every other driver plan in
  this batch), Redis Cluster and Sentinel support, Lua scripting,
  streams, and `MULTI`/`EXEC` transactions (all named above), and any
  higher-level caching abstraction (a TTL-aware cache wrapper, a
  memoization helper) — this plan is a command-surface driver, not a
  caching framework.
