## Concrete proof this plan targets

```ruby
Http.serve(8080) { |req: HttpRequest|
  if req.path == "/hello"
    HttpResponse.new(200, "hello " + req.method)
  else
    HttpResponse.new(404, "not found")
  end
}
```

Run against a real client from the same test harness (not `.em` source
— a Rust `#[test]` inside `emerald-cli/tests/examples.rs`'s own
integration-test scaffolding, spawning the compiled binary, issuing one
`GET http://127.0.0.1:8080/hello` via `std::net::TcpStream` or `ureq`
itself, and asserting the raw HTTP response): a request to `/hello`
gets back status `200` with body `hello GET`; a request to `/missing`
gets back status `404` with body `not found`. This is deliberately
**not** a network-dependent proof the way plan 100's is — the server
and its one test client both run on `127.0.0.1`, entirely inside the CI
sandbox, no external service required. A buggy implementation that (a)
inlined the block at compile time the way `.each`'s block normally would
(plan 10/34's default) would fail to compile or link at all, since
`Http.serve`'s handler must be called an unbounded, runtime-determined
number of times from native code, not a fixed number of times unrolled
into `main`; (b) got the request-method/path/body marshaling wrong would
produce a body other than `hello GET`; (c) let a handler's own crash
propagate past the trampoline would kill the whole server process
instead of returning a `500` for that one request.

## Decision log

- **`tiny_http` over an async, `hyper`-based server — the "advanced"
  server is explicitly plan 106's job, not this plan's.** `tiny_http`
  0.12.0 (released Oct 6, 2022 — its most recent crates.io release,
  confirmed this session; see the staleness note below) is 100% blocking,
  needs no runtime at all, and its own README states its philosophy
  plainly: "Everything else (parsing... routing, etags, cache-control,
  HTML templates, etc.) must be handled by your code... I strongly
  recommend using a framework instead of this library [for a website]."
  That is the correct trade for a v1 stdlib primitive: a minimal,
  synchronous request/response server that composes with plan 94's
  sync-first posture with zero bridging, at the cost of no HTTP/2, no
  built-in routing, no middleware. A `hyper`/`axum`-based server (this
  batch's own brief names plan 106 as that "advanced" follow-up)
  requires plan 94's heavier `tokio::Runtime`-behind-`block_on` bridging
  for every single request, a materially bigger commitment this plan
  declines to make for a v1 primitive whose whole purpose is proving the
  native-calls-back-into-Emerald mechanism works at all.
- **A real, disclosed maintenance caveat: `tiny_http`'s crates.io
  releases stopped in October 2022, though the GitHub repository shows
  continued activity.** Checked this session, not assumed: `tiny_http`
  0.12.0 is dated Oct 6, 2022 on `lib.rs`; no newer version has shipped
  to crates.io since. Its GitHub repository (`tiny-http/tiny-http`,
  fetched directly this session) is still active by every other signal
  — 1.1k stars, 58 open issues, 18 open PRs, 556 commits on `master` —
  and its `master`-branch README already documents a feature
  (`native-tls` support alongside `OpenSSL`/`Rustls`) that the last
  *released* version's own README does not mention, meaning real,
  unreleased work exists on top of 0.12.0. Downloads remain substantial
  (4.89M/month, used in 1,029 crates including the `rouille` web
  framework) and no RustSec advisory is known as of this session (to be
  re-confirmed via `cargo audit` at execution time, per plan 95). This
  is stated plainly as a real trade-off this plan accepts rather than
  hides: `tiny_http` is stable and widely deployed, but a maintainer who
  needs a crates.io release for a specific unreleased fix would have to
  either vendor a git dependency or wait — a genuine, disclosed risk a
  v1 stdlib dependency carries, weighed against the alternative (a
  `hyper`-based server needing plan 94's full async bridge) and still
  judged the better v1 choice.
- **The central, load-bearing decision: per-connection dispatch does
  NOT go through an Emerald actor, even though the task framing that
  motivated this plan suggested exactly that — rejected here for a
  real, concrete, sourced reason, not by default.** Plan 55's own
  Decision log, read in full this session, states two facts that
  together make actor-based request dispatch technically impossible as
  designed today: first, "a cross-actor-reachable method must declare
  no return type... sema requires every method declared on an `actor`
  to omit its return type entirely" (the one exception, `initialize`,
  is called only synchronously by `.spawn` before any mailbox exists);
  second, "this plan does not add futures/promises/an `ask` pattern" —
  a cross-actor call is a fire-and-forget mailbox enqueue with no
  mechanism to get a value back, ever. An HTTP handler is fundamentally
  a request/response function: it must produce an `HttpResponse` that
  flows back out over the *same* TCP connection the request arrived on.
  Routing each connection to a "worker actor" per the task's own
  suggested framing would require that worker actor's `handle_request`
  method to *return* an `HttpResponse` across a cross-actor call — a
  capability plan 55 explicitly does not have and explicitly declined to
  build ("a real, substantial, separate design surface"). Building an
  `ask`-pattern extension to plan 55 as a prerequisite for this plan
  would be a large, separate undertaking, disproportionate to what an
  HTTP server v1 needs to prove. This plan therefore does not use actors
  at all for request dispatch: `tiny_http` already provides real
  OS-thread concurrency internally ("each client connection will be
  dispatched to a thread pool... one thread per client," confirmed from
  its own README this session), so the concurrency problem is already
  solved at the native layer, and each request's handler trampoline is
  called directly, synchronously, on whichever `tiny_http` worker thread
  produced that request — a plain function call, not a mailbox enqueue.
- **The handler block is compiled as a genuine, standalone, uniform-ABI
  function — a real, disclosed departure from plan 10/34's own
  call-site-inlining default, reusing plan 55's trampoline *concept*
  instead.** Every prior block-accepting construct in this language
  (`.call` on a `Proc` local, `yield` inside a `&blk`-declaring
  function, `.each { |x| ... }`) compiles its attached block "fresh per
  call site," per plan 10's own Decision log — effectively inlined
  into the one place it's invoked, known and fixed at compile time.
  `Http.serve`'s block cannot work that way: it must be callable an
  unbounded, runtime-determined number of times, from a thread that
  did not exist at compile time, dispatched by *native Rust code*
  holding nothing but a function pointer — structurally the same
  problem plan 55 solved for cross-actor dispatch with its own
  trampoline: "a uniform ABI... void trampoline(i8* self, i64* argv)...
  data flowing through a queue, the same category of thing as a C
  `qsort` comparator argument, never a runtime lookup." This plan reuses
  that exact idea (a plain, statically-resolved function pointer with a
  fixed calling convention, synthesized once at the `Http.serve(...) {
  ... }` call site and handed to native code), but not plan 55's
  runtime machinery (no mailbox, no actor scheduling) — only the
  underlying insight that a block whose identity is fully known at
  compile time can cross an FFI boundary as a bare function pointer with
  no first-class-closure-value machinery required. This is the one
  piece of infrastructure that makes this plan shovel-ready where plan
  103's analogous problem is not (see that plan's own Decision log):
  `Http.serve` has exactly one call site producing exactly one handler,
  known statically; `tonic`'s generated service trait needs one such
  pointer *per RPC method name*, discovered from a `.proto` file, a
  materially bigger code-generation problem this plan does not share.
- **No resource handle is returned to Emerald source in v1 — `Http.serve`
  blocks the calling "thread" (in codegen terms, the calling function's
  control flow) forever, mirroring `tiny_http`'s own blocking
  `incoming_requests()` iterator, which never terminates on its own.**
  Plan 93's opaque-`u64`-handle-plus-`.close()` model is the right shape
  for a server a caller might want to stop — deliberately deferred here
  rather than half-built: `emerald_rt_http_serve` runs its accept loop
  to completion (i.e., never, absent a process signal) on whatever
  Emerald call invoked it, the same "runs forever" contract as, for
  instance, an ordinary blocking `while true` loop already has in this
  language. A stoppable server (`Http.serve` returning a handle,
  `.stop()` closing the listening socket) is real, disclosed, deferred
  work — plan 93's model is the right target for it once a concrete need
  exists, not invented speculatively here.
- **A panicking handler must not crash the server — the FFI panic
  boundary from plan 91/92 is enforced per-request, not just per
  process-lifetime call, a real refinement this plan needs that plan
  91's own single-shot `emerald_rt_fnv1a_hash` proof didn't need to
  demonstrate.** `emerald_rt_http_serve`'s Rust-side request loop wraps
  *each* call to the handler function pointer in its own
  `std::panic::catch_unwind`, not one `catch_unwind` around the whole
  accept loop — a panic inside one request's handler must not tear down
  the loop that is still serving every other connection. A caught panic
  is converted into a `500 Internal Server Error` response for that one
  request (mirroring `tiny_http`'s own documented behavior: "If a
  `Request` object is destroyed without... `respond` being called, an
  empty response with a 500 status code... will automatically be sent
  back," confirmed from `tiny_http`'s real `Request` docs this session
  — this plan's explicit `catch_unwind`-then-500 path makes that
  guarantee deliberate rather than relying on `tiny_http`'s own
  destructor-triggered fallback, which fires on early-`Drop`, not
  specifically on a Rust panic having occurred).
- **A new hazard class this plan is the first to open: ordinary,
  non-actor Emerald code now genuinely runs concurrently, on multiple
  real OS threads, with no isolation.** Every prior concurrency
  mechanism in this language (plans 54/55/57) is actor-isolated by
  construction — plan 55's own safety argument is "at most one
  in-flight message per actor... no lock around the actor's own fields
  at all" specifically *because* only actor code ever runs on more than
  one thread. A `Http.serve` handler block is ordinary code, and
  `tiny_http`'s own thread pool may invoke the *same* synthesized
  handler function concurrently, from different OS threads, for
  different simultaneous requests. Per plan 10's "captures are by
  value... a snapshot at closure-creation time," the block's own capture
  environment is written once (at the `Http.serve(...)` call site) and
  only ever read afterward, which is safe under concurrent access with
  no synchronization — but if the handler body reads or writes any
  *other* shared mutable state (a field on a class instance captured
  and shared across requests, say), nothing in this plan or in the
  language today protects that access. This is stated here explicitly
  as a real, novel gap this plan opens, not one it closes — the
  practical mitigation for v1 is that a handler block that only reads
  its own request parameter and captured-by-value locals (exactly this
  plan's own Concrete Proof) is safe by construction; anything beyond
  that is the caller's own responsibility, undocumented and unchecked.
- **Out of scope.** Routing (`Http.serve` dispatches every request to
  one handler block; a path-based router is a separate, higher-level
  stdlib feature that could be built *in Emerald* on top of this
  primitive, not this plan's job), request headers (only method/path/
  body are marshaled in v1 — see Not yet decided), streaming
  request/response bodies, HTTPS (`tiny_http`'s own `ssl-rustls`
  feature is the integration point, deferred to align with plan 99's
  real, landed TLS convention), graceful shutdown, and any
  multi-port/multi-handler `Http.serve` call are all declined. A
  `DEPENDENCIES.md` ledger entry for `tiny_http` (plan 95's checklist,
  including this plan's own disclosed crates.io-staleness caveat above)
  is this plan's responsibility.

concretely (contrast plan 103, where the analogous problem has no comparably

**Zero new grammar, zero new block-typing mechanism — both confirmed false
worries in the plan's own text.** `grammar.lalrpop`'s `ChainCallExpr`
production already parses `<Ident>.<method>(<args>) <DoBlock>` for ANY

... end` needed zero grammar changes. `infer_lambda_type` (`emerald-sema`)
already resolves a block param's declared type generically via `resolve_type`
against `classes` (works for `HttpRequest` the identical way it already works
for every other registered newtype) and infers the block's return type from
its own body — the "extends the block-typing mechanism" leaf this plan's own
text worried about needed zero new sema machinery either.

**`HttpRequest` is an `Int64` newtype over the handle registry**, not a new
hardcoded `Type::HttpRequest` compound variant — mirroring plan 100's own
`HttpResponse` precedent exactly, for the identical reason (avoids touching
every exhaustive `Type` match throughout the compiler).

**`HttpResponse.new(status, body)`, exactly as the plan's own Concrete Proof
writes it, can never reach reserved-namespace dispatch at all** — `"new"` is a
grammar-reserved keyword parsing unconditionally into `Expr::New` (real class
instantiation), the identical finding plan 109 already made for
`Sha256.new()`. Renamed `HttpResponse.build(status, body)`.

**The genuinely new mechanism: the calling convention.** The attached block
compiles via `build_inline_lambda` — the SAME machinery `.each do |x| ... end`
already uses to compile ITS OWN block into a real, separate, standalone
top-level LLVM function (`Linkage::Internal`, `fn(env_ptr, params...) -> ret`)
— a real, disclosed correction to the plan's own "effectively inlined... a
fixed number of times unrolled" framing: every block literal in this compiler
already compiles to a genuine function, not inlined instructions; what
`Http.serve` needed was a way to call that function from NATIVE Rust code
holding nothing but a function pointer. Built as a hand-written, call-site-
unique `extern "C-unwind" fn(i64) -> i64` trampoline (named/keyed by the
block's own source span, so multiple `Http.serve` call sites in one program
never collide) that: stores the block's own closure pointer into a call-site-
unique `Linkage::Internal` global (the standard "thunk with captured state
behind a global" technique a plain function pointer needs when it also needs
closure state — referenced only by its raw ADDRESS from Rust, never by symbol
name, so no multi-TU ODR concern the way plan 55's own actor trampolines had
to solve with `WeakODR`); loads the closure and its own function pointer back
inside the trampoline body; wraps the real indirect call to the compiled block
body in the IDENTICAL `setjmp`/`push_handler` catch frame
`declare_actor_trampolines` already establishes for actor methods (plan 57's
crash-isolation pattern, reused verbatim) — an uncaught Emerald exception
inside a handler becomes a real `HttpResponse.build(500, "Internal Server
Error")` value constructed INSIDE the trampoline itself, never a `longjmp`
reaching across the Rust FFI boundary at all (the same "unwinding/`longjmp`ing
across a plain `extern "C" fn` boundary is UB" reasoning `emerald-rt`'s own
module doc already states, applied here in the opposite direction).

**A real, empirically-found Rust-level correction**: `emerald_rt_http_serve`'s
own `handler` parameter is `extern "C-unwind" fn(i64) -> i64`, not the plan's
own literal `extern "C"`. Verified directly by writing this plan's own
required panic-inside-a-handler test: a plain `extern "C" fn` that panics has
its unwind turned into an immediate process `abort()` by Rust itself the
moment it tries to leave that function's own frame — BEFORE the panic ever
reaches `http_serve`'s own `catch_unwind` wrapping the call, making that
`catch_unwind` a genuine no-op for exactly the case it exists to catch.
`extern "C-unwind"` (stabilized alongside the ABI of the same name, Rust 1.71)
is Rust's own real fix. Harmless for the real, compiled-Emerald-trampoline
case (which never uses Rust's own unwinding at all, per the paragraph above) —
`http_serve`'s own `catch_unwind` is a real, but strictly secondary, second
layer; the PRIMARY protection is the trampoline's own `setjmp` frame.

**Two further real, previously-undisclosed codegen bugs found and fixed**,
both because this plan's own Concrete Proof is the FIRST use, anywhere in this
session, of a reserved-namespace newtype-constructing call used inside an
inline block literal:

1. `free_vars_in_lambda`'s own `collect_idents_in_expr` is purely syntactic

   no notion of a reserved-namespace/class-static-call receiver —
   `Expr::MethodCall(recv, ..)`'s own arm walked into ANY `recv`, so
   `HttpResponse.build(...)` used inside the block body made `build_inline_
   lambda` treat `"HttpResponse"` as a free variable this block must capture
   from its enclosing scope, hard-erroring since no such local variable exists

   `free_vars_in_lambda`'s own result against `ctx.classes`/`ctx.newtypes`
   before resolving captures — a name that's actually a registered class/
   newtype is never a real capture. Real, disclosed scope limit: this only
   covers names already registered as a class/newtype (which is what

   entry at all (`Env`, `Random`, `Json`, none of which are ever registered as
