# Plan 135 — Brotli Compression

Brotli is the one format in this sub-batch where "pure Rust or C
binding" is a genuinely subtler question than a one-line crate
description answers, and this plan verifies it rather than assuming
either direction. The `brotli` crate (`dropbox/rust-brotli`, currently
authored/maintained primarily by Daniel Reiter Horn) states its own
"Project Requirements" plainly in its README: **"Direct no-stdlib port
of the C brotli compressor to Rust... no dependency on the Rust
stdlib."** This is not a wrapper generated by `bindgen` against
Google's C headers, and it is not a thin FFI shim calling into a
compiled `libbrotli.so`/`.a` — it is Google's reference C
implementation's actual algorithm, control flow, and data structures,
manually or semi-mechanically transliterated into Rust source, function
by function, compiled as ordinary Rust code with the ordinary Rust
compiler. The crate's README even states the reverse relationship is
also true and load-bearing: rust-brotli "is a drop-in replacement for
the official... C implementation" — good enough, byte-for-byte, at
compression levels 0-9 (per the README's own "Compression Usage"
section) that Dropbox has historically built `libbrotli.so` *from this
Rust source* as a replacement for the real C library in production.
That is the real, verified distinction from plan 131's `zstd`: this is
a transliteration that stands on its own as compiled Rust, not a Rust
API layered over compiled C.

## Concrete proof this plan targets

```ruby
original: Bytes = "the quick brown fox jumps over the lazy dog, the quick brown fox jumps over the lazy dog".to_bytes()
fast: Bytes = Brotli.compress(original, 1)
puts Brotli.decompress(fast) == original

best: Bytes = Brotli.compress(original, 11)
puts Brotli.decompress(best) == original
puts best.length <= fast.length
```

Expected output: `true`, `true`, `true` — round-trip correctness at
both ends of brotli's real `0..=11` quality range, plus the same
"higher quality never produces a larger output than lower quality for
the same input" check plan 131 used for zstd's own level range — the
genuinely verifiable claim this format's own tunable-quality feature
makes, not merely "compression happened."

## Decision log

- **"Transliteration, not bindings" is a real, verified technical
  distinction, not a rhetorical one — and it is exactly what plan 95's
  policy asks this plan to nail down precisely rather than wave at.**
  The crate's own README, read in full this session, is unambiguous:
  its stated project requirement is a "no-stdlib port," and its
  changelog (`brotli` 8.0.x/9.0.0 entries, also read this session)
  describes ongoing Rust-native FFI-boundary hardening work — "Wrap the
  mutable Broccoli FFI entry points in a local `catch_unwind` helper,"
  "Return `NULL`... rather than writing state through a NULL pointer,"
  "Reject serialized BroCatli buffers with out-of-range... fields
  before constructing the state" — the kind of memory-safety and
  panic-boundary fixes that only make sense to describe and land inside
  a crate that *is* the implementation, not inside a thin wrapper whose
  correctness would instead be entirely the upstream C library's
  problem. Per plan 95's central axis, `brotli` is a pure-Rust crate;
  its own optional, explicitly-opt-in `ffi`/`ffi-api` features (declined
  by this plan, see the scaffolding leaf) exist so *other, non-Rust*
  programs can link against rust-brotli as if it were the C library —
  a consumer-facing compatibility surface this plan's own Rust-to-Rust
  usage has no reason to enable.
- **Compression quality is a real, exposed `Int64` parameter (`0..=11`),
  on the same footing as plan 131's zstd level, not plan 130's fixed
  DEFLATE default or plan 134's parameterless LZ4.** Brotli's own
  design (and its README's own "Compression Usage" section, read this
  session) documents a real, wide quality range with a real
  documented compatibility guarantee at the low end ("bitwise identical
  to the brotli C compression engine at compression levels 0-9") —
  precisely the kind of genuinely useful, checkable tuning knob this
  sub-batch's Decision logs have consistently chosen to expose (plan
  131) rather than fix (plan 130, plan 134) when the format itself
  makes it a real value proposition rather than an incidental detail.
- **HTTP `Content-Encoding: br` is this format's real, primary use case
  today, and this plan states that tie to plans 100/101 explicitly
  rather than treating `Brotli` as a generic, undifferentiated fourth
  compression option.** Brotli was designed by Google specifically for
  HTTP content compression and is a registered IANA HTTP content
  coding; modern browsers advertise `Accept-Encoding: gzip, deflate,
  br` by default, and brotli routinely beats gzip's compression ratio
  at comparable or better decompression speed for the kind of
  text-heavy payloads (HTML, JSON, JS, CSS) HTTP traffic is mostly made
  of — the concrete reason this plan exists in the same 130-136
  sub-batch as the general-purpose formats rather than being deferred
  entirely until an HTTP plan needs it. Plans 100/101 (HTTP client/
  server, authored elsewhere in this batch) are the plans expected to
  actually call `Brotli.compress`/`Brotli.decompress` when negotiating
  `Content-Encoding`; this plan itself builds no HTTP-specific glue
  (header parsing, content-negotiation logic) — that is those plans'
  job, layering on top of this one exactly as plan 132's `Tar` layers
  on top of plan 130's `Gzip`.
- **`std` is kept as an explicit feature rather than pursuing this
  crate's real `no_std` capability, matching plan 134's identical call
  for `lz4_flex`.** rust-brotli genuinely supports `no_std`/no-allocator
  operation (its README's "Using the C interface" and manual-memory-
  management sections describe building the decompressor against
  caller-supplied stack/heap-backed allocators with zero libc calls,
  aimed at kernel/embedded/sandboxed use) — real capability, irrelevant
  to `emerald-rt`, which already links Rust's full standard library.
  Declared for the same disclosure reason as plan 134's equivalent
  bullet: not an oversight, a real capability this target environment
  has no use for.
- **No custom-dictionary support (`attach_dictionary`/
  `attach_serialized_dictionary`, new in the crate's `9.0.0` release, verified this
  session against its changelog) in v1.** A real, recently-added feature
  letting a decoder/encoder share a pre-agreed LZ77 prefix dictionary
  across many small, structurally-similar payloads (directly analogous
  to plan 131's declined zstd-dictionary feature, and useful for the
  same class of problem — many small, similar HTTP responses) — this
  plan declines it for the identical reason plan 131 declined zstd
  dictionaries: no training-corpus/dictionary-management API surface
  exists in this stdlib yet for either format, and `Brotli.compress`'s
  one-shot shape has no natural place to pass one through.
- **No stream concatenation (`-bare -appendable`/`-catable`, `BroCatli`)
  surface in v1.** A real brotli-specific capability (cheaply
  concatenating independently-compressed chunks into one valid stream,
  documented at length in the crate's own README) with no
  corresponding need in this plan's own streaming `BrotliWriter`/
  `BrotliReader` design, which always produces/consumes one complete,
  standard, non-bare brotli stream per file.
- **Out of scope.** No custom dictionaries (above), no stream
  concatenation/`BroCatli` (above), no `ffi`/`ffi-api` C-ABI-compat
  surface (above — irrelevant to Rust-to-Rust calls), no `no_std` build
  (above), no multithreaded compression (the crate's own multithreaded
  `CompressMulti` API exists but is not wired in), no HTTP-specific
  content-negotiation logic (plans 100/101's job, layered on top).
