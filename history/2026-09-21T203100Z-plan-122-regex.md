# Plan 122 — Regular Expressions

Verified directly against `crates/emerald-sema/src/lib.rs`'s real `Type`
enum (plan 59's own finding, re-cited here rather than re-derived: `Int64,
Float64, String, Boolean, Void, Symbol, Nil, Class, Array, Hash, Tuple,
Enum, Result, Supervisor, Pair` — no `Regexp`, nothing pattern-matching
shaped) and against plan 45's own Decision log, which states plainly: "A
`Regexp` type/engine is explicitly out of scope... a real, separate
design question... deserving its own future plan." That gap has stood
unfilled since plan 45 (2026-09-09). This is that future plan. It is a
genuine capability upgrade, not an incremental stdlib addition — Emerald
programs today cannot express a single pattern-matching operation on a
string without hand-rolling substring search.

The crate chosen — `regex` (`rust-lang/regex`, owned by the Rust project
itself, current release 1.13.1 as of 2026-07-15, 91.8M downloads/week,
used directly or transitively by over 105,000 crates, verified this
session via lib.rs) — is a deliberate, security-relevant choice, not the
only option. Its own README states the load-bearing guarantee plainly:
"all regex searches in this crate have worst case `O(m * n)` time
complexity, where `m` is proportional to the size of the regex and `n`
is proportional to the size of the string being searched." This is a
real, structural property of its finite-automata architecture — the
crate lacks backreferences and lookaround specifically because, per its
own documentation, these are "not known how to implement efficiently"
within that guarantee — not a performance claim to take on faith.
Independent verification this session (HackTricks' own ReDoS reference
page, a 2026-01-08 HeroDevs security writeup, and a 2026-03-30 itnext.io
engine-internals piece) all name this crate, alongside Go's `regexp` and
Google's RE2 itself, as members of the small set of regex engines immune
to catastrophic backtracking by construction, not by mitigation. Most
languages' default regex engines (PCRE, Python's `re`, Ruby's `Onigmo`,
JavaScript's native `RegExp` outside newer linear-time opt-ins) are
backtracking NFA implementations with genuine exponential worst-case
behavior on adversarial input — a real, exploitable denial-of-service
class (ReDoS) that this crate's architecture makes structurally
unreachable for any pattern it accepts to compile at all. Choosing it as
Emerald's *only* regex engine, rather than a more backtracking-featureful
one, is a real, disclosed tradeoff: some genuinely useful constructs
(backreferences, lookaround) are permanently unavailable — see Out of
scope.

## Concrete proof this plan targets

```ruby
result: Result[Regex, String] = Regex.compile("(\\d{4})-(\\d{2})-(\\d{2})")

case result do
  when Ok(re) do
    puts re.is_match("shipped on 2026-09-21")

    found: Option[String] = re.find("shipped on 2026-09-21")
    match found do
      Some(m) do
        puts m
      end
      None do
        puts "no match"
      end
    end

    caps: Option[Array[Option[String]]] = re.captures("shipped on 2026-09-21")
    match caps do
      Some(groups) do
        year: Option[String] = groups[1]
        match year do
          Some(y) do
            puts y
          end
          None do
            puts "no year"
          end
        end
      end
      None do
        puts "no captures"
      end
    end

    puts re.replace_all("2026-09-21 and 2026-01-08", "$3/$2/$1")
  when Err(msg) do
    puts msg
  end
end
```

Expected output, in order: `true` (a real match exists), `2026-09-21`
(the whole-match text), `2026` (capture group 1, the year), and
`21/09/2026 and 08/01/2026` (both dates reformatted via `$N`
capture-reference replacement, proving `regex`'s own `Replacer` impl for
`&str` is reached unmodified through the FFI boundary).

## Decision log

- **No existing pattern-matching mechanism collides with this plan.**
  Confirmed against plan 45's Decision log directly (quoted above) —
  `.split`/`.strip`/`.slice` are all literal-substring operations with
  zero pattern syntax; there is nothing to migrate or deprecate.
- **`Regex` is a resource handle, not a value type, and its exact
  representation depends on plan 93.** A compiled `regex::Regex` owns
  Rust-side heap state (its own automaton tables) that must outlive
  every call using it and be freed exactly once — this is precisely the
  "resource with a lifetime distinct from an Emerald value's own scope"
  problem plan 93 is named to solve. This plan assumes plan 93's
  contract supplies *some* opaque handle wrapper (most likely a
  `Box`-then-raw-pointer pattern with an explicit dispose/finalize
  call) and slots `Regex` into it; if plan 93 lands with a materially
  different shape, this plan's handle plumbing — not its Emerald-facing
  method surface — is what would need to change.
- **Strings cross the boundary with zero conversion, reusing plan 59's
  already-verified finding, not a new (ptr,len) buffer.** Regex
  operates on human-readable pattern/haystack/replacement text, which
  Emerald's `String` already represents as a bare malloc'd,
  null-terminated UTF-8 buffer (plan 59, plan 45) — bit-identical to
  what `regex::Regex::new`/`.is_match`/`.find` etc. accept via
  `CStr::to_str()`. Plan 92's binary-safe `(ptr, len)` buffer convention
  (built for base64/bincode/protobuf/arrow's genuinely non-UTF-8,
  possibly-NUL-containing payloads) is the wrong tool here and is not
  used — a real, deliberate distinction between "this is text" and
  "this is bytes" this plan makes explicit rather than reaching for the
  newer convention reflexively.
- **Boolean crosses the boundary as a widened `Int64`, following the
  codebase's own existing precedent for the identical hazard, not a new
  rule.** Plan 59 found that Emerald's `Boolean` is a bare LLVM `i1`
  while a real C ABI boundary expects a full byte, and that the existing
  runtime already handles this directly: `emerald_bool_to_string`
  "takes a plain `long long`, not a C `_Bool`/`i1`... codegen
  zero-extends the `i1` value before calling it." `emerald_rt_regex_is_
  match` returns an `i64` (0 or 1) for the identical reason, and codegen
  narrows it back to a genuine `i1` with an `icmp ne 0` at the call
  site — the same trick run in reverse, not a new marshaling scheme.
  This differs from plan 59's own conclusion that Boolean is simply
  *declined* as an extern-signature type: that finding is about
  user-declared `unsafe extern "C"` blocks, where the compiler cannot
  verify the real callee's ABI. Here the compiler controls both sides
  of the call (the `emerald-rt` Rust source and the LLVM declaration in
  `emerald-codegen`), so it can choose and enforce a safe convention
  itself rather than trusting an unverified external signature.
- **`Array[T]`-returning methods (`find_all`, `split`) each ship a
  `_count` sibling, reusing plan 45's own forced workaround rather than
  inventing a new one.** `Array[T]` still carries no runtime length
  metadata (plan 45, re-verified as still true this session — no change
  to that representation has landed in any plan between 45 and 91).
  `.find_all_count`/`.split_count` perform an independent second scan,
  exactly the "disclosed, accepted inefficiency" plan 45's own `.split`/
  `.split_count` pair already normalized for this codebase.
- **`.captures` returns `Option[Array[Option[String]]]`, not a flat
  `Array[String]` with empty-string sentinels for non-participating
  groups — a real, deliberate improvement plan 45's own `.split` could
  not have made.** Plan 45 predates plan 73's `Option[T]` entirely (`nil`/
  `T?` were still the only nullable mechanism at the time), so its own
  workarounds for "a slot might not have a value" default to sentinels.
  Plan 73 replaced that mechanism outright with a real generic `Some`/
  `None` sum type built on plan 52's ADT machinery. A `regex` crate
  capture group inside an alternation (e.g. `(a)|(b)`) genuinely may not
  participate in a given match — `Option[String]` represents that
  faithfully; an empty-string sentinel would be indistinguishable from a
  group that matched an empty string on purpose. This plan uses the
  current, better mechanism rather than copying an older plan's now-
  superseded pattern reflexively.
- **Compile errors surface as `Result[Regex, String]`, using plan 53's
  real, already-shipped `Result[T, E]`/`Ok`/`Err`/`case ... when` — not
  a runtime abort.** Unlike `File.read`'s disclosed abort-on-error
  precedent (plan 45, matching `Hash[K,V]`'s own miss-aborts behavior),
  an invalid regex pattern is routine, expected, user-triggerable
  failure — the kind of error plan 53's own Decision log identifies
  `Result` as existing precisely for, in contrast to the harder-to-
  recover-from failures plan 38's exception model handles. `E` is a
  plain `String` (the `regex::Error`'s own `Display` output) rather than
  a richer error-class hierarchy — no new error-class ADT is invented
  for one failure mode.
- **Every exported function is wrapped in `std::panic::catch_unwind`,
  matching plan 91's mandatory convention exactly, proven once already
  in working code (`emerald_rt_fnv1a_hash`) and generalized here to a
  crate with real internal invariants that could theoretically panic
  (an out-of-bounds slice index inside `regex`'s own matching loop,
  say) rather than only a hand-written arithmetic function that
  structurally cannot.**
- **Out of scope.** No backreferences or lookaround (structurally
  excluded by the crate's own linear-time architecture — this is the
  disclosed cost of the security property this plan exists to deliver,
  not an oversight); no named capture groups (`(?P<name>...)`) — exposing
  a name-to-value map needs a `Hash[String, Option[String]]` return
  shape and a decision about duplicate/absent names this plan defers;
  no `regex::bytes::Regex` (matching on non-UTF-8 `&[u8]` — Emerald has
  no byte-array type distinct from `String` yet outside plan 92's
  handle-shaped `Bytes`, and wiring that in is a follow-up, not this
  plan); no `RegexSet` (simultaneous multi-pattern matching); no
  replace-with-a-block/closure (Emerald blocks aren't threaded through
  any FFI boundary anywhere in this batch); no compiled-pattern caching
  sugar at the language level (the crate's own README recommends
  `std::sync::LazyLock` for reuse across calls — Emerald has no static/
  lazy-value binding mechanism to hang that on yet, so callers simply
  call `Regex.compile` once and hold the resulting handle themselves,
  same as any other resource plan 93 will define).
