# Plan 131 — Zstandard Compression

This is the plan in the 130-136 sub-batch where plan 95's crate-vetting
policy is genuinely contested, not a formality — and it is answered
here plainly rather than deferred. The official `zstd` Rust crate
(`crates.io/crates/zstd`, maintained at `gyscos/zstd-rs`) is, by its
own GitHub repository description verified this session, **"a rust
binding for the zstd compression library."** That is not this plan's
paraphrase; it is the maintainer's own one-line description of the
crate. Zstandard is Facebook/Meta's format (RFC 8878), and the
reference C implementation (`facebook/zstd`) is the algorithm's own
canonical, most-optimized, most-complete implementation — this plan's
own verification this session (`zstd-sys`'s real `build.rs`, read in
full) confirms the Rust crate does not reimplement the algorithm at
all: it vendors `facebook/zstd`'s actual C source tree as a git
submodule and compiles it with the `cc` crate at Rust build time, then
exposes it through thin `zstd-safe`/`zstd` wrapper layers. This plan
adopts that binding anyway, as a deliberate, disclosed exception to
pure-Rust-first, because — verified this session against `ruzstd`'s own
current (`0.9.0`, July 2026) documentation — no pure-Rust
implementation yet matches it: `ruzstd`'s own crate docs state its
decompressor is "about 3.5 times slower" than the C original on highly
compressible data and its *compressor*, while real and usable as of
this crate's recent `0.7`/`0.8`/`0.9` releases, explicitly "does not
yet reach the speed, ratio or configurability of the original zstd
library" in the maintainer's own words.

## Concrete proof this plan targets

```ruby
original: Bytes = "the quick brown fox jumps over the lazy dog, the quick brown fox jumps over the lazy dog".to_bytes()
compressed: Bytes = Zstd.compress(original, 3)
puts compressed.length < original.length
restored: Bytes = Zstd.decompress(compressed)
puts restored == original

high: Bytes = Zstd.compress(original, 19)
puts Zstd.decompress(high) == original
puts high.length <= compressed.length
```

Expected output: `true`, `true`, `true`, `true` — the first three lines
mirror plan 130's own round-trip proof shape (real compression
happened, real decompression recovers the exact original bytes); the
fourth line is Zstandard-specific: a real, higher compression level
(`19`, out of the format's genuine `1..=22` range) must never produce a
*larger* compressed output than a lower level (`3`) for the same
input — the actual, verifiable ratio/level tradeoff this format is
chosen for, not merely "compression happened at all."

## Decision log

- **This is a real, disclosed C-binding exception to plan 95's
  pure-Rust-first policy — stated plainly, not minimized.** Per plan
  95's own axis (name every crate's pure-Rust-vs-C-backed status
  explicitly, never default silently), `zstd` fails the pure-Rust test:
  its own maintainer-written GitHub description says "binding," and
  `zstd-sys`'s real `build.rs` (read this session) proves it by
  compiling `zstd/lib/{common,compress,decompress}/*.c` (excluding
  `xxhash*.c`, inlined via `zstd`'s own "PRIVATE API" mode) plus, on
  `x86_64`, one real assembly file
  (`zstd/lib/decompress/huf_decompress_amd64.S`) through `cc::Build`.
  This is not a system-library runtime dependency, though — no
  `pkg-config`, no `apt install libzstd-dev`, no dynamically-linked
  `.so` a deployed `emerald-cli` binary would need present on the
  target machine. It vendors the C source and compiles it at `cargo
  build` time into a static archive, then that archive becomes part of
  `crates/emerald-rt`'s own `staticlib` output — structurally the
  identical "compile a vendored C tree at Rust build time, embed the
  resulting `.a`" shape plan 91's own `build.rs` already uses for
  `runtime/emerald_runtime.c`, just with `zstd-sys`'s `cc::Build`
  standing in for `emerald-driver`'s own. The redistributable-binary
  guarantee plan 91's Decision log established — a copied `emerald-cli`
  binary needs no repo/source access at a user's link time — holds
  identically for this C exception; it is a real compile-time
  dependency on a C compiler being present in the *build* environment
  (already true today: `cc` is already a build-dependency of
  `emerald-driver` for the existing C runtime), not a new deployment
  requirement.
- **`ruzstd` was verified this session, not assumed stale, and the
  honest finding is more favorable to it than the task's own initial
  framing assumed — worth stating precisely rather than repeating a
  now-outdated "decode-only" characterization.** `ruzstd` 0.9.0 (crates.io
  sparse-index-verified, published 2026-07-26) ships both a `decoding`
  module (the crate's own docs: "a complete implementation of a
  Zstandard decompressor") and an `encoding` module with real level
  support (`Uncompressed`/`Fastest`/`Default`/`Better`/`Best`, roughly
  levels 1/3/7/11), checksums, and dictionary support — no longer
  decode-only as of this session's real check. The crate's own docs are
  nonetheless explicit that its compressor "does not yet reach the
  speed, ratio or configurability of the original," and its own
  benchmark numbers put decoding at "about 3.5 times slower" than
  `libzstd` on highly-compressible data (closing to "only... 1.4 times
  slower" on harder-to-compress data like a `.iso`). That gap is real
  and, for a compression stdlib module whose whole value proposition is
  "fast enough to be worth calling instead of gzip," disqualifying for
  v1 — but `ruzstd`'s decode side in particular is genuinely mature
  ("currently actively maintained," fuzzed, tested against real `.zst`
  corpora) and is named here as the concrete, real candidate for a
  future plan wanting Zstandard *decompression* with zero C toolchain
  dependency — e.g. a `wasm32-unknown-unknown` target where `zstd-sys`'s
  vendored-C-and-`cc`-compile approach may not apply the same way plan
  64's existing `wasm32-wasip1` runtime path does. That future plan is
  not this one.
- **Compression level is a real, exposed `Int64` parameter here, unlike
  plan 130's fixed-default choice for gzip/deflate/zlib — because
  level is Zstandard's actual headline feature, not an incidental
  tuning knob.** Zstandard's whole design premise (per RFC 8878 and
  `facebook/zstd`'s own documentation) is a wide, genuinely useful
  speed/ratio tradeoff range (levels `1` through `22`, with `0` meaning
  "library default," verified against the crate's own `bulk::compress`
  signature taking a `level: i32`) — collapsing that to one fixed level
  the way plan 130 did for DEFLATE's comparatively narrower `0..=9`
  range would throw away the actual reason a program reaches for `Zstd`
  over `Gzip` in the first place. Out-of-range values are the real C
  library's own problem to reject (libzstd itself validates and returns
  a real error code for a level outside its supported range) —
  Emerald-side range validation is explicitly not duplicated here.
- **`zstd::bulk` is the tentative one-shot API surface, not
  `zstd::stream::{encode_all,decode_all}` — a real, disclosed
  uncertainty, not a final decision.** `bulk::compress`/`bulk::
  decompress` operate on plain `&[u8]`/pre-allocated output buffers with
  no intermediate `Read`/`Write` adapter, which maps more directly onto
  plan 92's `(ptr, len)` boundary convention than `stream::encode_all`'s
  `io::Read`-based signature does — but `bulk::decompress` requires the
  caller to know (or over-allocate) the decompressed size ahead of time,
  which is a real usability gap `zstd`'s own frame-content-size header
  can sometimes but not always fill in. This plan states the intended
  direction (`bulk`) rather than asserting it as settled, consistent
  with plan 91's own precedent of marking a genuinely unverified
  technical detail (there: platform link flags) as \"confirm empirically\"
  rather than asserted fact.
- **Streaming handles deliberately mirror plan 130's `GzipWriter`/
  `GzipReader` shape exactly, not a Zstandard-specific variant.**
  `zstd::stream::{Encoder,Decoder}<std::fs::File>` wrapped behind plan
  93's opaque-handle-plus-`.close()` model, same `.write_chunk`/
  `.read_chunk`/empty-`Bytes`-means-EOF conventions as plan 130. A
  program switching between `Gzip`/`Zstd` for the same streaming
  workload changes one namespace name and nothing else about its
  control flow — a real, deliberate consistency choice across this
  sub-batch's two general-purpose compression formats, not an
  accidental convergence.
- **No dictionary-based compression, no multi-threaded compression
  (`zstdmt`), no advanced/experimental API surface in v1.** `zstd-sys`
  gates a `zstdmt` feature (real multi-threaded compression, `-pthread`
  linked in) and a `legacy` feature (decoding older, pre-1.0 zstd frame
  formats) — both left off by this plan's `default-features = false`
  dependency declaration. Dictionaries (`zstd::dict`, useful for
  compressing many small, structurally-similar payloads — e.g. JSON API
  responses — better than any single one compresses alone) are a real,
  useful zstd feature this plan declines for v1: building a dictionary
  needs a training corpus and its own API surface, and `Zstd.compress`/
  `Zstd.decompress`'s bulk one-shot shape has no natural place to pass
  one through yet.
- **Out of scope.** No `zstd` CLI-compatible framing options
  (`--rsyncable`, content checksums beyond the format default, long-
  distance matching window tuning), no dictionary training/use (above),
  no multi-threaded compression (above), no `ruzstd` integration of any
  kind in this plan (named only as a future alternative, not wired in).
  `.tar.zst` composition is plan 132's job, layering `tar`'s archive
  format over this plan's `Zstd.compress`/`ZstdWriter`, exactly as
  `.tar.gz` is plan 132's job over plan 130.
