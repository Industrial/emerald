# Plan 99 — TLS (Transport Layer Security)

Every plan in this batch that needs to speak an encrypted protocol —
this plan's own `Tls.connect`/`Tls.listen`, and, per this session's own
stated numbering, plans 100-102 (an HTTP client and server that must
handle `https://` URLs, and WebSockets over `wss://`) — depends on this
one TLS implementation rather than each rolling its own. This is also
the single clearest test case in the entire 101-plan batch for plan
95's pure-Rust-first policy, because the obvious alternative is not a
hypothetical: TLS in a systems language has historically meant linking
OpenSSL, a large, C-implemented library with its own long, well-known
history of memory-safety CVEs (Heartbleed being the canonical example,
though not the only one) precisely because TLS parsing is exactly the
kind of untrusted-input-handling code memory-unsafe languages get wrong
most consequentially. `rustls` exists specifically to remove that
failure class by construction — written in Rust, no `unsafe`-heavy
C parser underneath — and this plan's Decision log states plainly why
it is chosen outright rather than merely tolerated: this is the one
domain in the batch where the pure-Rust option is not a "close enough,
avoids a dependency" choice, it is the *more secure* choice on its own
technical merits, verified against real audit and advisory history
rather than asserted from reputation.

Depends on: plan 91 (`emerald-rt` archive/link mechanism), plan 92
(catch-unwind and canonical error shape for every `Tls.*` call), plan
93 (the handle model `TlsStream`/`TlsListener` are built on, identical
in shape to plan 96's sockets), plan 95 (the pure-Rust-first policy
this plan is the flagship example of, and the docs+example+test
checklist), plan 96 (the raw `TcpStream`/`TcpListener` this plan wraps
directly — `Tls.connect`/`Tls.listen` open a plan-96 socket first and
layer `rustls`'s handshake on top, never opening a socket of their
own). This plan is a hard, explicit dependency for plan 99 itself (its
own worked proof needs a real TLS handshake to prove anything) and for
plans 100-102 (HTTP client/server, WebSockets, per this session's own
stated numbering) — say so plainly, as instructed: none of those three
plans can implement `https://`/`wss://` without this module existing
first, and none of them should reimplement a second TLS wrapper of
their own once this one exists.

## Concrete proof this plan targets

```ruby
conn: TlsStream = Tls.connect("example.com", 443)
conn.write("GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
status_line: String = conn.read(64)
puts status_line
conn.close()
```

Expected output: a string beginning `HTTP/1.1 200 OK` (or another valid
status line — the exact remainder of the 64-byte read is not asserted
verbatim, only that it begins with a well-formed `HTTP/1.x <code>`
status line, since `example.com` is IANA's own reserved, stable-by-
design example domain, and its response headers are not a contract
this proof depends on beyond "TLS handshake succeeded and an HTTP
response started arriving"). This is a real, network-dependent proof by
necessity — TLS has no meaningful loopback-only worked example the way
plan 96's raw-socket proof does, since the entire point being proved is
a real X.509 certificate chain validating against a real, OS-trusted
root — `leaf-tests-and-example` additionally specifies a fully local,
network-independent test using a self-signed certificate for CI
determinism; this Concrete Proof is the human-readable one exercising
the real default trust-store path end to end.

## Decision log

- **`rustls` is chosen as the flagship pure-Rust-first win in this
  batch — actively audited and actively maintained, verified from real
  primary sources this session, not asserted from reputation.** Cure53
  performed a real, named, independent security audit of `rustls`
  (alongside `ring` and `webpki`) in May-June 2020, funded by ISRG —
  Let's Encrypt's own parent organization, a body with direct financial
  and reputational stake in TLS security actually being correct — and
  published the resulting report (`cure53.de/pentest-report_rustls.pdf`,
  independently covered by LWN.net's 'Rustls: memory safety for TLS'
  and cataloged on Read Rust's own security page). This is not a stale,
  one-time credential: `rustls` continues to receive real, current
  RustSec-tracked advisories and fixes — RUSTSEC-2026-0285 (affecting
  versions `>=0.23.13, <0.23.45`) is a concrete example this session
  found referenced against real downstream dependency-audit tooling,
  fixed in `0.23.45`, proof of an active maintenance and disclosure
  pipeline rather than a project coasting on an old audit's reputation.
  Adoption is real and recent, not aspirational: the Zed code editor's
  own public migration off OpenSSL onto `rustls` (covered on r/rust,
  'Zed switched from OpenSSL to Rustls') is a named, shipping example
  this session verified rather than assumed.
- **OpenSSL/`native-tls` is rejected as unnecessary, not merely
  disfavored — the distinction this task explicitly asked this plan to
  make.** A C-backed TLS library is the traditional default precisely
  because, historically, it was the only mature option; that is no
  longer true. `rustls` covers this plan's entire worked surface
  (client handshake against a real public host, server-side PEM-loaded
  certificates) with no missing capability forcing a fallback to a
  C-backed library. Pulling in OpenSSL here would mean this plan
  becomes the first (and, given plans 100-102's direct dependency on
  it, load-bearing) place in the entire 101-plan batch where a C
  library re-enters the trusted computing base for exactly the kind of
  code — parsing untrusted, network-attacker-controlled input — where
  memory-unsafety has historically been most consequential (Heartbleed
  remains the canonical illustration of exactly this failure mode in
  exactly this kind of code). This plan states the rejection outright,
  per this task's own instruction, rather than hedging it as "rustls
  unless a gap is found later."
- **`rustls-native-certs`, not `webpki-roots`, is the default root
  source — a real, verified tradeoff, not an arbitrary pick between
  two equally good options.** `webpki-roots`' own docs.rs description,
  read directly this session, states plainly it is "suitable for use in
  applications that can always be recompiled and instantly deployed"
  and recommends `rustls-platform-verifier`/native-store alternatives
  "for applications that are deployed to end-users and cannot be
  recompiled." Emerald-compiled programs are exactly the opposite of
  `webpki-roots`' own stated best case — a compiled Emerald binary is a
  redistributed artifact whose deploying operator has no reason to
  expect a recompile-and-redeploy cycle just because Mozilla's root
  store changed, and an operator running on an internal network
  frequently needs their organization's own privately issued root CA
  trusted, which a build-time-bundled Mozilla-only root set can never
  provide. `rustls-native-certs` reads whatever the OS already trusts
  at connect time, correctly reflecting both cases with zero Emerald
  rebuild. This plan does not reject `webpki-roots` outright, though —
  `leaf-root-cert-source-decision`'s `connect_with_roots` override
  keeps it available for the narrower case its own docs recommend it
  for (a fully static, always-redeployed artifact that wants build-time
  -pinned trust independent of the host OS's own, possibly-compromised
  or misconfigured store).
- **`rustls::StreamOwned` is a genuinely synchronous, blocking API —
  this plan needs none of plan 94's `tokio`/`block_on` bridging at
  all.** Verified directly against `rustls`'s own docs.rs page:
  `StreamOwned` "implements `io::Read` and `io::Write`, encapsulating"
  a connection and a socket-like object — `rustls`'s core protocol
  state machine is itself "sans-IO" (it does not perform I/O directly;
  it produces/consumes byte buffers), and `StreamOwned` is the crate's
  own official adapter gluing that state machine onto any ordinary
  blocking `Read`/`Write` implementor, `std::net::TcpStream` (plan 96)
  included, with no async runtime, no `Future`, nothing to `block_on`
  at all. This is a stronger case than plan 97's (which merely prefers
  `hickory-resolver`'s separate sync API over its async one): here,
  synchronous operation is not a secondary mode the crate happens to
  also offer, it is the natural, idiomatic way `rustls` is meant to be
  driven over a blocking socket. Plan 94's guidance ("prefer a crate's
  sync API") is satisfied about as cleanly as any crate in this batch
  can satisfy it.
- **A `TlsStream` closing also closes its underlying TCP connection —
  a real ownership consequence of `StreamOwned`'s own by-value socket
  capture, not an arbitrary plan-99 policy choice.** `rustls::
  StreamOwned` takes ownership of the socket it wraps; there is no
  supported way to hand back a live, un-TLS-wrapped `TcpStream` after
  a `TlsStream` has been built from it. This plan's `.close()` therefore
  cannot offer a "close the TLS layer but keep the raw socket open"
  mode — a real, disclosed constraint inherited from the wrapped
  crate's own API shape, not a limitation this plan introduces on its
  own initiative.
- **Certificate/key loading uses `rustls-pemfile` (already an implicit
  dependency of the broader `rustls` ecosystem, not a new independent
  vetting target) for PEM parsing — DER-only or PKCS#12 input formats
  are out of scope.** PEM is the overwhelmingly common format
  certificate authorities and tools like `certbot`/`openssl` actually
  hand operators; requiring PEM input for `Tls.listen`'s `cert_path`/
  `key_path` covers the realistic deployment case with no format-
  conversion step this plan would otherwise have to build.
- **Out of scope.** Mutual TLS / client-certificate verification on the
  server side (`Tls.listen` accepts any client, does not request or
  verify a client certificate); TLS version/cipher-suite pinning or
  configuration beyond `rustls`'s own safe, modern defaults (`rustls`
  itself, per its own docs.rs description, "requires no configuration
  to achieve" good security — this plan does not expose a knob to
  weaken that); ALPN protocol negotiation (needed by HTTP/2, genuinely
  relevant to a future plan 100/101 HTTP client but not this plan's own
  narrower client/server-stream worked proof); certificate pinning;
  OCSP stapling/revocation checking beyond whatever `rustls-native-
  certs`'s underlying OS trust-store lookup already provides; and
  `webpki-roots` as anything other than an explicit, opt-in override —
  it is not this plan's default (see Decision log)."
