# Plan 120 — YAML

This is plan 120 of the 91-191 batch, sibling to plan 118 (JSON), whose
`JsonValue` tagged-union enum and `emerald-rt` mechanism this plan
depends on and does not re-derive.

This plan's crate choice is the one place in this whole batch where
following stale, pre-cutoff intuition would produce a genuinely wrong
answer, so it gets its own dedicated research leaf rather than a single
citation. **`serde_yaml` — historically the obvious, default choice for
YAML-plus-`serde` in Rust, and the crate a less careful version of this
plan would have picked without checking — is dead.** Verified this
session directly against its own real, current `lib.rs` crate page: the
latest release is `0.9.34+deprecated`, published **March 25, 2024**,
with the crate's own README stating outright, in its own words, "*This
project is no longer maintained.*" and `lib.rs` itself tagging the crate
"deprecated" and "[minimal maintenance]" in its page title. This is not
a rumor or an inference from an old changelog — it is the crate's own,
currently-published self-description, read directly this session, over
two years after that final release.

**`saphyr` is the real, current, actively-developed replacement**,
verified against its own real `lib.rs`/`docs.rs` pages: a fully YAML 1.2
compliant library (its own README's stated first design priority is
"correctness," ahead of performance and API friendliness), 52
contributors, owned by `Ethiraric`/`davvid`, with a **new `0.1.0`
release published September 19, 2026** — during the same month as this
session — following a real, active `0.0.x` release history stretching
back to April 2024 (`0.0.6` in June 2025, `0.0.11` in July 2026, `0.0.12`
in August 2026). Its download trend is real and growing, not merely
nonzero: 271,241 downloads per month, climbing from roughly 40,000/week
in June 2026 to roughly 64,000-80,000/week by September 2026 (verified
against `lib.rs`'s own download-history chart), used in 142 crates. A
sibling crate, `serde-saphyr`, exists under the same GitHub organization
for `serde`-derive-style integration on top of `saphyr`'s core parser —
noted here for completeness but not used by this plan, which needs the
same dynamic-value (not schema-first) parsing plan 118 already commits
to. `yaml-rust2` (a maintained fork of the older, pre-`saphyr`
`yaml-rust`) was also considered as a candidate per the task's own
prompt; `saphyr` was picked over it because `saphyr-rs`'s own GitHub
organization (verified: `saphyr`'s `lib.rs` page lists `yaml-rust2` as
a "See also" — a related, not identical, project) is the more actively
developed lineage as of this session's real, checked release cadence
(a brand-new `0.1.0` this same month, versus no comparably recent
major-version signal found for `yaml-rust2` in this session's research)
and because `saphyr`'s own stated correctness-first design goal (full
YAML 1.2 test-suite compliance, verified against its own README) is the
more defensible bar for a stdlib module this project ships to every
Emerald program.

## Concrete proof this plan targets

```ruby
input: String = "name: Ada\nlanguages:\n  - math\n  - cs\nactive: true\n"

match Yaml.parse(input) do
Ok(doc) do
  name: JsonValue? = doc.get("name")
  name ||= JsonNull()
  case name
  when JsonString(s)
    puts s
  else
    puts "missing"
  end

  langs: JsonValue? = doc.get("languages")
  langs ||= JsonNull()
  case langs
  when JsonArray(items)
    puts items.count
  else
    puts "missing"
  end
end
Err(msg) do
  puts msg
end
end
```

Expected output:
```
Ada
2
```
A real proof YAML's own block-style mapping (`name: Ada`) and block
sequence (`languages:` followed by `- math`/`- cs`, indentation-
delimited, not `[...]`-bracketed) both lower into the identical
`JsonObject`/`JsonArray` shape `Json.parse`/`Toml.parse` already
produce from their own, textually unrelated syntaxes — the same
`JsonValue`-consuming Emerald code (`.get`, `case`/`when`) works
unmodified regardless of which of this batch's three parser plans
produced the tree. A second, real negative proof: `Yaml.parse("key:
  - a\n  b")` (a real YAML indentation error — mixing a sequence item
and a scalar at the same nesting level) reaches `Err(msg) do ... end`
with `saphyr`'s own real parser-error text, not a crash.

## Decision log

- **`saphyr` over `serde_yaml`, with the maintenance-status evidence
  stated first because it is the actual reason, not a footnote.** See
  above — this is restated here as the plan's own first Decision log
  entry deliberately, since the task's own instructions single this
  question out as the one place stale pre-cutoff knowledge would
  silently produce a wrong recommendation if not actively checked.
- **`saphyr`'s core API is `Yaml`/`YamlData`, not a `serde`-integrated
  `from_str::<T>` — this plan uses it exactly as directly as `serde_
  json`'s `Value` enum is used in plan 118, not through a derive-style
  path.** Verified against `docs.rs/saphyr/latest/saphyr/enum.YamlData.
  html`: `YamlData`'s real variants are `Value` (a scalar — string/
  int/float/bool/null, exposed via `as_str`/`as_integer`/`as_floating_
  point`/`as_bool` accessor methods, verified present on the same page),
  `Sequence`, `Mapping`, plus `Alias`/`BadValue`/`Representation`/
  `Tagged` for YAML-specific concepts (anchors/aliases, parse failures
  represented as a value rather than an early `Result::Err`, raw
  unparsed scalars, and explicit `!Tag` annotations respectively) that
  have no JSON equivalent at all. This plan's lowering function walks
  `Sequence -> JsonArray`, `Mapping -> JsonObject` (mirroring `toml::
  Value::Table -> JsonObject` in plan 119, same recursive-walk shape),
  and each of `Value`'s own scalar sub-kinds into the matching
  `JsonValue` scalar variant (`Integer`/`Floating` both widen to
  `JsonNumber(Float64)`, same numeric-widening decision plan 118/119
  already made and this plan does not re-litigate).
- **`Alias` resolves transparently during lowering — this plan's own
  walk follows a YAML anchor/alias (`&anchor`/`*anchor`) to its
  resolved target value before ever producing a `JsonValue`, rather
  than inventing a `JsonValue` concept for "this is secretly the same
  object as that other node."** JSON has no aliasing concept at all;
  representing one would mean either a `JsonValue` carrying real
  reference-identity semantics (a structural change plan 118's whole
  variant list deliberately avoids — every existing `JsonValue` producer
  in this batch, including `Json.parse` itself, treats a tree as a pure
  value, never a graph) or silently duplicating the aliased subtree at
  lowering time. This plan chooses duplication (walk the resolved value
  as if it had been written out in full at each alias site) — `saphyr`'s
  own parser already resolves an `Alias` to its target `Yaml` node
  internally (confirmed by `YamlData::Alias`'s own presence as a
  variant a caller can match on if it wants to detect this case, which
  this plan's lowering function does not; it follows the resolution
  `saphyr` itself already performs rather than re-implementing anchor
  tracking). A real, disclosed cost: two anchored-and-aliased subtrees
  that were meant to be update-together-stay-together in the original
  YAML document become two independent, textually-identical `JsonValue`
  trees after lowering — a one-way simplification, same posture as
  plan 119's `Datetime`-folds-into-`JsonString` decision.
- **`Tagged`/custom `!Tag` values lower to whatever their own untagged
  content would (the tag itself is discarded), rather than rejecting
  the document or inventing a `JsonValue` concept for a YAML tag.** A
  `!!str`/`!!int`/core-schema tag is handled by `saphyr`'s own resolver
  before this plan's lowering ever sees the value (already an ordinary
  scalar `Value` by the time it reaches this plan's walk); a genuinely
  custom, application-defined tag (`!MyType {...}`) is rare in
  hand-written config-file YAML (this plan's own primary target use
  case, alongside JSON/TOML) and, when it does appear, still carries a
  real, well-formed mapping/sequence/scalar underneath the tag that
  lowers correctly — only the tag name itself is dropped. Preserving
  custom tag names would need an eighth `JsonValue` variant with no
  JSON or TOML equivalent, the same asymmetric-complexity argument
  plan 119 already made against a `JsonDatetime` variant.
- **Multi-document YAML streams (`---`-separated) are narrowed to the
  first document only — a real, disclosed v1 scope cut.** Verified
  against `saphyr`'s own README example: `Yaml::load_from_str` returns
  a real `Vec<Yaml>` — YAML's grammar genuinely allows more than one
  top-level document in a single stream, unlike JSON or TOML, both of
  which are always exactly one document per input. `Yaml.parse` reads
  index `0` of that `Vec` and errors (`Err("empty YAML document
  stream")`) if it's empty rather than silently returning `JsonNull()`.
  Exposing all documents (an `Array[JsonValue]`-returning `Yaml.
  parse_all`, say) is real, buildable, disclosed future work this plan
  declines to fold in — every one of this plan's own use cases (a
  single config file) needs exactly one document, and adding the
  multi-document form is a strictly additive follow-up, not a breaking
  change to this plan's own `Yaml.parse` signature.
- **`.to_yaml` uses `saphyr::YamlEmitter`, and is total (`String`, not
  `Result[String, String]`) — unlike plan 119's `.to_toml`.** Every
  `JsonValue` variant (including `JsonNull()`, which TOML genuinely
  cannot represent) has a direct YAML equivalent — YAML's own `null`
  literal (bare `~` or the word `null`) covers exactly the gap that
  forced `.to_toml` to be fallible. `JsonValue -> saphyr::Yaml` lifting
  is therefore a total function, and `emerald_rt_json_to_yaml` returns
  a plain `String`, following `.to_s`'s (plan 118) total signature
  instead of `.to_toml`'s (plan 119) fallible one — a real, disclosed
  asymmetry between this batch's three format plans, caused by a real
  difference in what each target format can express, not an
  inconsistency this plan failed to notice.
- **No `YamlValue`, no schema-first path, no typed derive deserialize —
  identical reasoning to plan 118/119, not re-derived.** Same macro-
  system/reflection gap, same "hand-write your own `from_json`-shaped
  function against the shared `JsonValue`" answer. Stated briefly here
  per the same "don't silently assume a sibling plan's answer travels"
  discipline plan 119 already applied.
- **FFI/ABI notes (plan 92) and error marshaling are identical in
  shape to plan 118/119 — one new fact, not a new mechanism.** `Yaml.
  parse`'s out-parameter error string comes from `saphyr::ScanError`'s
  (the concrete error type `saphyr-parser` raises on a real syntax
  fault) own `Display` implementation, allocated via the same shared
  `emerald_alloc` symbol every other `Err` string in this batch's three
  plans already uses — no new FFI convention introduced.
- **Out of scope.** `Yaml.parse_all` (multi-document — see above);
  `Tagged`/custom-tag preservation; YAML anchor/alias-preserving
  round-trip through `.to_yaml` (an emitted document re-duplicates any
  aliased subtree rather than re-introducing `&anchor`/`*alias`
  syntax — `saphyr::YamlEmitter`'s own default behavior, not overridden
  here); comment preservation (`saphyr`, like `toml`'s plain parser,
  discards comments on parse — a format-preserving YAML editor is a
  substantially different, unbuilt tool); YAML 1.1-specific quirks
  `saphyr`'s own 1.2-only compliance target deliberately does not
  reproduce (e.g. YAML 1.1's `yes`/`no`/`on`/`off` boolean sigils,
  removed in the 1.2 core schema this crate implements) — a real,
  disclosed behavior difference from some other tools' YAML parsers,
  inherited from `saphyr`'s own stated spec target rather than
  introduced by this plan.
