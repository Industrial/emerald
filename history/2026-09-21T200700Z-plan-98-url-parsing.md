# Plan 98 — URL Parsing

This plan exists because plans 100 and 101 (this session's own stated
numbering for the coming HTTP client and server) both need to take a
URL apart — scheme, host, port, path, query string — before they can do
anything useful with it, and getting that right by hand is a genuinely
hard, well-documented trap: the WHATWG URL Standard is not "split on
`://` then split on `/`," it specifies exact percent-encoding rules,
punycode/IDNA host normalization for non-ASCII domains, scheme-specific
default-port tables, and a state-machine parser with real edge cases
(URLs with no path, URLs with an empty host, `file:` URLs with drive
letters) that a hand-rolled splitter reliably gets wrong at the margins.
Building this once, correctly, as its own plan — rather than letting
plan 100 or plan 101 each grow an ad hoc URL splitter as a side effect
of their own worked proof — is the entire point: neither of those
plans should need to re-derive URL handling, they should both just
depend on this one already-correct implementation.

Depends on: plan 91 (`emerald-rt` archive/link mechanism), plan 92
(catch-unwind and canonical error shape for `Url.parse` failures), plan
93 (the handle-representation convention `Url` values are stored under,
even though — per `leaf-url-panic-boundary-and-handle-representation`
above — a `Url` is not a true plan-93 *resource*), plan 95 (crate-
vetting ledger and docs+example+test checklist). Plans 100 and 101
(HTTP client/server, per this session's own numbering) depend on this
plan directly and are the reason it exists — say so explicitly, per
this task's own instruction: an HTTP client built on plan 96's raw
`TcpStream` needs to parse the URL a caller hands it into a host, a
port, and a request path before it can even open a connection, and an
HTTP server needs the identical parsing for whatever `Host`/request-line
target it receives. Both consume this plan's `Url` class rather than
parsing strings themselves.

## Concrete proof this plan targets

```ruby
u: Url = Url.parse("https://example.com/search?q=emerald#results")
puts u.scheme
puts u.host
puts u.port
puts u.path
puts u.query
puts u.fragment

plain: Url = Url.parse("https://example.com")
puts plain.port

built: Url = Url.build("https", "example.com", "/api")
q: Url = built.with_query("id=42")
puts q.path
puts q.query
```

Expected output, in order:
```
https
example.com
443
/search
q=emerald
results
443
/api
id=42
```
The second `puts plain.port` (`443` from a URL with no explicit port at
all) is the real proof of `.port()`'s `port_or_known_default()`-backed
scheme-default fallback — a bare string-splitting implementation would
naturally return an empty/absent port here, and getting this specific
case right without the `url` crate's own scheme-default table would
require this plan to hand-maintain one, exactly the kind of
easy-to-get-wrong detail this plan exists to avoid re-deriving.

## Decision log

- **The `url` crate is chosen because it is the ecosystem's own
  reference implementation, not merely "a" URL-parsing crate — verified
  this session, not assumed from name recognition.** crates.io's own
  listing for `url` states its scope in one unambiguous line: "URL
  library for Rust, based on the WHATWG URL Standard." It is published
  under the `servo` GitHub organization — the same organization behind
  the Servo browser engine, whose own recent `crates.io` publication
  (covered by a DEV Community piece this session found: "Servo Now on
  crates.io... a full-featured, spec-compliant web engine") underscores
  that `url` was built to satisfy a real browser engine's own
  correctness bar, not written as a standalone utility guessing at the
  spec secondhand. The crate carries a release dated January 2026 per
  this session's own crates.io check — current, not abandoned. This is
  the crate every major Rust HTTP stack (`reqwest`, `hyper`'s own
  ecosystem, `cargo` itself for registry URLs) already depends on;
  choosing anything else for plans 100-101 to build on would mean
  Emerald's own HTTP stack disagreeing with the rest of the Rust
  ecosystem about what a URL even parses to, a real, avoidable
  compatibility liability.
- **WHATWG, not RFC 3986, is the correct spec target — a real,
  deliberate distinction, not an arbitrary choice between two
  equivalent standards.** RFC 3986 is the older, more permissive IETF
  URI grammar; the WHATWG URL Standard is what every real browser
  implements for `fetch()`/`XMLHttpRequest`/the address bar, is
  actively maintained as a living standard, and is stricter about
  normalization (percent-encoding of exact character sets, IDNA/
  punycode host normalization, explicit state-machine parsing of
  malformed input rather than grammar rejection). Since Emerald's own
  eventual HTTP client (plan 100) is far more likely to be judged
  against "does this behave like a browser/`fetch()` would" than
  against RFC 3986's stricter-grammar reading, WHATWG compliance is the
  materially more useful property, and it is what the `url` crate
  actually ships.
- **Pure Rust, zero C dependency, confirmed by dependency tree, not
  assumed from the crate being "popular."** `url`'s own real
  dependencies — `form_urlencoded`, `idna`, `percent-encoding`, and an
  optional `serde` — are all pure-Rust siblings from the same
  maintainer ecosystem; none of them link a C library. This keeps the
  crate inside plan 95's pure-Rust-first policy with no caveat needed,
  unlike plan 99's TLS story, which has to affirmatively justify
  rejecting a C-backed alternative — there is no analogous C-backed URL
  parser this plan needs to argue against, since the Rust ecosystem's
  own default choice is already pure Rust.
- **Non-mutating construction methods, deliberately diverging from
  `url::Url`'s own real in-place `set_*` API, to match this codebase's
  existing convention rather than the wrapped crate's own idiom.**
  Verified directly: plan 45's Decision log states, project-wide, "no
  method on *any* type mutates its receiver in place today... only
  `Stmt::SetField`... and `Stmt::SetIndex`... both plain assignment
  statements, not method calls." `url::Url::set_path`/`set_query`/
  `set_port` all mutate `self` in place in real Rust. This plan's
  Emerald-facing `.with_path`/`.with_query`/`.with_port` instead clone-
  then-mutate internally and return a new `Url` handle, preserving the
  existing project-wide non-mutating-method convention rather than
  becoming the first method surface in the standard library that
  writes through its receiver — a real, deliberate divergence from the
  wrapped crate's own API shape, stated explicitly rather than left for
  a reader to notice as an inconsistency.
- **An absent host raises rather than returning an empty string — a
  real correctness decision about a genuine edge case, not an
  oversight.** The WHATWG spec allows URLs with no host at all (e.g.
  `mailto:user@example.com`, `data:text/plain,hello`) — `url::Url::
  host_str()` returns `Option<&str>`, `None` in exactly this case. This
  plan's `.host()` raises plan 92's canonical exception on `None`
  rather than collapsing it to `""`, specifically because `""` is
  already a legitimate value for `.query()`/`.fragment()` when those
  components are present-but-empty (e.g. `https://example.com/x?#`),
  and reusing the same "empty string means absent" convention for
  `.host()` would make an absent host indistinguishable from the
  (impossible-in-practice, but not type-system-impossible-to-imagine)
  case of a URL with a literally empty host string. This plan accepts
  the resulting asymmetry (`.host()` raises on absence, `.query()`/
  `.fragment()` don't) as the more honest behavior rather than forcing
  false consistency across components that don't actually behave the
  same way in the underlying spec.
- **`Url` values are stored behind plan 93's handle convention for
  representational consistency, even though they are not resources in
  plan 93's own sense.** A parsed URL holds no file descriptor, lock,
  or any other OS-level resource requiring an explicit `.close()` — it
  is closer to an owned, `Clone`-able Rust value. This plan still
  stores it as an opaque u64 handle (see `leaf-url-panic-boundary-and-
  handle-representation`) rather than inventing a second, parallel
  compiler-provided-value representation alongside plan 93's handle
  table, on the grounds that having exactly one representational
  pattern for "a compiler-provided type with Rust-side state" is worth
  more than saving one representation for the (so far, entirely
  hypothetical) case of a genuinely resource-free compiler-provided
  type. Whether plan 93 ultimately wants a distinct "value handle, no
  `.close()` required" variant of its own convention is plan 93's
  design question, not resolved here.
- **Query-string *parsing* into individual key/value pairs is
  explicitly out of scope for this plan.** `.query()` returns the raw,
  still-encoded query string (`"q=emerald"`, `"id=42"`) rather than a
  decoded `Hash[String, String]` — `url`'s own `form_urlencoded` sibling
  crate can do the actual `key=value&key2=value2` splitting and
  percent-decoding, but exposing that as a structured Emerald `Hash`
  return type is real additional design work (percent-decoding,
  repeated-key handling, `+`-as-space in the query-string dialect of
  percent-encoding vs. path-segment encoding) this plan's narrower
  component-accessor scope does not need to resolve to unblock plans
  100-101, both of which can (and, per HTTP semantics, sometimes must)
  treat the query string as an opaque value on the request line.
- **Out of scope.** General multi-component `Url.build` covering every
  WHATWG field in one call (kept to the fixed `scheme`/`host`/`path`
  triple plus targeted `.with_*` mutators); query-string key/value
  parsing (see above); IDNA/punycode-specific accessors beyond what
  `.host()` already returns (the crate normalizes internally; this plan
  does not expose a separate "raw vs. punycode-normalized" pair of
  accessors); URL-relative resolution (`Url::join`, resolving a
  relative reference against a base URL) — genuinely useful for an HTTP
  client following redirects, deliberately deferred to whichever of
  plan 100/101 actually needs it rather than speculatively added here;
  serialization/`Display` round-tripping back to a full URL string
  beyond what the individual component accessors already provide.
