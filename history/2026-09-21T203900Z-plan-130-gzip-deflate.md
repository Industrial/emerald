# Plan 130 — Gzip/Deflate/Zlib Compression

Every plan in the 130-136 sub-batch (gzip, zstd, tar, zip, lz4, brotli,
7z) is a tenant of plan 91's `crates/emerald-rt` archive and plan 95's
crate-vetting policy: prefer a vetted, widely-used Rust crate to
hand-rolled C, and for every crate pulled in, make an explicit,
honest call on whether it is pure Rust or wraps a C library, per that
policy's central axis. This plan is the one member of the group where
that call turns out to be easy rather than contested: `flate2`
(`rust-lang/flate2-rs`, the same GitHub org that owns `rustc` itself)
is DEFLATE/zlib/gzip compression exposed as `Read`/`Write` streams,
and — verified this session directly against its real, current
`Cargo.toml` — its own **default** feature set (`default =
["rust_backend", "runtime_detection"]`) already resolves to the
pure-Rust `miniz_oxide` backend, not any C `zlib`. There is no
tempting-but-wrong default to accidentally inherit here the way there
would be for a crate whose maintainers ship a C backend by default;
the risk this plan actually has to manage is a *documented future
change to that default* (flate2's own feature comment: `rust_backend`
"at some point may be switched to use `zlib-rs` instead" — still pure
Rust, still no C compiler required, but no longer the specific
`miniz_oxide` implementation), which is why this plan pins the
concrete `miniz_oxide` feature name rather than the `rust_backend`
alias.

## Concrete proof this plan targets

```ruby
original: Bytes = "the quick brown fox jumps over the lazy dog, the quick brown fox jumps over the lazy dog".to_bytes()
compressed: Bytes = Gzip.compress(original)
puts compressed.length < original.length
restored: Bytes = Gzip.decompress(compressed)
puts restored == original

deflated: Bytes = Deflate.compress(original)
puts Deflate.decompress(deflated) == original

zlibbed: Bytes = Zlib.compress(original)
puts Zlib.decompress(zlibbed) == original
```

Expected output: `true`, `true`, `true`, `true` — the repeated input is
genuinely compressible so `compressed.length < original.length` proves
real compression happened (not a pass-through stub), and each format's
`decompress(compress(x)) == x` proves a real, correct round trip through
all three of gzip's/zlib's/raw-deflate's actual wire formats, not just
one. `.to_bytes()`/`Bytes`/`.length`/`==` on `Bytes` are plan 92's
surface, assumed present and working by this plan's own EXECUTE gate —
see Decision log.

## Decision log

- **`flate2`'s pure-Rust backend is its actual, current default — this
  plan verified the real `Cargo.toml`, not the crate's marketing copy,
  and the finding holds.** Read in full this session, from
  `rust-lang/flate2-rs`'s `main` branch: `default = ["rust_backend",
  "runtime_detection"]`, and `rust_backend = ["miniz_oxide",
  "any_impl"]`. The competing C-backed features — `zlib` (system
  `libz-sys`), `zlib-ng`/`zlib-ng-compat` (`libz-ng-sys`, "Requires a C
  compiler"), and `cloudflare_zlib` (now just an alias that "falls back
  to `libz-sys`") — are all `optional`, none is in `default`, and
  enabling any of them means passing an explicit non-default feature
  flag this plan's dependency declaration never does. This directly
  matches plan 95's policy in the easiest possible way: no override is
  needed to land on pure Rust, only vigilance not to accidentally add
  one of the four C-feature names later. Also confirmed distinct from
  `zlib-rs`: a *fifth*, separately-optional backend, itself pure Rust
  and requiring no C compiler either, but described by flate2 as "the
  fastest backend overall... with some `unsafe` code" — not chosen here
  because `miniz_oxide`'s "uses only safe Rust code" is the stronger,
  more conservative match for a compiler runtime whose only other
  native code today (`runtime/emerald_runtime.c`, plan 91's own
  `emerald-rt`) either predates Rust entirely or is written specifically
  to keep `unsafe` narrowly scoped (plan 91's `catch_unwind`-at-every-
  boundary convention).
- **The dependency is pinned to the literal `miniz_oxide` feature, not
  the `rust_backend` alias, specifically because flate2's own docs say
  the alias may repoint itself.** This is the one piece of real,
  disclosed risk in an otherwise easy pure-Rust call: if `rust_backend`
  is later redefined to mean `zlib-rs` instead of `miniz_oxide` (flate2
  states this as a real possibility, not a hypothetical), a dependency
  declaration written as `features = ["rust_backend"]` would silently
  start compiling `emerald-rt` with a different pure-Rust implementation
  than the one this plan's Decision log just chose and justified —
  still satisfying plan 95's pure-Rust requirement, but not the specific
  fully-safe-Rust implementation this plan picked. Depending on the
  concrete `miniz_oxide` feature name instead means a future flate2
  major-version bump that actually removes `miniz_oxide` support would
  be a loud `cargo build` failure (a missing feature), not a silent
  backend swap — the same "prefer a loud, verifiable failure over an
  silent behavior change" posture plan 91 itself used for `panic =
  "unwind"` vs `panic = "abort"`.
- **`Bytes`, not `String`, is the correct receiver/return type here —
  and this plan cannot itself introduce it.** Plan 59 found, verified
  directly against `runtime/emerald_runtime.c`, that Emerald's `String`
  is "a plain, `malloc`-backed, null-terminated buffer" — bit-for-bit
  C's own `char*` convention. Compressed data is not text: it is
  arbitrary bytes, routinely containing embedded `NUL`s and non-UTF-8
  sequences (gzip's own 10-byte header alone can contain a `0x00` OS
  byte), so passing it through a null-terminated `String` would
  silently truncate or corrupt real payloads — exactly the class of bug
  plan 92's binary-safe `(ptr, len)` buffer convention exists to close
  project-wide, not something this plan should patch over locally with
  its own one-off marshaling scheme. This plan therefore has a hard,
  structural dependency on plan 92 having landed a `Bytes` type (the
  exact Emerald-level name/representation is plan 92's call, assumed
  here per this batch's shared brief) before `leaf-emerald-surface-
  gzip-deflate-zlib-modules` can compile against anything — mirrored on
  plan 45's own citation style for its two parallel-authored soft
  dependencies (interpolation, symbols), except this one is a hard
  blocker, not a soft compatibility note.
- **Three format namespaces, not one, because gzip/zlib/raw-deflate are
  three genuinely different wire formats sharing one algorithm — and
  `flate2` already exposes exactly this split.** gzip adds a 10-byte
  header plus an 8-byte CRC32+size trailer (the format HTTP
  `Content-Encoding: gzip` and the real `gzip(1)` tool use); zlib adds a
  2-byte header plus a 4-byte Adler-32 trailer (the format PNG's `IDAT`
  chunks and TLS-layer deflate use); raw deflate has neither, just the
  compressed bitstream itself (what `zip`'s own DEFLATE method uses
  internally, and what plan 133's ZIP archive plan will call directly
  rather than going through this plan's `Gzip`/`Zlib` namespaces).
  `flate2::{read,write}::{Gz,Zlib,Deflate}{Encoder,Decoder}` already
  separates these three cleanly at the Rust API level — this plan's
  `Gzip`/`Deflate`/`Zlib` Emerald namespaces are a direct, undistorted
  reflection of that existing split, not a new taxonomy invented here.
  Mixing formats (feeding gzip-compressed bytes to `Deflate.decompress`)
  is a real, expected user error this plan does not attempt to detect
  ahead of the underlying decoder's own parse failure — plan 92's error
  convention surfaces that failure; no format-sniffing/auto-detection is
  attempted.
- **Streaming handles exist because the one-shot `Bytes`-in-`Bytes`-out
  API has a real, disclosed ceiling: both the input and the compressed
  output must fit in memory simultaneously.** A multi-gigabyte log file
  or database dump gzipped through `Gzip.compress` would need its full
  uncompressed bytes, its full compressed bytes, and flate2's own
  internal buffers all resident at once — a real problem for exactly
  the kind of large, incremental data this format group is most useful
  for. `GzipWriter`/`GzipReader` (plan 93's opaque-handle-plus-explicit-
  `.close()` model, applied here for the first time in this batch) wrap
  `flate2::write::GzEncoder<std::fs::File>` and
  `flate2::read::GzDecoder<std::fs::File>` respectively, each held in a
  handle table exactly as plan 93 specifies, so compression/
  decompression happens in bounded chunks against a real file on disk
  rather than one giant in-memory buffer. An unclosed handle leaks its
  underlying `File` and any buffered-but-unflushed compressed bytes —
  a real, disclosed limitation, not a bug, matching `emerald_alloc`'s
  own already-disclosed "no free... no lifetime tracking" precedent
  (plan 45's citation) rather than inventing a new leak-prevention
  mechanism this plan doesn't need.
- **`runtime_detection` is kept enabled (it rides along in flate2's own
  `default` feature set) rather than stripped for a smaller/simpler
  dependency footprint.** It gates CPU-feature-based runtime dispatch
  inside `miniz_oxide`/`crc32fast` (SIMD-accelerated CRC32/adler32 paths
  selected at runtime rather than compile time) — real performance,
  zero API surface change, zero `unsafe` this plan's own code has to
  reason about (the dispatch logic lives entirely inside the vetted
  upstream crates). Nothing about `crate-vetting policy` distinguishes
  "default feature that happens to add runtime CPU dispatch" from any
  other default feature; there is no reason to disable it here.
- **Compression level is fixed at `flate2::Compression::default()` in
  v1, not exposed as an Emerald-level parameter.** `flate2::Compression`
  ranges `0..=9`, but plumbing an `Int64` level argument through the
  `emerald_rt_gzip_compress` extern boundary, validating its range, and
  deciding what an out-of-range value does (clamp? error?) is a small
  but real additional design surface this plan's own Concrete Proof
  doesn't need to exercise. `.compress(data)` uses the crate's own
  documented default (level 6, DEFLATE's traditional "good balance"
  default) uniformly; a `.compress_with_level(data, level)` overload is
  explicitly deferred, not designed away — it is additive whenever a
  future plan needs it.
- **Out of scope.** No compression-level parameter (above), no gzip
  multi-member/concatenated-stream support (`flate2`'s `GzDecoder`
  reads only the first member by default; `MultiGzDecoder` exists
  upstream but this plan does not wire it in), no `.gz` filename/mtime
  header metadata surface (`GzBuilder`'s extra fields — `flate2`
  supports setting them, this plan's `Gzip.compress` does not expose
  them), and no dictionary-based deflate (`Compress::new_with_window_
  bits`-style low-level tuning). `.tar.gz` composition is explicitly
  plan 132's job, layering `tar`'s archive format over this plan's
  `Gzip.compress`/`GzipWriter` — this plan provides the compression
  primitive, not the archive format.

## Not yet decided (blocking EXECUTE)

   as two separate `Int64`/pointer arguments at the extern boundary,
   with no single aggregate `Bytes` LLVM value at all?) — this plan's
   own `emerald_rt_gzip_compress` signature is written against whichever
   convention plan 92 settles on, not against a guess made here.
2. Whether `GzipWriter`/`GzipReader`'s handle table is per-thread,
