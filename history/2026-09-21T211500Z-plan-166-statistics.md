# Plan 166 — Statistics Primitives (Stretch Tier)

**Stretch-tier, stated in the overview and restated here.** Descriptive
statistics and probability distributions matter for a real but narrow
slice of Emerald programs — data analysis, simulation, A/B-test
analysis, scientific scripting — not for the median CLI tool or web
service this compiler's mainline stdlib plans (strings, I/O, HTTP)
target. This plan is scoped deliberately narrow for v1: basic
descriptive statistics over a fixed dataset, and `pdf`/`cdf`/moments for
three of the most common named distributions, nothing more.

`statrs` is the clear, uncontested pick: verified this session,
`statrs-dev/statrs` on GitHub, `docs.rs/statrs` describes it as "a
functional port of the Math.NET Numerics... Distribution package" —
purpose-built, focused on exactly this problem, with no live rivalry
this session's research surfaced (unlike plan 160's `chrono`/`jiff`
question). The design work this plan actually has to do is answering,
concretely, this batch's recurring representation question for TWO
different shapes of statistical value in one plan — a raw numeric
result (mean, stddev — trivially a `Float64`) and a reusable,
parameterized object (a distribution you query repeatedly — genuinely
needs a handle) — and it answers them differently, on purpose.

## Concrete proof this plan targets

```ruby
data: Array[Float64] = [2.0, 4.0, 4.0, 4.0, 5.0, 5.0, 7.0, 9.0]
n: Int64 = 8

mean: Float64 = Stats.mean(data, n)
puts mean

stddev: Float64 = Stats.stddev(data, n)
puts stddev

bad_percentile: Result[Float64, String] = Stats.percentile(data, n, 150.0)
case bad_percentile
when Ok(p)
  puts p
when Err(e)
  puts e
end

dist_result: Result[NormalDist, String] = NormalDist.new(0.0, 1.0)
case dist_result
when Ok(dist)
  puts dist.pdf(0.0)
  puts dist.cdf(0.0)
when Err(e)
  puts e
end

bad_dist: Result[NormalDist, String] = NormalDist.new(0.0, -1.0)
case bad_dist
when Ok(dist)
  puts "unexpected"
when Err(e)
  puts e
end
```

Expected output, in order: `5` (the mean of the fixed dataset, a
textbook example — population values `2,4,4,4,5,5,7,9`); `2` (the
population standard deviation of the same dataset, another
hand-verifiable textbook value); a disclosed error string for the
out-of-range percentile request; `0.3989422804014327` (the standard
normal distribution's density at `x=0`, the closed-form value
`1/sqrt(2*pi)`, computed by `statrs`'s own real implementation, not
hardcoded here); `0.5` (the standard normal CDF at its own mean is
exactly `0.5` by symmetry); and `statrs`'s own real constructor-error
text for the invalid negative standard deviation.

## Decision log

- **Flagged stretch-tier, matching plan 165's own posture exactly — a
  real, narrow-audience capability, not a stdlib essential.** Stated
  plainly rather than inflated: the overwhelming majority of Emerald
  programs will never call a function this plan adds, the same honest
  framing plan 165 applies to linear algebra.
- **Scalar statistics and distribution objects get deliberately
  different representations, in the same plan, for a concrete reason —
  this batch's representation question answered twice, correctly, in
  one document.** A mean/stddev/percentile computation consumes a
  dataset and produces exactly one `Float64` — there is nothing to hold
  onto after the call returns, so no new type is needed at all, the
  same "round-trips through an existing type" answer plan 162's
  `humantime` gives for durations. A `NormalDist`, by contrast, is a
  reusable, parameterized object a caller queries repeatedly (`.pdf`
  at many different `x` values) — re-parsing/re-validating the
  distribution's parameters on every single query, the way a
  stateless `Stats.normal_pdf(x, mean, std_dev)` free-function design
  would require, throws away the validation work `NormalDist.new`
  already did and burdens every call site with re-supplying both
  parameters. The opaque handle here exists for the same amortization
  reason plan 161's `CronSchedule` handle does: pay the
  construction/validation cost once, reuse the result many times.
- **Descriptive statistics take an explicit `n: Int64` count parameter
  alongside the `Array[Float64]`, not a bare array — this plan does not
  invent a new workaround, it reuses plan 45's own already-precedented
  one.** `Array[T]` carries no runtime length metadata at all (plan
  45's own finding, verified against `build_array_lit`'s doc comment:
  "no length prefix, no bounds checking"); `.split_count` pairing with
  `.split` is that plan's own disclosed fix for the identical problem.
  This plan's `Stats.mean(data, n)` is the same shape applied to a new
  domain, not a new idea — consistency with an established, already-
  reviewed precedent is preferred here over inventing a differently-
  shaped workaround for what is structurally the same gap.
- **Random sampling from a distribution (`.sample()`) is explicitly
  deferred, not silently reduced to a lesser version of itself.** A
  real `.sample()` needs a source of randomness — `statrs`'s own
  sampling API is generic over `rand::Rng` — and this plan declines to
  also decide, as a side effect, what RNG this project uses project-
  wide (a seeded, reproducible generator? the OS's own CSPRNG? does
  Emerald get a `Random` class of its own, seeded how, exposed to
  source how?). That is a real, separate design question a future
  RNG-focused plan should answer once, for the whole project, not one
  this narrow statistics plan should answer unilaterally as a
  byproduct of wanting `.sample()` on three distribution classes. `pdf`/
  `cdf`/moments need no randomness at all and are fully deterministic,
  which is why they ship in v1 and sampling does not.
- **No hypothesis testing, no regression, no correlation matrices.**
  `statrs` offers some of this territory (and the wider Rust ecosystem
  has `rs-stats` and others reaching further into it) — this plan
  scopes to descriptive statistics and named-distribution queries only,
  the smallest slice that is still genuinely useful on its own, rather
  than attempting a full statistical-computing surface in one stretch-
  tier plan.
- **Distribution constructors return `Result`, propagating `statrs`'s
  own real parameter validation directly — not a hand-rolled
  pre-check.** `statrs::distribution::Normal::new(mean, std_dev)`
  itself returns `Result<Normal, StatsError>` for an invalid parameter
  (e.g. a negative or non-finite standard deviation); this plan's
  `NormalDist.new` wraps that real `Result` via `emerald_rt_result_err`
  (plan 92) rather than re-deriving the validity rule independently —
  the single source of truth for "what makes a valid `Normal`
  distribution" stays inside `statrs`, not duplicated in this plan's
  own code.
- **Out of scope.** No random sampling (above); no hypothesis
  testing/regression/correlation (above); no additional distributions
  beyond `Normal`/`Poisson`/`Binomial` (a real, disclosed narrow v1 set
  — `statrs` offers many more, e.g. `Gamma`, `StudentsT`, `Weibull`,
  `Exponential`, each a small additional leaf a follow-up plan can add
  once this plan's representation pattern is established); no
  streaming/online statistics (a running mean/variance over an
  unbounded stream, useful but a genuinely different API shape than
  this plan's fixed-dataset design); no plotting or visualization of
  any kind.
