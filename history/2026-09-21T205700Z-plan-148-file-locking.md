# Plan 148 — File Locking

Coordinating access to a shared file — a config file two processes might
both want to rewrite, a lightweight file-backed database, a PID file
guarding against a second instance of a program starting — is a real,
common need with no primitive in Emerald today. `fd-lock` (v4.0.4,
actively maintained per its own crates.io release history this session)
is the chosen crate over the older `fs2`: `fs2` v0.4.3's own crates.io
page shows a release date of "over 8 years ago" with no README, and a
real, findable downstream GitHub issue (`denoland/celld#138`, "Consider
replacing fs2") states plainly "the crate appears to have been
unmaintained for nearly 8 years" — a real, current, citable fact this
plan bases its choice on, not a guess about which of two similarly-named
crates might be better. `fd-lock`'s own `docs.rs` page states its
contract in the precise language this plan adopts throughout: "advisory
locks are locks which programs must opt-in to adhere to... they can be
used to coordinate file access, but not prevent access."

## Concrete proof this plan targets

```ruby
lock: FileLock = FileLock.acquire_exclusive("plan148_demo.lock")
puts "acquired"

second: FileLock? = FileLock.try_acquire_exclusive("plan148_demo.lock")
second ||= FileLock.none
puts second.is_none

lock.close
puts "released"

third: FileLock? = FileLock.try_acquire_exclusive("plan148_demo.lock")
third ||= FileLock.none
puts third.is_none
third.close
```

Expected output, in order (run from a fresh temporary working directory):
```
acquired
true
released
false
```

Trace: the first `acquire_exclusive` succeeds unconditionally (nothing
else holds the lock yet). While it is still held, `try_acquire_exclusive`
against the same path returns `nil` (`second.is_none` is `true`) — real
contention, proving the lock is genuinely held at the OS level, not merely
tracked as an in-process flag. `lock.close` releases it; the third
`try_acquire_exclusive` now succeeds (`third.is_none` is `false`),
directly proving `.close()` released a real, observable OS-level lock
rather than doing nothing.

## Decision log

- **`fd-lock` over `fs2`, on real, dated maintenance evidence, not
  familiarity or alphabetical convenience.** Verified this session:
  `fs2`'s own crates.io page lists its last release as roughly 2018 with
  no README file at all; a real GitHub issue from a downstream consumer
  (`denoland/celld#138`) independently confirms the same conclusion —
  "unmaintained for nearly 8 years." `fd-lock`'s own `docs.rs` page, by
  contrast, states its precise advisory-locking contract in its own
  words and carries an active v4.x release line (v4.0.4, March 2025).
  Per plan 95's crate-vetting policy, an unmaintained crate is a real,
  disqualifying signal on its own regardless of whether its existing
  code still technically compiles — this plan does not adopt `fs2` even
  though it is arguably the more historically familiar name.
- **This is advisory locking, full stop — a real, load-bearing caveat
  stated plainly, not hedged.** An advisory lock only constrains a
  process that itself calls `FileLock.acquire_*` before touching the
  file; nothing in this plan, `fd-lock`, or the underlying OS primitive
  it wraps (`flock(2)` on Linux, `LockFileEx` on Windows) stops a
  completely unrelated process — one that never calls into this API at
  all, e.g. a plain `cat`, a text editor, a different program entirely —
  from reading or overwriting the same file while the lock is held. This
  is not a limitation specific to this plan's implementation; it is what
  "advisory" means everywhere the term is used, and `fd-lock`'s own
  documentation states exactly this. Any Emerald program using `FileLock`
  as if it were a mandatory, OS-enforced access-control mechanism (the
  way, say, a Windows-exclusive-open share-mode denial can be) is relying
  on a guarantee this plan never claims to provide — the caveat belongs
  in this Decision log precisely because it is the single most likely
  way this feature gets misused.
- **`FileLock` needs plan 93's full explicit-close resource-handle
  model — it is one of this batch's clearest genuine resources, not a
  borderline case.** It holds a real, live, kernel-tracked lock
  (`flock`'s lock table entry) tied to an open file descriptor; releasing
  it has an observable effect on every other process on the same
  machine racing for the same path, exactly the property plan 93's
  model exists to govern. `.close()` is mandatory in the same sense
  plan 147 already established for `Tempfile` — a forgotten `.close()`
  leaks a held lock for the life of the process (or, on POSIX, until the
  file descriptor is otherwise closed at process exit by the OS itself —
  `flock`-based locks are automatically released when their owning file
  descriptor closes, a real, favorable backstop plan 147's `Tempfile`
  does not get for free, worth stating as a genuine difference between
  these two siblings rather than assuming the same risk profile).
- **Blocking `acquire_exclusive`/`acquire_shared` versus non-blocking
  `try_acquire_exclusive` are both real, both needed, and intentionally
  not unified into one call with a flag.** A PID-file-style "wait until
  I can get exclusive access" use case wants a blocking call; a "check
  whether another instance is already running and exit immediately if
  so" use case wants the non-blocking `try_` variant returning `nil`
  rather than parking the calling thread (or, worse, an entire actor's
  worker thread, stalling that worker's whole mailbox — see below).
  Ruby, Python, and Rust's own `fd-lock` API all expose this same
  blocking/non-blocking pair rather than a single parameterized call;
  this plan follows that precedent rather than inventing a different
  shape.
- **A blocking `acquire_exclusive`/`acquire_shared` call genuinely
  blocks the OS worker thread it runs on — a real interaction with
  plan 55's actor scheduler this plan discloses rather than hides.**
  Emerald's actor model runs actor message handlers on a fixed-size
  worker-thread pool (plan 55); a `handle` method that calls a blocking
  `FileLock.acquire_exclusive` against a heavily-contended path can stall
  that worker thread — and therefore delay every other actor the
  scheduler would otherwise have run on it — for as long as the lock
  stays held elsewhere. This is the same category of hazard any blocking
  syscall already presents to this scheduler (todo, not unique to file
  locking), and this plan does not attempt to solve it generally
  (that would be a scheduler-level async-I/O redesign, far outside this
  plan's scope) — it is named here so a reader choosing between the
  blocking and `try_` variants inside actor code understands the real
  tradeoff rather than discovering it as a production stall.
- **Out of scope.** Mandatory/OS-enforced locking (not what `flock`-
  family primitives provide on any of this project's target platforms,
  and not what `fd-lock` claims to provide either); lock timeouts /
  poll-with-deadline (a real, small, useful addition — `try_` plus an
  Emerald-side retry loop already gets most of the way there without new
  runtime machinery, so this plan declines a dedicated timeout parameter
  for now); locking a byte-range within a file rather than the whole
  file (POSIX `fcntl` byte-range locks are a different, lower-level API
  `fd-lock` does not wrap, and this plan's own use cases — config files,
  PID files, lightweight coordination — never need less than whole-file
  granularity); any change to `runtime/emerald_runtime.c`.
